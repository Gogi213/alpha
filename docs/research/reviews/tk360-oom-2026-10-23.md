## Корень

1. `tk360-memq.py: avail()` читает `MemAvailable` **машины** (`/proc/meminfo`), а предел — `MemoryMax` **юнита** (56 ГБ).
   Внутри cgroup машина всегда «свободна» → KILL (`avail < 2,5`) не срабатывает никогда, ядро бьёт по memcg раньше.
2. Резерв задачи = текущий пик × 1,15 + 0,5 на момент допуска; задача растёт после допуска (1–3 → 6,7 ГБ), сумма резервов
   не ограничивает сумму реальных RSS. BUDGET 48 при этом не защищает.
3. systemd по умолчанию `OOMPolicy=stop`: один OOM-kill внутри юнита останавливает весь юнит — повтор задачи в memq
   не успевает сработать.

Перезапуск без правки упадёт третий раз — бессмысленно.

## Что сделать (инженер)

- `avail()` = min(`MemAvailable`, `memory.max − memory.current` своего cgroup: `/sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup)`);
  KILL — по этой величине (порог ≥ 4 ГБ: шаг роста задачи ≈ 3–4 ГБ за такт не исключён).
- Учёт допуска — по сумме **текущих** RSS (`memory.current`), а не только по резервам.
- Заявке — `OOMPolicy=continue` (если alsched/systemd-run даёт свойство), иначе — только защитный KILL memq.
- Проба 1 сутки (2026-02-04, где вырос до 6,7 ГБ) до боевого перезапуска; готовые 257 задач — пропуск, как было.
- Новый wait_for — на rc нового задания.
