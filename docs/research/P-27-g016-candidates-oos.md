## 3. Правило вердикта (заморожено до счёта)
**Часть A** (на каждого кандидата отдельно). «Подтверждён вне выборки» — только если одновременно:
1. нетто ячейки на OOS > 0 и нижняя граница 95 % бутстрапа (монето-сутки), с поправкой Бонферрони на 2 испытания (односторонний α=0,025), > 0;
2. нетто > контроля (5 случайных входов той же монеты, тот же знак и длительность);
3. n ≥ 30 эпизодов и эфф. N ≥ 30 монето-суток;
4. нетто > 0 минимум в 4 из 6 недель, где у недели ≥ 5 эпизодов (недель с < 5 эпизодов не считаем ни за, ни против; если таких недель > 3 — «не хватает данных»).
«Не подтверждён» — OOS-оценка ≤ 0 или условие 1/2/4 нарушено при n ≥ 30. «Не хватает данных» — n < 30 или эфф. N < 30. Промежуточных вердиктов нет.
Слабее-нуля OOS при плюсе in-sample = признак выбора по шуму (регрессия к нулю), записывается как есть.

**Часть B** (класс): форма F — «край есть» при тех же условиях, что P-26 §1: нижняя граница 95 % по монето-суткам > 0 **и** > контроль после Бонферрони на 96, **и**
≥ 2 монет по отдельности с нетто > 0 и ≥ 30 эпизодов; плюс условие 4 по неделям. Иначе — «край не доказан»; эфф. N < 30 — «не хватает данных».
Ячейки, прошедшие на 15–22.10 (4 pass_all), на OOS проверяются теми же условиями и отдельно помечаются как повторные.

## 4. Solana-середина (запасной путь по спецификации аудита TK-384 п.3)
Состояния пулов Solana в выгрузке нет. Для монет Solana (AGENCY, ALLINU, SI и др.) цена DEX = цена исполнения, сдвинутая на **½ комиссии пула против стороны свопа**
(покупка: цена / (1+f/2); продажа: цена · (1+f/2)); f — комиссия конкретного пула из `tk380-pools`. Помета `mid=exec` в каждой строке; результаты отдельно от `mid=sqrtP`/`mid=sync`.
`mid=exec` — оценка с неопределённой ошибкой (проскальзывание не вычтено): **сама по себе «край есть» не даёт**, только «не противоречит» либо «отрицательно (даже без вычета проскальзывания)».

## 7. Поправки до счёта (24.10 ~20:45, по замечанию CEO; протокол ещё не утверждён, счёта нет)
1. **Тариф — по бирже, не подгонка.** Публичный `contracts` Gate USDT-фьюч (`LAPTOP_USDT`, `Q_USDT`): `taker_fee_rate` 0,00075 = **7,5 бп/нога**, `maker_fee_rate` −0,0001 = **−1 бп/нога** (ребейт).
   В `tk386-converge.py` (`TK, MK = 5.0, 2.0`) и P-26/P-27 стояло 5 / 2 — это ошибка. В `tk388-converge.py`: `TK, MK = 7.5, -1.0`; контроль — `2*TK` с новым TK.
   Эффект на круг (вход+выход, выход везде тейкер, как в коде): формы a/b — **−5 бп** (2·2,5); форма c (вход мейкер, выход тейкер) — **+0,5 бп** (+3 вход, −2,5 выход).
   CEO оценил форму c в +6 — по коду выход у c тейкер, поэтому +0,5; расхождение — Судье. Пересчёт строки TK-386 (аналитически, −5 на эпизод): Q +79 → **≈ +74**, LAPTOP +14 → **≈ +9**
   (контроль −24 → ≈ −29; разность нетто−контроль не меняется). Реплика п.1 §1 сверяется со **старым** тарифом (5/2) байт в байт, боевой счёт — с новым; тариф — параметр окружения `FEE_TK`/`FEE_MK`.
2. **Отбор 13 монет задним числом.** Монеты выбраны по обороту на 23.10 → для 01.09–14.10 это отбор выжившими (смещает плюс вверх: монеты, не взлетевшие/не листингованные в сентябре, отсутствуют).
   В отчёт: таблица «монета — дата листинга фьюча на Gate — первые сутки с данными — суток в OOS» из охвата TK-387; монета, листингованная после 01.09, считается только с даты листинга (правило §2), и
   вердикт части B дополнительно считается **без монет, листингованных ≤ 30 суток до 01.09** (чувствительность, справочно). Смещение отбора в вердикт числом не вычитается — пишется как оговорка.
