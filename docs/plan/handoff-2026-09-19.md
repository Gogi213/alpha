## 0. Цель и критерий

Цель этапа (владелец, 19.09): **найти альфу или намёк на неё** — форму сделки-отскока и набор монет,
у которых нижняя граница `net_fill` > 0 (гейты В-60: `n ≥ 100` кругов, ≥ 7 суточных кластеров,
`DSR`). До этого живой торговый контур не пишется («нечего кодить, если альфы нет»). Любой замер —
**с разбивкой по монетам** (В-67): вопрос не «работает ли по пулу», а «на каких монетах».

Честная точка отсчёта ([разбор 19.09](../findings/base65-2026-09-19.md), ранний вердикт `v68lat`):
ни одна форма не показала плюс с нижней границей > 0; лучшая `pct1-1to1-3600` — +0.37 bps на сигнал,
нижняя −0.70, 79 кругов на 3 сутках; по монетам 1–7 кругов. Тормоз — поток сигналов при жёстких
флорах, не код.

## 2. Решения, которые действуют (не переоткрывать)

- **В-64** база из файлов практиков прежде любых нововведений; **В-65** формы стопа/тейка и их имена;
  **В-66** номинал ≥ $10k; **В-67** сила = плотность / оборот монеты за час (×поток), киты по порядку:
  время жизни → объём → сила → спуфинг → другие биржи (потом); разбор по монетам.
- **В-68** задержка — измеренная тройка `place=4200000,cancel=3980000,taker=5650000` нс (p95
  `4790000/4550000/6420000`), флаги обязательны, одно число = прежняя форма `assumed`.
- **В-69** E7: `half1to1`, `eat<h>x<a>` (`eat50x80`), `--order-qty-mult 2`; «остаток по замедлению» —
  не формализован (владелец: «хз»), остаток бежит до стопа/дедлайна.
- **В-70/В-71 (владелец 19.09, вечер):** **15 минут с постановки — жёсткий флор:** плотность моложе
  15 мин не торгуется ни в одной форме. **Возраст выше флора — ось**, которую надо выяснить: лучший
  порог для пула, для нескольких пулов, или вывод «возраст уникален для каждой монеты». Сила ×поток
  ≥ 100 % и возраст ≥ 15 мин **не пересекаются** (3 касания/сутки) — силу под флором возраста
  балансировать заново (25–50 %), не держать 100 %.
- Правила работы: одна переменная за раз; каждая сетка — строка предрегистрации в `runs.csv` **до**
  чтения данных; результат — `docs/findings/<тема>-<дата>.md` (+ csv/json рядом); «где мы» — только
  раздел «Состояние» в `CLAUDE.md`; ключи биржи — только окружение процесса, на диск не писать,
  число живых сделок согласовывать с владельцем **до** запуска (`lob latency` 19.09 сделал 612
  сделок по $10 — владелец удивился).

### H2. Ось возраста под жёстким флором 15 мин (В-71) — главный вопрос владельца
- Вопрос: лучший порог возраста для пула / для нескольких пулов / уникален по монете?
- Шаг 1 (дёшево, по касаниям): кривые «ход за час и за 10 мин − комиссии» × «сигналов/день» по
  порогам возраста `{15, 30, 45, 60, 90, 120}` мин **по монете**, при силе любой и ≥ 10 % —
  расширить [`floors-balance.py`](../../tools/compute/floors-balance.py) (вход `study/touches*`).
  Нужен свежий `touches` за все сутки — см. H3.
- Шаг 2 (проверка «уникален ли»): для каждой монеты — лучший порог на сутках A, ход на сутках B
  (split по суткам, как CPCV в вердикте); сравнить с одним порогом на пул и с порогами по кластерам
  монет (кластеры — по обороту/тику/цене из `instruments.csv`, без подгонки под ответ). Если
  по-монетный порог out-of-sample не бьёт пуловый — возраст не уникален.
- Шаг 3 (дорого, сетка): база В-65 при `--min-age-secs` ∈ {900, 2700, 3600} × сила {0, 10 %} —
  предрегистрация в `runs.csv` **до** запуска (число форм × порогов), `bin/run-grid.sh` на счётной
  машине (шаблон — `/tmp/chain-v70bal.sh` там же, копия в этом репо не нужна — переписать под
  задачу), вердикт на каждый порог.
- Выход: `docs/findings/age-axis-<дата>.md` + csv; решение владельцу: один порог / по пулам / по
  монетам. → H1, H3.
