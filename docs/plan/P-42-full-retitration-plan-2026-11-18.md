# П-42: план перетитровки сетапа на всех данных (TK-599) — 18.11.2026

Слово владельца (18.11): «так ну вот у тебя теперь есть что титровать и тестить»; «сделай план и прогони его на критика». Постоянный приказ В-160: титровать стоп и все параметры/признаки сетапа на текущей конфигурации.

## Зачем другой план, чем TK-595

TK-595 титровал на A (30 сут.), стадиями, принимая шаги с Δ_A внутри 1 SE (+0,25…+1,60 $/сут. при SE 0,4–2,4). Итог: собранный C в августе хуже простой базы на ~3 $/сут. на обеих сторонах. Вывод для метода: шаги в пределах шума складываются в подгонку; на 30 сутках отличить шаг +1 $/сут. нельзя. Теперь данных ~135 сут. — SE падает примерно в √(135/30) ≈ 2,1 раза, и можно проверять **саму процедуру отбора** вперёд по месяцам, а не одну клетку.

## Что титруем (каждый параметр — сетка вокруг простой базы стороны)

Базы — простые `L_base` / `S_base` (TK-595, заморожены), не C.
1. Вход: отступ входа от уровня `e` (в т. ч. es15 = 0,15) и `e2`; вход 0,3 % / у уровня (TK-591).
2. Стоп: жёсткий `s`; NATR-стоп (`sn sg sr`); стоп за дальним краем зоны + k·NATR, k 0,5–1 (TK-591).
3. Безубыток / трейл: `bm`, `rr`, `tj`, безубыток за уровнем вместо точки входа.
4. Выходы: по времени без пробоя T мин после касания; при возврате за уровень (глубже f, t с) (TK-591).
5. Фильтры сетапа: `t_high`, `q`, `rf`, `natr_min`, ослабление пула.
6. Признаки, уже в движке (фильтры F): 15 клеток TK-595 (`maxmv1`, `tpm15` и др.), отсечки — квинтили.
Сетки — те же значения, что в §13.21/§13.19, плюс расширение на край, если лучшая клетка на краю.

## Порядок

1. **Шаг 0** — инвентарь, кэш, манифест; простые базы и C TK-595 на всём окне помесячно (описательно, ориентир).
2. **Координатный проход** от простой базы, по одной группе 1–6, в записанном заранее порядке (стоп → выходы → вход → безубыток → фильтры → признаки). Правило принятия шага (строже TK-595):
   - парная Δ $/сут. по всему окну ≥ 2 SE (блочный бутстреп по суткам, блок 4);
   - знак Δ тот же не менее чем в 4 из 5 месяцев (июль, август, сентябрь, октябрь, 01–13.11 — как месяц);
   - плато: оба соседа клетки с Δ ≥ 0,5 Δ клетки;
   - устойчивость: без 2 лучших суток и без 2 лучших монет Δ > 0.
   Иначе шаг не принимается, параметр остаётся как в базе.
3. **Совместная проверка**: принятые параметры — сетка из 2 лучших значений каждого (≤ 2^k клеток); выбор по тому же правилу; сравнение с базой.
4. **Проверка процедуры вперёд (walk-forward)**: та же процедура (шаги 2–3, автоматом, без ручных решений) на расширяющемся окне — подбор на июле → проверка на августе; июль–август → сентябрь; … → 01–13.11. Итог: Δ(отобранная − база) на каждом следующем месяце, сумма по 4 проверкам. Это и есть свидетельство, что подбор что-то находит, а не подгоняет. Если сумма Δ вперёд ≤ 0 — итог «перетитровка не превосходит простую базу», заморозка = простая база.
5. **Заморозка** итоговой конфигурации стороны (шаги 2–3 на всём окне) до чтения вперёд; чтение один раз на 14.11–30.11 (17 сут., дата конца — сейчас); при < 14 опубликованных сутках на момент чтения — описательно. Монеты с 404 у источника — списком.

## Вопросы критику

1. Правило шага (2 SE + 4/5 месяцев + плато + устойчивость) — не слишком ли строго для 136 сут. (мощность), не слишком ли мягко (подгонка)?
2. Координатный проход + совместная проверка vs сразу совместная сетка / случайный поиск — что честнее при таком числе клеток?
3. Walk-forward с расширяющимся окном и 4 проверками — достаточно ли, нужна ли схема «месяц без одного»?
4. Простая база как старт vs C TK-595.
5. Разные источники фандинга по месяцам — допустимо ли смешивать в одном окне.
