# Дорога к альфе — большой план для любого исполнителя (2026-09-19, поздний вечер)

Этот документ — для того, кто садится за проект **с нуля**: сильная модель, младшая модель, следующий
чат, другой ИИ. Он говорит, что делать шаг за шагом, чем проверять, куда класть, и когда остановиться
и спросить владельца. Он не заменяет карту проекта ([CLAUDE.md](../../CLAUDE.md)), оперативный план
([handoff-2026-09-20.md](handoff-2026-09-20.md)) и решения ([SETTLED.md](SETTLED.md)) — он их
**связывает в одну дорогу с воротами**.

Цель дороги (владелец, 19.09): **найти альфу или намёк на неё** — форму сделки-отскока от плотности
стакана и набор монет, где нижняя граница `net_fill` > 0 по гейтам В-60, — и только потом строить
торговый контур. Нулевой ордер до этого. Деньги — сильно после.

### A2. Правила, которые нельзя нарушать (каждое стоило времени или денег)

1. **Числа не изобретаются.** Измеримое измеряется, назначаемое — решением владельца `В-##`. Флаги
   форм/флоров без умолчаний — это нарочно.
2. **Одна переменная за раз.** Сетка меняет одну ось относительно контроля; иначе результат не читается.
3. **Предрегистрация до данных.** Строка `prereg` в [runs.csv](runs.csv) **до** запуска сетки; после
   вердикта — строки `bounce_form` с контекстом (`POOL`, «— <метка> <сутки> (<условия>), verdict:
   <итог>; <док>»). DSR считает эти строки — журнал честный или вердикт ложный.
4. **По монетам.** Любой замер — с разбивкой по монетам (В-67). Пуловая сумма — карта, не P&L.
5. **Артефакт на диске, по адресу.** Текст — `docs/findings/<тема>-<дата>.md`; компактный csv/json
   рядом; сырьё — `data/` (локально, gitignored) или `study/` (счётная); «где мы» — `CLAUDE.md`
   «Состояние», затем digest в `.memory/` (index → `projects/active/alpha.md` → `log.md`).
6. **Живая биржа.** Ключи — только окружение процесса, на диск не писать, значения не печатать. Живые
   ордера — только с числом сделок, согласованным с владельцем **до** запуска.
7. **Коллектор не трогать** без ранбука (`COMMANDS.md`); остановка — файл `stop`, не `kill`.
8. **Счётная машина.** Ожидания — в скриптах-цепочках с логом в `study/`; перед уходом убить своих
   сирот (`pgrep -fa "[c]hain|[h]1-"`); пруфы не в `/tmp`.
9. **Контекст.** Файлы секциями, вывод через `tail`/`grep`, разведка субагентом; скрипты — файлом,
   не heredoc'ом (оболочка агента портит `\1`/`\n`).
10. **Никакого фандинга** (владелец) и **никакого торгового контура** до альфы.

### A3. Чеклист начала и конца сессии

Начало: прочитать A1-цепочку; `git log --oneline -5`; на счётной машине — `tail -5
study/nightly-<сегодня>.log` и `systemctl list-units "alpha-grid-*"`; убедиться, что ничего чужого не
крутится. Конец: коммит; `CLAUDE.md` «Состояние» — абзац; `.memory/index.md` блок «Состояние»,

## Часть B0. Где дорога на 22.09 (владелец, В-84) — читать перед этапами

**Что дала первая настоящая сетка (F10, 5 суток 16–20.09, вход мейкером на подходе, очередь по объёму):**
живая ветка одна — **лонг от старых бид-стен (≥ 45 мин), полоса взвода 20 bps**: 128 сделок, +29.5 bps на
сделку (+$377 на $1000-лоте), win 58 %, просадка −$78; фильтр «BTC в минусе за 4 ч» поднимает до +37 bps

(19.09) — минус у обеих веток. **Ворота альфы не пройдены** (нижняя граница < 0): знак есть, доказательства нет.

**Порядок дальше (В-84), приоритет сверху вниз:**
1. **Сценарии мгновенного слива** — прежде чем докручивать доход, найти, при каком контексте ветка теряет
   быстро и много (стопы −2 %, дни разворота). Без этого живой контур опасен при любом среднем.
2. **Титрование гиперпараметров найденных семейств** — по одной оси за раз (выход, дедлайн, возраст стены,
   полоса взвода, тейк), коротким списком форм каждую ночь; широкие сетки по 144 формы — только для разведки.
3. **Режимы рынка** — не искать «лучший», а разложить дни на типы (рост / флэт / снижение / всплеск) и
   смотреть поведение ветки в каждом; для снижения — ждать дней.
4. **Докручивать найденное** — после ворот (этап 6), не раньше.

Этапы ниже остаются картой ворот; этап 1 (сторона) — лонг подтверждён по знаку, шорт считается 22.09;

## Часть B. Дорога с воротами

Каждый этап: цель → что делать → артефакт → ворота (чем проверяется) → что, если ворота не открылись.
Порядок — приоритет; этапы 1–2 идут параллельно с ночной автоматикой.

### Этап 0 — Подтвердить, что база в порядке (день)

- Цель: убедиться, что ночная автоматика даёт утром всё нужное без рук.
- Делать: две ночи подряд читать `study/nightly-<день>.log`: касания по новым суткам (`.done`),
  `floors-<сутки>.txt`, шесть вердиктов; при `FAILED` — причина из `<SYM>.log`, не молчать.
- Ворота: две ночи без ручных шагов (H3b «готово, когда»).
- Не открылись: чинить скрипт (`tools/compute/nightly-grid.sh`), не переписывать.

### Этап 1 — Ось стороны: лонг от бид-стены против шорта от аск-стены (2–3 дня)

> **Посчитан 19–20.09** — `docs/findings/side-axis-2026-09-19.md` (лонги +19 bps/круг, шорты 0 форм из 32 в плюсе, ворота ждут дней
> падения). Решение владельца 20.09: пороги по сторонам разные → этапы 1–2 дальше идут по
> **[side-plan-2026-09-20.md](side-plan-2026-09-20.md)** (S0–S7: возраст/съедание по стороне, режим пула, растяжка, шорт от снятия).


- Почему первой: единственный найденный «намёк» ([side-asymmetry](../findings/side-asymmetry-2026-09-19.md)):
  в семье «старые стены» лонги +12…+17 bps на круг (79–82 круга), шорты −16…−19; три сутки были ростом,
  так что сторона от режима пока неотличима.
- Делать: (1) код — `--side bid|ask` у `lob bounce-grid` (фильтр касаний по `touch.side`; тест; имя
  сетки `<семья>-<side>`); (2) предрегистрация: «семьи a45 и s100 × сторона × 32 формы = 128
  испытаний»; (3) сетки на всех сутках корня; (4) вердикт на каждую; (5) док `side-axis-<дата>.md` по
  монетам и по суткам, с разделением дней роста/падения (медианная дневная доходность пула —
  `floors-by-coin`/цены в касаниях).
- Ворота: у лонг-половины — нижняя граница > 0 на ≥ 7 сутках? Если да — это кандидат на альфу, идти в
  этап 6 (подтверждение). Если знак лонгов держится только в дни роста, а в дни падения меняется на
  аск — это **режим**, идти в этап 2.
- Не открылись (обе стороны ≤ 0 после ≥ 7 суток): сторона не ось; продолжать этапы 2–3.

### Этап 2 — Режим рынка как фильтр (E12) (3–5 дней, нужны дни падения)

- Гипотеза из данных: знак хода за час/за 4 часа и/или `σ_H` (уже в `touches`) определяет, какую
  сторону торговать; 09-18 (+7.3 % по пулу) убил все шорты и часть лонгов.
- Делать: ось «направление за прошлый час/4 часа» × сторона — сначала по касаниям
  (markout, `floors-balance.py` с новой колонкой), потом одна сетка «торговать по направлению» против
  контроля; пороги — титрование, не назначение.
- Ворота: форма «по направлению» с нижней границей > 0 на ≥ 7 сутках, включая дни падения.
- Не открылись: режим не спасает — пересмотреть семьи флоров (этап 3).

### Этап 3 — Возраст и сила: семьи флоров и «уникален ли возраст по монете» (H2, параллельно)

- Инструменты готовы: `floors-balance.py --by-coin`, `age-axis.py` (out-of-sample по парам суток:
  пул / кластер / по монете), `family-table.py`. Ночной набор уже гонит `a15-s10`, `a30`, `a45`, `a60`,
  контроль `s100`, E7.
- Делать: (1) запустить `age-axis.py` по `study/touches` при ≥ 4 сутках, каждые новые сутки —
  повторить; (2) `family-table.py` по ночным вердиктам — таблица семей; (3) док `age-axis-<дата>.md`.
- Ворота: устойчивый ответ на вопрос владельца — «один порог / по пулам / по монете» — устойчивый
  значит одинаковый на ≥ 4 разбиениях суток. Число порога называет владелец.
- Помнить систематику: возраст обнуляется в 00:00 (трекер суточный) — первый час суток недосчитывает.

### Этап 4 — Хвост пула и приор по монете (H5, E11) (после ≥ 5 суток)

- `pool-tail.py`: сколько монет остаётся при порогах {10, 30, 100} касаний/сутки и что они дают в
  круги; E11 — доля отскоков и снятий за прошлые сутки как фильтр монеты (out-of-sample по суткам).
- Ворота: порог назначает владелец; фильтр монеты входит в сетку, только если out-of-sample улучшает
  нижнюю границу, а не точку.

### Этап 5 — Остальная база E (E8 → E9 → E10), по одному, только если этапы 1–2 не дали ворот

- E8 прилипание/стекание (досрочный выход есть; «стекание» = подход < 0 как фильтр), E9 переставления
  (`moved`, N ∈ {3, 5}), E10 подлинность (четыре признака → распределения → оси). Каждый — предрег,
  сетка против контроля, док, по монетам.

### Этап 6 — Подтверждение кандидата (ворота альфы)

Кандидат = форма × семья флоров × (сторона/режим) × набор монет. Ворота, все сразу:
1. `n ≥ 100` кругов (`CONFIRM_MIN_N`), суток с кругами ≥ 7 (`G_MIN`), кластер — сутки (В-60).
2. Нижняя граница `net_fill` > 0 (wild cluster bootstrap-t по суткам).
3. `DSR ≥ 0.95` при честном числе испытаний в `runs.csv`; PBO/CPCV по матрице форма × сутки не
   красные.
4. **По монетам:** плюс не на одной-двух монетах; каждая монета набора — с нижней границей > 0 или,
   если кругов мало, хотя бы с точкой > 0 в ≥ 2/3 суток.
5. Out-of-sample: кандидат выбран на сутках A, ворота 1–4 пройдены на сутках B (не пересекаются).
6. Ёмкость: `net_fill` точка ≥ `GREEN_NET_BPS` (3 bps) — иначе «зелёный без ёмкости».
Итог — `docs/findings/alpha-candidate-<дата>.md`, решение владельца.

### Этап 7 — После ворот: бумага, потом контур (недели; не начинать раньше)

- Бумажный режим: каждый день бэктест кандидата на вчерашних сутках против «что было бы» — 7 дней
  совпадения знака.
- Контур (H9): коннектор `LiveBot` на WS trade (+ приватный стрим как источник «исполнено»),
  лимиты (число позиций, дневной стоп, kill-switch файлом, как `stop` у коллектора), сверка позиций,
  плечо по монете из `leverage-<дата>.csv`; пилот $10–100 на 1–2 монетах с согласованным числом
  сделок; масштаб — отдельным решением.

### Если дорога не даёт ворот к ~7–10 суткам записи

По порядку, каждое — решение владельца: (а) расширить флоры (сила 25 % / возраст 30 мин) ценой
хода на сигнал; (б) спот Bybit как второй фид (нужен коллектор спота); (в) другие биржи (в теории,
владелец: «пока пробуем Bybit»). Не делать всё сразу.

## Часть C. Плейбуки для младших моделей (делай ровно так)

### C1. Прочитать вердикт

Файл `study/bounce-verdict-<метка>.log`, последняя строка: `ИТОГ=<мало данных|красный|зелёный без
ёмкости|зелёный> · форм N · символов M · суток D · испытаний T (журнал J) · лучшая <форма> · кругов n
· суток с кругами d · net_fill точка=p нижняя=l · DSR=x · PBO=… · CPCV=…`.
- «мало данных» = гейты по n/суткам не пройдены → ничего не решать, копить.
- «красный» = гейты пройдены, нижняя ≤ 0 или DSR < 0.95 → формы в этом виде не работают.
- «зелёный» = кандидат → этап 6, не радоваться раньше.
Всегда рядом — срез по монетам: `python3 bin/grid-coins.py b5/<метка>/forms.csv --top 6 --min-fills 5`.

### C2. Запустить сетку на счётной машине

```
ssh root@13.140.29.171
cd /opt/alpha-compute
# 1) строка prereg в журнале-копии (и в репо!) — ДО запуска
# 2) сетка (systemd transient-юнит, лог b5/<метка>/grid.{out,err})
THREADS=3 bin/run-grid.sh <метка> --day 2026-09-16 --day 2026-09-17 \
  --h3-mode notional --h3-usd 10000 --min-age-secs 2700 \
  --stop-form pct0.5 --stop-form pct1 --stop-form pct2 --take-form 1to1
# 3) ждать: while systemctl is-active --quiet alpha-grid-<метка>; do sleep 30; done  (внутри скрипта!)
# 4) вердикт
bin/alpha lob bounce-verdict --grid-dir b5/<метка> --runs-csv study/runs-2026-09-19.csv \
  --out study/bounce-verdict-<метка>.csv --log-trials > study/bounce-verdict-<метка>.log
# 5) перенести строки bounce_form из study/runs-2026-09-19.csv в docs/plan/runs.csv с контекстом
```
Задержка В-68 уже в `run-grid.sh`. Новый бинарник: `git archive HEAD src Cargo.toml Cargo.lock tools
rust-toolchain.toml` → scp → `tar -xzf … -C src` → `cd src && cargo build --release --bin alpha -j 3`
→ `bin/alpha-<hash>` + симлинк `bin/alpha`. Ночью сетки идут сами — не ставить своих в 02:00–10:00 UTC.

### C3. Добавить ось в код (образец — `--side`)

1. `src/commands/lob/bounce_grid.rs`: флаг в `BounceGridArgs` (doc-комментарий с источником решения),
   фильтр касаний рядом с `min_age_secs`/`min_flow_pct`, значение в шапку `forms.csv`.
2. Тест в `bounce_grid/tests.rs` (фикстура есть); `cargo test --release --target-dir target-ci`,
   `cargo clippy --release --target-dir target-ci --all-targets -- -D warnings`, `cargo fmt`.
3. `docs/COMMANDS.md` строка команды; `SETTLED.md` — только если владелец что-то решил.
4. Коммит с текстом «что и почему», не «fix».

### C4. Написать док в `findings`

Шапка: что за прогон (метка, сутки, флоры, задержка, размер, монет в сетке); таблица вердикта; по
суткам; по монетам (лучшие/худшие с числом кругов); «что видно» нумерованным списком; «что дальше»;
«журнал» (сколько строк перенесено). Числа — только из артефактов, с путями. Оговорки — явно
(размер, режим, n на монету).

### C5. Обновить память

`CLAUDE.md` «Состояние» (абзац, ссылки на доки) → `.memory/index.md` блок «Состояние» (≤ 8000 знаков
весь файл) → `.memory/projects/active/alpha.md` §ПЕРЕДАЧА (дельта) → `.memory/log.md` строка
`## [дата] <kind> | <title> (<коммит>)`. Всё в одном коммите с работой.

### C6. Когда спрашивать владельца

Только когда нужно **назначить число или выбрать** (порог возраста, порог хвоста, семья флоров как
стандарт, число живых сделок, расширение флоров/бирж). Всё, что измеримо, — измерить и показать три
варианта с ценой. Не спрашивать «правильно ли я понял» — сделать и показать артефакт.

### C7. Чего не делать никогда

Печатать/писать ключи; ставить ордера без согласованного числа; трогать коллектор; править
`BUSINESS-TASK.md`; удалять доки (только `docs/archive/` тем же коммитом); вносить в `.memory/index.md`
целые доки; называть свои числа «дефолтами»; оставлять циклы ожидания после сессии.
