## 3. Как проверяется правильность

REST Gate хранит **полную историю сделок по времени** (`/futures/usdt/trades?contract=&from=&to=&limit=1000`, `to` не включает секунду `to`, от новых к старым; проверено на 30 суток назад), поэтому — как у OKX — **отложенный проход после лестницы** (`restpass.sh`, п. 23: на хосте во время окон ничего постороннего), и он идёт по **всем символам окна** (не по выборке): для каждого окна 180 с — каждый контракт, страницы по 1 000 сделок, до 10 запросов/с при лимите биржи 200 за 10 с.

- **пропуск** — сделка из REST в окне, id которой нет в файлах; в критерий — после covered (первые секунды окна, пока шарды подписываются, не считаются);
- **лишнее** — записанный id в окне, которого нет в REST; **расхождение** — тот же id, но другая цена, размер (без знака), сторона (`m`) или время (мс, точно);
- **покрытие «символ × секунда»** — доля клеток (символ, секунда) с хотя бы одной сделкой в REST, где в файлах тоже есть сделка;
- **mark**: у Gate нет канала с постоянным темпом (`futures.tickers` — ≈ раз в секунду на контракт и **только при изменении**), поэтому критерий «запись каждую секунду» (`mark_cov` остальных бирж) не применим. Оракул — REST-свечи mark (`candlesticks?contract=mark_<символ>&interval=10s`): (а) 10-с клетка, где свеча сдвинулась (high ≠ low), а записи нет; (б) записанный mark вне диапазона свечи своей клетки и двух соседних, расширенного на один шаг цены. **Серия свечей — не серия потока до шага** (измерено: 84,6 % записанных mark лежат в свече своей клетки, 99,6 % — в свечах клетки и соседей; у тихого контракта свеча двигается на 1–7 шагов, а поток держит старый mark; поток тикера шлёт только при изменении полей тикера), поэтому оба признака — **назначаемые** пороги: (а) отказ при > 1 % сдвинувшихся клеток без записи (измерено 0–0,11 %, всегда малоликвидные символы; остановка или потерянная пачка дала бы десятки клеток сразу), (б) отказ при > 5 % записей вне диапазона (измерено 0–1,0 %).
- **Нет непрерывности id как второго оракула:** id сделок Gate не сплошные (биржа пропускает отдельные id, и в REST тоже: ETH `977283578`), поэтому пропуск id в файлах не признак потери — оракул REST.
- Остальные критерии окна — как у других бирж: 0 обрывов живой сессии (`error`), 0 остановок (`timeout` + `ping_degraded`), 0 шард-секунд без сессии, все шарды подключены, 0 поздних записей книги (> 2 с) после covered.

## 4. Лестница нагрузки

Методика OKX/BingX 13.11, один в один: один процесс Gate за раз (на srv параллельно работали `collect-binance`, `collect-okx`, `collect-bingx`, `soak-bybit`, страницы здоровья и арбитража — не трогались), ступени N = 10, 20, 40, 80, 160 и весь пул (286 символов; топ-N по обороту `volume_24h_quote`), 3 окна по 3 мин на ступень, каждое окно — новый процесс `collect run --exchange gate --lanes 2` с флагами боевого запуска (`--reactor --worker-inline --reactor-window-us 10000 --rx-stamp kernel --sub-in-reactor`), пул из файла ступени, пауза 20 с, один юнит `steps.sh`, строка на окно в `status.txt`. Условия — рядом с числами: нагрузка хоста (load1 и PSI cpu за последние 10 с окна) и поток книги (записей/с после дедупа) — рынок воскресной ночи (акции закрыты: 270–1 335 зап/с книги; в рабочие часы больше — предел «в тихий час» не равен пределу в пик).

Колонки: «быстрых (подкл.)» — доля соединений с RTT рукопожатия ≤ 300 мс (всего подключений; у Gate все 236–240 мс, «медленного маршрута» нет); лаг книги p50 / p99 / max, мс (приём − `t`, после дедупа); «поздних» — записей книги с лагом > 2 с (всего / после covered); «остановок» — `timeout` + `ping_degraded`; «обрывов» — `error` живой сессии; REST — пропущено / лишних / расхождений (из N сделок окна после covered); «клеток» — (символ, секунда) с сделкой в REST без сделки в файлах (из N); «свеча mark без записи» — сдвинувшихся 10-с клеток без записи (из N); «mark вне свечей» — записей вне диапазона (из оценённых); CPU — % одного ядра процесса.

### 4.2 Происшествие лестницы 1: запасные пути шарда mark отбраковывались проверкой пути

В окнах с числом подключений больше шардов × линий (n20-w2: 8 из 6, n80-w1: 11, n80-w2: 16, весь пул w1: 43 при 18 нужных) у шарда `mark00` шли подряд события `path_rejected` (p50 лага 376–672 мс при пороге 350 мс). **Причина [измерено]:** `lag_ms` адаптера брал для тикера `t` — время снимка, на **≈ 456 мс старше кадра** (`time_ms`, p50; p90 738, p99 993 мс), поэтому лаг пути у шарда mark всегда выше порога проверки пути — запасная линия шарда mark не принималась (до 12 отказов подряд, 12 подключений впустую на шард). Данные не терялись (REST: 0 пропусков), страдали число подключений и надёжность запасной линии. **Исправление:** лаг тикера для проверки пути — по `time_ms` кадра (отправка шлюзом: p50 ≈ 118 мс, как у книги), коммит `c9334944`; лаг записи `m` в файле по-прежнему `rx − E` с `E = t` (как шлёт биржа; лаг `m` по `E` не сравним с лагом `b`). После исправления (`alpha-gate-3`) подключений ровно шарды × линии на всех окнах: п. 4.3–4.6.
