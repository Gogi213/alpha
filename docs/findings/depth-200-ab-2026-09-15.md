# Глубина стакана: `.50` против `.200` — живой A/B (2026-09-15)

Вопрос владельца: «50 уровней — это 0.18 % от цены, надо тянуть 200». Проверено замером, а не на глаз.

## Как мерилось

Два коллектора **одновременно** на одном и том же пуле из 20 монет (10 самых ликвидных + 10 самых
тихих из боевого пула), по 600 с, на боевом сервере, рядом с идущей записью. Различалась только
глубина: `orderbook.50` против `orderbook.200`.

- Бинарник `.200`: в исходниках временно `ORDERBOOK_DEPTH = 200` и `CAPACITY` книги `128 → 256`
  (при 128 уровнях книга не влезает: половина книги — 200 уровней). Собран на старом сервере
  (там остался cargo 1.93.1), md5 `f573e4bc70a0e66a885ba28e9f3ff5ec`, исходники после сборки
  восстановлены побайтово.
- Разница объясняется не только глубиной: у глубоких топиков Bybit публикует реже.

## Расход (20 монет, 600 с, обе записи шли одновременно)

| CPU (session.json) | 4.17 % ядра | **2.32 % ядра** | **−44 %** |
| CPU max | 5.03 % | 3.10 % | |
| RSS конец | 17.6 МБ | 18.0 МБ | +2 % |

| queue p99 | 389 мкс | 377 мкс | |

## Почему так: сообщений меньше, а уровней в каждом больше

LSK (одна и та же монета, один и тот же час):

| | `.50` | `.200` |
|---|---|---|
| записей | 768 803 | 944 980 (+23 %) |
| сообщений биржи | 64 262 | **28 422 (−56 %)** |
| записей на сообщение | 12.0 | **33.2** |
| байт/запись | 2.86 | **2.51** |

Частота сообщений (интервал между сообщениями, мс):

| монета | глубина | медиана | p90 | p99 | сообщений/с |
|---|---|---|---|---|---|
| LSK (активная) | `.50` | 3.0 | 22 | 56 | 107 |
| LSK | `.200` | 3.0 | **85** | **107** | 47 |
| SENT (тихая) | `.50` | 21 | 835 | 3008 | 4 |
| SENT | `.200` | **97** | 736 | 1021 | 5 |

## Что это значит

1. **Данных больше, а места и процессора меньше.** Глубже книга, вдвое меньше сообщений — и на них
   тратится меньше и байт (заголовок сообщения теперь амортизируется по 33 записям вместо 12), и
   процессора (меньше разборов JSON и системных вызовов на то же число записей). Для тихих монет
   выигрыш по байтам особенно велик: у них раньше каждое сообщение несло 1–3 уровня.
2. **Но время становится грубее.** `.50` приходит пачками по ~20 мс, `.200` — по ~100 мс. У тихой
   SENT медиана интервала выросла с 21 до 97 мс. Таймстампы в записи по-прежнему биржевые (ничего не
   выдумано), но события приходят **уже сгруппированными за ~100 мс**.
3. Это бьёт по самому мелкому горизонту проекта: `m_100ms` и `within_touch_100ms` (В-45) — как раз
   100 мс. Горизонты 1 с / 10 с / 60 с не страдают.

## Склейка потоков: индустриальный механизм и защита от дрейфа

Вопрос владельца: «нам не надо 200 так же часто, как 50 — есть ли индустриальный механизм склейки
и защита от дрейфа». Есть, и он даже описан в библиотеке, на которой стоит проект.

- **Название**: fusing depth feeds — hftbacktest даёт это отдельным туториалом
  ([Fusing Depth Data](https://hftbacktest.readthedocs.io/en/latest/tutorials/Fusing%20Depth%20Data.html))
  и утилитой `FuseMarketDepth` / `convert_fuse`. Оттуда же подтверждение частот Bybit:
  **BBO — 10 мс, 50 уровней — 20 мс, 200 уровней — 100 мс** (наш замер это подтвердил).
- **Защита от дрейфа, которую даёт сама биржа**: поле **`seq` — «cross sequence»**: по документации
  Bybit его назначение — «сравнивать данные разных уровней стакана: меньше `seq` — данные
  сгенерированы раньше» ([Full Orderbook](https://bybit-exchange.github.io/docs/v5/websocket/public/full-ob)).
  То есть порядок между потоками разных глубин определён биржей, а не выдумывается нами.
  `u` — счётчик внутри топика (`u+1`), разрыв `u` = потеря, нужен ресинк.
- **Что уже есть у нас**: непрерывность `u` внутри топика с автоматическим перезапросом снапшота
  (`conn.rs`, флаг `resyncing`); выравнивание книги со REST-снапшотом **по `seq`** каждые 5 минут
  (`verify_sidecar`) и файл `verify-<SYMBOL>.status`. То есть первый и последний слои защиты уже
  реализованы для одного потока.
  **Поправка 2026-09-17 (аудит V3):** сайдкар подключён только к `lob record`; в `lob session`
  (боевой олвейс-он) его нет, поэтому «расхождение книги с биржей в проде» этой строкой **не**
  покрыто — подключение либо снятие формулировки вынесено в отдельный тикет (D7 плана
  `dev-plan-2026-09-17.md`, с замером бюджета REST на 100 инструментов).
- **Как это делают индустриально** (перечень из туториала, в порядке важности):
  1. по каждому потоку — своя книга и своя проверка `u` (разрыв → ресинк);
  2. между потоками порядок по `seq`; на один ценовой уровень — правило «новейший по биржевой метке
     выигрывает», устаревший апдейт отбрасывается;
  3. **две отдельные книги, а не одна склейка**: склеенная книга бывает внутренне противоречива
     (быстрый поток уже показывает лучшую цену, а в глубоких уровнях висят устаревшие значения) —
     туториал говорит это прямым текстом; поэтому честный путь — хранить оба потока, а склейку
     делать на стороне чтения;
  4. периодическая сверка с независимым REST-снапшотом — у нас она уже есть.

## Варианты для нас

| | частота | глубина | цена |
|---|---|---|---|
| A. `.50` (сейчас) | 20 мс | 50 | — |
| B. `.200` | 100 мс | 200 | −19 % байт, −44 % CPU (замер выше) |
| C. `.50` + `.200` склейка | 20 мс у середины, 100 мс в глубине | 200 | две книги, мердж по `seq`, признак источника в записи |
| D. `.50` + REST-снапшоты глубины | 20 мс у середины, глубина раз в N секунд | до 10 000 уровней/сторону | сайкар уже есть, лимиты REST (~10 запросов/с на IP) |
| E. `orderbook.full.<symbol>` | 200 мс | полная | только дельты, начальный снапшот — из REST; самый тяжёлый поток |

Для нашей задачи (стены, касания, отскок) разумны C или D: узкая полоса у середины остаётся
20-миллисекундной, глубина приходит редко и помечена. C честнее по данным (два потока хранятся
как есть), D дешевле по работе (сайкар уже написан и выравнивается по `seq`).

## Цена перехода

- Код: `ORDERBOOK_DEPTH` (сейчас `50`) и ёмкость книги `CAPACITY` (`128 → 256`); плюс тесты и
  документация, которые на эти числа ссылаются. Формат не меняется: файл v3 читается как есть,
  старые записи (50 уровней) остаются валидными.
- Решение о горизонтах: если нужен именно 100-мс анализ — `.200` его размывает; если нужны «стены»
  и контекст дальше 25 bps — `.200` даёт их почти бесплатно (и даже дешевле по ресурсам).
- Третий вариант, если нужно и то и то: подписка сразу на `.50` и `.200` по одной монете (тонкий
  поток для динамики у середины, глубокий — для контекста). Это уже изменение модели данных: сейчас
  в записи нет признака источника, а книга строится из одного потока.

Прототипы и артефакты: `examples/depth_probe.rs`, `examples/cadence_probe.rs`; файлы A/B лежат на
сервере в `/opt/alpha/ab50` и `/opt/alpha/ab200` (их можно удалить).
