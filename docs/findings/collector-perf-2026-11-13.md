Ядерные RX-метки времени ВМ отдаёт — HFT-пункт выполним.
- **Busy-poll** (`SO_BUSY_POLL=3000 мкс`, тот же стенд): **работает** (p50 114 → 47 мкс, p99 520 → 330 мкс, p99.9 1,4 → 1,0 мс, переключений 23 тыс. → 0,7 тыс.), но **поток жрёт 87 % ядра против 25 %** (sys 19 с из 25) на 1,1 тыс. кадров/с одного соединения. Первые прогоны через Python-таймаут (poll до recv) busy-poll не включали — не считаются. **Вывод: при цели «ядра вниз» неприменим**.
- **Прерывания:** у virtio-net хоста **нет** `VIRTIO_NET_F_NOTF_COAL` → `ethtool -C … rx-usecs` невозможна; доступна программная модерация NAPI (`napi_defer_hard_irqs`, `gro_flush_timeout` — сейчас 0); очередей 8 (макс. 8), RPS выкл.
- **io_uring** включён (`io_uring_disabled=0`, ядро 6.12); **AF_XDP**: сокет создаётся; **нативный и generic XDP на virtio_net прикрепляются** (проверено на Sofia, virtio, 6.8: `xdpdrv` и `xdpgeneric` приняты и сняты; на боевом srv не прикреплялся).
- **Защита от уязвимостей ЦП (`p1/vulnerabilities.txt`):** `meltdown: PTI`, `mds` и `mmio_stale_data`/`taa`: Clear CPU buffers (VERW на каждом выходе из ядра), `spectre_v2: Retpolines` + IBPB conditional + IBRS_FW, `spec_store_bypass` через prctl. Каждый вход в ядро (вызов, IRQ) дорог → **число входов в ядро — главный драйвер цены** (≈ 48 мкс на recvfrom, ≈ 17 мкс на futex). `mitigations=off` — решение владельца (безопасность), здесь не трогается; цена только отмечена.
- **Часы (`p1/chrony.txt`):** clocksource `kvm-clock` (vDSO работает), chrony stratum 2 (`ntp1.lwlcom.net`), смещение +68 мкс, RMS 271 мкс, root dispersion 0,62 мс, интервал 1 037 с; `/dev/ptp*` нет. Абсолютная точность метки ограничена часами (≈ 0,1–0,6 мс); выигрыш ядерной метки (50–500 мкс) реален для относительных/джиттерных сравнений внутри srv, не для абсолютной задержки биржа→srv.
- XPS: `xps_cpus` tx-k = CPU k (1:1) уже настроен; sysctl задержки ACK (delack) в ядре нет (`tcp_comp_sack_*` — другое).
- Железо srv: Broadwell (AES-NI, PCLMUL, AVX2, BMI2; без AVX-512), steal 6,6 %. Сборка: в `Cargo.toml` **нет `[profile.release]`** — LTO выкл., codegen-units 16, без `target-cpu`; глобальный аллокатор — счётчик поверх glibc malloc (`mimalloc` — фича, выкл.); боевой бинарь — plain `binrel`, не PGO.

### 2.2 Порядок (координатор 13.11) и условия отказа

0. **Базовая линия machine-wide** (окна по 5 мин, без изменений), затем **K1 → K2 → K3' → K4** по одной ручке, обратимо, попеременно с базой (база–ручка–база), до/после в §4. Без сборки, ≈ 2–3 ч окон. Канарейка в каждом окне — `ts_probe.py` (ядро→поток p50/p99/p99.9) + health (lag_in, queue_lag, lag_out, recvq).
1. **H0 стенд** (параллельно): `replay` (готов) + режим «чередование» (16 шардов по кругу в одном потоке — реалистичный кэш; гейт вычислений) + `replayd` (paced по записанным интервалам и меткам отправки) + запись настоящих gzip-кадров BingX + счётчик аллокаций на петле rx + **G4/G5**.
2. **S0 / S0b / фрейм-поинтеры**: mimalloc (промежуточный), gunzip, сборка с `-C force-frame-pointers=yes` для разбора [unknown].
3. **S1'** — пакетная передача: потоки чтения кладут кадры в SPSC-блоки, поток-рабочий шарда просыпается по таймеру раз в W, а не на кадр (futex 0,57 + park 0,13 уходят; интерфейс «читатель→рабочий» тот же, что нужен реактору; mutex-вариант S1 снят, критик 1 п. 8 / критик 2 п. 11).
4. **S2 реактор**: сначала **проба** `SO_TIMESTAMPNS` на multishot recvmsg (io_uring, ядро 6.12) → если работает, **io_uring основной** (multishot recv + кольцо буферов + `DEFER_TASKRUN|SINGLE_ISSUER`, один `io_uring_enter` на W для всех сокетов процесса); иначе epoll level-triggered, один recvmsg на готовый сокет за такт, буфер 64 КБ. Реактор делает только recv + TLS + WS-кадрирование + метка; разбор/дубли/кодировщик — в рабочем (S1'), кадры > 16 КБ — всегда в рабочем.
5. **S4** предфильтр дублей по хешу тела кадра (xxh3-128 + длина), ноль аллокаций, S6 стадии/chrony/TCP-счётчики, K5 ACK-эксперимент, A8 «меньше соединений».
6. **S3c/S2b** (epoll busy-poll с prefer_busy_poll и отложенными IRQ) — только если после реактора ядро всё ещё ≥ 0,6.

Каждый шаг: повтор (ЦП на Мкадр, медиана 5, **плюс чередующийся повтор** — гейт вычислений) + **G1** → H0 A/B → боевые окна 3 мин попеременно старый/новый, без сборок на srv во время окон → **G6** (1 ч бок о бок) → накат по биржам по одной (те же аргументы, `Restart=always`, `*.prev`, страница здоровья). **Условие отказа шага:** < 50 % нижней оценки выигрыша; `queue_lag` p99 > W + 3 мс; любые потери/дубли/пропуски ≠ 0; петля реактора p99.9 > 3 мс.

### 2.4 Гейты

- **G1** — повтор записанных кадров старым и новым бинарём: разжатые файлы идентичны байт в байт (детерминированный повтор, готов); + **гейт вычислений по чередующемуся повтору** (16 шардов по кругу, реалистичный кэш).
- **G2** — сквозной (replayd → коллектор, plain ws): мультимножество записей без `rx` = источнику, 0 потерь/дублей.
- **G3** — боевой: REST-оракул Binance/Bybit (`restcheck.py`), `accept_ws.py` (пропуски id, невозрастание).
- **G4** — метки: replayd шлёт с записанными временами отправки; распределение `rx − отправка`, монотонность `rx` по сокету, **запись из дедупа несёт минимум ядерной метки по линиям** (внутри такта кадры читаются отсортированными по метке; записанная запись не переписывается — закрытый такт эмитится целиком).
- **G5** — граница TLS/WS (фаззинг): 1-байтовые TCP-записи, TLS-записи 16 КБ, кадр 82 КБ в ≈ 60 сегментах, WS continuation, пинг посреди большого кадра, gzip-кадры, разрезанные записями TLS; «50 кадров в одной TLS-записи и тишина 10 с — все 50 выданы сразу»; запись, разрезанная на 3 сегмента с паузой 5 мс; остановившийся приёмник пира (запись с WouldBlock); пауза диска 30 с — ноль потерь.
- **G6** — бок о бок 1 ч, старый и новый на одних и тех же 2 шардах биржи (**единственное исключение из «один процесс на биржу»**, бюджеты подключений делятся: сумма ≤ лимита биржи): мультимножества записей без `rx`; распределение `rx_new − rx_old` (ожидание p50 ≈ −100 мкс, без положительного хвоста > 1 мс); `rx` не убывает по линии.

### 2.5 Метка `rx`: решение координатора 13.11

- В файле `rx` = **ядерная метка приёма** (`SO_TIMESTAMPNS`), **формат не меняется**; пользовательская метка и гистограмма «пользователь − ядро» — только health.
- **Семантика (документируется в `docs/collector-ws-format.md`):** метка — на **чтение**, у самого нового пакета, вошедшего в это чтение (кадры, пришедшие одним чтением, делят метку; ранние кадры чтения получают метку позже истинной не более чем на длительность пачки, т. е. однобокая ошибка ≤ W; с отсрочкой NAPI — ещё ≤ `gro_flush_timeout`); размер чтения на сокет ограничивается, чтобы чтение редко охватывало два всплеска биржи; в health — число кадров, делящих метку.
- **Дедуп хранит минимум ядерной метки по линиям** (G4); порядок обработки внутри такта — по метке.
- **Точность ограничена часами:** chrony смещение +68 мкс, RMS 271 мкс, root dispersion 0,62 мс, без PHC; проверить `ptp_kvm` + chrony PHC refclock, если хост отдаёт (µs-уровень); смещение и дисперсия — в health, тревога > 1 мс. Для абсолютной задержки биржа→srv метка не точнее часов; для относительных сравнений (lead-lag) выигрыш реален.
- **Датированное переключение:** до переключения `rx` = пользовательская метка (после пробуждения: p50 +114 мкс, p99.9 +1,2–1,5 мс); после — ядерная (в среднем раньше на 0,1–0,5 мс). Дата и время переключения (UTC и GMT+4) фиксируются записью в `.claude/decisions.md` и в `docs/collector-ws-format.md`, а метка источника (`rx_stamp: user|kernel` с датой) — в манифесте суток `pool-<день>.json` (поле добавляется в манифест, не в формат файла данных, В-172).

### 2.6 Вторая линия (решение координатора по опции D)

Опция D как общее правило **отклонена** (критики: линия не чистая копия — BingX book03 69 % записей только по одной линии, у Bybit раньше +58 % состояний книги; 17:43 был srv-wide и затронул обе линии; запасная линия теряет секунды при подписке). Вместо неё — **измерение вклада по потоку**: 3-минутное по записанным кадрам готово (§1.8); на сутки — счётчик в писателе (S6) + замер 7 суток, числа показать владельцу; «запасная» — только по шардам, где вклад ≈ 0 по всем трём метрикам (уникальные записи, первая-по-линии > 1 мс, секунды тишины), отдельным решением позже. Ожидание от такой точечной замены — ≈ 0,1–0,2 ядра после остальных шагов.
