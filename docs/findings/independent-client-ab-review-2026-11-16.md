## Вердикт: принять с правками

Главные выводы подтверждены: независимый клиент не раньше боевого, покрытие равное, всплеск в :00 виден независимым клиентом и совпадает со steal гипервизора. Но формулировка «лаг соединения» в Вопросе 1 неверна по сути (см. правку 1), а «необъяснённый» рост `queue_lag` на book BingX объясняется и указывает на наш код (правка 3).

## Вопрос 1 — пересчёт

Окно 16:20:00–19:05:30; join по (символ, id); независимый лаг = ядерная метка − `T` своего сообщения; боевой `T` восстановлен из строки `t` как `rx_мс − lag − ET`.

| что | отчёт | пересчёт |
|---|---|---|
| лаг p50 / p99 по соединениям | 93,0–129,4 / 240,8–307,2 | 93,05–129,41 / 240,76–307,21 |
| боевой f00 / s03 p50, p99 | 99,5 / 108,0; 187,5 / 196,9 | 99,51 / 107,98; 187,50 / 196,91 |
| мин(пары) − боевой, медиана по 12 парам | −2,16…+0,28 | −2,12…+0,27 |
| первый из 4 − боевой, медиана | s03 −4,82, f00 −0,61 | −4,76 / −0,66 |
| доля ΔT ≠ 0 по парам (кроме f001+f003) | 0,946–0,995 | 0,946–0,995 |
| корр(ΔT, Δприход) | 0,83–0,93 | 0,827–0,933 |
| f001+f003: ΔT ≠ 0, Δприход p5/p95 | 0 %, −5,5/+5,4 | 0 %, −5,44/+5,30 |
| покрытие (T в окне ±120 с, «только у одной стороны» — по полному множеству другой) | s03 4/1, f00 4/0 | s03 0/0 (728 446 / 728 457), f00 0/0 (665 543 / 665 545) |
| дубли в боевых строках по (символ, id) | — | 0 и 0 |

Числа совпадают до сотых; расхождения в покрытии — краевые (у меня 0 / 0). Join и источник `T` верны: у каждого соединения свой `T`, боевой лаг считается по своему же сообщению. Отброшенный прогон «боевой rx − `T` чужого соединения» отброшен правильно: боевой `T` совпадает с `T` хотя бы одного из четырёх независимых только у 23,2 % (s03) и 50,4 % (f00) сделок.

**Правка 1 (обязательна): «медленное соединение» — смещение `T`, а не позднее получение.** По приходу (ядерная метка) смещение соединения от медианы четырёх по 10-минуткам: `s033` −0,1…+0,1 мс (среднее 0,0), `f000` −0,1…+0,3 (0,0), остальные −1,1…+3,3. А `T` − медиана `T` четырёх: `s033` −22,0…−6,0 мс (среднее −15,1), `f000` −35,0…+2,5 (−11,0). То есть `s033` получает сделки одновременно с остальными, но BingX ставит ему более ранний `T`; его «+25 мс лага» целиком из `T`. Неверны в отчёте: «Лаг соединения держится десятки минут и часы: `s033` выше медианы… на +6,8…+39,1», «доля быстрых соединений… `f000` и `s033` выше на +32,6 и +33,3», п. 11 «почему `s033` постоянно медленнее на +25 мс». Нужно: разделить «приход» и «`T`»; сказать прямо — устойчивого отставания соединения по приходу нет (медианы ±3 мс), есть разброс отдельной сделки между соединениями p5/p95 ±105…200 мс, и он идёт вместе с разностью `T` (поэтому — на стороне BingX до нашего хоста). Формулировку «на стороне BingX» оставить как «до нашего хоста (BingX/CDN)»: CloudFront от BingX этим замером не отделён.

Следствие для кода (не блокирует отчёт, задача отдельно): метрика `lag = rx − T` у BingX сравнивает соединения неправильно; проверка пути (`path_ok`/`path_rejected` по `p50_ms`/`p99_ms`, `src/collector/session.rs`) у BingX может браковать соединение со смещённым `T`, хотя оно не позже. Порог не проверялся — «вывод», проверить отдельной задачей.

Подтверждено:
- Steal в :00 — не от нашей и не от чужой нагрузки: 13.11 (до задач `hold_*` и до клиентов) он выше всего (32,4 %); в секунды пика `busy` гостя падает (17:00: 51 → 20 % при steal 69 %, idle 11 %) — CPU забирает гипервизор, а не наш спрос.
- Таймеров на :00 нет, кроме суточных в 00:00 (в отчёте «нет таймеров» — уточнить); фоновые демоны `arb_daemon`/`arb_turnover` идут в +15 / +30 с пятиминуток; `cron` неактивен. Perf exec/fork повторно не пересчитывал.
- `hold_*` (с 16:59:03) поднимают фон, но :00 не создают (см. дни и 14:00–16:00 в профилях).

**Правка 2: причинность «steal → лаг» не отделена от часового всплеска рынка.** В 0…+2 с одновременно: поток Binance ×2,5–2,7 (отчёт), CPU коллекторов и клиентов в 17:00:01 вдвое выше (`pidstat`: `alpha-collect-ab1` 132 %, `ksoftirqd/0,5` 56–62 %), и steal. Внутренняя задержка Binance не растёт: `E − T` bookTicker в +2 с p50 0 мс (фон 0), aggTrade 150 мс (фон 150) — значит, позже не ставится сама метка `E`; задержка после `E` на стороне биржи этим не исключается. Для «не наш код» это неважно (независимый клиент видит то же), но заголовок «Хост/гипервизор (steal)» надо смягчить до «совпадает со steal гипервизора; вклад часового всплеска на биржах не отделён».

## Рост `queue_lag` на book BingX (+7,6…+9,3) — объяснён, это наш код под нагрузкой хоста

Отчёт сводит «во время» в одно окно 16:21–19:05. Разбивка (медиана по шардам медиан `queue_lag_p99_ms`, без :00 и пятиминуток):

| группа | до 15:30–16:10 | клиенты 16:21–16:58 | клиенты + `hold_*` 17:01–19:05 |
|---|---|---|---|
| BingX book | 11,6 | 12,9 | **30,0** |
| BingX mark | 27,4 | 28,4 | **49,7** |
| BingX trade | 15,7 | 17,2 | 26,4 |
| OKX book / trade | 10,5 / 15,2 | 11,0 / 17,7 | 14,9 / 23,6 |
| Gate book / trade | 10,4 / 12,4 | 11,6 / 13,6 | 17,2 / 20,7 |
| Bybit book / trade | 16,9 / 22,4 | 15,2 / 21,5 | 20,4 / 28,9 |

Хост: idle 55,2 % → 23,5 %, steal 3,46 → 4,70 %. Клиенты рост не дают (+1,3 / +1,5 мс у BingX — как у контроля); рост приходит с `hold_*`, и процесс BingX к нему чувствительнее всех: book +18,4 мс против +4,4 (OKX), +6,8 (Gate), +3,5 (Bybit); mark BingX (клиенты на него не подписаны) +22,3. Выводы Вопросов 1–2 это не подрывает: все сравнения лага идут по ядерным меткам, до очереди. Но это свойство нашего коллектора BingX (вероятно, разжатие gzip в потоке приёма — «вывод», не мерил) — завести задачу; в отчёте заменить «не объяснён» этой разбивкой.

## Что исправить в отчёте

1. Вопрос 1: разделить приход и `T`; убрать «медленное соединение `s033`/`f000`», заменить числами смещения прихода (±3 мс) и `T` (−15,1 / −11,0 мс); «на стороне BingX» → «до нашего хоста (BingX/CDN)».
2. Вопрос 2: заголовок смягчить (steal совпадает; рыночный всплеск на часе не отделён); «нет таймеров» → «нет почасовых таймеров; суточные в 00:00».
3. «Бой не пострадал»: заменить «не объяснён» разбивкой A/B/C; добавить в «что не установлено» чувствительность BingX к CPU-нагрузке и задачу на неё.
4. Отдельной задачей: проверка пути BingX по `lag = rx − T` при смещённом `T` соединения.
