# Планировщик v2 (TK-071, постановка CEO 08.10 15:55): договор до кода

Исходное: alsched.py f129cc93 — пакует по заявленным `--cores` (и вычитает голые юниты по КВОТЕ), замер = заморозка всего
производства, `DISK_SLOTS=16`. Владелец: «считалось параллельно, ресурсы сервера использовались, забитый канал надолго — плохо».

## Что меняю (по пунктам постановки)

1. **Пакование по факту.** Решение о старте: `host_busy` (скользящее по 60 с, /proc/stat) < 0,90 и память в бюджете;
   `--cores` — нижняя оценка (резерв EASY сохраняется), не замок. Не больше одного нового старта за tick + «отстой»
   30 с (иначе перелёт: новая задача набирает ЦП не сразу). `legacy_busy` — по факту (used), не `max(used, quota)`.
2. **Диск.** Флаг подачи `--io seq` (HDD-тяжёлое последовательное чтение: волны, импорт, перепаковка): ≤ 1 задание `seq`
   на диск; остальные (ЦП-счёт, `DISK_SLOTS`=16 по калибровке 06.10) идут параллельно. ЦП-задания с чтением — как раньше.
3. **Замер без остановки сервера.** Класс measure получает изолированные ядра: cpuset `measure.slice` = K целых
   физических ядер (оба SMT-соседа), prod-слайс получает `AllowedCPUs` = остальные; память: `MemoryMax` prod-слайсу =
   MEM − резерв замера, своп у prod-слайса = 0 (п.4). Заморозка ВСЕГО — только `--exclusive` (веха по стене, редко).
4. **Своп в окне = 0**: `MemorySwapMax=0` соседям на время окна; перед стартом — `swapoff -a && swapon -a`, если
   MemAvailable > занятого свопа (замечание Судьи 08:00); иначе окно ждёт.
5. **Автоповтор** ok:false: демон переподаёт замер сам (≤ 2 раза), пишет причины; роль не участвует.
6. **Куски**: `submit --chunks сутки|месяц` — длинное сквозное задание нарезается на куски с наследуемым prio; короткое
   с меньшим `max_runtime` обгоняет между кусками (в EASY-резерве короткие и так бэкфиллятся, но кусок освобождает ядра).

## Метрика замера на изолированных ядрах (ПРОШУ СОГЛАСОВАТЬ — п.3 постановки)

- Промежуточные решения (А/Б вариантов, ×N): **user-CPU-секунды замеряемого юнита** (cgroup `cpu.stat user_usec`) и
  **instructions:u** (`perf stat`, если доступен; иначе только CPU-с). Стена в этом режиме — справочная.
- Допуск повторяемости: пара одинаковых прогонов, один в пустом окне, другой при полной нагрузке prod на остальных
  ядрах: |Δ CPU-с| ≤ 1 %, |Δ instr| ≤ 0,5 %. Если не держится (общий L3/память давит) → замеры идут на сокращённом prod
  (prod ограничен N ядрами на время замера), N подбирается калибровкой; ни при каком N — только `--exclusive`.
- Годность окна (ok:true): чужое ЦП на ядрах замера ≈ 0 (по-ядерный /proc/stat, ≤ 1 % ядро-времени окна), своп 0,
  чужое чтение того диска, с которого читает замер — по текущим правилам judge_window (фон BG_OPS_S, SEEK_S).
- Веха по стене (±1 %): только `--exclusive` — прежнее окно, как сейчас.
- Открытый вопрос Судье: допустима ли для вех «×5, ×10» стена, пересчитанная из CPU-с + I/O отдельно, или стена только
  в пустом окне? Моё предложение — стена только в `--exclusive`.
