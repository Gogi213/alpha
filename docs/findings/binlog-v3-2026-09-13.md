# Формат бинлога v3: замер A/B на живой записи (2026-09-13)

Тикет 43 (`.autopilot/2026-09-11-lob-density-ed3/tickets/43-binlog-v3.md`) — там же
**пререгистрация**: метрики M1, M1b, M1i, M2, M3, M4, M5, M6 и пороги решения назначены до
кода. Замер сделан командой `lob binlog-stats --path <файл> --reencode` (только чтение), счётчики —
`lob binlog-stats` без флага.

**Материал:** закрытые файлы суток `2026-09-12` каталога `data/always-on/20260912T201737Z`
(все десять инструментов пула, 29 203 623 записи, 34 785 кадров), плюс метаданные файлов суток
`2026-09-13` для M2. Живой коллектор не трогался: процесс не перезапускался, писался только
новый бинарник.

## Что сделано в коде

Формат v3: запись = `ev` группы, `block` (бит `attrs`), цена и размер; метки `exch_ts`/`local_ts`
хранятся **один раз на сообщение биржи** (группу), `order_id`/`fval` в формате нет, `ival` заменён
битом. Читатель понимает **обе** версии: v2 — та форма, которую пишет живой коллектор до
перезапуска (В-41), её счётчики мёртвых полей (`Reader::legacy_dead_fields`) остались
воспроизводимыми. `--reencode` перекодирует те же записи тем же zstd-1 (`ZSTD_LEVEL`) и сравнивает.

## Почему порог не взят — полевой бюджет

Сырые байты на запись (тот же замер, `reencode поля`):

| поле | v2 SOL | v3 SOL | v2 LSK | v3 LSK |
|---|---|---|---|---|
| `ev` | **5.00** | 2.14 | **5.00** | 0.37 |
| `exch_ts` (+ эпоха) | 4.96 | 2.13 | 4.62 | 0.35 |
| `local_ts` | 4.95 | 2.12 | 4.48 | 0.33 |
| цена | 1.02 | 1.02 | 1.04 | 1.04 |
| размер | 2.22 | 2.22 | 1.91 | 1.91 |
| заголовок группы | 0 | 0.85 | 0 | 0.15 |
| мёртвые (`order_id`/`ival`/`fval`) | 3.00 | 0 | 3.00 | 0 |

Три вывода, которые объясняют результат:

1. **`ev` (5.00 Б/запись) — самое дорогое поле живого лога.** Это флаги `hftbacktest` вида
   `0x50000001`, то есть пятибайтовый varint в каждой записи. В v3 он уезжает в заголовок группы
   и падает до 0.37–2.14, но остаётся крупнейшим после цены и размера.
2. **Снятая избыточность частично забирала работу у zstd.** Сырое тело v2 сжимается в 2.8 раза,
   v3 — в 1.4: повторяющиеся метки времени и флаги zstd и так давил почти в ноль. Отсюда разрыв
   между экономией сырых байт (вдвое) и экономией на диске (5–26 %).
3. **Экономия тем больше, чем крупнее сообщение.** LSK (13.7 записей на сообщение) даёт −25.6 %,
   SOL/NEAR/DOGE (2.3–2.4 записи на сообщение, то есть почти «одна запись — одно сообщение») —
   1–3 %. Мёртвые поля (3.00 Б/запись ровно, как и обещал прошлый замер: 0 % ненулевых) убраны на
   всех десяти.

## M1i — «кодировать уровень индексом» — отклонён числом

Симуляция: у книжной неснапшотной записи дельта цены заменена одним байтом индекса (при ≤ 50
уровнях стороны индекс < 128, uvarint = 1 байт; снимок кадра 0 всё равно несёт абсолютные цены),
тот же zstd-1.

| инструмент | «индекс» от v3-пачки |
|---|---|
| SOLUSDT | 101.3 % |
| SUIUSDT | 101.8 % |
| ZECUSDT | 102.2 % |
| STORJUSDT | 105.5 % |
| LSKUSDT | 111.0 % |

Индекс **дороже** дельты цены на всех пяти файлах: соседние уровни одного сообщения отстоят на
1.0–1.1 байта варинта, а индекс — ровно байт, плюс он не сжимается как дельта. Порог ≥ 10 %
экономии не взят, поэтому вариант отклонён — и это не только про байты: чтобы индекс стал
настоящим, читателю нужна **книга инструмента**, то есть «кадр читается независимо» (Decision 7)
ломается, а вместе с ним — независимость усечённого хвоста и возможность читать кадр без
предыдущих суток. Вдобавок `Book::apply` требует `u` (последовательность обновлений), которого в
логе нет; хранить его — отдельная правка формы, и она покупала бы отрицательную экономию.

## M2 — объём на топ-100 (экстраполяция, не замер)

Пул десяти инструментов за сутки `2026-09-13` (по метаданным, ~20 ч записи): **786.4 МБ**;
LSKUSDT — 440.3 МБ, то есть 56 % пула. К суткам ≈ 0.94 ГБ на пул. Экстраполяция ×10 (топ-100
по обороту — не замер): **≈ 9.4 ГБ/сутки v2 → ≈ 7.7 ГБ/сутки v3** (≈ 3.4 → 2.8 ТБ/год).

Отдельно: `LSKUSDT-2026-09-12.binlog` — 18.9 млн записей за 3.2 часа, 79.7 МБ (≈ 600 МБ/сутки) —
в двенадцать раз больше SOL на сопоставимом числе записей. Это не артефакт формата, а свойство
инструмента (13.7 записей на сообщение: глубокий стакан с мелким шагом), и именно он выигрывает
от v3 больше всех. Бюджет Decision 23 (150 МБ/символ-сутки) не нарушен ни в v2, ни в v3.

## M4 / M5 / M6 — потерь нет

- **M4:** round-trip v2 → v3 → v2 — **0 расхождений** на всех 29 203 623 записях десяти файлов;
  перекодировка v2 совпала с файлом на диске **на всех 34 785 кадрах** (значит, замер сравнивал
  именно те байты, что лежат в записи, а не свою реконструкцию).
- **M5:** все кадры v2 прочитаны новым читателем, ни одной ошибки формата; версия 2 распознана как
  legacy, счётчики мёртвых полей на живых файлах — нули (как и в прошлом замере).
- **M6:** ни один кадр не отвергнут потолком заголовка ни при чтении, ни при перекодировке.

## Вердикт

1. **Формат v3 принят в код** — он нигде не хуже: байты 74.4–98.8 % от v2 (пул 82.1 %), кодирование
   и чтение в 2–3 раза дешевле, потерь ноль, старая запись читается.
2. **Пререгистрированный порог −25 % на диске (`M1 ≤ 0.75`) взят только на LSK.** Причина названа
   числом: zstd уже снимал повторяющиеся метки, а сообщение среднего инструмента — 2.3–2.4 записи.
   Поэтому раскатка v3 на **живой** коллектор — решение владельца; до него процесс пишет v2, и это
   безопасно, читатель знает обе версии.
3. **Отклонены замером:** кадр на сообщение (M1b, 129–273 % от v2) и «уровень индексом» (M1i,
   101–111 % от v3 — дороже дельты, плюс требует состояния книги у читателя).
4. **Следующий кандидат — код типа события.** `ev` стоит 5.00 Б/запись сырых байт на **каждом**
   инструменте, а различных значений в файле 4–6; таблица «код → `ev`» на кадр (с escape для
   незнакомых значений) сняла бы почти всё это. Ожидание по сырым байтам — до −4.5 Б/запись, но
   сжатый эффект из этого замера не следует (см. вывод 2), поэтому вариант обязан идти **своей
   предрегистрацией и своим замером**, а не «по очевидности».
   Второй кандидат — уровень zstd на меньшем теле (уровень 1 выбран замером на v2, T25).

## Цена решения

Правка трогает формат, `Record` (нет `order_id`/`fval`, `ival` → `block`), `export`/`replay`/
`verify`/`session::sink`/`record` в местах построения записи, `binlog-stats` (+`--reencode`) и
тесты. Горячий путь по аллокациям не изменился (те же гейты `write_path_allocates_nothing_*`
зелёные), семь запретов `interfaces.md` не задеты: кодировщик не аллоцирует, групповая разбивка —
просмотр вперёд по уже собранному срезу. Тесты: 707 passed, 0 failed, 5 ignored; clippy и fmt
чистые.

## Остановка записи и одно расхождение в счёте объёма

Владелец 2026-09-13: «выключай коллектор местный … будем переезжать на сервер». Запись остановлена
**штатно** (файл `<root>/stop`, В-41) в 16:22Z: процесс завершился, `session.json` записан с
`closed=true`, `records_total = 209 594 979`, `reconnects = 3`, `resyncs = 0`,
`frames_failed = 0`. Итог по диску: 20 файлов двух суток, **928.2 МБ** (09-12 — 139.2 МБ за 3.2 ч,
09-13 — 789.0 МБ за ~19.6 ч).

**Расхождение, которое стоит помнить перед сервером:** `session.json.bytes_written = 827.3 МБ`
против 928.2 МБ на диске (−11 %). В коде это `session.rs:660` — сумма
`writer.get_ref().bytes_written()` по **текущим** `FrameSink` каждого инструмента, а счётчик живёт
внутри приёмника одного файла, то есть части, закрытые раньше (ротация суток), в итог не попадают.
Числа дня `2026-09-13` (789.0 МБ) с показанием 827.3 МБ всё же не сходятся, поэтому механизм
назван, но **не доказан**: это отдельный вопрос, и он важен ровно тем, что объём — предмет
оптимизации владельца. Для M2 выше брались размеры файлов (метаданные), а не счётчик, так что
экстраполяция на топ-100 стоит на том, что лежит на диске.
