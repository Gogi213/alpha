## Раскладка строки Event: байты горячего пути на бумаге (08.10, TK-048)
Читано: `vendor/hftbacktest/src/types.rs:344–364` (`Event`), `backtest/mod.rs:653–667` (`advance`), `src/lob/backtest.rs:3512–3527` (развёртка ленты в `buf`), `compact.rs:130–175`.
- `Event` = 64 Б, `align(64)` — ровно одна строка кэша на событие. Горячий путь читает `ev, exch_ts, local_ts, px, qty` = 40 Б (62,5 %); `order_id, ival, fval` = 24 Б (37,5 %) нули и не читаются. `advance` (local и exch — два прохода по `data`) читает `ev` и `exch_ts/local_ts`; `process` — `ev, px, qty, ts`.
- Поток байт на строку (лента сжатая): источник `CompactEvent` 32 Б читается один раз → `expand` пишет 64 Б в `buf` → local читает 64 Б-линию → exch читает ту же линию. Для полной ленты (`as_events()` = Some) `buf` нет. Строк кэша на событие: 1 при любой раскладке до 64 Б; сжать «строку ленты» ниже линии можно лишь до 32 Б (убрать нули и сжать метки), т. е. −50 % байт ленты, но `Processor`/`Reader<Event>` движка требуют `&[Event]` — переписывание типа во всём vendor (десятки сигнатур), не флагом.
- Что можно выиграть: только собственное время `advance` (5,45 %, из них часть — промахи по линии `data[rn]`) + запись `buf`. Верхняя граница при НУЛЕВОЙ стоимости всех обращений к строке ленты = 5,45 % ⇒ потолок ×1,06. Порог Судьи (сжатие ≥30 % байт горячего пути) формально достижим только переписыванием `Event` (−50 %), но выигрыш ≤ 5,5 % ЦП < порога 3 % в обоих порядках после накладных — не окупает риска «байт в байт».
- Не замерено: размер `buf` на попытку (строк × 64 Б) — если он больше L2, то запись+два чтения идут из L3/ОЗУ; в d15 счётчик `note_attempt` это даёт, но решение не меняет (потолок выше).
- Вывод: раскладка строки Event закрыта числом: ×1,06 в пределе. Серия ЦП-рычагов внутри строки исчерпана (e22–e25 ≤0,8 %, К-3 <1 %, 2+3 ≤3 %, Event ≤5,5 %). Для ×10 остаётся ЧИСЛО строк (2,1·10⁹ при ленте 190 М, перечитывание ×11) — алгоритмический уровень, а не стоимость строки.
