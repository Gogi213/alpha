# Steam Deck ↔ Storage Box: замеры, причина медленности, формула (TK-026, 02.10.2026)

Артефакты: `docs/findings/deck-box-speed-2026-10-02.csv` (все замеры), скрипт замеров `tools/compute/tk026-bench.py`,
конвейер `tools/compute/tk026-pipeline.py`. На ящике ничего не менялось и не удалялось (только `ls`, чтение, `dd`).

## Итог цифрой

1. **Потолок доступа деки к ящику ≈ 6,5–7 МБ/с (≈ 55 Мбит/с).** Его берёт **один любой поток** (ssh `dd`, sftp, scp, rsync:
   5,0–7,2 МБ/с); 2/4/8/16 потоков не дают больше (6,1–6,9). Тот же потолок — к любому ЦОД Hetzner (Falkenstein 6,7,
   Nuremberg 6,5, Ашберн 5,9, Хельсинки 5,7 МБ/с при RTT 71…170 мс) → это **не задержка и не ящик, а ширина участка
   «дека ↔ дом»** (раздел «Причина»).
2. **Медленность sshfs (`~/sb`) — вторая, отдельная причина: окно чтения.** Один читатель через sshfs — 1,9–2,9 МБ/с
   (потолок 6,5 не достигается), 16 читателей — 6,35. Это в 2,2–3,4 раза ниже потолка, **лечится** (ниже), но выше потолка
   не поднимет.
3. **Сжатие бесполезно:** бинлог уже zstd-кадрами (`src/binlog/mod.rs`, v3; архив — один zstd-поток); zlib-1/3/6 на 24 МБ
   образца — ×1,00; `ssh -C` 6,4 МБ/с (без прибавки).
4. **Формула (раздел ниже): доставка — rsync, 2 потока, конвейер «сутки N+1 качаются, пока считаются сутки N»**. Сутки пула
   1,14–2,20 ГБ в среднем по месяцу — доставка 3–6 мин на потолке; счёт суток на деке 50–60 мин (TK-018) → **доставка
   полностью прячется за счётом, дека упирается в счёт, а не в ящик**. Янв–июн 260,9 ГБ — 11,1 ч доставки при 166 ч счёта.
5. **Замер подкачки в RAM деки (`/dev/shm/alpha-stage`, В-162), 02.10 ~03:00:** 01-01 — 1,18 ГБ за 173 с = **6,80 МБ/с**;
   01-02 — 2,01 ГБ за 263 с = **7,65 МБ/с**; sha256 копия↔ящик совпала у обоих суток (270 файлов: 54 бинлога + 216 D20).
   Скорость та же, что на диск (потолок канала). **Цена RAM-stage — память заданий**, не скорость (раздел «Stage в RAM»).
   По В-163 (владелец ~03:10: «деку пока не трогаем») подкачка остановлена; доставлены и сверены только 01-01 и 01-02,
   сутки 01-03…01-08 не доставлены.

## Замеры

Деке: Wi-Fi 5 ГГц (SSID MAGTI, сигнал −68…−75 дБм, **tx 351 Мбит/с, rx 104 Мбит/с — VHT-MCS 5, NSS 2**), RTT до шлюза
3,7 мс, до ящика 71,8 мс (88.99.48.227, Falkenstein; тот же RTT, что до `fsn1-speed.hetzner.com`). Дека простаивала

## Причина (подтверждена замером)

**А. Потолок ≈ 6,5–7 МБ/с — домашний интернет до Германии (общий для деки и ПК), а не Wi-Fi деки, не задержка и не ящик.**
- Один поток ssh/sftp/rsync/curl уже даёт 6–7 МБ/с, добавление потоков (2…16) суммы не увеличивает → окно TCP не
  ограничивает (ss: `rcv_space` 2,3 МБ при 72 мс = 32 МБ/с на поток).
- Те же 5,7–6,7 МБ/с к четырём ЦОД Hetzner на разных RTT (71, 150, 170 мс) → потолок не зависит ни от пути, ни от RTT.
- Wi-Fi деки потолком не является: ПК→дека по LAN 10,5–11,3 МБ/с и дека→ПК 10,9 МБ/с (ssh, 400 МБ; замер CEO 02:40,
  провод ПК 1 Гбит/с); у деки rx-битрейт 104 Мбит/с (≈ 13 МБ/с физически) при сигнале −68…−75 дБм.
- Канал общий: у ПК и деки один внешний IP (212.58.120.61); пока дека тянула с ящика ≈ 5 МБ/с, проводной ПК получил от
  Hetzner fsn1 всего 0,5–0,85 МБ/с (CEO 02:38) и 4,1/6,0 МБ/с в другие минуты (мои замеры) — канал плавает, суммарно
  ≈ 6–7 МБ/с. Чистого замера «ПК один, дека молчит» нет: подкачка суток для задания владельца идёт без перерыва, останавливать
  её ради теста не стал.

**Б. sshfs — упор в задержку (окно чтения).** Один поток через sshfs читает с окном readahead ≈ 128 КБ (4 запроса SFTP по
32 КБ): 128 КБ / 72 мс = 1,8 МБ/с — измерено 1,9–2,9 МБ/с. Предсказание проверено масштабированием: N читателей → N окон →
2,9 / 4,6 / 5,2 / … 6,35 МБ/с до потолка А; `direct_io` с блоками 8 МБ — 4,1 МБ/с одним читателем, 6,6 — четырьмя.
(Прямой проверки `read_ahead_kb` именно fuse-устройства не делал — `read_ahead_kb` нужен root; вывод о 128 КБ —
по формуле и по поведению.) **`direct_io` для программы не годится:** `binlog::Reader` читает по `File` мелкими кадрами —
без кэша ядра каждое `read` стало бы сетевым раундом 72 мс. Поэтому читать программе нужно **локальную копию**.

## Как программа читает сутки (замер по коду)

`open_replay_feed` → `ReplayFeed::open(0, File)` → `binlog::Reader` (`src/commands/lob/backtest/feed.rs:42`,
`src/binlog/mod.rs:1394`): файл открывается целиком и читается **последовательно от начала до конца** кадр за кадром
(`u32 длина | zstd-кадр`); `events_from_paths` складывает все события частей суток в один `Vec` (в память). Вразброс
(seek) не читает; байт за сутки читает ровно столько, сколько весят файлы суток символа (по всем монетам пула —
1,14–2,20 ГБ/сутки в среднем по месяцу). Для границы D/D+1 (`session_parts_for`) нужны также файлы D+1.

## Формула

**Доставка.** `rsync` по ssh (порт 23, ключ `id_storagebox`), `--partial --files-from`, **2 потока** (один уже на
потолке; второй — запас на разброс окна и на мелкие файлы), шифр по умолчанию, без `-C`. Целостность: код возврата rsync
(контрольная сумма файла) + совпадение размера с `ls -l` ящика. Альтернативы в пределах шума: sftp 6,6–7,2, ssh `dd`
6,0–6,9; rsync выбран за контроль целостности и дозагрузку.
**Конвейер** (`tk026-pipeline.py`): сутки N+1…N+K качаются, пока считаются сутки N (`--ahead`), счёт стартует на сутки с
маркером `.ready`; после кода 0 каталог суток **удаляется только внутри stage** (симлинки не трогает), остаётся маркер
`_done/<сутки>`; на ящике ничего не удаляется. Актуальная версия (В-162): stage — RAM `/dev/shm/alpha-stage`,
`--budget-gb 6 --reserve-gb 1` (новые сутки не начинаются, пока занято + сутки > 6 ГБ или MemAvailable − сутки < 1 ГБ),
`--meta-dir ~/alpha/stage` (`_done/` и `pipeline.csv` — мелкие, на диске); сутки качаются **строго по хронологии** (так
`.release` суток D, который ждёт счёта D и D−1, не даёт тупика на бюджете 6 ГБ). Первая, дисковая версия (`--ahead 2`,
`--budget-gb 8`, `--reserve-gb 12`) заменена и не запускалась после В-162.

### Stage в RAM (замер 02.10 ~03:00–03:10)

Формат стыка с Исследователем: `<stage>/<D>/root/` (бинлоги, `rsync -t`, `.events` не качаются), `<stage>/<D>/D20/`,
`.ready` пишется последним, `.release` — потребителем (тогда каталог удаляется только внутри stage). Целостность:
размеры == `ls -l` ящика + sha256 (`tools/compute/tk026-sha.sh`: хэши считает ящик — канал не грузится, оболочка ящика
принимает по одному `sha256sum` на `ssh`, число строк ответа проверяется).

| сутки | ГБ | время | МБ/с | sha256 |
|---|---|---|---|---|
| 2026-01-01 | 1,18 | 173 с | 6,80 | ok, 270 файлов |
| 2026-01-02 | 2,01 | 263 с | 7,65 | ok, 270 файлов |

**Память — главный эффект.** tmpfs вычитается из `MemAvailable`: 11,5 → 7,6 ГБ при 4,6 ГБ в stage. Очередь `alpha-gridq`
считает место заданий по `MemAvailable` минус резерв (1536 МБ): в 03:08 — «голове нужно 3072 МБ, свободно под задания
2895 МБ». При заполненном stage 6 ГБ под задания остаётся ≈ 4,5 ГБ — **одна полоса** (проход 1 на 4 ГБ либо 1–2 прохода
2/3 по 3 ГБ): 181 сутки ≈ 166 ч вместо ≈ 55 ч при трёх полосах. Своп деки — zram0 7,2 ГБ (сжатая RAM, не диск) +
swapfile 1 ГБ на диске (используется, только когда zram полон). Варианты, которые не выбраны (решение CEO/владельца,
дека заморожена В-163): (А) оставить, срок покажет неделя; (Б) бюджет stage 4,5 ГБ (D, D+1, D+2) — полос столько же;
(В) заявки `--mem-gb` по измеренным пикам вместо 4/3/3 ГБ — вероятно 2 полосы; (Г) stage на диск деки — владелец против.
Рекомендация: А+В.

**Время (по замеру потолка 6,5 МБ/с = 23 ГБ/ч; счёт — 50–60 мин/сутки на деке из TK-018, 13:05, замер Исследователя
для всей сетки ~320 клеток; для одной клетки или гейта счёт — минуты):**

| набор | суток | ГБ | доставка (6,5 МБ/с) | через sshfs сейчас (2,4 МБ/с) | счёт на деке (55 мин/сутки) |
|---|---|---|---|---|---|
| январь–июнь | 181 | 260,9 | 11,1 ч | 30,2 ч | 166 ч |
| август–сентябрь | 61 | 109,7 | 4,7 ч | 12,7 ч | 56 ч |
| **итого** | 242 | 370,6 | 15,8 ч | 42,9 ч | 222 ч (≈ 9,3 сут) |
| одни сутки (средние: янв–июн 1,44 ГБ / сентябрь 2,20 / макс 3,18) | 1 | 1,44 / 2,20 / 3,18 | 3,7 / 5,6 / 8,2 мин | 10 / 15 / 22 мин | 50–60 мин |

С конвейером полный счёт на деке = **счёт + 4–6 мин на первые сутки** (≈ 222 ч); без конвейера, читая через sshfs, —
+ 43 ч (+19 %). Деке не нужен другой способ доставки: **«супер быстро» упирается не в ящик, а в счёт** (50–60 мин на
сутки сетки). Ускорение доставки имеет смысл только для коротких задач (одна клетка, гейт, проба на сутках пула):
3,7 мин вместо 10–15 мин через sshfs. Если нужно быстрее полных 222 ч — это уменьшение работы на сутки (клеток) или ядра
для счёта, не ящик — вне этого тикета.

Сухой прогон конвейера (первая версия, 2 суток авг 21–22, фальш-счёт `sleep 90`, 2 потока): доставка 2,31 и 2,29 ГБ за
442 и 425 с = 5,2 и 5,4 МБ/с (параллельно шли мои LAN-тесты); сутки N+1 качались во время счёта N (ожидание счёта второй
суток доставкой 334 с = остаток; первой — 445 с); после кода 0 каталог суток удалён (только внутри stage), маркеры
`_done/` на месте, диск 28 ГБ → 28 ГБ, на ящике ничего не менялось (только `ls` и чтение).

## Что не измерено / ограничения

- Потолок отнесён к домашнему интернету по косвенным признакам (LAN 11 МБ/с, любой ЦОД Hetzner 5,7–6,7, потоки не
  прибавляют, канал общий с ПК); чистого «ПК один / дека молчит» и замера у другого провайдера нет — если канал будет
  расширен, все сроки доставки пересчитываются, конвейер остаётся тем же (меняется только `--streams`).
- Разброс окна к окну ±15 % (Wi-Fi, сигнал −69 дБм); значения 4,5–7,2 МБ/с у разных способов — в пределах этого шума.
- Время счёта суток (50–60 мин) взято из TK-018, моим замером не является.
- RAM-stage измерен на двух сутках (01-01, 01-02); 01-03…01-08 не доставлены (В-163). В `/dev/shm/alpha-stage` на деке
  остались 01-01, 01-02 и частичные 01-03 — очистка и дальнейшая работа по узлам — TK-027, на деке ничего не менялось.
- Влияние стейджа на скорость счёта (одна полоса вместо трёх) — расчёт по заявкам памяти, не замер недели.
- Проходы Исследователя на 01-01 (p1 77 с, p2 32 с при rc=0, логи по 12 байт) — не проверены мной, передано ему.
