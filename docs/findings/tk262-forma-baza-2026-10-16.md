**Мерка:** `tools/compute/bs-launch.sh` (ветка `tk262`) — настоящий `tools/launch/run-launch.sh` → `day-cells.sh` (xargs -P 12 по суткам),
BIN `alpha-tk231-pgo` (MANIFEST), флаги те, что ставит форма. Срез: план F1 (TK-231), март 2026, первые 10 std-клеток × 24 суток из 31
(день-порядок «тяжёлые первыми», выброшена каждая 4-я: веса 33…6 символов сохранены). Выход — `/data/tk0262/w1/pass-<метка>/` (вне Летописи и канона,
хешей не заводит). Окно — `benchrun.sh wave`, кэш сброшен перед проходом. Режим A/B: `BIN_B=<бинарь>` для меток B*.

- Шум A1/A2 — 0,2 %. Выходы A1 и A2 совпали байт в байт (984 файла).
- ЦП (из 16 потоков): user 8,9 %, sys 2,2 %, **iowait 46,4 %**, простой 42,4 %.
- Слотов занято 11,2 из 12 (занятость слотов 96,6 %, Σ grid 2394 с), но ЦП работает ≈1,8 потока: процессы ждут диск.

- Бинлоги суток 24 дней по символам b1 — 7,46 ГБ, прочитано 12,3 ГБ (×1,65): разница — carry-root D−1, approaches/touches, режим. Разбивка по стадиям — ниже.

**Вывод:** форма упирается в HDD (iowait + простой ЦП ≈ 89 %), а не в ЦП и не в хвост. Кандидаты «было/стало» по числам формы (по убыванию отдачи, оценка — не результат):
1. число читателей/слотов при том же диске: `NX=12` против меньшего (A/B через `NX`/`EXTRA_B`) — 60 МБ/с на HDD при 12 потоках чтения похоже на потерю на поиске;
2. общий кэш суток (Э-18: группы клеток одних суток подряд, G=8, TK-259) — читать сутки один раз;
3. лишние ×1,65 чтения (carry, approaches) — через разбивку по стадиям.

**Не сделано в этом запуске:** 3 против 10 клеток (срез 10 клеток единственный; сравнение — отдельным заказом).
Сделано п.3: `docs/COMMANDS.md` (новая мерка, стенд помечен), `tools/compute/calibrate.sh` (строка в шапке).

## Стадии (проход C1, `E2E=1`, тот же срез, стена 212,1 с)

C1 = A + учёт `ALPHA_E2E`: стена +2 % (212,1 против 208,0), выходы совпали с A кроме `manifest.txt` (в него пишется строка `env:ALPHA_E2E=…`, 528 файлов
из 984; остальные 456 — байт в байт). Учёт идёт в один файл из 12 процессов: 90 из 4929 строк (1,8 %) перемешаны и отброшены — отчёт `e2e-report.py`
по 444 монето-суткам, доли надёжны, сумм как абсолютов не брать. Отчёт и сырьё — `/data/tk0262/w1/pass-C1/e2e*`.

| стадия | ЦП, с | ожидание (стена−ЦП), с | прочитано, ГБ |
|---|---|---|---|
| events (decode+carry+count) | 126 | **702** | 8,2 |
| touches_load | 42 | **369** | 2,3 |
| setup | 3 | 144 | 0,0 |
| windows + drive + prep | 89 | 0 | 0,0 |
| итого | 260 | 1215 | 10,5 |

- **82 % ожидания — две стадии чтения:** events 58 % и touches_load 30 %; ЦП-стадии (windows/drive) ожидания не имеют. ЦП — 18 % всего времени монето-суток.
- Внутри events: decode ЦП 107 / стена 350 с, carry ЦП 22 / стена 303 с — carry (чтение суток D−1) ждёт диск почти полностью.
- touches_load читает 2,3 ГБ при ЦП 42 с, ожидание 369 с — самая «дорогая» по секундам на гигабайт стадия (160 с/ГБ против 85 с/ГБ у events).
- setup 144 с ожидания при 0 ГБ — вероятно, открытие/метаданные на HDD (требует отдельной пробы).

**Что мерить «было/стало» первым (по числам формы):** (1) `NX` ниже 12 на тех же сутках (читатели делят один sdb); (2) общий кэш суток Э-18 —
сразу бьёт в events+carry (60 % ожидания); (3) touches_load — читать touches один раз на сутки, а не на клетку.
