Плагин role-play-vibing 1.8.35: `bus/{bus,busclient,watcher}.py`, `dispatcher/{bus_link,dispatch,watch}.py`.
v2 после возврата Судьи (20:21): v1 неверно назвал корень инцидента.

## Факт инцидента 12.10 (dispatch.run.log 21277…22123)

00:26→01:40 каждая сверка `_reconcile` к calc (89.163.242.211) **и** vps (13.140.29.171) — ssh код 255 «Connection timed out». Шина живёт на
calc:8788 (тот же хост). Это разрыв ПК(диспетчер) ↔ calc/vps, а не падение процесса шины. Событие «готово» не терялось — сторож и шина на calc;
очередь с ack и курсором `after` выдала бы его по возврату связи (будка wait_for-met 01:52 = возврат ssh). `ssh-calls.log` пишется ДО ssh —
«сверка шла» по нему ложно. Ошибка видна только в `dispatch.run.log` раз в ~10 мин (троттлинг `_wait_err`). **Дыра: нет детектора «диспетчер слеп».**

## Дизайн (порядок = приоритет)

**(в) Детектор слепоты + тревога вне calc — ПЕРВЫЙ пункт.**
- Диспетчер ведёт счётчик подряд идущих неудач связи: ssh код 255/таймаут сверки и пробы по **каждой** машине из набора `host:` + неудача запроса к шине
  (`Link.disp.up is False`). «Слеп» = все машины и шина недоступны (или каждая из тех, к которым есть живые `wait_for`) дольше `RPV_BLIND_ALERT_S`
  (по умолчанию 300 с = 5 мин, принято Судьёй; env + ссылка на вердикт 12.10, CEO оформит В-## при влитии). Связь самого ПК (`watch.pc_link_up`)
  отличает «обрыв ПК» от «лежат машины» — в тревоге указывается.
- Канал тревоги не зависит от calc: (1) файл `.claude/dispatcher/ALERT-BLIND.txt` (атомарно, содержит время начала, список машин, число ждущих тикетов);
  (2) звук/окно на ПК (Windows: `msg`/`[console]::beep` через `hide.run`, без сети) ; (3) `PushNotification` владельцу, если сеть ПК жива;
  (4) строка в `ceo-wake.log` (локально). Повтор раз в 30 мин, пока слеп; одна строка «зрение вернулось (простой N с)» после первого успеха.
- Реализация: `dispatch._wait_err` уже видит каждую неудачу — добавить `blind.record(alias, ok)` в точках `_reconcile`/`_host_probe`/`Listener._state`;
  решение — чистая функция `blind.evaluate(state, now)` (тестируемо без сети).

**(б) Сверка по факту при возврате зрения.**
- Триггер — не только `bus-up`, но и **первый успешный ssh после серии неудач** по любой машине: немедленная `_reconcile()` (флаг `_RECON_NOW` +
  `_WAIT_NEW.set()`), плюс `watch.triage_waits` со всеми формами (`host:`/`job:`/`ci-run:`/`ticket:`), будить по `met`/`done`.
- Пока `blind` или `Link.down_since` — период сверки 60 с вместо 300 с. Гарантия: роль проснулась ≤ 60 с после снятия разрыва.

**(а) Журнал событий — меньший пункт.** Дыра реальна, но только при падении процесса шины: `busclient.post` при `None` кладёт в spool
`%TEMP%/rpv-bus-spool.jsonl`, досыл — только со следующим удачным post того же процесса; `watcher.py` ставит «послано» (`running.pop`, `files_seen.add`,
`jobs[...]`) после `post→None`. Исправление: spool в постоянный путь (`~/.rpv/outbox.jsonl`), досыл по таймеру 15 с в самом watcher'е, «послано» —
только по ответу шины. Второй транспорт и маркеры `~/rpv/events` читаемые диспетчером по ssh **не делаем** (при разрыве ПК↔calc бесполезны, шина и так
держит очередь с ack).

**(в2) Наблюдение за процессом шины — как есть + мелочь.** `Restart=always` уже есть; добавить `GET /health` и пинг сторожа раз в 30 с; автоперезапуск
по ssh — оставить как запасной, не как защита от инцидента 12.10.

## Тест приёмки

1. **Стенд разрыва (главный):** правило брандмауэра Windows на ПК, блокирующее исходящее на 89.163.242.211 и 13.140.29.171 на 5 мин, во время
   короткого задания (jobrun.sh, sleep 90 + файл хода). Критерии: тревога (файл + звук + Push) ≤ `RPV_BLIND_ALERT_S` + 1 цикл; после снятия правила
   тикет `wait_for host:calc:<файл хода>` проснулся ≤ 60 с. Правило снять в `finally` (риск: оборвать собственную сессию — задавать правило только на
   адреса машин, не на весь исходящий).
2. Юнит-тесты: `blind.evaluate` (все недоступны → тревога после порога; одна жива → нет; повтор раз в 30 мин; возврат → одна строка); «первый успех
   после серии неудач» → `_RECON_NOW`.
3. Доп.: остановка процесса шины на 5 мин + watcher с `post→None` — событие приходит ≤ 15 с после возврата, без дублей (`events.id UNIQUE`).
4. Регрессия: `fastcheck.py` плагина.
