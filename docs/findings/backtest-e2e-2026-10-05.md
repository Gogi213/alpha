# «Вне стадий» разобрано + стенд /dev/shm (бинарник a3 с `ts`, 05.10 ~06:50)

**QUICK5 a3** (`/data/tk048/orch-q5a3.out`, 40 единиц, 3 560 слот-с по `units.txt`): запуск шелла → строка «запуск» 4,9 с на все единицы; последняя стадия → выход процесса 0,6 с; старт процесса → первая стадия 114 с (2,8 с на единицу — разбор вердикта/планов до первого символа). Старт и выход — не причина.
**Главная корзина «вне стадий» = 567 с из 3 440 (16,5 %): 391 зазор перед `setup` нового символа, в среднем 1,45 с** (ещё 23 зазора после `touches_load`, 23 с). Это `shared.set_pre(symbol, prescan_t0(symbol))` в цикле `--extra-runs` (`bounce_grid.rs` 270–282): перед каждым символом для каждого прогона читается и разбирается кэш касаний (`cached_touches`) только ради списка `t0`; затем `run_symbol` читает те же касания второй раз (стадия `touches_load`). То есть касания разбираются дважды на символ. Режется: брать `t0` из тех же уже загруженных касаний (одна загрузка на символ и прогон) — вычёркивает ≈ 16 % слот-с QUICK5 без изменения результата (кандидат для TK-049/TK-048; гейт «байт в байт»). Для волны 15 суток (a2, без `ts`) тот же механизм вероятен (16,0 % «вне стадий»), подтвердить a3-прогоном волны.

**Стенд /dev/shm** (a3, ALPHA_E2E, `--threads` по умолчанию стенда, без замка, CPUQuota 200 %): сутки 01-15 — 261 монето-суток, стена 568 с (старт→первая стадия 1,2 с, после последней стадии до `.done` 12 с), ЦП процесса 546 с (drive 381, events 120 = decode 94 + carry 26, windows 34, touches_load 6, setup 3), ожидание ≈ 0; сутки 01-01 — 251 монето-суток, стена 196 с, ЦП 185 с (drive 40, events 114 = decode 82 + carry 32, windows 25). Пик RSS 3,1 / 2,3 ГБ. Вывод: без диска стена = ЦП процесса (~1 ядро); пол суток 01-15 = 546 слот-с ЦП, из них круги 70 %; на дисках волны те же сутки стоят в разы дороже (чтение events + довесок D+1 + «вне стадий»).
