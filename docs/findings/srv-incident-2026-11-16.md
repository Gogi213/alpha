## 2. Ряд пауз: поздние строки `lost_ms`

**Дефект (прежний, `38d14b34` = `3835be7b`):** `series::minute_row` учитывает паузу в минуте её начала, а строка минуты пишется один раз, до конца паузы. Пауза, закончившаяся позже строки её минуты, в `series-minutes.jsonl` не попадала: 15 пауз BingX по ≈ 125 с дали `lost_ms 0` во всех строках, страница — `lost_1h_s` 0,0 при `gaps_1h` 15.

**Исправление (`src/collector/series.rs`):** `Booked` помнит, сколько пауз (число, мс в `lost_ms`, мс всех пауз) уже учтено у минуты; на каждом `flush` один проход по `gap_spans` шардов (с конца, до самой ранней записанной минуты) считает паузы по минуте начала и пишет разницу поздней строкой той же минуты `{"t","lost_ms_late","gaps_late","pause_ms_late"}`:

- `lost_ms_late` — то, что вошло бы в `lost_ms` строки (у бирж с дозапросом или проверкой REST — только книга и mark; шарды сделок — в `pause_ms_late`); **поле есть всегда, даже 0** — прежний `v3.py` узнаёт поздние строки по нему и не заменит строку минуты;
- `gaps_late` — число пауз; `pause_ms_late` — мс всех пауз (только у бирж с `pause_ms` в строке);
- ровно один раз на прирост; пауза в минуте запуска (строки нет) тоже; паузу дольше 3 часов (`BOOKED_MIN`) строка не догоняет;
- та же строка несёт `lost_ids_late` / вердикт проверки REST, если они пришли в тот же `flush`.

**Страница (`tools/collector_health/v3.py`):** поздняя строка — любая без `lost_ms` с одним из `lost_ids_late | lost_ms_late | gaps_late | pause_ms_late` (`LATE_KEYS`); складывается со строкой минуты. `tools/collector-perf/incident.py` печатает новые поля. Документы: `docs/collector-ws-format.md` (строка «Поздние потери»), `docs/COMMANDS.md` (порядок выкладки).

**Что даст на происшествии (расчёт по данным 12:50, не живой прогон):** строка BingX 12:50 получила бы `lost_ms_late` 1 250 000 (10 шардов книги и mark × ≈ 125 с), `gaps_late` 15, `pause_ms_late` 1 875 000; `lost_1h_s` страницы — 1 250 (было 0,0).

**Порядок выкладки:** страница раньше коллектора (как в `COMMANDS.md`); новая строка совместима и с прежним `v3.py` (`lost_ms_late` в ней всегда).

**Тесты:** Rust `a_pause_that_ends_after_its_minute_row_is_written_as_a_late_row_once` (пауза до строки — в строке; после — одна поздняя строка с `lost_ms_late` 245 000 и `gaps_late` 2; минута запуска; биржа с дозапросом: пауза сделок — только `pause_ms_late`, `lost_ms_late` 0; книга — `lost_ms_late` 125 000), Python `test_late_pause_rows_add_lost_ms_and_never_replace_the_minute_row`.

## 3. Дозапрос BingX для горячих символов

**Что произошло:** 883 пропуска (46 049 номеров) найдены в 12:52:12–12:52:59 после возобновления; REST BingX отдаёт 1 000 последних сделок символа; очередь дозапроса шла по порядку подтверждения (10 с) через `MIN_CALL_GAP` 1,5 с — ≈ 22 мин на 883 запроса. 866 пропусков получены целиком, **17 — частично** (4 084 номера потеряны; итоги 3–10 мин после находки: HYPE 177 с, ETH 380 с, остальные 520–640 с). Горячий символ за это время ушёл за окно в 1 000 сделок.

### 3.1. Замер (`tools/collect_gap/bfwindow.py`, по файлу дозапроса и записям сделок ws запуска `1794829630`)

Запрос в момент T отдаёт номера ≥ `свежий(T) − 999`, свежий — по приёму наших записей символа. **Модель проверена на факте:** боевой порядок и время запросов (`rg`) дают потерю **4 064** против боевых **4 084** (−0,5 %).

- Потеря почти целиком — **очередь**: порядок по сроку окна возвращает 3 672 из 4 084 номеров (−90 %) при том же темпе запросов (1,5 с) — нагрузка на общий с пулом и сверкой лимит BingX на IP не растёт.
- Раньше подтверждать — малая добавка: 10 с → 2 с даёт 74 номера (2 %), 10 с → 1 с — 85: узкое место не подтверждение.
- Пол — **297 номеров**: `HYPE-USDT`, пропуск 1 294 номера больше окна 1 000 (через 1 с годно 987); ни одна очередь и ни один момент запроса его не вернёт (запроса по номеру у BingX нет, `bingx.rs:279`).
- Замер перестановок линий (54 мин до происшествия, 11:53–12:48, пять шардов сделок): **10 464** пропущенных номеров (5 733 открытых пропуска) пришли все, **максимум ожидания 0,71 с**, через 1 с не пришло ни одного — подтверждение 2 с даёт 2,8 запаса без лишних REST-запросов на закрывающиеся пропуски.

### 3.2. Решение в коде

- `Exchange::trade_window()` (BingX — 1 000, прочие — `None`) и `GapReq::deadline_ms(window)`: срок = найден + (окно − номеров) / темп, где темп — номеров пропуска за его длительность (приём до → после); пропуск не меньше окна — срок уже наступил, он первый. `work()` берёт из очереди готовый пропуск с ближайшим сроком (без окна сроки равны — первый по порядку: Binance, OKX, Gate работают как раньше).
- `Exchange::gap_confirm_ms()`: BingX — `BINGX_CONFIRM_MS` 2 с, прочие — `CONFIRM_MS` 10 с (`IdTracker::with_confirm`).
- Тесты: `a_windowed_exchange_fetches_the_gap_that_leaves_the_rest_window_first` (порядок HUGE → HOT → CALM с окном, CALM → HOT → HUGE без), `the_id_tracker_confirms_a_gap_after_the_exchange_confirm_time`.
- Не менял: `MIN_CALL_GAP` 1,5 с (по сроку окна темп не нужен: 392 при 1,5 с и при 0,2 с), логику `partial`.

**Назначаемое — решение Судьи:** `BINGX_CONFIRM_MS` = 2 с (основание — замер 0,71 с; 1 с даёт на 11 номеров меньше потерь при 1,4 запаса вместо 2,8). Остальное — измерено.

**Ожидание на повторе тех же 883 пропусков:** потеря **318** номеров против 4 084 (расчёт по проверенной модели, п. 3.1; живой прогон возможен только при новом обрыве), из них 297 — пол, пропуск `HYPE-USDT` больше окна.
