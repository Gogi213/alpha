# Робот ФК «Викинг» — что он умеет под арбитраж схождений (крипто-перпы, 2026-11-10)

Источник: локальная база `C:\visual projects\viking` (doc-ru актуальна на 10.11.2026; PDF 2024–25 не использовались как опора).
База URL: `D = https://fkviking.github.io/bot-doc/docs/`. Только чтение; ничего в viking не менялось.

## 1. Как устроен арбитраж
- Портфель = ≤200 в роботе, инструменты ≤600; одна нога `Is first` (главная, котируется лимиткой), остальные — вторая нога, хеджируются после сделки по первой — `D/introduction.html#robot_short`.
- Спред считается по лучшим bid/ask ног: `Sell = bid1·r1 − offer2·r2`, `Buy = offer1·r1 − bid2·r2` (Absolute) или `(bid1·r1/offer2·r2 − 1)·100` (Relative, %) — `D/params-description.html#p.sell`; метод — `#p.calc_method`.
- Порог = `Lim_sell` / `Lim_buy` (в единицах метода: цена или %): заявка на первой ноге при `Sell ≥ Lim_sell` / `Buy ≤ Lim_buy` — `#p.lim_s`. Выход — противоположный лимит, смещаемый `TP` от цены удара — `#p.tp`. Лимиты двигаются `K` (K1, K2, X) после каждой сделки ≥ v_in_left, а также по таймеру `Limits timer`/`Percent` — `#p.shift_mode`, `#p.k`, `#p.timer`.
- `Price_s/Price_b` — цена, по которой робот реально ставит первую ногу (обратная функция Sell/Buy от лимита, минус k) — `#p.price_s`.
- `Ratio` (+ или ×) — константа или C++-формула `Ratio buy/sell formula` на инструмент — `#s.ratio_type`, `#s.ratio_b_formula`.
- Порог задаётся числом (ручное поле/API) либо вычисляется формулой через `set_lim_s/set_lim_b` — `D/c-api.html#portfolio-field-access`.

## 2. Адаптивный порог
- Лимиты — редактируемые поля портфеля; API `portfolio.update` меняет любые поля, не входящие в список «нельзя менять при торговле» (там Ratio, Count, Is first, Type price…; `Lim_sell/Lim_buy`, `K`, `TP`, `v_*` в нём нет) — `D/api.html` («Изменить портфель»), список — `D/params-description.html` («Запрещается менять следующие параметры»).
- C++-формулы (C++17, без файлов/сети, только тело функции, ≤12000 байт, один поток): вызываются на каждое обновление стакана любой ноги + раз в секунду; доступ к ценам всех инструментов, `mid_price()`, `funding_rate()`, любым полям других портфелей; Shift formula может писать `set_lim_s/b` — `D/c-api.html`, `#indicators-docs` (там же SMA, EMA, Var, StdDev, BB, Min/Max, RSI; таймфрейм от 1 с; история в RAM, при рестарте теряется, если не класть в shared memory).
- Пользовательские поля `uf0…uf19` (читаются в формулах и API, переживают рестарт) и `Extra field#1/2` — `D/params-description.html#p.user_fields`, `#p.ext_field1_`.
- Расписание (интервалы по дням/времени, UTC для крипты, включает/выключает re_sell/re_buy, закрытие в конце интервала) — `#p.use_tt`.
- Ограничений частоты изменения самих лимитов нет; есть ограничения канала API (п. 6) и бан по round-trip (п. 3).

## 3. Исполнение
- Первая нога: лимитка (котирование `Quote` или выставление при сигнале); `Only maker` = «снять, если станет taker» (если биржа поддерживает), требует `Quote`, обычно с `Simply first` (не глубже 1 шага в спред) — `#p.maker`, `#p.simply_first`. `Threshold`: при сильном уходе спреда виртуально отключает Only maker/Simply first — `#p.threshold`. Переставление котирования: `Delta`, `First delta` — `#p.delta`.
- Вторая нога: после сделки по первой, лимитка по лучшей цене стороны ± `k` (отступ в пунктах); рыночных заявок нет, «маркет» имитируется большим `k` — `D/algorithm-comments.html` («О ценах выставления заявок второй ноги»), `D/faq.html#faq.order_type`, `#s.k`.
- Опция `Equal prices` (2 инструмента): цена второй ноги берётся так, чтобы Sell=Lim_sell, а не по текущей — `#p.equal_prices`.
- Не исполнилась вторая нога: `SL/SLE` (стоп от цены заявки) и `Timer/TE` — снять и перебросить по рынку с `k_sl`, далее каждую секунду — `#s.sle`, `#s.te`, `#s.k_sl`, `D/algorithm-comments.html#sl_timer`. `Hedge (sec)` — автохедж невыставленной второй ноги через N с; `Overlay` — допуск расхождения; `Max not hedged` — стоп первой ноги при N незахеджированных/ошибках — `#p.hedge_after`, `#p.overlay`, `#p.max_not_hedged`.
- Проскальзывание/защита: `Price check` (не ставить, если цена глубже N пунктов от лучшей), `Market volume` (очередь перед нами), `Percent of quantity` (объём второй ноги достаточен до выставления первой), `Type price = Orderbook` + `Depth OB` (цена со стакана под объём), `Max trans time` + `Ban period` (стоп по round-trip), уведомления `Severe sell/buy change`, `FinRes fall` со стопом торговли — `#p.price_check`, `#p.mkt_volume`, `#s.percent_of_quantity`, `#s.max_trans_musec`, `D/params-description.html#notification-parameters`.
- Фильтр выбросов цены в самой доке: только рекомендации писать проверки в формулах (ненулевые цены/объёмы и т.п.) — `D/c-api.html#md-filter`.
- Объём: `v_min/v_max`, `v_in_left/right`, `v_out_*` — в штуках портфелей; `Count` на инструмент; округление под лот биржи — `#p._volumes`, `D/algorithm-comments.html` («Об объёмах»). Числа минимального лота по биржам в доке не даны.

## 4. Биржи
- Крипто-подключения в доке: `BINANCE` (спот), `BINANCEFUT` (USDT-M), `BINANCECM`, `OKX`, `BYBIT` (USDT perp; аккаунт One-Way), `BYBITSPOT`, `BITGETFUT`, `BITGETSPOT`, также Kraken(+fut), Bitfinex, KuCoin, Huobi, Deribit, Bequant — `D/creating-connection.html#tc.BINANCEFUT.name`, `#tc.OKEX.name`, `#tc.BYBIT.name`, `#tc.BITGETFUT`. Все — Websocket+REST.
- **Gate и Hyperliquid в документации не найдены** (поиск по ru/en).
- Binance: потоки `binancefut_listen` (со стаканом), `_top` (только лучшие цены); для `Simply first` `_top` не подходит, одновременно top и стакан не рекомендуется — там же.
- Ноги на разных биржах: у инструмента портфеля свои `Exchange` и `Client code`; FAQ «потеря связи на одной из ног» описывает портфель с ногами на разных биржах — `#s.client_code`, `D/faq.html#faq.connection_lost` (прямой фразы «межбиржевой портфель поддерживается» нет — подтверждаем у поддержки).
- Rate limits бирж: докa лишь упоминает учёт («рейт-лимиты учитываются»), числа не даёт.

## 5. Комиссия и финрез
- На инструмент: `Commission type` (`%` от цены сделки или `pt`) и `Commission` — `#s.comission_sign`. `Fin res = Opened + Commission sum + Σ позиция×bid/offer×mult` (по лучшей цене на закрытие), `Fin res wo C` — без комиссии — `#p.fin_res`, `#p.fin_res_wo_c`. Раздвижка в таблицах — только при сделке по главной ноге.
- Комиссия в порог Lim_sell/Lim_buy автоматически **не** закладывается; в формулу — вручную через формулы/внешний код. Фандинг в финрез не входит (в формулах есть `funding_rate()`).

## 6. Внешнее управление
- WebSocket API `wss://bot.fkviking.com/ws`: подписка на портфель/поля (обновления не чаще 1 раза в 300 мс на подписку), `portfolio.update`, `portfolio.test_formula`, стоп/сброс/«в рынок», купить/продать портфель, подписка на сделки, логи, финрез, история изменений полей — `D/api.html#api.updates_rate`.
- Лимиты: 10000 пунктов/10 с, сообщение = 49 (≈204 сообщений/10 с, пакет до 50 сообщений = 49), ping `7` = 1; сессия ≤12 ч, молчание >5 с — разрыв; ≤16 соединений на ключ — `D/api.html#api.rate_limits`.
- Задержки применения параметров в доке не заявлены; формулы блокируют основной поток.

## 7. Готовые механизмы «порог не ниже издержек + маржа» и «подстройка под диапазон»
- Готового параметра «не торговать ниже издержек + мин. маржа» **нет**; делается формулой/внешним кодом (`Lim = издержки + маржа`), либо `Extra field`/`uf` как входы.
- «Диапазон» косвенно: `K/K1/K2/TP/X` (смещение лимитов после сделок), `Limits timer`+`Percent` (сдвиг при неисполнении), `FUT move limits` (суточный сдвиг к экспирации — для сроков, не для перпов), расписание — `#p.shift_mode`, `#p.timer`, `#s.move_limits`. Подстройка под скользящее среднее/банды — только своей формулой на индикаторах (SMA/EMA/BB/StdDev).
