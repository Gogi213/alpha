### Выбор канала для `b` (лучшие bid/ask с размером)

Замер на одних и тех же 100 символах (топ по обороту), **одновременно**, 3 мин, S1, 12.11 13:03:55–13:06:55 UTC, [измерено]:

|---|---|---|---|---|
| **SBE `books1`** | **3 783** | 305 | 680 172 | 133 / 489 / 9,2 % |
| v3 JSON `books1` | 2 460 | 541 | 441 757 | 129 / 400 / 4,5 % |
| v2 JSON `books1` | 1 242 | 283 | 223 354 | 125 / 217 / 0,01 % |

Разных состояний верха (bid, bsz, ask, asz; без первых 5 с): у SBE 662 799 из 662 799 записей (каждая запись — смена верха), у v3 JSON 429 019 из 431 261.

В занятую минуту (C1, 13:10:37, 6 с окна [5; 11) после старта, 100 символов; разбор по символам): SBE даёт `BTCUSDT` 1 234 обновления/с, `ETHUSDT` 1 192, `SOXLUSDT` 913; v3 JSON — 158 / 197 / 161; v2 JSON — 68 / 73 / 73; сумма по 100 символам 11 641 против 3 806 и 2 343 зап/с (SBE в 3,1 раза больше v3 JSON, в 5,0 раза больше v2 JSON). JSON-каналы — **склеенные по времени** (v3 ≈ 6 мс, v2 ≈ 14 мс на символ в этот момент), SBE — каждое изменение верха.
Сверка SBE с JSON v3 на общих `(символ, seq)`: **430 675 общих, 0 расхождений значений** (сравнение числовое, `Decimal`); только в SBE 232 124, только в JSON 586 (края окон). На топ-10 в один момент v3 JSON отдал 104 243 разных состояния верха за 180 с против 44 123 у v2 JSON (в 2,36 раза); `books1` и `books5` на общих `seq` совпали (v3: 11 678 пар, v2: 4 056 пар, 0 расхождений).
`ticker` на этих же 10 символах: 3 887 разных состояний верха за 180 с (v2) — 9 % от `books1`; `books5` (v2) — 11 022 (25 %).

**Вывод: `b` — SBE `books1`** (самый частый, фиксированная раскладка, ≈ 80 байт на кадр, разбор без JSON), запасной — v3 JSON `books1`, консервативный — v2 JSON `books1`. Цена SBE: хвост лага выше (p99 489 мс, 9 % > 250 мс на 100 символах в одном соединении) и обрывы соединений на высокой частоте (п. 5); «auto-culling» из документации — биржа сама может отбросить устаревшее событие под нагрузкой (потери по разрывам `seq` не проверить: `seq` сквозной, внутри символа с пропусками — например, +144 за 2 мс на BTCUSDT). Решение по SBE против v3 JSON — за координатором: SBE даёт в 1,5–3 раза больше записей, ценой бинарного разбора и лага; формат записи `b` у обоих один.

### Правила разбора (контракт для Rust-разбора)

| запись | источник → поля формата | заметки |
|---|---|---|
| **b** (SBE) | кадр WS opcode 2: заголовок 8 байт (`blockLength` u16, `templateId` u16 = 1002, `schemaId` u16 = 1, `version` u16 = 4 на 12.11); корень длиной `blockLength` = 64: `ts` u64 (мкс, точность мс) @0, `bid1Price` i64 @8, `bid1Size` i64 @16, `ask1Price` i64 @24, `ask1Size` i64 @32, `priceExponent` i8 @40, `sizeExponent` i8 @41, `seq` u64 @42, `sts` u64 (мкс, время выдачи сервисом) @50, `category` u8 @58 (1 = usdt-futures), 5 байт padding; затем символ: 1 байт длины + UTF-8. Поля формата: sym = символ как есть (`BTCUSDT`); **T = ts/1000**, **E = sts/1000** (ET = E − T ≈ 1–2 мс, p99 2 мс), u = `seq`, цена/размер = мантисса × 10^экспонента, строкой | читать по `blockLength` кадра (прямая совместимость: в примере документации `blockLength` 56, `version` 2 — без `sts`/`category`; на бирже сегодня 64/4). **Ключ дедупа — `seq`**: общий для SBE, v3 JSON и разных соединений (общие ключи SBE↔JSON — выше). Строка цены из мантиссы имеет все `|exp|` знаков (`1.9887`), JSON-строка бывает без хвостовых нулей — значения равны, строки нет; как хранить — решение координатора (п. 6.8) |
| **b** (JSON) | v3: `{"action":"snapshot","arg":{"instType":"usdt-futures","topic":"books1","symbol":…},"data":[{"a":[[ask,asz]],"b":[[bid,bsz]],"seq":…,"pseq":0,"ts":"…"}],"ts":…}`; v2: `…"channel":"books1","instId":…`, `"asks"`/`"bids"` вместо `a`/`b`. T = `data[0].ts` («Match engine timestamp(ms)»), **E = `ts` кадра** («Data streaming time»; push−T p50 1–2 мс, p99 7–21 мс), u = `seq` | `action` всегда `snapshot`; пустая сторона/другая форма → `r` (в пробах 0) |

Идентификаторы **не плотные** (19 знаков, шаг ~10¹² между разными ордерами) — `da`/`f` формата станут огромными числами, но точными. **Кадры `action = snapshot` при подписке — последние ≈ 50 сделок за прошлое**: не писать (до подписки, без ключа порядка); [док] «Effective in demo trading on November 4, 2026, and expected in live trading on November 17, 2026: after a successful subscription, this channel will no longer push snapshot data» ([New Trades Channel](https://www.bitget.com/legacy-docs/classic/contract/websocket/public/New-Trades-Channel)). **`isRPI` (Retail Price Improvement) — флаг типа сделки от биржи: yes у 3,7 % сделок (1 005 из 27 242), 3,1 % в V1**; в формате столбца нет (п. 6.8) |

## 6. Что нужно от ядра (в терминах контракта, не Python)

1. **Лимитер подключений.** 300 запросов/5 мин на IP, ≤ 100 соединений; общий `ConnectBudget` с окном 300 с (как у Binance), запас; при обрывах не ходить повторными попытками чаще бюджета («IP repeatedly disconnected may be blocked» — [док]). Замена линии при обрыве — тот же механизм.
2. **Пинг.** Текстовый `ping` раз в ≤ 30 с, ответ `pong` текстом; протокольный пинг **не годится** (п. 5). Нужен пинг, задаваемый адаптером (кадр и ответ), и метрика `g` по нему.
3. **Двоичные кадры SBE.** Приём opcode 2 с разбором фиксированной раскладки (п. 3); ядро должно уметь принимать и текст, и бинарные кадры на одном соединении (подписка и `pong` — текст, данные — бинарно); неизвестный `templateId`/`schemaId` → в `r`.
4. **Обрыв без кадра закрытия.** Закрытие приходит как EOF/сброс без кода; нужна быстрая замена линии (двойные линии — две подписки на один набор; `seq`-дубли снимаются писателем).
5. **Снятие дублей и сброс нумерации.** Ключи: `b` — `seq`, `t` — `tradeId`, `m` — `(символ, data.ts)` v2 `ticker`. [Док]: `seq` может сбрасываться при релизах/перезапусках (`pseq = 0` у `books1` всегда, признака сброса нет); писатель с правилом `k ≤ last` отбросит все записи символа до догоняющей нумерации — нужен сброс `last_key` по сигналу адаптера (скачок `T` вперёд при убывании `seq`, или переподключение). Окно релизов — вт/чт 06:00–10:00 UTC.
6. **Шардинг по частоте, не по числу.** Нагрузка на соединение зависит от частоты символа (BTC — 1 234 зап/с SBE, хвост пула — единицы): раскладывать по ожидаемому потоку; держало окно 150–180 с: v2 JSON `books1` 100 и 399 символов (1,2–2,4 тыс. кадр/с), v3 JSON `books1` 100 символов (4,5 тыс. кадр/с — один раз из двух, второй раз оборвано на 4,9 с), SBE ≈ 1,4–2,4 тыс. кадр/с на соединение (4 из 5). Число «лучшего набора» — после лестницы.
7. **Подписка.** `{"op":"subscribe","args":[{"instType":"USDT-FUTURES"|"usdt-futures","channel"|"topic":…,"instId"|"symbol":…}]}`: v2 — `channel`/`instId`, v3 — `topic`/`symbol` (регистр `instType` отличается!); пачки ≤ 40–60 аргументов (4 096 байт), пауза 0,2 с (проверено: 30 запросов за 6 с, без `error`); ответ `subscribe` приходит на каждый аргумент; **кадры `action = snapshot` по `trade` при подписке не писать**.
8. **Формат: решение координатора.** Нужны: столбец `isRPI` сделки (3,1–3,7 % сделок; «данные как на бирже», В-172), открытый интерес (`holdingAmount`/`openInterest` в тикере), представление цены SBE (мантисса и экспонента против строки), `da`/`f` для несмежных `tradeId`. Иначе потеря.
9. **Объём `m` и «свежесть» RWA.** Кадр `ticker` — по таймеру ≈ 106 мс на символ: 3 633 зап/с на 399 символах (≈ 314 млн/сутки [вывод]) при том, что `(mark, index, fundingRate)` меняется в 21 % кадров (≈ 66 млн/сутки); решение координатора: писать каждый кадр или изменения плюс сердцебиение. Символы RWA вне торговой сессии базового рынка молчат по `books1` — метрика свежести/«символов с данными» не должна считать их отказом.
10. **Пути.** Входы: `ws.bitget.com` (4 CloudFront, IPv4), `ws.bitgetapi.com` (2 адреса IPv4, не CloudFront; не документирован), `vip-ws.bitget.com` — 403. Хвост лага > 250 мс (4–9 % на v3/SBE на 100 символах в одном соединении против 0,01 % на v2) — мера по записям `rx − T > 2 с` в окнах не достигла (макс. 1,2 с на SBE 399).
11. **Сервер.** ядро `dial` берёт первый адрес `getaddrinfo` (на srv — IPv4 CloudFront, IPv6 нет); линии разводятся `--entrance ws.bitget.com@<ip>` или `ws.bitgetapi.com@<ip>`.
