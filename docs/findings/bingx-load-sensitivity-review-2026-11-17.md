## Вердикт

**Выкладка — после правок.** Код быстрого пути верен: блокирующих ошибок нет (п. 1), выход защищён CRC32 + длиной, необычное уходит в libdeflate. Перед выкладкой обязательны: копия рядом с боевым со сверкой записей (В-156, п. 13 приказов — не сделана, отчёт сам это признаёт) и исправление выводов отчёта (п. 2–4): «2–5× не подтверждено» неверно (в окне C ×2,8–5,3, совпадает с задачами `hold_*` другого вида, чем повторённые в W3–W5), решения пути после 19:54 не учтены. Выигрыш правки — −9…−12 % циклов реактора; на `queue_lag` под той нагрузкой, что даёт рост (окно C), правка не проверялась.

## 1. Код (`inflate.rs`, `gzip.rs`)

Прочитано построчно против RFC 1951/1952.

- **Битовый поток.** После `refill` в накопителе ≥ 56 бит; наибольший расход между доборами — 38 бит на символ с повтором (код ≤ 10 + 5 + ≤ 10 + 13), добор при `n < 40` — переполнения нет. Заголовок блока (3 бита) — после `refill`; коды длин — добор при `n < 8` / `n < 24`. Чтение за концом тела даёт нули, а `consumed().div_ceil(8) == body.len()` отбрасывает и недочитанные, и лишние байты. `stored()` выравнивает по `n & 7` — верно, `consumed = pos·8 − n`.
- **Таблицы.** `build`: переполнение (`left < 0`) — отказ; неполный код — только один код длины 1 (вторая ячейка 0 → отказ при попадании), как разрешает RFC для смещений; полный код заполняет все 2^max ячеек, поэтому таблица прошлого кадра не протекает. Пустой код смещений → ячейка 0 = «нет кода» → отказ при первом повторе. Код длиннее 10 → `None` → libdeflate.
- **Повторы.** `distance > o` и `o + len > out.len()` — отказ; копия по 8 байт только при `distance ≥ 8` и запасе 8 байт в `out` — источник всегда уже записан (`s + 8 ≤ d`), запись за `o + len` перезаписывается дальше (иначе `o ≠ size` → отказ).
- **Символы-ловушки.** Фиксированные литералы 286/287 и смещения 30/31 дают `None` через `LEN_BASE.get` / `DIST_BASE.get`; `hlit > 286`, `hdist > 30` — отказ; код 16 без предыдущей длины — отказ; конец блока без кода — отказ.
- **Заголовок gzip.** FHCRC и зарезервированные флаги → прежний путь; FEXTRA/FNAME/FCOMMENT разбираются с проверкой границ. Несколько членов и лишние байты → `consumed ≠ body.len()` → прежний путь; вердикт `Gunzip` = вердикт libdeflate (п. 0, тесты).
- **Паники.** Все индексы через `get`, сдвиги ≤ 16 бит. Единственное хрупкое место: медленная ветка `refill` может довести `n` до 64, и тогда `63 − n` в быстрой ветке ушло бы в переполнение; сейчас недостижимо (`pos` только растёт, `stored()` сбрасывает `n = 0`). Замечание, не блок: `debug_assert!(self.n <= 63)` в быстрой ветке или `while self.n <= 56` → `< 56`.
- **Память и горячий путь.** На кадр — ноль выделений после прогрева: `Tiny` — один `Box` на поток (≈ 6 КБ), буфер `Gunzip` только растёт и ограничен 64 КБ на быстром пути (16 МБ — прежний путь, как было). Счётчики `fast`/`fallback` — `fetch_add Relaxed` на кадр в одном потоке реактора; HashMap/BTreeMap/`f64` нет.
- **Покрытие тестов исполнителя.** Повреждения в `damaged_frames…` и в долгом прогоне (456 тыс.) почти всегда ломают CRC, и оба пути отвечают `None` — так проверяется отказ, а не сам декодер. 135 462 кадра сверены на стенде одной FNV-суммой склейки выходов двух декодеров (`gzbench.rs:294`), в репозитории — 360 кадров. Оба пробела закрыты тестами проверяющего (п. 0).

## 2. Замеры (правило 23)

- **Стенд −41 %** (4 570 → 2 694 нс, София): декодеры попарно на каждом кадре, порядок сдвигается — условия равные. Подтверждаю способ; srv-прогон −39 % шёл 20:59–21:10 — внутри общего происшествия 21:06 (п. 4), но попарность делает сравнение равным.
- **Копии рядом, −11,7 % / −9,2 % циклов на кадр** (68 464 → 60 452; 63 206 → 57 385): `perf stat -t` обеих копий запускается одновременно на те же 210 с, шарды одни, кадров/с 1 794 / 1 800 и 1 769 / 1 773 — **условия равные**, порядок запуска чередуется. Ограничения: два окна; копии по 7 шардов несут 1,8 тыс. кадров/с против 6,9 тыс. у боя (циклов на кадр 60–68 тыс. против 48 тыс.), так что −10 % — оценка для боя, не замер боя.
- **`queue_lag` в окне 1 — не точка нагрузки.** W1 шёл 21:11–21:17 сразу после общего происшествия 21:06 (`sar`: sys 37–49 % в 21:09–21:11); у обеих копий хвосты до 2,6–3,0 с (строк > 100 мс: старая 64 из 224, новая 37 из 224, мой пересчёт). Вывод отчёта п. 7.2 «старая копия ×2,9 при смене idle 60,8 → 18,7 % — чувствительность воспроизведена» сравнивает разные минуты (W1 и W2) — по правилу 23 это не вывод.
- **Нагрузочные окна W3–W5 — не повтор окна C.** W3 — 6×`xz -9`, W4 — `dd bs=1` и mmap 256 МБ, W5 — `hold_*` того вечера (`hold-tol`, `zstd -dc | mawk`). В окне C работали другие задачи (журнал systemd, п. 3): `hold_scan` (пик памяти 16,1 ГБ, 2,9 ядра), `hold_marks` (7,2 ГБ), `hold_raw` (14,9 ГБ), `hold_check raw` (2,7 ГБ) — Python с гигабайтами памяти. Нагрузка по памяти в окнах не запускалась (отчёт это пишет). Мелочь: в `raw/rep-w5.txt` фазы подписаны «memory bandwidth hog» / «memory latency hog», хотя нагрузчики не стартовали (в журнале нет `tk580-bwl-*`/`tk580-chl-*` после 22:08) — подписи надо исправить.

## 3. «2–5× не подтверждено» — неверно

Пересчёт тем же способом, что TK-535, по полным файлам (TK-535 читал последние 8 000 строк — на результат не повлияло): BingX book **11,6 → 12,9 → 30,0 мс** (A / B / C) — совпадает с TK-535 до десятых.

**Почему корзины idle этого не видят.** Сравнение «окно C против остальных строк при том же idle» (10-с строки с 14.11):

| idle хоста | BingX book: C / остальное | OKX book | Bybit book | Gate book |
|---|---|---|---|---|
| < 20 % | **34,3 / 15,5** (n 1 412 / 21 274) | 16,3 / 12,7 | 23,3 / 15,7 | 18,7 / 11,6 |
| 20–35 % | **33,3 / 13,4** (n 1 030 / 6 917) | 15,5 / 11,1 | 20,2 / 12,4 | 28,9 / 10,6 |
| 35–50 % | 15,0 / 12,4 | 12,2 / 10,9 | 17,2 / 12,4 | 11,6 / 10,1 |
| > 65 % | **50,7 / 10,9** (n 174) | 11,1 / 10,4 | 20,2 / 10,6 | 10,9 / 9,9 |

При одном и том же idle BingX в окне C хуже, чем вне его, в 2,2–4,7 раза (корзины < 35 % и > 65 %; 35–50 % — ×1,2); OKX и Bybit — ×1,1–1,9; Gate book ×1,1–1,6, кроме корзины 20–35 % (×2,7; ряд Gate book шумный и вне C, p90 > 140 мс). Idle хоста не описывает ту нагрузку, к которой BingX чувствителен: самые загруженные по ЦП часы трёх суток (15.11 21:00, idle 3,8 %; 16.11 10:00, idle 6,9 %) дают BingX book 15,7–16,0 мс — норма. Поэтому таблица отчёта по корзинам idle (×1,43–1,57 «как у Bybit/OKX») разбавляет эпизод сутками ЦП-нагрузки другого вида и не опровергает TK-535.

**Окно C по 10 минутам** (медиана `queue_lag_p99`, book, мс):

| 10 мин | BingX | OKX | Bybit | задачи `hold_*` (журнал systemd) |
|---|---|---|---|---|
| 17:00–17:20 | 12,9–13,7 | 11,6–12,2 | 16,6–18,7 | `hold_scan` пилот (до 17:17, 4,9 ГБ) |
| 17:30 | 24,8 | 17,7 | 25,9 | старт `hold_scan` (16,1 ГБ) + `hold_marks` (7,2 ГБ) 17:33 |
| 17:40–18:10 | **36,4 / 47,6 / 43,5 / 55,8** | 12,4–18,2 | 19,2–27,9 | они же, до 18:11 / 18:13 |
| 18:20 | 18,7 | 12,7 | 15,8 | пауза, `hold_raw` с 18:22 |
| 18:30–18:50 | **59,9 / 25,9 / 68,6** | 15,7–16,6 | 22,3–27,4 | `hold_raw` (14,9 ГБ), `hold_marks2`, `hold_check raw` |
| 19:00 | 17,7 | 12,4 | 18,2 | `hold_raw`, `hold_check` закончились |

По 10 минутам 17:30–18:50 BingX book растёт к фону 12,9 мс в 1,9–5,3 раза, **в 6 из 9 десятиминуток — в 2,8–5,3 раза** (OKX — до ×1,6, Bybit — до ×1,7): факт «в 2–5 раз чувствительнее» TK-535 **подтверждён** (измерено). Рост включается и выключается вместе с крупными по памяти задачами Python, а не с idle; доля ЦП самого коллектора BingX в C не меняется (pidstat: 29,7 % против 31,3 % в B, `%wait` 0,2), PSI cpu some 23,9 против 9,2. Механизм не измерен: давление на кэш/память (у BingX таблицы libdeflate ≈ 10 КБ на кадр строятся заново) — **гипотеза**; проверка — копии старой и новой сборки рядом под нагрузчиком памяти (`tk580_memhog.c` уже готов) или под повтором `hold_scan`, а не под ЦП/`dd`/`mmap 256 МБ`.

Следствие для правки: она уменьшает рабочее состояние разжатия (≈ 6 КБ вместо ≈ 10 КБ, без перестройки 2^11 таблицы), то есть может действовать именно на этот вид нагрузки, — но это не измерено; «правкой не снята» в отчёте относится к ЦП/syscall/page-fault нагрузке, не к нагрузке окна C.

Вне окна C за 14–16.11 других часов с BingX book ≥ 20 мс нет (часовые медианы: максимум вне C — 17,7 мс): эпизод один; он совпадает по времени с составом нагрузки окна C, восстановленным по журналу systemd и pidstat (отчёт п. 9.1 «состав не восстановлен» — данные были: `/data/indep-ab/host/pidstat.log`, `psi.log`, журнал юнитов `hold-*`).

## 4. B: решения по пути и сдвиг `T`

Пересчёт с парой по времени (переключение ↔ `ping_degraded` старой сессии того же шарда за 0–180 с до него), данные до 22:16 UTC — отчёт обрезал журнал на 19:54, хотя писался в 22:29:

- С начала 29d981c0: `path_switch` **46** (не 10), из них 43 — через 27–140 с после `ping_degraded` (медиана 42 с); 3 без события (21:16 book02, 21:48 book00, 22:04 trade04): новая сессия прошла `path_ok`, `ping_degraded` за 200 с до этого нет — значит, сработал сторож лага (`PathWatch::judge`, p50 > 2 000 мс), который события не пишет. Это пробел журнала, не `T`.
- `path_rejected` по лагу с начала сборки — **11, не 0**: все в 21:06:27–21:25:58, p50 222–6 009 мс. Это общее происшествие хоста/маршрута 21:05:52–21:07: таймауты и отбраковки по RTT одновременно у всех пяти бирж (RTT подключения до 9,5 с у BingX, 8,9 OKX, 7,8 Bybit, 7,2 Gate, 8,2 Binance; `sar`: sys 22–49 % в 21:06–21:11). Отчёт об этом происшествии не пишет, хотя его стенд srv (`tk580-gzb-1/2`, 20:59–21:10) и окно W1 (21:11) шли в нём.
- Запас порога: book `path_ok` p50 **348 мс** (21:06:30, в происшествии) — запас 2 мс, а не 165; trade — максимум 224 мс.

**Вывод отчёта по сути верен:** ни одно решение не объясняется сдвигом `T` 10–35 мс — переключения идут по pong, отбраковки — при лаге в сотни–тысячи мс общего происшествия. Числа «10 из 10», «`path_rejected` 0», «запас book 165» надо заменить на пересчёт до конца данных.
