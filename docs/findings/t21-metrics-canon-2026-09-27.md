Проверил сам два подозрения разведчика — **оба не ошибки**:
- `exit-sim` считает мейкером только `take`, `portfolio-sim` — `take` и `horizon`. `Horizon` бывает только у плана
  `SpreadHold` (`strategy.rs:1537-1543`), а `exit-sim` моделирует только `Bounce` — у него нет исхода `horizon`.
  Расхождения по деньгам нет; в общем модуле множество одно — `{"take","horizon"}`.
- стоп дня в portfolio-sim (`:371`): «реализованное за день входа» = сумма закрытий с `t1` в тот же день до `t0`
  (`settle(t0)` выше). Это правильная мера «сколько уже потеряно сегодня».

## 2. Канонические определения (предложение)

Принцип: одно число владельцу — одна функция в `_lib`; отчёты и дашборд берут готовое. Где выбираю между
вариантами — по смыслу «что увидит бот на счёте», не по тому, какой даёт лучшие числа (чисел «после» ещё нет).

| что | было | станет | почему |
|---|---|---|---|
| **доллары сделки** | Ф1…Ф6 | Ф1: `pnl_usd = net_bps / 1e4 × notional_usd`, `notional_usd = qty × entry_vwap` (исполненный объём); комиссии — внутри `net_bps` (Rust, В-63); при пересчёте выхода — нога своего типа (`MAKER_EXIT_REASONS = {"take","horizon"}`); фандинг — `--funding` у базы и вариантов одинаково (Судья `82b0454`) | это деньги счёта; план × доля (Ф2) — приближение Ф1, план без доли (Ф3) и $1000 (Ф4) — не деньги, а масштаб bps; Ф5 — производная; Ф6 — только если производитель CSV назван (см. §3) |
| отчёты в bps (Ф3/Ф4) | «$» при фиксированных $1000 | подписывать **bps** или «$ на $1000 плана», не «$» | чтобы не читались как деньги счёта |
| **сделки счёта** | часть скриптов без правил | всё, что показывает $ владельцу, идёт через `_lib.portfolio` (одна позиция на монету + флаги правил) | «отчёты, не прошедшие через portfolio-sim, видят другой счёт» (аудит, У6) |
| **день сделки для денег** | `t1` / `t0` / `day_utc` | **день выхода `t1`, UTC** — для дневного P&L, худших суток, календаря, Шарпа, KPI | деньги реализуются на выходе; так уже считает portfolio-sim (плитки счёта) и kpi-newhigh |
| день для отбора сигналов | `t0` / `day_utc` | **день входа `t0` (сутки сигнала `day_utc`), UTC** — только для фильтров и срезов (номер подхода, эпизод BTC, стоп серии по месяцу входа) | правило решает в момент входа |
| **месяц** | 4 смысла | окно по `t1` `[начало месяца, начало следующего)` UTC; конец данных сентября — **2026-09-24 00:00 UTC, не включая** (= «01–23.09», 23 суток); имя эпохи — только где лежат прогоны | окно по `t1` = та же привязка, что день денег; «09-24 не включая» и «23.09 включительно» — одно и то же в сутках, но по `t1` сделка, открытая 23.09 и закрытая 24.09, выпадает — это явно записать |
| сделки, закрытые после конца данных | по-разному | не бывает: прогон режет сутки; перенос через полночь (В-94) — сделка в месяце своего `t1` | — |
| **просадка владельцу** | П1…П7 | **П1** (минутная переоценка открытых позиций, пик счёта от депозита; $ и % депозита) — главная; П2 (по закрытиям) — справочно рядом; П3′ (эпизоды по закрытиям) — только для KPI «до перехая» | П1 — то, что видно на счёте; KPI П-07 определён на закрытиях (правило Судьи) |
| П3/П4/П5 | от нуля по закрытиям / по входам / по дням | убрать как «просадку»; где нужна кривая от нуля — строить из П2 | три разных числа под одним именем |
| П7 (`ddScaled`) | линейный масштаб в JS | прогон `portfolio-sim --size` на каждый размер (уже есть для плеча ×1…×5); масштаб — только с подписью «≈» | нелинейно при потолках и стопах |
| П6 | бутстреп суток | остаётся: это интервал, не просадка | — |
| **Шарп** | 4 места | один: дневной P&L по `t1` за **все календарные сутки месяца (включая нулевые)**, среднее / σ × √365; `breakdown.sharpe_trade` → переименовать в `t_trade` | нулевые дни — часть результата счёта |
| **`--epoch`** | 4 синтаксиса | один разборщик `_lib.parse_epoch`: `имя=<дом>:<прогон>[,<прогон>…][@<с>..<по>]`; повтор имени — **дописывает**; Б/В/Г — через него (синонимы старых форм читаются) | один синтаксис; перезапись в portfolio-sim молча теряет прогоны |
| **строка сделки** | синонимы | `_lib.trade_row`: `symbol, day_utc, t0_ns, t1_ns, net_bps, pnl_usd, notional_usd, entry_vwap, fill_frac, reason, fee_bps`; `usd` на входе → `notional_usd` в строке сделки и `pnl_usd` в агрегатах; мс → нс при разборе | снимает главную неоднозначность `usd` |
| исключённые монеты | 8 флагов + 10 зашитых `{"TRXUSDT"}` | одна константа `_lib.DROP_DEFAULT = {"TRXUSDT"}` (В-105) + общий `--drop` | одно место решения владельца |
| Rust (У5) | Python разбирает формы регулярками | аддитивные колонки за флагом или новым файлом (Инженер); старые имена — синонимами | Судья п. 6 |
