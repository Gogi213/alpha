### 1.1 Инцидент «v3 перезаписан старой сборкой из очереди» — причина
`tools/p42/build-srv.sh` (режим `build`) ставит результат `install -D $SLOT_TGT/release/$BIN_NAME $BIN_OUT` в путь, заданный
при постановке в очередь. Замок `build.lock` берётся опросом `flock -w 10` — порядок не FIFO (пример сейчас: запрос 46231
пришёл 23:18 и взял замок раньше 46026, пришедшего 23:14). Значит, запрос, поставленный раньше, может отработать позже и
затереть более новый бинарь в том же пути. Сейчас то же самое ждёт `alpha-feat-v3`: p42-46026 перезапишет 02976bb0 (TK-609
это и задумывал, копия `alpha-feat-v3-lut-only` сохранена). Тот же риск: `vps-check.sh bin` (`$BIN_OUT-plain/-r2`, плюс `rm -f`
перед сборкой — путь пуст во время сборки), `/data/p42-tk611/bin/alpha-feat-f12`, замена `bin/alpha-master` у TK-599 (`install`
поверх пути, из которого читают TK-599 и TK-610). Дополнительно: `vps-check.sh` при каждом вызове перезаписывает общий
`/opt/rbuild/run-srv.sh` версией из своего дерева — старое дерево откатывает раннер для всех.

### 1.2 Боевые пути защищены — чем
`tk599-run`: md5 бинаря движка пишется в каждую серию npz (`bin_md5`), отчёт собирает список md5 (TK-599 v11); `built-by.json` у
каждой таблицы признаков. Этого достаточно, чтобы задним числом увидеть подмену, но не чтобы её не допустить.

### 1.3 Исправление (предлагаю в `tools/p42/build-srv.sh` и `tools/vps-check.sh bin`)
1. Ставить по содержимому: `M=$(md5sum release/$BIN | cut -c1-8); install -D … $BIN_OUT.$M; ln -sfn $(basename $BIN_OUT.$M) $BIN_OUT.new && mv -T $BIN_OUT.new $BIN_OUT` — старые файлы не затираются, путь-ссылка меняется атомарно.
2. Не ставить устаревшее: в команде сборки запомнить время прихода запроса `T0` (раннер его уже знает); если `$BIN_OUT` новее `T0` — ссылку не трогать, напечатать «устарело, оставлено `$BIN_OUT.$M`».
3. Потребители зовут `…/<имя>.<md5>` (не ссылку) и сверяют `md5sum` с принятым перед стартом: `rustfeat_run.py` (TK-599 ftab), `tk610_run.sh` (движок; допустимые md5 уже шестым аргументом — сверять ДО запуска), `rustfeat_f12_ga.sh`, `rustfeat_ga*.sh`. Строка ворот — с md5.
4. `run-srv.sh` в `vps-check.sh` выкладывать по хешу (`run-srv.<sha>.sh`) и звать его, а не общий файл.

## 4. Очередь rbuild

Измерено (`/opt/rbuild/res`, 14 последних): сборка после взятия замка 4–23 мин (одна 81 мин), ожидание замка до 30–50 мин
(`18660e1be37bff26` пришёл 22:45, старт 23:15; `627085ca9b6182c8` 22:22 → 23:11). Причины:
1. Один замок, опрос `flock -w 10` — порядок случайный, приоритета нет: сборка бинаря для ворот ждёт за чужим `all`.
2. `all` = fmt + clippy + lint-gate (свой target) + тесты с debug-assert (свой target `-dbg`) — три полных компиляции крейта `alpha`; при этом `touch` всех `*.rs` (нужен: tar сохраняет mtime, без него cargo взял бы чужую сборку) — каждый запрос компилирует крейт с нуля.
3. Ядра: `build-srv.sh` передаёт `SRV_CORES=2`, `vps-check.sh` — нет (6). Под весом 100 при загрузке 30 сборка получает 1–2,7 ядра.
4. Отмена: раннер проверяет «клиент ушёл» только на ожидании замков; во время сборки (`systemd-run --scope`) — нет, сборка доходит до конца и ставит бинарь (это и есть механизм инцидента §1.1). Убить клиента на ПК (фоновый bash агента) часто не убивает `ssh`.
5. София: свободно 24 ГБ < `VPS_MIN_GB` 28 ⇒ `CHECK_HOST=vps` отказывает (rc 76), а София простаивает (load 0,02, 4 ядра). Порог правильный (сторож режет при < 23 ГБ, пик сборки ≈ 3 ГБ), снижать нельзя — надо освободить ≥ 5 ГБ: `/tmp` 1,8 ГБ, `/opt/alpha-compute/jall` 1,2 ГБ, журнал в `/var` (5,7 ГБ: `journalctl --vacuum-size=500M`), старые `alpha-pumponset-v*`, `build-*.log` — по приказу координатора.

Исправление:
- Приоритет и порядок: файл очереди `/opt/rbuild/queue/<приоритет>-<время>-<pid>`; замок берёт старший приоритет, при равном — раньше пришедший. Приоритет 0 — бинари для критического пути (`build`), 1 — ворота, 2 — `all`. Ставится переменной `RBUILD_PRIO` у `build-srv.sh`/`vps-check.sh`.
