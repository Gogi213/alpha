# Канонический хеш клетки Летописи (TK-186, В-213/В-224), 11.10, ред. 2 (по возврату Судьи)

`tools/registry/cellhash.py::cell_hash(cfg)` — sha256[:16] от полного нормализованного конфига: вход, стоп, тейк, дедлайн, ttl,
early, форма выхода; набор (side, min_age, max_age, ctx, flow, usd_min, r1_born_shift, signal, driver, lot, entry_ttl, post_only,
band_exit); σ-каталог; исполнение (rtt, queue, h3, hold_step, busy_skip); вариант R1/R2; **вселенная монет** (`universe`);
`batch` (партия прогона — только там, где результаты расходились); `logic` = `bounce-v1`. Повторная нормализация идемпотентна.

**442 клетки Летописи → 441 канонический хеш** (`cellhash-map-2026-10-11.csv`: старый id; хеш; источник конфига; форма; набор; прогон).
Единственная пара: `p05-a1/p05-a45-u10k` = `p07m-main/t-bid-btc4h-q1` (оба — набор B1, age 2700, без flow/usd; результаты равны по
всем месяцам).

## Что изменено против ред. 1 (замечания Судьи)

1. **Наборы — из `--set` командных файлов прогонов на calc, не из имён и не по умолчанию.**
   - p05 (все 133 клетки b/c/a1/a2): `docs/registry/files/tk040-sets-jan.txt` (165 `--set` из
     `/data/tk046/jan/home/alpha/tmp-p07/cells-by-day/jall-jan-2026-01-02.sh`). Набор без `aNN` в имени = age 2700 (не 7200):
     `p05-b/p05-f25-u25k` (age 2700) ≠ `p05-c/p05-f25-a120-u25k` (age 7200). Допущение «возраст p05-b = 7200 из шапки группы» ложно, снято.
   - e106-pop: `age=2700,side=bid,btc4h_max=-44.55,r1_born_shift_cbps_min=-9e18` (`/data/tk0115/tk115-delta-day.sh:38`) — это **не** B1.
   - g87-fresh: `age=2700,agemax=3600,side=bid,btc4h_max=-44.55` (`/data/tk065/r2-gen.py:21`) — `agemax` в хеше.
   - Остальные группы пула (p02/p07*): набор `t-bid-btc4h-q1` — метка, признаки в шапке группы (hdr_*): уникальность имён нет, шапка совпала с `--set` там, где он есть.
2. **Исполнение — из тех же команд:** `--busy-skip off`, `--hold-step skip`, `prob:3`, rtt В-68, h3 notional — для пула TK-040 и для e106/p12.
   В ред. 1 пулу ошибочно приписан busy-skip on — исправлено (B1 пула и B1 П-12 теперь отличаются только вселенной/партией).
3. **Вселенная монет — в ключе:** `v171b` (пул TK-040) / `v171c-drop:TRUMP,TRX,BCH` (TK-182/183). Один конфиг на разных вселенных даёт разные результаты.
4. **B1 в p12-r1 и p12-ext (авг 398 vs 402 сделки, $248,76 vs $261,12):** вселенная и конфиг по источнику одинаковы, причина расхождения
   в доступных артефактах не названа (другой запуск/сборка дерева). Безопасная сторона В-213: развести ключом `batch` (p12-r1 / p12-ext) —
   лишний пересчёт возможен, ложный пропуск — нет. Выяснить причину можно сверкой `drop2/ext` с `drop2/r1` по суткам авг — отдельным шагом, если понадобится слить.
5. **Самопроверка в `map` (`cellhash_reg.check`):** группа равных хешей обязана дать равные trades/sum_net_bps по всем общим месяцам results.jsonl,
   иначе `map` отказывает. Первая версия правила (набор пула из `--set` по имени для p07*) её не прошла (150 расхождений) — и была исправлена по п.1.
6. **Тесты (6, `tools/registry/test_cellhash.py`):** два пути — один хеш; разный конфиг — разный; происхождение не входит; p05-b ≠ p05-c;
   e106-pop ≠ B1; B1 r1 ≠ B1 ext; самопроверка results = пусто; plan по каноническому хешу.

## Остаточные допущения (Судье)
- hold_step=skip и busy-skip off для p12-r1/ext/R2-A приняты по командам pool/TK-115 (`poolc-c.sh`), своего командного файла у дропа p12 нет.
- Группы p02/p07* различаются по шапке; прочие флаги группового прогона (не попавшие в hdr_*) не восстановимы без командных файлов этих групп — самопроверка по results их не опровергла.
