## §0. Итог

1. **Jev установлен настоящий, но используется с подменой понятий.** Ходим в `api.typesafe.ai/v1/systemone`,
   отвечает `jev-1.13.0`, ключ работает. Но: (а) жёсткие правила (две семьи флоров, коллизия имени) код уже
   вычисляет сам — и отдаёт модели пересказать, решение принимается по ответу модели, а без ключа проверка
   не выполняется вовсе; (б) ответы модели попадают в разборы как измерения («риск подгонки 0.68»,
   «уверенность 1.62/3»); (в) судья вердикта с наводящей рамкой переименовывает «красный» в «перспективный».
2. **Живая ветка (+$377 на 128 сделках) — не «отскок» практиков, а удержание лонга на 2 часа после подхода к
   старой бид-стене.** 108 сделок из 128 (84 %) закрыты по дедлайну, тейк сработал 17 раз, стоп 3; стену сняли
   в 77 сделках (60 %). Защита уровня в прибыли почти не участвует.
3. **Около 40 % результата — общий рост рынка.** Контроль «лонг той же монеты в тот же день на 2 часа в
   случайную минуту» минус комиссии даёт +12.0 bps из +29.5 на сделку. Превышение над контролем: +17.5 bps в
   среднем, медиана +9.5. 18.09 — чистый рост рынка (54.6 против 54.8), 19.09 — хуже контроля (−16.4 против −5.0).
4. **«Шарп 3.6» — это не Шарп**, а t-статистика по 128 сделкам как по независимым (`breakdown.py:80`,
   пересчёт — 3.55). Формальный вердикт того же прогона — «красный», нижняя граница −1.1 bps; кластеры —
   часы UTC, а не сутки, потому что суток меньше семи (`bounce_verdict.rs`, `G_MIN = 7`).
5. **Деньги посчитаны на лот $1000, а очередь смоделирована для лота $2–4.** Модель очереди `prob:3` взята
   из примера крейта, не измерена (В-80). 11 исполнений из 106 (10 %) — по оптимистичному пути «цена дошла
   до заявки без сделки», где крейт исполняет весь остаток, не проверяя объём на уровне. Пик — 8 позиций
   одновременно, то есть под $377 нужен капитал около $8 000, а не $1 000.
6. **66 % прибыли дают 4 монеты из 27** (WIF +$107, ATOM +$54, LTC +$46, ONDO +$43); остальные 24 — +$127.
7. **Главное правило практиков — выходить сразу при «прилипании»** (у S, D, T и в соседних видео) — в коде
   есть (`ExitReason::Early`), но в сетке выключено жёстко (`bounce_grid.rs:1317`,
   `early_exit_ns_from_secs(None)`). Ни F10, ни ночь его ни разу не проверяли.
8. **Ночные базовые наборы нереализуемы вживую:** по умолчанию `--entry-ttl-secs touch`
   (`nightly-grid.sh:133`) — заявка живёт ровно столько, сколько длилось касание, а это известно только
   задним числом (`backtest.rs:1656-1663`).
9. **Сильная сторона проекта:** задержки и комиссии измерены, а не выдуманы; DSR нормирован на все 1380 строк
   журнала, а не на удобную выборку; гейты «те же байты» на каждое изменение движка; счётчики оптимизма

**Правильно.** Эндпоинт, заголовок, модель `jev-latest`, повторы на 429/529 — по контракту API
(`tools/typesafe/judge.py:34-35, 71-107`). Ключ только из окружения, в репозитории и логах не встречается.
Живой запрос: ответ `jev-1.13.0`.

**Живые проверки (счётная машина, 22.09):**

| проверка | ответ | что это значит |
|---|---|---|
| noul «состояние — ровно слово ping?» при состоянии `ping` | 0.73 | даже тривиальный факт — не 1.0; модель даёт вероятность, а не проверку |
| score, критерии массивом | 200, `score` 0.0 | как в документации |

**Подмена 1 — правило стало мнением.** `prereg-guard.py` сам вычисляет `has_age`, `has_flow` и совпадение
ключей с ночным набором (`:79-95`), пишет это модели текстом и решает по её ответу
(`:176: bad = verdict == "invalid" or both >= 0.5 or coll >= 0.5`). Детерминированный результат в решение не
идёт. Без ключа страж выходит с кодом 2, и прогон **продолжается** (`f10-approach-run.sh:29-30`). В В-81 это
записано как «прогон не блокируется молча» — по смыслу «прогон идёт без проверки». На деке ключа нет,
значит страж там выключен. Тот самый невалидный набор E15, ради которого страж делали, код поймал бы
однострочником без модели.

**Подмена 2 — мнение модели подано как измерение.** `loss-judge.py:117-150`: выбор из 7 кандидатов, а в
состоянии описаны максимум два (фильтр `shown`) — «`pool_4h` 0.92» почти вынужден. Вопрос с идентификатором
`confidence` на деле Score (средневзвешенный уровень 0…3), а не поле `confidence` API. В
`loss-atoms-2026-09-22.md` §7 всё это стоит в разборе рядом с долларами как «уверенность 1.62 из 3» и «риск
подгонки 0.68». `nightly-read.py:157` печатает в скобках `confidence` у Choice («СЛОМАНО (0.99)»). Это
концентрация распределения, а не вероятность правильности; документация TypeSafe прямо предупреждает не
читать её как точность.

**Подмена 3 — наводящая рамка.** `verdict-read.py` (CONTEXT, `:124-145`) вкладывает в модель тезис «форма с
60 сделками и +12 bps — сильный сигнал» и определяет вариант `promising` как «нижняя граница объяснима малой
выборкой». Машинный вердикт «красный / мало данных» судья с такой рамкой переименует в «перспективный» —
это не независимое чтение.

**Прочее.** Версия модели не пишется в артефакты (`jev-latest` меняется — суждения невоспроизводимы).
Точность ни одного из шести судей не измерена: набора размеченных случаев нет, порог 0,5 не проверен (по
документации порог выбирают по измеренной точности на своих данных).

**Правильная граница (рекомендация).** Правила, числа и статусы — код, с жёстким отказом: семьи флоров,
коллизия имени, упал ли юнит, число тревог, число тестов. Jev — только там, где нужна семантика свободного
текста: «у каждого числа в строке предрегистрации есть ссылка», класс ошибки по трассировке, подсказки
ревью по диффу. В разборах ответы модели — отдельной пометкой «мнение модели», не рядом с метриками.
Логировать `model` из ответа. Разметить 20–30 прошлых случаев (ночи, наборы, строки prereg) и измерить
точность каждого судьи до того, как ему что-то блокировать. Исправить тип `Judge.score` на список.

## §2. Стратегия заново по первоисточнику против реализации

Реконструкция по расшифровкам (ссылки — таймкоды [S]/[D]/[T]). В проекте сейчас есть «живая ветка»:
набор `a45-bid`, подход D = 20 bps, лестница `ladder3x2..20w2`, срок жизни входа 1800 с, стоп 2 %, тейк 1:1,
дедлайн 2 ч.

| элемент | практики | проект сейчас | расхождение |
|---|---|---|---|
| горизонт | S: «секунда максимум» [S 15:52]; D: от часа до дней [D 30:02] | 2 ч, 84 % выходов по дедлайну | тестируется свинг на дрейфе, а не скальп-отскок |
| выход без реакции | «не ждать стопа», выходить руками при прилипании — повторяется минимум в 4 файлах [S 17:06; T 2:10:35; D(A) 17:06; S(N) 1:27:16] | `ExitReason::Early` в стратегии, **выключен в сетке** (`bounce_grid.rs:1317`) | главное правило ни разу не проверено |
| стоп | перед стеной или внутрь толпы фронтранеров [D 12:56–13:41; S 31:26] | `pct2` — 2 % от входа | на порядок дальше, чем у практиков; позиционные стопы в сетке дают −9…−10 bps |

| число касаний | 2–3 норма, 4+ — риск пробоя [S 12:50–14:15] | `repeat_before` — только атом разбора, не ключ фильтра | не используется |

| «снялся» | единственный вход в шорт [D 31:56–34:35]; переворот [S(SU) 42:19] | переворотов нет (решение владельца), шорты от аск-стен в минусе | шорт по правилу D не тестировался |

**Вывод §2.** В проекте фактически две разные стратегии, и проверена только одна. (1) **Скальп-отскок
практиков**: минуты, стоп у стены, быстрый выход без реакции. Его ни разу не проверили в реалистичном
исполнении: вход в касание оказался тейкерским в 77 % (M14), выход по прилипанию в сетке выключен.
(2) **«Дрейф от старой стены»**: 2 часа, широкий стоп. Его проверяют, и прибыль идёт от хода рынка после
входа. Стена работает как фильтр момента входа, а не как защищённый уровень.

## §3. Как устроено сейчас — коротко

Коллектор пишет стакан (v3) → сверка K1 → трекер уровней (`levels.rs`): касания и подходы строго
причинные, фронтранер берётся из кадра за секунду до касания (`:77-95, 884-901`), поток — только прошлые
минуты (`:1254-1267`) → кэши касаний и подходов по суткам → `bounce-grid`: одна стратегия `on_event` с
фазами, формы потоками над одним буфером событий, драйвер по окнам сигналов → крейт с измеренными
задержками и комиссиями → `rounds.csv`/`forms.csv` → вердикт (bootstrap-t по кластерам, PBO/CPCV, DSR по
журналу). Движок в хорошем состоянии; риски сосредоточены в допущениях модели исполнения и в оценке.

## §5. Тонкие места — корректность модели

- **Т1. Срок жизни входа `touch` — утечка будущего.** Длительность касания известна только постфактум
  (`backtest.rs:1656-1663`). Это умолчание ночи (`nightly-grid.sh:133`), поэтому все ночные базовые вердикты
  нереализуемы вживую. F10 этим режимом не пользуется.
- **Т2. Путь исполнения 3 оптимистичен по размеру.** `partialfillexchange.rs:135-146, 185-194`: «лучшая цена
  дошла до нашей» — исполняется весь остаток. Счётчик есть (`n_fill_by_cross`: 11 из 106), поправки нет.
- **Т3. Суточный сброс возраста.** Трекер в корне-сутках стартует в 00:00 UTC. Стена, пережившая полночь,
  выглядит молодой, а до 00:45 UTC возраст ≥ 45 мин недостижим. В живой ветке за 5 суток на час 00 UTC
  пришлась 1 сделка (возможны только после 00:45), на час 01 — 10. Это не только недосчёт возраста, но и
  отбор по времени суток; для семьи «возраст» нужен трекер, переживающий полночь.
- **Т4. Ошибка в разборе убытков (L3).** `loss-atoms.py:153-160, 267-271`: когда на один взвод приходится
  несколько подходов (16 сделок из 128), `pick_wall` берёт ближайший к цене входа, не проверяя правила
  набора. В итоге у 9 сделок набора «возраст ≥ 45 мин» атом возраста ≈ 0 минут: к сделке приписана чужая
  молодая стена, вместе с её размером и судьбой. Статистика «судьба стены» и атомы стены в M18 слегка
  загрязнены. Правка: отбирать кандидатов по ключам набора (`age ≥ 2700`, `side = bid`).
- **Т5. Лот суток по цене последнего касания** (`backtest.rs:773-830`) — небольшая утечка будущего для денег и
  порога полушага в очереди. На `net_bps` не влияет.
- **Т6. Стоп и тейк срабатывают по котировке, а не по сделке** (`strategy.rs:1266-1269`) — стандартно для
  L2, при тонкой книге чуть быстрее реальности.
- **Т7. Ёмкость считается на пару «монета × форма».** Лимита позиций на пул нет — для исследования нормально,
  для живого контура нужен.
- **Т8. `LiveBot` не подключён.** Обещание «одна стратегия для бэктеста и живого бота» (A6) пока проверено
  только с одной стороны.
- **Т9. Python-конвейер разметки** (`approach-signal`, `fill-capacity`, `regime`) на утечки будущего целиком не
  проверялся. Одна утечка там уже была (`regime.py`, закрыта `7cd3502`).
- **Т10. DSR считает строки сетки**, но не пороги, подобранные в python-разборах (L3, фильтры `pool_4h`):
  реальное число испытаний выше учтённого.

## §6. Места буста и роста — по отдаче на усилие

1. **Контрольная выборка в каждом вердикте** (дёшево, python, минутные середины уже есть). Вычитать из каждой
   сделки рост той же монеты в тот же день на том же горизонте (и отдельно — рост пула в ту же минуту).
   Отделяет преимущество от беты сразу по всем формам.
2. **Включить выход по «прилипанию» в сетку** — флаг до `bounce_grid.rs:1317`, числа N — замером
   длительности касаний и реакции (M14 уже измерил касание 0.1 с в медиане). Это ось, которую все три
   практика называют главной.
3. **Развести две стратегии.** Скальп-отскок (минуты, стоп у стены, выход без реакции) и «дрейф от старой
   стены» (часы) — свои формы, свои горизонты, свой контроль. Сейчас они смешаны в одной сетке через дедлайны.
4. **Снятие стены — сигнал, а не шум.** 60 % стен в позиции снимаются. Причём «выход по снятию» на 128 сделках
   стоил −$188: снятие не означает разворот. Замер «ход цены после снятия, по стороне» (S9 в плане) и правило
   D «снялся → шорт» — кандидат на вторую ногу стратегии.
5. **Калибровка очереди.** Измерить `n` для `ProbQueueModel` на своих данных или микро-тестом живыми заявками
