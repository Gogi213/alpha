# TK-259 — ОЗУ против HDD: малый замер на calc (разведка, не внедрение)

Дата 15.10 (GMT+4). Ветка `tk259` (скрипт `tools/compute/tk259-io-probe.py`, свод `tools/compute/tk259-io-agg.py`), в master не вливается.
Сырое: `docs/findings/tk259-io-probe-2026-10-15.jsonl` (93 строки). Заявка alsched `1015204335723` (`--kind gate --cores 3`),
rc=0, 8,9 мин, calc свободен (счёта нет), `/dev/shm/tk259` убран (`shm_left=false`), readahead возвращён (65536 КБ на sda и sdb).

## Что вышло

1. **Повтор чтения тех же суток из кэша страниц ОС в 36 раз быстрее холодного HDD** (0,111 с против 3,99 с на 466 МБ);
   tmpfs после первой загрузки быстрее кэша страниц лишь на 6 % (0,105 с) — отдельный tmpfs смысла не имеет, кроме защиты от вытеснения.
2. **Восемь групп G=8 на одни сутки: 32,3 с без общего кэша против 4,6 с с общим — в 7,1 раза** (с диска 3726 МБ против 466 МБ — ровно ×8).
   Это главный рычаг: он бесплатен по железу и по коду чтения, нужен порядок запуска «сутки целиком, группы подряд».
3. **Порядок чтения по расположению на диске и readahead — в пределах шума** (±7 %) для цельных файлов одним потоком.
   **Параллельное чтение хуже последовательного**: 8 потоков дают 85–105 МБ/с против 110–122 МБ/с одним (−12…−28 %).
4. **approaches-*.csv с HDD читается вдвое хуже по МБ/с, чем события** (61 против 117 МБ/с, диск занят на 93 %); из tmpfs — в 35 раз быстрее.
   `.abin` тех же 12 символов в 5,5 раза меньше (4,2 против 23,3 МБ) и читается холодным в 9 раз быстрее (0,042 против 0,385 с).

## Единица измерения (выбор назван)

Сутки **D = 2026-01-15**, группа **k = 0 из G = 8** (каждый 8-й символ по имени): **12 символов**, как у реальной группы волны.
Пути: `E=/data/tk046/jan/home/alpha/epochs/e-jan` (events+csv), `AB=/data/tk048/abin-t46m/study/approaches/D20` (abin).
Файлы: `approaches-<SYM>.csv` 23,3 МБ, `<SYM>-D.binlog` + `.binlog.carry-events` 442,6 МБ, `.csv.abin` 4,2 МБ.
Всего читается 465,9 МБ (csv+события); на сутки целиком (≈ 8 таких групп) ≈ 3,7 ГБ — **оценка** по группе k=0.
Довесок D+1 не читался. Свободной ОЗУ в начале 48,5 ГБ; в tmpfs выкладывалось ≤ 0,5 ГБ (лимит 8 ГБ).

**Важно про диски:** csv и события этой единицы лежат на **sda** (466 МБ), `.abin` — на **sdb** (4,2 МБ). Скрипт ожидал csv на sdb —
это не так для пути e-jan; «sdb 94 % при 41 МБ/с» из волны относится к другим эпохам/путям. Здесь загрузка sda при холодном чтении тоже 91–95 %.

## Метод

- Холодный кэш — **не `drop_caches`** (глобальный, портит чужой кэш и холодит соседей по серверу), а `posix_fadvise(DONTNEED)` по файлам единицы.
  Проверка в каждой холодной пробе: прочитано с диска (`/proc/diskstats`) ≥ 0,9 × размер единицы — выполнено везде (sda 465,8 из 465,9 МБ).
  Тёплые пробы: ноль байт с диска (поле `sda_MB` отсутствует = 0).
- Метрики: wall (`perf_counter`), МБ/с = МБ/wall, диск — МБ и занятость `io_ticks`/wall из `/proc/diskstats` (iostat на calc нет), ЦП — `process_time` (user+sys процесса).
- ×5 повторов каждой ячейки; ниже **медиана [мин–макс]**. Читает один процесс Python `os.read` по 1 МиБ; запись нигде не делалась, Storage Box не трогали.

## Экстраполяция на волну — оценка, не измерение

Из бюджета волны ожидание диска ≈ 36 % (чтение approaches 18,7 %, событий 14 % — по замерам репозитория, не этой пробы).

- **События, 14 %:** если все 8 групп одних суток идут в окне жизни кэша (сутки ≈ 3,7 ГБ против 48 ГБ свободной ОЗУ — влезает ≈ 13 суток), доля дисковой работы падает в 7,1 раза → экономия до 14 × (1 − 1/7,1) ≈ **12 % бюджета**.
- **approaches, 18,7 %:** если файл читается ≥ 2 раз за окно кэша, повторы бесплатны (×35 на байт csv); верхняя граница до **≈ 18 %**, сколько файлов читается повторно — **не знаю**, из этой пробы не видно.
- **Итого верхняя граница ≈ 30 % бюджета → волна быстрее не более чем ×1,4**, при условии, что группы одних суток не разнесены по времени дальше окна кэша. Если волна уже идёт «сутки-мажорным» порядком, выигрыш частично уже получен и оценка завышена.
- 15 слотов читают параллельно: проба с 8 потоками показала просадку −12…−28 % МБ/с, волна даёт 41 из 136 МБ/с — то есть перемежение на одном диске хуже, чем у пробы. Воспроизведено **не** (нужен гейт с ЦП-нагрузкой слотов).

## Чего эта проба не показывает

- Один день, одна группа, читатель на Python с `os.read` по 1 МиБ — не Rust-читатель `feed/replay` (mmap/размер чтения/декодирование v3 не сняты).
- Нет ЦП-нагрузки слотов: у волны чтение и счёт перемежаются, тут чистое чтение.
- Читал один владелец кэша (мой процесс); влияние чужих читателей и вытеснение кэша при соседнем счёте не измерено.
- Страницы кэша в пробе тёплые лишь секунды; поведение кэша за время волны (десятки минут, 15 слотов, запись `out`) не измерено — отсюда условие «окно жизни кэша».
- `drop_caches` не использовался (глобальный сброс); `posix_fadvise(DONTNEED)` проверен по диску (≥ 0,9 × размер).

## Рекомендация по В-170 (узкое место → способы → замер → решение)

Узкое место подтверждено: холодное чтение — это 94 % занятости диска при ≈ 117 МБ/с (потолок диска 136), повторы тех же суток в 8 раз раздувают трафик.
