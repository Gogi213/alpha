Не `debug` по смыслу: два живых прогона ниже — данные о **записи** (разбор,
очередь, аллокации, CPU, RSS, байт на запись), не о рынке; `session.json.debug

Пул — восемь инструментов из `instruments.csv` в корне (отладочное окно 300 с,
`CLAUDE.md`, «грабли»): `SOLUSDT, ADAUSDT, XRPUSDT, DOGEUSDT, HYPEUSDT,
NEARUSDT, PUMPFUNUSDT, ENAUSDT`. Владелец 2026-09-12: «начать с оптимизации
коллектора. супер оптимизировать. далее запустить его и пусть крутится» —
этот файл закрывает первую часть числами, вторая — таск 25.

## Что изменилось в коде (зона таска)

1. **Разбор без DOM** (`src/bybit/ws.rs`). `parse_message` строил
   `serde_json::Value` на каждое сообщение — узел дерева на каждый объект,
   массив и строку. Теперь — типизированный `serde_json::from_str` в
   `RawOrderbookMsg`, а уровни и сделки разбираются визиторами **на лету**:
   пара `["цена","размер"]` превращается в `(i64, i64)` через `parse_e9` в
   момент чтения (`LevelsE9`, без промежуточного `Vec<(&str,&str)>`), сделка
   кладётся прямо в буфер вызывающего (`TradesInto`, без промежуточного
   `Vec<RawTradeItem>`). Новый вход `parse_message_into(raw, &mut Vec<Event>)`
   — буфер живёт в `bybit::conn::Connection::run` один на соединение,
   `handle_raw` вычерпывает его `drain(..)`; `parse_message` — обёртка над
   ним. `f64` для цены/размера по-прежнему нет (`parse_e9`).
2. **Батчинг кадра в `lob session`** (`src/commands/lob/session.rs`). Раньше
   — zstd-кадр на **каждое** сообщение в голый `File`. Теперь
   `SymbolState::batch` копит до `record::FRAME_TARGET_RECORDS` (1000 —
   существующая константа `lob record`, «кадр раз в ~10 с живого потока»),
   сброс по порогу, по таймеру `FLUSH_INTERVAL_NS` (= `record::
   HOURLY_REFRESH_SECS`, тот же периодический `flush`, что у продового
   рекордера — см. оговорку ниже) и на выходе; `File` за `BufWriter`.
   Формат на диске не менялся: `binlog::Reader` читает новые файлы без
   правок — тест `write_market_event_batches_many_messages_into_few_frames_
   and_round_trips` (2500 событий → 3 кадра, записи побайтно те же) и живой
   `lob verify` на «после» (`updates=7399 gaps=0 violations=0`).
3. **Гистограмма вместо `Vec` задержек**. `parse_latencies_ns`/
   `queue_latencies_ns` копили `i64` на каждый кадр без потолка. Теперь
   `LatencyHistogram` — фиксированный массив 48 октав × 64 бина (`[u64;
   3072]`, 24 КиБ, аллоцируется один раз), целочисленные log2-бины по
   старшему биту и шести следующим; относительная ширина бина ≤ 1/64 =
   **1.5625 %** (точная граница, печатается рядом с p99); перцентиль —
   «ближайший ранг», как в `bybit::probe`; значение — нижняя граница бина
   (не выше точного, не ниже его больше, чем на ширину бина). `session.json`
   печатает те же поля `parse_p99_ns`/`queue_p99_ns`.
4. **Вторая книга снята.** `session.rs` держала `Book` на инструмент и
   делала `apply` на каждое обновление — но `bybit::conn::handle_raw` уже
   применил то же обновление к своей книге и не пересылает ничего, что не
   прошло `apply`; вторая книга повторяла ту же последовательность над
   идентично инициализированной книгой и не могла дать другого исхода. Ни
   одно поле `Record` не читает состояние книги. Причина — в doc
   `write_market_event`.
5. **Аллокации на сообщение — измерены**, не прочитаны: гейт
   `session::tests::parse_book_write_path_allocations_per_message_after_warmup`
   — 10⁶ сообщений формата площадки через `parse_message_into → Book::apply →
   write_market_event`, `alloc_count::measure` вокруг трёх шагов, ожидаемые
   числа названы до прогона и утверждаются по каждому сообщению.

## Офлайн-бенч разбора (`tests/collector_bench.rs`)

Один и тот же файл без правок на HEAD и на коде таска (второй набор строк
`/into` — путь `parse_message_into`, добавлен после замера «до»; строки без
суффикса — `parse_message`, единственный вход HEAD). Фикстуры — снапшот
`orderbook.50` 50+50 (2122 Б), дельта 1–5 уровней на сторону (260 Б),
`publicTrade` 1–10 сделок (851 Б); n = 50 000 / 500 000 / 200 000; медиана и
p99 — «ближайший ранг»; аллокации — `alloc_count` по 4096 сообщениям после
прогрева. Разрешение `Instant` на Windows — 100 нс.

| Вид сообщения | до: медиана / p99 | после `parse_message`: медиана / p99 | после `parse_message_into`: медиана / p99 | аллокаций/сообщение: до → после (`_into`) |
|---|---|---|---|---|
| снапшот 50+50 | 55.3 / 116.2 мкс | 14.5 / 48.6 мкс | 14.5 / 64.5 мкс | 328.0 → 9.0 (8.0) |
| дельта 1–5 | 6.1 / 14.0 мкс | 2.1 / 5.6 мкс | 2.0 / 5.1 мкс | 38.3 → 3.0 (2.0) |
| лента 1–10 | 16.9 / 45.2 мкс | 4.1 / 13.7 мкс | 3.5 / 9.5 мкс | 92.8 → 1.8 (0.0) |

Медиана разбора — в 2.9–4.8 раза быстрее, p99 — в 2.4–4.8 раза; аллокаций
— в 19–41 раз меньше (лента — ноль). p99 снапшота `/into` (64.5) выше

(в `/into` в замер входит освобождение двух `Vec` по 64 пары предыдущего
снапшота), медианы равны; снапшот приходит раз на соединение/ресинк.

## Гейт аллокаций: разбор → книга → запись (10⁶ сообщений, после прогрева)

| Вид | n | аллокаций/сообщение, среднее | максимум | Что это |
|---|---|---|---|---|
| дельта (0–5 уровней на сторону) | 899 990 | 1.665 | 2 | по одному `Vec<(i64,i64)>` на **непустую** сторону — `book::Update` владеет `bids`/`asks` и уходит владельцем в канал `ConnEvent::Message`; утверждается точно по каждому сообщению |
| лента (1–10 сделок) | 100 000 | 0.000 | 0 | сделки — прямо в буфер вызывающего |
| снапшот 50+50 | 10 | 8.000 | 8 | 2 стороны × (первая ёмкость 8 + три роста 8→16→32→64) |

`Book::apply` и `write_market_event` — ноль (в сумме с разбором числа выше
ровно равны аллокациям `Vec` уровней; прежний тест `million_events_through_
replay_feed_allocate_nothing_after_warmup` на `write_market_event` — ноль на
10⁶, с батчингом и `write_frame` внутри). Сверх этого в бою — одна `String`
сырого кадра в `tungstenite` (`PLAN.md` 6.1: «транспорт ≤ 1 на кадр,
принято»).

**Оставшееся названо, а не спрятано:** 1–2 аллокации на книжное сообщение
— это `Vec` внутри `book::Update` (`src/book/**` вне зоны таска 24) плюс
владеющая пересылка через `ConnEvent::Message`. Ноль на этом пути достижим
только фиксированной ёмкостью в `Update` или возвратом буферов через канал —
оба меняют `book::Update`/`ConnEvent` и всех их читателей (`record`, `pick/
measure`, `react`, `feed`). По правилу пункта 5 таска («решать по замеру: если
после п. 1–4 укладывается — не усложнять») — не усложнялось: p99 разбора на
живом пуле ушёл под бюджет (ниже), а строка «аллокации, разбор + книга +
разметка + триггер: ноль» гейта GC (`PLAN.md` 6.1) остаётся **не
выполненной на 1–2 аллокации на книжное сообщение** — честно красная, с
названной причиной и названным путём.

**Что не уложилось — честно.** (1) Гейт «ноль аллокаций на разбор + книга»
— 1–2 на книжное сообщение, причина и путь названы выше; закрыть — отдельный
таск с правкой `book::Update`/`ConnEvent` (вне зоны). (2) Один живой прогон
«до» и один «после» на разных минутах публичного интернета — по правилу
таска ровно два; разброс между двумя пятиминутками на одной сборке в таске
20 достигал 2×, поэтому живые 248.7 → 104.4 мкс и 670 → 299 мкс — одно
наблюдение, подтверждённое офлайн-бенчем (детерминированные фикстуры,
2.4–4.8× по p99 и 19–41× по аллокациям), а не самостоятельное
доказательство; повторяемость даст сбор таска 25. (3) Таймер сброса —
часовой (`HOURLY_REFRESH_SECS`), потому что это единственный существующий
периодический `flush` `record.rs`; на активном инструменте кадр закрывается
порогом 1000 записей (≈ секунды), таймер страхует только мёртвый инструмент;
потеря при крахе ≤ 1 незакрытый батч + буфер `BufWriter` на инструмент.
Число «раз в ~10 с» из doc `FRAME_TARGET_RECORDS` — комментарий, не
константа; вводить константу 10 с значило бы изобрести число.

## Вердикт

Разбор p99 на пуле из восьми — **в бюджете 200 мкс** (104.4 мкс) впервые
за четыре замера проекта; CPU средний 1.74 % (< 5 %); RSS плоский по 30-с
сэмплам; байт на запись −53 %; `gaps = 0`, `verify = ok`, формат бинлога и
все читатели не тронуты; 615 тестов (было 607 до таска 24), `clippy -D
warnings` — 0, `cargo fmt --check` — чисто. Одна строка гейта GC остаётся
красной по построению типов вне зоны — «аллокации, разбор + книга» = 1–2 на
книжное сообщение, ноль на ленту и на запись — и не выдаётся за зелёную.
