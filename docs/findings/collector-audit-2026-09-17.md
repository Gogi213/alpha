## 1. Что собирает, откуда, как хранит

Подробно — приложения A §1, C §1. Коротко: категория `linear`, топики `orderbook.50`,
`orderbook.200`, `publicTrade` на инструмент, все три — одним неделимым блоком на одном сокете
(`src/feed/live.rs:140-164`), N сокетов → один `mpsc` → один поток решений (A3). Запись
`binlog::Record` (`src/binlog/mod.rs:324-352`): `ev`, `exch_ts_ns`, `local_ts_ns` (на группу-сообщение),
`price_ticks`, `qty_lots` (целые, A1), биты `block`/`rpi`. Локальное время — `Clock` сразу после
`recv`, до разбора. Файлы `<SYMBOL>-<день>.binlog` (+ `deep/` для `.200`), кадр ≤ 1000 записей или
на снапшоте, zstd-1 по кадру, ротация по UTC-полуночи с синтетическим снапшотом. Ресинк —
повторная WS-подписка на глубину и символ, не REST. Контрольной суммы в `orderbook` Bybit нет, в
коде — тоже (только структурная валидность zstd).

## 3. Корректность данных (дельта; полностью — приложение A)

- Снапшот + дельты одной `Book::apply` (`src/book/mod.rs:213-271`): `u=1` — перезапись, повтор или
  разрыв `u` — `SequenceGap` → ресинк; после применения — проверка `Crossed`. `.50` и `.200` —
  раздельные книги и раздельные `u`; склейки на чтении нет.
- Пинг `{"op":"ping"}` раз в 20 с (`LIVE_PING_INTERVAL`, `src/feed/live.rs:75`), бэкофф без
  предела попыток, сбрасывается только после «полезной» сессии. **Ответный `pong` не отслеживается,
  таймаута чтения нет** (`grep timeout src/bybit/conn.rs` — 0).
- **Ошибка `connect()` глотается** (`src/bybit/conn.rs:602-611`): нет `ConnEvent`, нет строки
  `gaps.csv`, нет `reconnects++` (ветка не достигнута). HTTP-статус рукопожатия отброшен
  (`conn.rs:983-985`) — 403 и 429 неотличимы от обрыва сети.
- `gaps.csv` пишет `Sequence`/`Frame`-потери построчно, но `Unrouted` — только счётчик в памяти до
  `finalize()`; `kill -9` его теряет.
- Hot-add — одной партией, удаление не поддерживается; `stop` — на тике ≤ 10 с, `flush_all`,
  `closed=true`.
- **Сервер, 25 ч, 100 монет:** `gaps.csv` — только заголовок; `reconnects/resyncs/frames_failed/unrouted`
  = 0. Журнал юнита: `StandardError=inherit` → journald, читается под `sudo` (56 строк, почасовые
  сводки `session: час N — records=… bytes=… gaps=0 … rss=… cpu=…`); пользователю `ubuntu` без
  `sudo` журнал не виден — группа `systemd-journal`/`adm` не выдана. Час 25: 1 628 423 819 записей,
  6.83 ГБ ⇒ **≈ 6.5 ГБ/сутки с `deep/`** (без него ≈ 3.9, если +69 % T45 верны), CPU 13–23 %.

## 4. Надёжность и производительность (дельта; полностью — приложение B)

- Потоки: решения (1) + ввод-вывод по сокету (N, свой `current_thread` рантайм) + ресурсы (1) +
  часы (1). `Mutex` на пути события — нет. Канал `4096 × pool` общий на пул: затор одного
  инструмента давит на все.
- Запись синхронно в потоке решений (§Выводы 5). `flush()` — до буфера ОС, **`fsync`/`sync_all`
  нигде** (устойчиво к `kill -9`, не к падению ВМ).
- Отказ записи: откат файла к границе кадра, `frames_failed++`, строка `gaps.csv` — но сама
  `append_gap_row` под `let _ =` (`session.rs:484`): при полном диске молчит и она.
- Аллокации: гейт 10⁶ сообщений — 1 аллокация на непустую сторону книжного сообщения, лента 0
  (красная строка признана 2026-09-12); `write_frame` — ноль отдельным тестом; сквозного
  «сессия → сброс кадра» под одним замером нет. `hot_path_guard`-греп есть у `live/replay/strategy/react`,
  у `session.rs`/`sink.rs` — нет.
- `book` — не кольцо (A4), а отсортированный `Vec` с memmove; комментарий в коде это признаёт,
  `ARCHITECTURE.md` — нет.
- Диск полон через ≈ 6.5 суток: код деградирует мягко (по чтению), живого прогона `ENOSPC` не было.

## 5. Хранение и воспроизведение (дельта; полностью — приложение C)

- v3: заголовок 25 Б, кадр `u32 len` + zstd-1, эпоха кадра, группы (`ev`, зигзаг-дельты времени,
  `attrs`, `count`), дельты цены/размера от предыдущей записи кадра. v2 — то же на запись, мёртвые
  поля; версия — из заголовка, декодер выбирается явно.
- Восстановление книги на момент `t`: последовательно с начала файла суток (кадр 0 — снапшот),
  индекса нет; на дашборде — 13 с на каталог. Глубина при реплее — константа 50, даже для `deep/`.
- Живучесть: файл кончается на границе кадра, кроме краха внутри `write_all`; тогда
  `watch/replay/verify/binlog-stats` падают целиком (`ShortRead`), `dashboard` — мягко по монете.
- `lob archive --delete-original` проверяет только маркер `ok`, не то, что часть закрыта — гонка с
  открытым файлом на POSIX теряет дописанное.
- `verify` (В-56): целостность ноль, тест 3 — доля < 0.1 %; **с REST не сверяет** (это только
  сайдкар, см. §3). На сервере статусы — в `verify-09015`, не в корне.
- Достаточность для `hftbacktest`: есть всё (цена/размер/сторона/время события, сделки с
  агрессором, блочные и RPI помечены); нет и не будет — ID ордеров (их нет у биржи).

## 1. Как устроено (факты кода)

**Источник.** Топики: `orderbook.50.<symbol>`, `orderbook.200.<symbol>` (`SUBSCRIBED_DEPTHS`,
`src/bybit/conn.rs:38-60`), `publicTrade.<symbol>` (третий топик на инструмент, `src/feed/live.rs:22-29`).
Категория — только `linear` (`CATEGORY_LINEAR`/`CATEGORY`, `src/bybit/rest.rs:39`, `src/bybit/probe.rs:42`,
`src/bybit/trade_ws.rs:51`); spot нигде не запрашивается.

**Хранимая запись** (`binlog::Record`, `src/binlog/mod.rs:324-352`): `ev: u64` (флаги стороны/типа события
из `hftbacktest::types`, сторона — не отдельное поле, а бит), `exch_ts_ns`, `local_ts_ns` — **одна пара меток
на группу-сообщение биржи**, а не на запись (`src/binlog/mod.rs:16-19,326-336`; экономия v3, В-49),
`price_ticks`, `qty_lots` (целые, A1), `block` (блочная сделка, бит 0 `attrs`), `rpi` (бит 1 `attrs`,
с 2026-09-16). **`u` и `seq` в записи на диске не хранятся** — сознательно (`src/bybit/verify.rs:9-16`:
«хранить `u` отдельным полем не стоит… плюс пять байт на событие»); в памяти они есть в `book::Update`
(`src/book/mod.rs:137-156`).

**Стакан.** Снапшот+дельты одной функцией `Book::apply` (`src/book/mod.rs:213-271`): `u=1` — не
ошибка, а полная перезапись книги (рестарт сервиса биржи); дельта до первого снапшота, повтор `u`
или `u ≤ prev`, разрыв `u` — все три `ApplyError::SequenceGap`; после применения — проверка
`best_bid ≥ best_ask` → `Crossed`. Для `.50` и `.200` — **раздельные книги и раздельные `u`**
(`session: books: Vec<Vec<Book>>`, `src/bybit/conn.rs:634-644,806-880`): разрыв одного потока не
считается разрывом другого. Ресинк — **повторная WS-подписка** на конкретную глубину и символ
(`ws::sub_orderbook`, `src/bybit/conn.rs:857-864`), не REST-снапшот; флаг `resyncing` не даёт слать
подписку второй раз, пока ждём. Bybit v5 orderbook **не несёт поля checksum/crc** — в `RawOrderbookMsg`
такого поля нет (`src/bybit/ws.rs`, полный список полей в шапке файла), и в коде нигде не проверяется.
Склейка `.50`+`.200` **на чтении не реализована**: глубокий поток пишется в свой файл
(`DEEP_STREAM`, подкаталог `deep/`, `src/bybit/conn.rs:63-66`), но `DEEP_STREAM` встречается только в
`conn.rs` и `session.rs` — ни один читатель (`parts.rs::session_binlog_for`, `dashboard.rs`, `replay.rs`)
про `deep/` не знает; фьюжн описан в `docs/findings/depth-200-ab-2026-09-15.md` как план («склейку делать
на стороне чтения»), а не как код.

**Время.** `local_ts_ns` ставится сразу после `recv`, до разбора (H12, `src/bybit/conn.rs:9-11,690-694`)
источником — трейт `Clock`/`SystemClock` (`src/bybit/conn.rs:70-96`). `exch_ts_ns` — из `cts`/`T` биржи
(мс → нс). Обе метки — на сообщение, не на запись (см. выше). `clock.csv` — отдельно, раз в час,
смещение хоста против NTP-пула и `serverTime` Bybit по одному протоколу (`src/bybit/clock.rs:1-50,64-70`),
не про сетевой поток данных.

**Переподключение/пинг.** `{"op":"ping"}` каждые `ping_interval` (Bybit требует ≤20 с) —
`src/bybit/conn.rs:236-241,733-741`; неудачный `send_text` пинга → `Disconnected`. Бэкофф —
экспоненциальный с потолком, без ограничения числа попыток (`BackoffConfig::delay_for_attempt`,
`src/bybit/conn.rs:179-199`); сбрасывается только если сессия была «полезной» (хоть одно сообщение
переслано, `src/bybit/conn.rs:747-762`).

**Дубли/порядок.** Все три топика одного инструмента упаковываются в подписку **одним неделимым блоком**
(`pool_args_chars` на инструмент, `src/bybit/ws.rs:591`; жадная упаковка `plan_connections`,
`src/feed/live.rs:140-164`) — значит один и тот же инструмент никогда не разбит между сокетами, и его
события идут в изначальном порядке одного TCP-соединения и одного `recv`-цикла. Между *разными*
инструментами на разных сокетах порядок — по прибытию в общий `mpsc`-канал (`src/feed/live.rs:34-42`,
один поток решений, A3), не по биржевому времени.

**Hot-add (T34).** `check_pool_file` (`src/commands/lob/session.rs:356-420`) сравнивает `mtime`, новые
строки — новые файлы + `feed.add()` одной партией; уже известные символы — no-op; удаление строки не

## 1. Как устроено (факты кода)

**Потоки.** На пул из 100 монет — 5 ОС-потоков (замер `deploy-2026-09-15…md:46`): один поток решений (главный, `run_session_loop`, `src/commands/lob/session.rs:856`), N потоков ввода-вывода — по одному на TCP-соединение, каждый со своим `current_thread`-рантаймом (`src/feed/live.rs:382-401`, `spawn_io_thread`), поток фонового сэмплера ресурсов (`resources.rs:118`, раз в 30 с/1 ч) и поток часового замера NTP/serverTime (`resources.rs:51-64`, свой ОС-поток, раз в `HOURLY_REFRESH_SECS`). При запуске — ещё поток `stop_on_ctrl_c` (`feed/live.rs:262-268`).

**Канал.** Один `tokio::sync::mpsc` на всю сессию, ёмкость `CHANNEL_CAPACITY_PER_SYMBOL(4096) × pool.len()` (`feed/live.rs:89`, `534-535`) — общий для всех соединений (`mpsc` многопроизводительный, приёмник один). Поток решений читает его синхронно: `self.rx.blocking_recv()` (`feed/live.rs:629`), не `async` — соответствует запрету 3 (`interfaces.md:47`).

**Mutex/блокировки.** На пути «сокет → разбор → книга → запись» — ни одного `Mutex`/`RwLock`: только канал. Единственный `Mutex` в модуле сессии — `Arc<Mutex<Vec<ResourceSample>>>` (`resources.rs:118`) между фоновым сэмплером (раз в 30 с) и потоком решений при записи `session.json`; не на пути события.

**Сокет.** `tokio-tungstenite` поверх `tokio::net::TcpStream` (`bybit/conn.rs:928-929`), неблокирующее чтение через `.next().await` внутри `tokio::select!` (`conn.rs:680, 954`). Таймаутов чтения нет: единственный механизм обнаружения мёртвого соединения — исходящий `{"op":"ping"}` раз в `ping_interval` (`conn.rs:669-677, 733-736`) и обрыв, который вернёт сам `tungstenite`/TCP; входящего идле-таймаута (`ждать pong не дольше N`) в коде нет — `grep timeout` по `conn.rs`/`record.rs`/`session*.rs` не находит ни одного (кроме комментария `session/args.rs:77`).

**Аллокации.** Гейт `alloc_count::measure` (`src/alloc_count.rs:58-71`, потоковый `thread_local` счётчик на `GlobalAlloc`) применён к коллектору тестом `session::tests::parse_book_write_path_allocations_per_message_after_warmup` (`session/tests.rs:612-773`): 10⁶ сообщений через `parse_message_into → book.apply → write_market_event`; утверждается точно — книжное сообщение 1 аллокация на непустую сторону (снапшот — 8), лента — 0 (`session/tests.rs:747-761`). Отдельный тест на `binlog::Writer::write_frame` (`binlog/tests.rs:561-602, 652-661`) доказывает ноль аллокаций после прогрева на самом сжатии/записи кадра. Между двумя тестами есть разрыв: `flush_symbol_batch` (сжатие+`write_all`, `sink.rs:441-464`) НЕ входит в измеряемый блок гейта `parse_book_write_path…` — измеряется только путь до накопления в `batch`, а не сам сброс кадра на диск в контексте сессии.

**`f64`/`HashMap`.** В `book/mod.rs` цена/размер — `i64` (тики/лоты), `f64` только на границе `MarketDepth` (A7, `book/mod.rs:325-376`). В `bybit/ws.rs::parse_e9` разбор без `f64`. Книга — не кольцо, а отсортированный `Vec<(i64,i64)>` с `binary_search`/`insert`/`remove` (`book/mod.rs:36-47`, коммент в коде прямо говорит: «Не кольцевой буфер… как предполагал черновик архитектуры» — расхождение с `ARCHITECTURE.md` A4, см. §2). Маршрутизация по символу — двоичный поиск по отсортированному массиву, не `HashMap` (`sink.rs:262-270`, `conn.rs` `Route::slot_of`).

**Часы.** `SystemClock` реализует трейт `Clock` через `SystemTime::now()` (`conn.rs:99-101`). В `bybit::conn::Connection::run` `local_ts_ns` берётся строго через `&clock` (`conn.rs:681-686`, до разбора). Но в `run_session_loop` поток решений сам напрямую зовёт `SystemClock.now_ns()` — не через параметр-трейт, а через конкретный тип — четыре раза на разных путях: проверка дедлайна (`session.rs:862`, раз в каждую итерацию цикла, то есть на каждое событие), расчёт `queue_latencies_ns` (`session.rs:877`, на каждое рыночное сообщение), плюс два раза вне цикла (`session.rs:621, 744`). `feed/live.rs` и `feed/replay.rs` защищены грепом «нет вызова часов» (`hot_path_guard`, `live.rs:712-731`), а `session.rs`/`sink.rs` — нет: такого теста для них не существует (грепнуто по всему дереву — есть только у `live.rs`, `replay.rs`, `lob/react.rs`, `lob/strategy.rs`).

**Запись на диск.** Синхронно, **в потоке решений**: `write_market_event` (`sink.rs:347`) вызывается из `run_session_loop` (`session.rs:906`) на каждое рыночное событие; при достижении `FRAME_TARGET_RECORDS` (1000) или на снапшоте вызывает `flush_symbol_batch` (`sink.rs:441`), который делает `writer.write_frame` (кодирование + zstd, `binlog/mod.rs:1303-1352`) и `writer.flush()` (`binlog/mod.rs:1356-1357`) — то есть сжатие и системный `write_all` идут на том же потоке, что читает канал. Отдельного потока записи нет. `flush()` — это `BufWriter`/`File::flush()`, доходит до буфера ОС; **`fsync`/`sync_all` нигде не вызывается** (grep по `binlog/mod.rs` и `session/sink.rs` — ни одного вхождения) — данные считаются «на диске», когда на самом деле они в кэше страниц ОС.

**Отказ записи.** `FrameSink::flush` (`sink.rs:136-166`) при ошибке `write_all` пробует откатить файл на границу последнего кадра (`truncate_to`, `sink.rs:53-61`); если и это не удалось — `boundary_lost=true`, часть закрывается и открывается следующая. Ошибка `flush_symbol_batch` не роняет процесс: `frames_failed += 1`, строка `gaps.csv` (`session.rs:487-494`), батч очищается — то есть до 1000 записей на поток теряются молча для данных, но не молча для мониторинга **если** запись `gaps.csv` сама удалась. Запись в `gaps.csv` — `let _ = append_gap_row(...)` (`session.rs:484`) — ошибка игнорируется полностью.

- Есть ли фактический входящий idle-таймаут у `tungstenite`/ОС TCP keepalive на используемых платформах (Windows-тесты, Linux-прод) — П-5 сформулирована по чтению кода, не по эксперименту.
- Реальная величина `queue_p99_ns`/риска обрыва пинга под давлением бэкапрешура (П-1) — замеры `docs/archive/findings/collector-2026-09-12.md` показывают рост `queue_p99` до 27.8 мс при 761 инструменте, но именно сценарий «диск затормозил → пинг не ушёл вовремя» не воспроизводился отдельно.
- Асимптота RSS для текущей раскладки T45 (два потока `.50`+`.200` на инструмент) на 100 монетах — задокументированный расчёт 150–260 МиБ дан для 761 инструмента и старой (однопоточной на инструмент) раскладки; не пересчитан под нынешние два потока/инструмент.
- `verify` не гонялся ни на одном боевом сервере (сам `CLAUDE.md`/`deploy…md:91`) — целостность реальных суток не подтверждена независимо от чтения кода.

## 1. Как устроено (факты кода)

**Заголовок суток**: `MAGIC="ABLG"` (mod.rs:236), `VERSION=3` (mod.rs:250), `VERSION_V2=2` (mod.rs:257);
`magic(4)+version(1)` читается отдельно (`MAGIC_VERSION_LEN=5`, mod.rs:264) от хвоста
`tick_e9(8)+step_e9(8)+max_records_per_frame(4)=20` (mod.rs:268), итого 25 Б (`HEADER_LEN`, mod.rs:271;
`Header`, mod.rs:283–295).

**Кадр на диске**: `u32 LEN_PREFIX` (mod.rs:276) + zstd-тело (по одному кадру, уровень 1, `Writer`
держит один переиспользуемый `bulk::Compressor`, mod.rs:1245–1256). Тело после распаковки: 8-байтовая
эпоха `i64 LE` — метка первой записи (`FRAME_EPOCH_LEN`, mod.rs:543; `encode_frame_payload`,
mod.rs:753–756), дальше — список **групп-сообщений**.

**Группа** = одно сообщение биржи: `encode_group_header` (mod.rs:659–701) пишет `ev` (uvarint),
зигзаг-дельту `exch_ts_ns` и `local_ts_ns` от эпохи кадра, uvarint `attrs` (бит0 `ATTRS_BLOCK`
mod.rs:549, бит1 `ATTRS_RPI` mod.rs:555, В-53), uvarint `count`. Границу группы решает
`same_message` (mod.rs:702–709): равенство `ev/exch_ts_ns/local_ts_ns/block/rpi`. Далее `count`
записей — зигзаг-дельты цены и размера **от предыдущей записи всего кадра** (`DeltaState` живёт
на кадр, не на группу, mod.rs:608–658).

**varint**: беззнаковый LEB128 (`write_uvarint`/`read_uvarint`, mod.rs:484,514); знаковый — зигзаг
(mod.rs:499–541). **zstd**: уровень 1, заморожен В-49 (уровни 3/6 и таблица `ev` дали 2–4.7 %,
ниже порога 5 %); параметр контрольной суммы (`checksumFlag`) нигде не выставляется —
`grep checksum` по `binlog/{mod,archive}.rs` пуст, то есть кадр не несёт собственной CRC сверх
структурной валидности самого zstd-потока.

**Record** (mod.rs:324–357): `ev:u64, exch_ts_ns:i64, local_ts_ns:i64, price_ticks:i64, qty_lots:i64,
block:bool, rpi:bool` — без `order_id/fval` (0 % ненулевых на 17–29 млн записей,
`docs/archive/findings/binlog-format-2026-09-13.md`).

**v2** (`decode_frame_payload_v2`, mod.rs:1022–1060): те же 8 байт эпохи, но **на запись**, а не на
группу: `ev, exch_ts, local_ts, price, qty, order_id(uvarint,мёртв), ival(zigzag→block),
fval(uvarint,мёртв)`; RPI в v2 не представим — `rpi` всегда `false` (mod.rs:1057). Версия читается
из заголовка **до** хвоста (mod.rs:1517–1526: `version != VERSION && version != VERSION_V2` →
`UnsupportedVersion`), и решает декодер в `read_frame` (mod.rs:1770–1780) — угадывания по содержимому
нет.

**Архив** (`archive.rs`): контейнер = один zstd-поток на весь файл, опознаётся **снаружи** магией
самого zstd (`ZSTD_MAGIC`, archive.rs:61, детект в `Reader::open`, mod.rs:1513), внутри —
`ABLA(4)+версия(1)+уровень zstd(1)` (`HEADER_LEN=6`, archive.rs:77) + обычный 25-байтный заголовок
v3 + кадры с `u32`-длиной, но **несжатыми** телами (доккомментарий archive.rs:1–15). Только источник
версии 3 (`write_container`, archive.rs:170, проверка версии перед кодированием).
