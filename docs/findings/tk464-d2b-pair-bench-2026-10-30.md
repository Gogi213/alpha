## Что отсюда следует для боевого D2b (по TWT как прокси всех 84 монет)

- ЦП на монету ≈ 351 с; 84 монеты на 15 ядрах при заполнении ядер процессами по парам «монета×ТФ» (как `run_pairs`
  в `tk463-lib.sh`): 84 × 351 / 15 ≈ **33 мин** счёта; по 15 потокам внутри пары (как замер) стена 44 с/монета →
  ≈ 62 мин (эффективность потоков внутри пары ≈ 53 %: 351/15 = 23 с против 44 с). Режим «пары по процессам» вдвое быстрее.
- Выход ≈ 295 МБ на монету (текст) → ≈ 25 ГБ на 84 монеты до сжатия; на calc `/data` свободно 466 ГБ.
- Узкое место — минутный проход `trade` (`N_BARS = 10` баров: 600 / 2400 / 14 400 минут окна для ТФ 60/240/1440):
  в среднем ≈ 6,4 мкс на (вход × ячейку) для ТФ 60 и ≈ 110 мкс для ТФ 1440 (окно 14 400 минут). Загрузка — 1,8 с на пару.

## Шаги (3) и (4) из тикета — граница выигрыша

- (4) одна загрузка свечей на монету для 3 ТФ: общая часть — разбор минут 1,58 + 1,54 + 1,39 с; общая загрузка
  экономит ≈ 3 с из 44 с (≈ 7 %) в режиме 15 потоков на пару и ≈ 3 / 351 ≈ **0,9 % ЦП** в режиме «пары по процессам».
  Не оправдывает перестройки `main`.
- (2) один проход по минутам на событие для всех ячеек: на ТФ 240+1440 приходится 59 % ЦП монеты (205 из 351 с), но доля минутного прохода внутри не измерена (`perf` на calc в окно запуска не уложился), поэтому **не реализован**:
  арифметика на минуту у каждой ячейки своя (стоп/цель/трейл/БУ/свинг/ОТ), общий проход экономит только загрузку
  `h/l` из L1/L2, а не вычисления. Решение о (2) — после профиля `perf record` одного пары ТФ 1440.

Алгоритм: варианты — (а) агрегация `--agg 1` (ООМ: каждая сделка — своя группа из-за ключа evk,cj), (б) парный `--pair`
(группа по суткам события; 2,5 млн групп на монету вместо 3·10⁹ строк), (в) один проход минут на событие, (г) одна
загрузка на монету; замер — таблица выше; выбран — (б) потому что единственный, у кого вывод ограничен (≈ 295 МБ/монету)
и гейт «результат в результат» против `tk461_d2a.one` пройден (18/18); (в) и (г) — не реализованы: (г) ≤ 0,9 % ЦП, (в) без профиля.

## Профиль пары ТФ 1440 (TWT, 449 ячеек, `--pair`, 1 поток, `perf record`) — шаг (2)

Скрипт `tools/compute/tk464-perf.sh`, данные `/data/tk0464/perf/{flat,children}.txt`, 27 118 выборок, счёт 52,9 с + загрузка 1,5 с.

- **96,3 % ЦП — функция `one`** (в неё встроен `trade`); весь остальной код (загрузка, разбор, запись) — < 3 %.
  По смещениям внутри `one` **95,1 % ЦП — 850-байтный участок минутного цикла** `trade` (по дизассемблеру: `l[m]<=cur`,
  `h[m]>t`, `max`/`ext`/`mfe`, трейл/свинг/БУ/ОТ); вне цикла — 1,0 %.
- Внутри цикла: **`idiv` — деление `(tm[m] + 60_000) % wms == 0` в ветке ОТ — 9,9 % выборок на самой инструкции и ≈ 19 % с
  соседними (`add`/`mov`/`movapd` вокруг)**; ещё ≈ 22 % — ожидание загрузок `l[m]`/`h[m]`/`o[m]` у начала итерации
  (массивы 14 400 минут × 4 × 8 Б — не в L1); остальное — ветви по `Option` (стоп/цель/часть/трейл/свинг/БУ) с
  переменными, пролитыми в стек.
- **(в) общий проход по минутам на событие**: делит между ячейками только загрузки `o/h/l/c` и префикс `ext`/`mfe`
  (≈ 22 % + ≈ 5 % цикла, верхняя граница по профилю ≈ 25–30 % ЦП), а арифметика стопа/цели/трейла/БУ/свинга/ОТ у каждой ячейки
  своя и остаётся (≈ 70 %). Перестройка `trade` в «ячейки внутри одного цикла» с гейтом «байт в байт» — большой
  объём ради ≤ 25–30 %; **отклонено числом**. Выбрана правка по профилю: деление в ОТ заменено границей окна
  (наименьшее кратное `wms` ≥ `tm[m]+60_000`, `tm` не убывает) — тот же результат, одна правка.
