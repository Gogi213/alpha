# Валидация внутри часа — дизайн `lob validate` (TK-038, В-169) — 03.10.2026

Статус: дизайн (шаг 1). Код — шаг 2, запуск по данным — шаг 3 (после TK-035, TK-037, TK-032). Источники: `src/commands/lob/gaps.rs` (TK-033), `src/bybit/verify.rs` (`KeepGoingReport::on_update`, `check_invariants`, `Verifier`, TK-034), `src/binlog/mod.rs` (`Record`).

## 0. Что бинлог умеет и чего нет

- `Record` = `ev, exch_ts_ns, local_ts_ns, price_ticks, qty_lots, block, rpi` (v3: метки один раз на группу сообщения). **Номеров `u`/`seq` в файле нет** (`verify.rs`, комментарий к `KeepGoingReport`: «файл `u` не хранит»). Следовательно «разрыв/дубль/откат u» по бинлогу напрямую **не проверяется**; его заменители (все в дизайне ниже): откат `exch_ts`, дубль группы (хеш содержимого), снимок посреди суток + дрейф книги против снимка, `delta_before_snapshot`. Прямая сверка по `u` — только сверка с REST-снимком (`compare_with_snapshot`, уже есть в `lob verify`). Если нужен именно `u` — это изменение формата записи (v4), вопрос владельцу; в этот проход не входит.
- Книга (`book::Book`) — отсортированные `Vec<(tick, qty)>`, без `BTreeMap`; `Update` держит `Vec` бидов/асков — **аллокация на обновление в конвертере** (`FileReplayer`/`records_to_updates`). Для «ноль аллокаций на событие» конвертер получает переиспользуемые буферы (clear без free) — шаг 2.

## 1. Проверки (идентификатор → что, разрешение, источник)

Единица учёта — монето-час UTC (по `exch_ts` записи); подмножество «минута» хранится в массиве `[Min; 60]` текущего часа, на выход идут часовые строки + минуты-исключения.

| ID | Проверка | Разрешение | Откуда |
|---|---|---|---|
| T1 | события/мин, число минут с 0 событий | минута | как `gaps` (h00..h23), но по минутам |
| T2 | самая длинная тишина (по `exch_ts` между соседними) и её начало; тишины >1м/>10м/>1ч | час (+ тишины через границу часа и файла приписываются часу начала) | `gaps` TK-033 |
| T3 | монотонность `exch_ts`: число откатов, максимальный откат (мс) | час | новое (замена «отката u») |
| T4 | задержка `d = local − exch`: min/p50/max за минуту (log-гистограмма 64 корзины, без аллокаций); «скачок» = минуты, где min d больше p50 часа/суток монеты на порог из п.3 | минута | новое |
| C1 | дубль группы: хеш (exch_ts, ev, цены, размеры) группы == хеш предыдущей | час | новое (замена «дубля u») |
| C2 | снимок посреди потока: число снимков, интервал между ними, снимок после битого состояния (`resync`) | час | `KeepGoingReport.resyncs` |
| C3 | **дрейф по снимку**: в момент снимка сравнить верх (N уровней/сторона) прежней книги и снимка; число расхождений = пропущенные дельты до снимка | снимок | новое; O(N) на снимок, `compare_with_snapshot` берётся как есть |
| B1 | инварианты после КАЖДОГО обновления, семантика `--keep-going`: crossed, nonpositive_size, unordered_levels, price_not_on_tick, qty_not_on_step, delta_before_snapshot | обновление → счёт на час и минуту | `BrokenKind` |
| B2 | доля времени в битом состоянии, мс по `exch_ts`, раскладывается по часам и минутам (интервал между обновлениями режется по границам минут) | минута | `broken_ms` TK-034 |
| X1 | сделки против книги: расстояние цены сделки до [лучший бид, лучший аск] в тиках — гистограмма (внутри, 1, 2, 3–5, 6–10, >10 тиков) отдельно для сторон; сделка при битой/пустой/несинхронной книге | час | `trade_in_range`, `price_held`, `trades_while_broken` |
| D1 | переход суток: состояние книги на конце файла D (хеш верха N уровней + `last_ts`) → начало файла D+1: что идёт первым (снимок или дельта), расхождение верха книги конца D и первого снимка D+1; пропуск между `last_exch(D)` и `first_exch(D+1)` | граница файла | новое; режим `--carry` |
| A1 | аномалии темпа: минута с 0 событий при обычной активности монеты; минуты с темпом ≪ медианы | минута | п.3 |

Все счётчики — целые; в CSV не пишется вывод, только числа и флаги — вердикты классифицирует свод (шаг 3).

## 2. Алгоритм: один проход на файл

1. `Reader::open` (v2/v3, `.zst`) → кадры → переиспользуемый `Vec<Update>` (clear). Один цикл по обновлениям и сделкам в порядке файла, как в `verify_one_file`.
2. На каждое обновление: T1–T4, C1, затем `apply` в `Verifier` (как `on_update` TK-034: синтетический `u` продолжает книгу, ошибка применения → вид нарушения, `broken=true`, возврат на снимке). Состояние T/C/B/X — плоские структуры фиксированного размера на символ: `[Min;60]` + счётчики часа, гистограммы (массивы), хеш последней группы. **Память = книга (O(уровней)) + O(1)** на символ; на файл — 1440 минутных ячеек для A1.
3. **B1 инкрементально**: `check_invariants` сейчас обходит ВСЕ уровни на каждом обновлении (O(глубины)). В `validate`: crossed — O(1) по лучшим бид/аск после обновления; nonpositive/порядок/тик/шаг — только по уровням, вошедшим в обновление (соседи точки вставки); полный `check_invariants` — на каждом снимке и на границе минуты (страховка). **Гейт эквивалентности:** суммы по видам `validate` == `lob verify --keep-going` на тех же файлах (байт в байт по `counts`/`broken_ms`).
4. Конец файла: решение по A1/T4 (в памяти 1440 минут), запись строк, состояние D1 (`--carry-out`), `status` (ok / truncated_tail / error: …, плохой файл — строка, а не падение, как `gaps`).
5. Объединение с TK-033: `lob gaps` = подмножество T1/T2 (вместе с `--sha256` одним чтением) — `lob validate` его вычисляет бесплатно; `gaps` остаётся как есть (не ломаем), в шаге 3 `validate` читает файл один раз вместо `gaps`+`verify --keep-going`.

## 3. Пороги — не числа с потолка

Правило проекта «изобретённое число запрещено»: пороги назначаются измерением на данных или решением владельца В-##.
- **A1 (минута 0 событий при обычной активности):** λ = медиана событий/мин монеты за сутки (из тех же 1440 ячеек). Минута с 0 событий — аномалия, если вероятность нуля при такой λ по модели Пуассона × 1440 минут < ε; ε = ожидаемое число ложных тревог на монето-сутки. **Предлагаю ε = 0,01 (≈ λ > 12/мин)** — решение владельца/Судьи, не код; ниже порога λ минута считается «нормально тихой» и идёт только в T1.
- **T4 (скачок задержки):** порог — кратное квантили распределения d той же монеты за сутки (p99,9 за сутки), калибруется на «чистых» сутках (HYPE-новый); в CSV пишутся сами min/p50/max по минуте, классификация — в своде.
- **X1 (допуск сделка/книга):** сначала гистограмма на чистых сутках (HYPE 2026-05-02 новый, один свежий день любой монеты), допуск = наибольшее расстояние, встречающееся там; не «±1 тик» заранее.

## 4. Ввод и выход

- Ввод: список файлов (`--list`), схема V2 перебора: **1 последовательный читатель + 8 обработчиков из page cache**, readahead 16 МБ, 136 МБ/с диска (источник — TK-031/ТЗ). Раздача — по файлам; у `--carry` файлы монеты идут одному обработчику по порядку дней (цепочка D→D+1), разные монеты — параллельно.
- Выход (`--out-dir`), три CSV:
  - `hours.csv`: `symbol, day, hour` + T1–T4, C1–C3, B1 (6 видов), B2 (`broken_ms`), X1 (гистограмма + сделки при битой книге), `status`;
  - `minutes.csv` (исключения): `symbol, day, hour, minute, kinds` (`silent`, `rate_anomaly`, `latency_jump`, `broken`, `ts_backward`, `dup_group`, `snap_drift`) + `events, broken_ms, d_min, d_p50, d_max`;
  - `files.csv`: `symbol, day, path, bytes, records, status, first/last exch, sha256 (опц.), D1-поля (carry_first_kind, carry_mismatch_levels, carry_gap_s)`.
- Подкоманда `lob validate` — только чтение, не пишет маркеров/`verify-*.status`.

## 5. Оценка времени (до замеров; уточняется на шаге 2)

Опорные числа: `gaps` — 0,37 с/файл 15,4 МБ вместе с sha256 (≈ 42 МБ/с на ядро); `verify --keep-going` HYPE 05-02 — 1,6 с/файл (778 тыс. обновлений ≈ 2 мкс/обновление); диск сервера 136 МБ/с (sdb, последовательно).
- На ядро `validate` ожидаю ≈ 25–35 МБ/с (разбор + книга + статистики; B1 инкрементальный дешевле нынешнего). 8 обработчиков ≈ 200–280 МБ/с > 136 МБ/с диска ⇒ **упор в диск**, не в ЦП.
- ≈ 22 тыс. файлов, объём по `/data/alpha` ≈ 532 ГБ (с учётом не бинлогов — верхняя граница) ⇒ **1,1–1,4 ч** чтения на всё + новые монеты TK-037 (+ по их объёму ≈ 2–4 % на каждую сотню ГБ… уточню по факту каталога). Запас ×1,5 ⇒ **закладываю 2 ч** на весь прогон; на один файл ≈ 0,3–1,6 с ЦП, но 0,1–1 с диска.
- Что может съесть время: `--carry` (последовательность дней одной монеты) — 76 цепочек по ~275 дней, при 8 обработчиках цепочек больше, чем обработчиков, — хватает параллелизма; C3 дорог только при очень частых снимках (проверится на HYPE).
