# Критик: простои 09.10 (TK-114 9 ч, TK-115 5 ч) — 2026-10-09

Срок владельца — 15 мин, поэтому: первопричины и защиты, без полной хронологии. Код не правился. Времена — GMT+4
(сервер в CEST = GMT+2, журнал сервера на 2 ч меньше). Редакция 2 — по разбору Судьи
(`docs/research/reviews/stall-critic-fixes-2026-10-09.md`, факты им сверены).

## Случай 1. TK-114: ждал файл, который лежал 9 ч

**Хронология.** `/data/tk0114/tier1.done` лёг 05:58 (03:58 CEST). Роль поставила `wait_for: host:calc:file:/data/tk0114/tier1.done`.
Тикет не просыпался до ручного вмешательства CEO в 15:25.

**Первопричина.** Форма `host:<алиас>:<путь>` не принимает префикс `file:` внутри, но и не отказывает:
- `ticket.py:137` (плагин 1.8.24, `parse_wait_for`): ветка `host:` отдаёт `("host","calc","path", rest)` для любого `rest`, кроме `unit:`.
  `rest = "file:/data/…"` — путь не проверяется на абсолютность. `tickets.py wait` (`cmd_wait`) вызывает только
  `file_wait_problem` (`ticket.py:171`), а она смотрит лишь `file:`-форму на Windows → `host:calc:file:…` принят молча.
- Диспетчер проверяет путь `file:/data/…` на машине (нет такого) → «ещё не готово» вечно.

**Почему молчала каждая защита.**
- Постановка (`cmd_wait`) — не проверяет вид пути у `host:`.
- Сторож `triage_waits` — `probe_wait_target` (`watch.py:191–197`) возвращает `unknown`, если `arg` не начинается с `/`;
  `watch.py:475` считает `unknown` «годным wait_for: не сирота». Битая форма классифицируется как здоровая.
- Ветка «цель есть, тикет не разбужен» (`MET_GRACE_MIN` 15 мин, `watch.py:180`) уже существует, но не сработала —
  цель не была опознана (`unknown`), значит «выполненной» не считалась.
- Сторож жизни/шина/alerts — событий не видели: тикет `waiting` с «годным» условием, процессов нет, ошибок нет.
- Будильники CEO сняты 04:25 в расчёте на сторожа → вторичной сетки не было.

## Случай 2. TK-115: 11 из 275 суток волны «умерли» без перезаявки

**Хронология (пример `1009075550927`, tk115-wa-2026-02-05).** Старт 10:12, конец 10:24, `active_s` 691 с при `max_runtime` 21600
→ не бюджет. В `jobs/…json`: `state: done, rc: 143`, `mem: 4`; файла `rc/1009075550927` нет — обёртка
`cmd; rc=$?; …; echo $rc > rc/<id>` (`alsched.py:514`) убита вместе с юнитом. journalctl 08:24:00 CEST: `Memory cgroup out of
memory: Killed process … (alpha-tk044k1-n) anon-rss 4167984kB` в `tk0s-tk115-wa-2026-02-05-1009075550927.service`,
`Failed with result 'oom-kill'`; за 08–09 CEST 6 строк oom-kill. Следом (08:24:15) то же для 02-06.

**Первопричина.** Не SIGTERM по расписанию и не окно stand, а **cgroup-OOM**: заявка с `--mem 4`, процесс
`alpha-tk044k1-n` вырос до 4,17 ГБ на «тяжёлых» сутках (11 из 275). Исследователь ловил OOM на 2 ГБ той же пробы (TK-115 лог:
переподана с `--mem 5`), но волна ушла с 4 ГБ. SIGTERM (143) — systemd, доубивающий остатки юнита после OOM.
Демон rc имеет (143), нет только файла от обёртки; беда не в отсутствии rc, а в том, что **rc≠0 никого не будит**.

**Почему молчали защиты.**
- alsched: `alerts.log` содержит лишь «сократить заявку» и «ждёт старта N мин» (об эффективности), алерта «задание упало rc≠0» нет.
- Сторож (`watch.py` ~300–330, `_wake_owner_job`) будит о «упавшем задании тикета» только для формы `job:`; у TK-115 ждущий
  юнит `tk0s-tk115-wa-done` ждал 275 `.done` вечно (дошёл до 264/275), юнит живой («producer») → не сирота. Ложных `.done` нет.
- Табло/шина не считают `rc≠0 без перезаявки`.

## Правки — минимальный набор (по разбору Судьи)

**БЛОКЕРЫ**
1. **К1.1** — `parse_wait_for`: у `host:…:path` путь только абсолютный (не `file:`/`host:`/`deck:`), иначе `wait` отказывает
   с подсказкой; та же функция проверки формы вызывается и в стороже (`watch.py:191–197`): неабсолютный путь у `host` =
   `invalid`. `unknown`→тревога для всех форм не делать (`unit:` и короткие имена тоже `unknown` — ложные тревоги).
   Поймала бы: `tickets.py wait TK-114 host:calc:file:/data/x` → отказ на постановке; тест `triage_waits` с `host:calc:file:/x` → тревога ≤ 3 циклов.
2. **К2.1 + К2.2** — alsched: при завершении юнита с `rc≠0` демон берёт `Result`/`ExecMainStatus` из systemd (различает
   oom-kill/timeout/сигнал), пишет `rc` сам (не обёртка), даёт алерт в `alerts.log` и будит исполнителя тикета с причиной
   («задание X упало rc=…, oom-kill»). Поймала бы: задание `--mem 1` с заведомо большим процессом → алерт ≤ 1 мин; TK-115 — будит в 10:24.
3. **П-1 (новое)** — сторож жизни смотрит ход работы, а не живость ждущего: тикет `waiting` с `host:`-целью, цель не
   выполнена и нет ни одного задания alsched в `running/queued` (имена несут номер тикета; адаптер
   `lifewatch.py`/`RPV_JOB_STATE_CMD` есть для `job:`) дольше 15 мин → будить исполнителя тикета с причиной («ждёшь X,
   работающих заданий 0, последние: rc …»). Закрывает класс «ничего не происходит N часов» и страхует К1.1. Поймала бы
   оба: TK-114 — задания tier1 кончились 05:58 → будит ~06:15; TK-115 — последнее 10:24 при 264/275 → ~10:40. Проверка:
   воспроизвести на копии состояния обоих тикетов — тревога ≤ 3 циклов.

**ПОТОМ**
4. **К2.5** — `--mem` = пик пилота (`calibrate`, В-178) + запас: профилактика, простой закрывают 2 и 3.
5. **К2.3** — автоповтор при OOM с `mem×1,5` один раз: удобство; при К2.1 исполнитель перезаявит сам.

**Вычеркнуто** (причины — в разборе Судьи)
- К1.2 — дубль К1.1 (слито с ним, одна функция проверки формы).
- К1.3 (потолок ожидания T ч) — ложные тревоги на законных долгих ожиданиях (TK-094 `at:` сутки, TK-048 волны 6+ ч); заменён П-1.
- К1.4 («цель есть, тикет не разбужен») — уже есть, `MET_GRACE_MIN` (`watch.py:180`); в случае 1 не сработал из-за `unknown`, закрывается К1.1.
- К2.4 (done-юнит волны считает N и падает) — частный случай, покрывается П-1.

## Итог

Один класс ошибки в обоих случаях: **неизвестное состояние трактуется как «жив»** (`watch.py:475` для кривой формы;
упавшее задание без алерта) и **нет защиты от «ничего не происходит N часов»**. Блокеры: К1.1 (закрывает случай 1),
К2.1+К2.2 (случай 2), П-1 (единственная закрывает класс; любая из 1/3 закрыла бы случай 1, любая из 2/3 — случай 2).
