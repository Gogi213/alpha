# Критик: простои 09.10 (TK-114 9 ч, TK-115 5 ч) — 2026-10-09

Срок владельца — 15 мин, поэтому: первопричины и защиты, без полной хронологии. Код не правился. Времена — GMT+4
(сервер в CEST = GMT+2, журнал сервера на 2 ч меньше).

## Случай 1. TK-114: ждал файл, который лежал 9 ч

**Хронология.** `/data/tk0114/tier1.done` лёг 05:58 (03:58 CEST). Роль поставила `wait_for: host:calc:file:/data/tk0114/tier1.done`.
Тикет не просыпался до ручного вмешательства CEO в 15:25.

**Первопричина.** Форма `host:<алиас>:<путь>` не принимает префикс `file:` внутри, но и не отказывает:
- `ticket.py:137` (плагин 1.8.24, `parse_wait_for`): ветка `host:` отдаёт `("host","calc","path", rest)` для любого `rest`, кроме `unit:`.
  `rest = "file:/data/…"` — путь не проверяется на абсолютность. `tickets.py wait` (`cmd_wait`) вызывает только
  `file_wait_problem`, а она смотрит лишь `file:`-форму на Windows → `host:calc:file:…` принят молча.
- Диспетчер проверяет путь `file:/data/…` на машине (нет такого) → «ещё не готово» вечно.

**Почему молчала каждая защита.**
- Постановка (`cmd_wait`) — не проверяет вид пути у `host:` (ticket.py:137, tickets.py `cmd_wait`).
- Сторож `triage_waits` — `probe_wait_target` (watch.py:191–197) возвращает `unknown`, если `arg` не начинается с `/`;
  `watch.py:475` считает `unknown` «годным wait_for: не сирота». Битая форма классифицируется как здоровая — самая
  опасная ветка, потому что «не знаю» трактуется как «живое».
- Сторож жизни/шина/alerts — не видели события: тикет `waiting` с «годным» условием, процессов нет, ошибок нет.
- Будильники CEO сняты 04:25 в расчёте на сторожа → вторичной сетки не было.
- Нет ограничения «ожидание дольше N ч без прогресса» (нет предела, кроме `at:`).

**Правки.**
1. БЛОКЕР: `parse_wait_for` — у `host:…:path` отклонять `rest`, не начинающийся с `/` (и с `file:`/`host:`/`deck:`); `cmd_wait` отказывает с подсказкой. Проверка: `tickets.py wait TK-114 host:calc:file:/data/x` → отказ.
2. БЛОКЕР: `watch.py:475` — `unknown` не равно «жив»: для `host`-формы неабсолютный путь = `invalid` → владелец будится. Проверка: тест `triage_waits` с `host:calc:file:/x` → тревога за ≤ 3 цикла.
3. ВАЖНО: потолок ожидания — `waiting` без смены цели дольше T (напр. 3 ч, либо 2× заявленной оценки) и файл-цель на хосте не появился/появился → запись в шину владельцу. «Поймал бы»: 9 ч → тревога на 3-м часу (и для «появился, а тикет спит» — сразу).
4. ВАЖНО: при каждом тике сверять «цель `wait_for` существует, а тикет не разбужен > 2 мин» — это ровно этот случай (диспетчер/сторож сверяют разные строки).

## Случай 2. TK-115: 11 из 275 суток волны «умерли» без перезаявки

**Хронология (пример `1009075550927`, tk115-wa-2026-02-05).** Старт 10:12, конец 10:24, `active_s` 691 с при `max_runtime` 21600
→ не бюджет. `rc/1009075550927` отсутствует (обёртка не дописала `echo $rc > rc/…`), в `jobs/…json` стоит `state: done, rc: 143`.
`journalctl` 08:24:00 CEST: `Memory cgroup out of memory: Killed process … (alpha-tk044k1-n) anon-rss 4167984kB` в юните
`tk0s-tk115-wa-2026-02-05-1009075550927.service`; «Failed with result 'oom-kill'», пик памяти 4G. Следом (08:24:15) то же для 02-06.

**Первопричина.** Не SIGTERM по расписанию и не вытеснение/окно stand, а **cgroup-OOM**: заявка подана с `--mem 4` (`"mem": 4`),
процесс `alpha-tk044k1-n` вырос до 4,17 ГБ на «тяжёлых» сутках (11 из 275 — февраль/апрель/июнь/июль). Исследователь уже
ловил OOM на 2 ГБ той же пробы (TK-115 лог: «OOM на 2 ГБ … переподана с --mem 5»), но волна ушла с 4 ГБ.
SIGTERM (143) — это systemd, доубивающий остатки юнита после OOM-убийства основного процесса.

**Почему молчали защиты.**
- alsched: код возврата при OOM-остановке юнита не записывается в `rc/<id>` (запись в самой обёртке, её прибили); демон
  заводит `state: done` и `rc: 143` без различения «успех/сбой». В `alerts.log` нет алерта «задание завершилось с rc≠0» —
  есть только «сократить заявку» и «ждёт старта N мин» (алерты — об эффективности, а не о сбое).
- Нет автоперезаявки с увеличением памяти при `oom-kill` (хотя причину видно в `memory.events`/`own/<id>`).
- Сторож (`watch.py` ~300–330, `_wake_owner_job`) будит владельца о «упавшем задании тикета» только для формы `job:`; у TK-115
  ждущий юнит `tk0s-tk115-wa-done` ждал 275 `.done` вечно: формы «N заданий волны» нет, юнит живой («producer») → не сирота.
- Табло/шина: ни один из них не считает `rc≠0 без перезаявки`.

**Правки.**
1. БЛОКЕР (alsched): при завершении юнита с `rc≠0` — алерт в `alerts.log` + шина владельцу/роли тикета: «задание X упало rc=…, причина oom-kill (memory.events)». Проверка: `--mem 1` с заведомо большим процессом → алерт ≤ 1 мин.
2. БЛОКЕР (alsched submit): `rc` пишет демон (по `systemctl show -p Result,ExecMainStatus`), а не обёртка; убитая обёртка не оставляет «done без rc».
3. ВАЖНО: автоповтор при `oom-kill` с `mem×1,5` один раз (или флаг `--retry-oom`), либо отказ в приёме сданной волны, если пилот показал пик > `--mem`.
4. ВАЖНО: завершающий юнит волны (`…-done`) должен считать ожидаемое число `.done` и по истечении «все задания закончены, а до N не дошло» — падать и звать владельца, а не ждать вечно.
5. ПОТОМ: в `calibrate`/подачу волны — `--mem` = измеренный пик пилота + запас (В-178, измеряемое измеряется).

**Кто послал SIGTERM:** systemd после cgroup-OOM-убийства основного процесса юнита; scheduler (`be.kill`) убивает с rc 124 и пишет `rc`-файл — здесь файла нет, значит не он.

## Итог

Один класс ошибки в обоих случаях: **неизвестное состояние трактуется как «жив»** (watch.py:475 для кривой формы; alsched — `done` без `rc` для убитой обёртки) и **нет защиты от «ничего не происходит N часов»**. Приоритет правок: (К1.1, К1.2, К2.1, К2.2) — блокеры, затем ожидаемое число/потолок ожидания, затем автоповтор по OOM.
