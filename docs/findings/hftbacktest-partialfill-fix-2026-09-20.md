# Крейт hftbacktest 0.9.4: баг `PartialFillExchange` и локальная правка (F3/F4 этапа F, 2026-09-20)

**Итог одной строкой.** В `hftbacktest 0.9.4` нога, исполненная сделкой **ровно до нуля**,
не удаляется из книги обмена и при следующей сделке по той же цене роняет весь прогон
(`InvalidOrderStatus`); без правки модель очереди по объёму (`--queue-model prob:<n>`, F3, В-78)
на живых сутках не работает. Правка — `>` → `>=` в двух местах крейта; подключена локальной
копией (`vendor/hftbacktest` + `[patch.crates-io]` в корневом `Cargo.toml`), других изменений в крейте нет, кроме `#[allow(dead_code)]` на `Value::get_string`
(`src/backtest/data/npy/parser.rs`, чтобы форк собирался с `-D warnings`; §3). Есть ли фикс в
апстриме новее 0.9.4 — офлайн не проверить (в реестре только 0.9.4, CHANGELOG в крейте нет).

## 1. Как нашли

F4 (частичная позиция) начал считать исполненное по ордерам крейта (`qty − leaves_qty`) и в
синтетическом тесте наткнулся на `BacktestError::InvalidOrderStatus`: нога 1.0 лота исполнилась
сделкой 1.0 по своей цене, а следующая сделка по этой же цене уронила `elapse`. На `risk-adverse`
ветки нет — баг живёт только в `PartialFillExchange`.

Затем баг воспроизведён **на живых данных** (счётная машина `13.140.29.171`, бинарник `b0122d2`,
сутки 16–18.09, 20 монет, `--order-qty-mult 2`, `--min-age-secs 900`):

```bash
bin/alpha-b0122d2 lob bounce-grid --root root \
  --median-rtt-ns place=4200000,cancel=3980000,taker=5650000 \
  --p95-rtt-ns place=4790000,cancel=4550000,taker=6420000 \
  --order-qty-from-pool --order-qty-mult 2 --threads 3 \
  --h3-mode notional --h3-usd 10000 --min-age-secs 900 \
  --stop-form pct2 --take-form 1to1 --day 2026-09-16 --day 2026-09-17 --day 2026-09-18 \
  --symbol 1000BONKUSDT … --symbol ENAUSDT --queue-model prob:3 --out-dir /tmp/prob-big
```

Прогон прошёл 11 монет (десятки кругов) и упал на двенадцатой:
`Error: форма #0: order status is invalid to proceed the request`.

## 2. Причина (файл и строки)

`hftbacktest-0.9.4/src/backtest/proc/partialfillexchange.rs`,
`check_if_sell_filled` (стр. 155) и `check_if_buy_filled` (стр. 195):

```rust
let exec_qty = if filled_qty > order.leaves_qty {   // было строгое «>»
    self.filled_orders.push(order.order_id);        // иначе заявка не удаляется из карты
    order.leaves_qty
} else {
    filled_qty
};
```

При `filled_qty == order.leaves_qty` (сделка ровно выедает остаток заявки) условие ложно:
`exec_qty = leaves_qty`, заявка получает `status = Filled`, но **не** попадает в `filled_orders`,
то есть остаётся в `orders`/`buy_orders`/`sell_orders` обмена. Следующая сделка по той же или
меньшей цене снова зовёт `fill()`, а он на `Status::Filled` возвращает `InvalidOrderStatus`
(там же, стр. 216–221) — ошибка поднимается через `elapse` и роняет весь прогон.

Почему проявляется не всегда: равенство — редкое событие, а большинство наших исполнений
приходит обновлением лучшей цены (путь (3) из `build_backtest`, он заявку удаляет корректно);
на 111 кругах пробного прогона падения не было, на 20 монетах × 3 суток — было.

## 3. Правка

`vendor/hftbacktest/` — копия `hftbacktest 0.9.4` (MIT, © nkaz001,
https://github.com/nkaz001/hftbacktest), только `src/` и `Cargo.toml` (примеры не копировались);
в `src/backtest/proc/partialfillexchange.rs` оба места стали `filled_qty >= order.leaves_qty`
(с комментарием «ЛОКАЛЬНАЯ ПРАВКА alpha»). Вторая, косметическая правка — `#[allow(dead_code)]`
на `Value::get_string` (`src/backtest/data/npy/parser.rs`): без неё сборка крейта даёт
`dead_code`-предупреждение в выводе `cargo clippy`, а правило проекта — ноль предупреждений.
Корневой `Cargo.toml`:

```toml
[patch.crates-io]
hftbacktest = { path = "vendor/hftbacktest" }
```

Смысл правки: при равенстве исполняется ровно остаток, и заявка штатно удаляется из карты
обмена — то же, что происходит при `filled_qty > leaves_qty` (там `exec_qty` тоже равен
`leaves_qty`). Логика модели очереди не меняется: расхождение возможно только в момент
«остаток исполнен целиком», где поведение обязано совпадать.

## 6. Что это значит для плана

- `--queue-model prob:<n>` теперь пригоден для сеток F8/F10 (В-78: частичное исполнение — норма).
- Правка живёт в репозитории, а не в реестре cargo: сборка на любой машине воспроизводит её
  без сети и без ручных шагов (`cargo` сам подставит `vendor/hftbacktest` по `[patch.crates-io]`).
- Обновление крейта до новой версии — отдельное решение: тогда патч проверяется заново (ветка
  `filled_qty >= leaves_qty`), и при исправлении в апстриме локальная копия удаляется.

План — `dev-plan-2026-09-20.md` §3 F3/F4; реестр — `EXPERIMENTS.md` (M15–M17 о замерах;
это техническая правка, не эксперимент).

## 7. Вторая правка (2026-09-21, F10-fix): остаток меньше половины лота

**Как нашли.** Переделанный прогон F10 на счётной машине (`alpha-grid-f10fix`, бинарник
`alpha-8cdeb38`, набор `a45-bid:age=2700,side=bid`, D20, `prob:3`) упал на первом же наборе после
ASTERUSDT 09-17: `Error: форма #2: order status is invalid to proceed the request` (`b5/f10fix-D20-a45-bid.err`,
18:19Z) — тот же `InvalidOrderStatus`, что в §1, уже при правке §3. Скрипт без `set -e` пошёл дальше
по наборам, артефакты первого набора — обрывок (11 932 строки `rounds.csv`).

**Причина.** `fill()` ставит `Filled`, когда остаток **округляется по лоту в ноль**
(`(leaves_qty / lot).round() == 0`), то есть при `leaves_qty > 0`, но меньше половины лота. Два пути к
такому остатку: (а) заявка не по лоту (в тесте — 1.04 при лоте 0.1: исполнение лотами 1.0, остаток 0.04);
(б) **ошибка плавающей точки при заявке по лоту** — лот от пула кратен шагу, но `0.1 + 0.1 + 0.1 ≠ 0.3`:
после двух исполнений по 0.1 остаток `0.10000000000000003`, третье исполнение `filled_qty = 0.1`, и условие
удаления §3 `filled_qty >= leaves_qty` ложно на `3e-17`, хотя `fill` ставит `Filled` (остаток `3e-17`
округляется в ноль лотов). В обоих случаях нога остаётся в карте биржи, и следующая сделка по цене (или проход
лучшей цены в `on_best_*_update`, где перебираются **все** заявки карты) зовёт `fill` на `Filled` → ошибка.
Путь (б) — почему падение случилось на живых сутках при лотах от пула.

**Правка** (`partialfillexchange.rs`, обе ветки `Ordering::Equal`): исполняемое — `filled_qty.min(leaves_qty)`,
а удаление — **по статусу после `fill`** (`order.status == Filled → filled_orders.push`), а не по сравнению
количеств. Тест — `strategy/tests.rs::a_sub_lot_remainder_does_not_leave_a_stale_filled_order_on_the_exchange`
(заявка 1.04 при лоте 0.1, две продажи по цене: вторая раньше роняла `elapse`; позиция — исполненное 1.0).

**Следствие для F10:** все прогоны `prob:<n>` с лотом от пула до этой правки могли упасть на любой монете, где
размер заявки не кратен лоту; E15 (17:19–17:37Z) прошёл лишь потому, что кругов почти не было (набор-пересечение).
Прогон F10-fix — перезапустить новым бинарником.

## 8. Третья правка (2026-09-24, R7 ревью 23.09): средняя цена исполнения по всем исполнениям заявки

**Что было.** `fill` крейта пишет в заявку только **последнее** исполнение: `exec_price_tick` — цена уровня этого
исполнения, `exec_qty` — его объём. Рыночная заявка (`OrdType::Market`, ветка `ack_new` в
`partialfillexchange.rs`) проходит книгу по уровням от лучшего до `+100` тиков и зовёт `fill` на каждом, поэтому
после свипа в заявке остаётся цена **последнего, худшего** уровня. Драйвер (`lob/backtest.rs`, цены входа и выхода
круга) и снимок ног стратегии (`lob/strategy.rs::entry_snapshot`) считали стоимость как `exec_price × (qty −
leaves_qty)` — весь объём по худшему уровню. Смещение консервативное (выход продажей — по нижнему биду, вход
покупкой — по верхнему аску), но это не цена сделки: на $500 с тонкой книгой разница — десятки bps на круг. У
лимитки, часть которой взяла книгу тейкером (`GTC` поверх аска: уровни до цены — тейкер, остаток встаёт в книгу
мейкером), цена тейкерской части терялась совсем — оставалась цена мейкерского остатка.

**Правка.** Поле `Order::exec_notional: f64` — накопленная стоимость `Σ exec_price × exec_qty` по всем
исполнениям; ведут `fill` всех трёх бирж модели (`partialfillexchange.rs`, `nopartialfillexchange.rs`,
`l3_nopartialfillexchange.rs`), копирует `Order::update` (локальная сторона видит итог), поле есть в
`Encode`/`Decode`/`Debug` и в литералах (`live/bot.rs`, тесты `queue.rs`). Читает его одно место —
`lob::backtest::executed_notional`: средняя цена исполненного — `exec_notional / (qty − leaves_qty)`. Если итог
нулевой при ненулевом исполненном (отклик площадки без поля — живой коннектор, который его не ведёт), —
прежний `exec_price × исполненное`, а не ноль; **живой коннектор обязан вести итог**, иначе средняя по свипу
снова станет ценой последнего уровня.

**Тесты:** `lob/backtest/tests.rs::market_sweep_over_two_levels_costs_the_weighted_average_price` (рыночная
покупка 2.0 при аске 1.0@101 + 5.0@102: `exec_price()` = 102, стоимость 203, средняя 101.5) и
`executed_notional_falls_back_to_last_price_when_the_venue_kept_no_total`.

**Следствие:** у `prob:<n>` (F10) меняются цены рыночных выходов (стоп, дедлайн, «съели/сняли») и входов-лестниц,
частично взявших книгу; у `risk-adverse` (`NoPartialFillExchange` исполняет рыночную заявку целиком по лучшей
цене одним `fill`) числа прежние. Кандидат пересчитывается бинарником с этой правкой (список
`docs/plan/review-fixes-2026-09-24.md` §3).
