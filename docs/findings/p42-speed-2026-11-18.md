# П-42: рычаги скорости счёта титровки (TK-607)

Приказ владельца: «ищи с критиком рычаки для ультра скорости сверхзвуковой». Цель — порядок величины (×10 и выше) для счёта П-42, в первую очередь для идущего TK-599 (юнит `tk599-run`, движок `/data/p42-t566/bin`-копия `/data/p42-tk599/bin/alpha-master`, md5 `a03c91df`).
Протокол §13.24 заморожен: правки только скорости, результаты — байт в байт. Всё ниже — чтение и замер (профилирование только чтением; `tk599-run` не трогали).
Условия замеров (п. 23 приказов): srv 8 vCPU, load 16–31, steal ≈ 8 %, 18.11.2026 15:30–15:55 GMT+4 (UTC+3 на часах srv 12:30–12:55); одновременно идут `tk599-run`, `tk600-stage1c`, `tk604-*`, семь коллекторов.

## Итог

1. **Узкое место — не движок, а повторное чтение сделок.** Один раунд раздачи = три вызова движка (окна `wa`, `wb`, `wc`), каждый заново распаковывает `unzip -p` и разбирает CSV ~170–200 млн строк. Фаза 1 (загрузка + сигналы) — 91–99,7 % времени вызова, медиана 98,5 % (измерено, 18 вызовов, §1.2). ~57 % ЦП вызова — внешний `unzip`, ~22 % — разбор CSV в движке; поиск сигналов по сделкам и выходы — единицы процентов (измерено perf, §1.3).
2. **Второй фактор — конкуренция за ЦП.** Те же входы (окно `wc`, 169 091 612 строк, 543 файла) фаза 1 прошла за 129…2052 с (×16) в зависимости от загрузки хоста; у `tk599-run` `CPUWeight=1`, `Nice=19`, в среднем 1,1 ядра из 8 (измерено).
3. **Рычаги (§2), все — без смены результатов:** (L1) бинарный склад сделок `<монета>/<дата>` с чтением-записью «по требованию» — декодирование ×60…100 быстрее разбора CSV (измерено микростендом, round-trip тождествен); (L2) кэш сигналов по `(SigCfg, сторона)` — 72–86 % раундов не меняют сигнальные ключи (модель на настоящих сетках, §2.2) и вообще не читают сделки в фазе 1; (L3) таблицы признаков группы 6 — досчёт только недостающих кандидатов; (L4–L5) ленивые NATR/бары и целочисленный быстрый путь; (L0) приоритет ЦП — решение координатора.
4. **Оценка прироста — модель на измеренном делении ЦП (метки в §3):** раунд ≈ 24 мин (среднее b0002–b0006) → ≈ 0,5–2,5 мин; остаток основной процедуры (≈ 38 раундов) ≈ 18 ч → ≈ 1–2 ч (+ досчёт признаков); сенс ×3 — до трёх таких же процедур (до ≈ 55 ч → ≈ 2–4,5 ч). Один L1 даёт ×5–7 на вызов, L1+L2+L4+L5 — ×17–21 в среднем по раундам.
5. **Перезапуск `tk599-run` на быстром пути ничего не теряет:** посчитанные клетки лежат в `npz/` (ключ — хэш конфигурации) и `out/<окно>/<vid>/DONE`; теряется только раунд в полёте (7–52 мин по замерам). Подробности — §4.

## 1. Замер

### 1.1 Единица стоимости — раунд

`drive()` собирает недостающие прогоны всех десяти генераторов (две стороны × четыре свёртки + полная) в один пакет; `Engine.launch` гоняет движок по окнам последовательно (`wa`, `wb`, `wc`), `--threads 6`. Движок группирует задания фазы 1 как различные `(SigCfg, сторона)`: чтение сделок суток — один раз на монету для всех заданий; число вариантов (клеток) на стоимость почти не влияет (фаза 2 — секунды). Поэтому «клеток в час» — следствие числа клеток в раунде (4…16), а не их цены.

## 2. Рычаги (по убыванию «выигрыш / усилие»)

Ограничение для всех: результаты — байт в байт с прежним движком; протокол не меняется; без аренды; cargo — только на srv (`tools/vps-check.sh`, `tools/p42/build-srv.sh`).

### L1. Бинарный склад сделок (движок, `src/breakout/tick.rs`) — главный

Идея: первая загрузка `(монета, дата)` пишет на диск компактный бинарный файл (дельты цены и времени, varint, `bm` в младшем бите; цена нормируется на НОД шагов — без потерь), следующие — читают его вместо `unzip -p` + CSV. Источник `ZipSrc` остаётся, склад включается ключом (`--tick-store <каталог>`; без ключа — прежний путь). Ключ склада — календарная дата (сетка выровнена по полуночи UTC), поэтому окна `wa/wb/wc` и сторонние запуски (tk604, сигнальные дампы G5, `P42_SIGSX_ONLY`) делят одни файлы. Запись — во временный файл и `rename` (параллельные процессы безопасны); в заголовке — размер и mtime исходного zip (устаревание), число строк, счётчики `LoadStat` (журнал не меняется). `Vec<Tick>` после склада тождествен прежнему (в т.ч. стабильная сортировка при `unsorted`) ⇒ индексы `idx` в `TSig` и всё дальше не меняются.

Замер микростенда (`tkbench.rs` — копии `parse_trades/parse_dec` движка + кодек; 5 реальных суток, `tkbench.txt`; load ≈ 16, обе стороны в тех же условиях): строк 10,8 тыс… 1,1 млн; **склад 2,26–3,26 Б/строку** (zip 12–15, CSV ≈ 66 Б), **декодирование склада 16–35 нс/строку** против `unzip` 717–1897 нс + разбор 263–579 нс на строку: **×60…100**, **round-trip идентичен на всех 5 файлах** (`Vec<Tick>` равны). Сортировка при `unsorted` не проверена на реальных файлах (в этих окнах `unsorted_files = 0`) — покрывается тестом.
**Формат v2 (18.11, по просьбе TK-609 — признакам потока нужна `цена × количество`; до ворот L1):** вторым блоком zstd идёт количество сделки (целое в единицах `10^-qty_dec`, НОД в заголовке) и флаги точности `f64` цены/количества. Путь движка читает только заголовок и блок сделок — выходы не меняются; признаки берут `ZipSrc::read_day` / `TickStore::read_day`. Объём с блоком количества — по замеру холодного прохода ворот (в итоговой строке `tick-store:` — «блок количества» и строки); цифры 2,26–3,26 Б/строку выше — только блок сделок.

Оценка выигрыша (модель на измеренном делении ЦП §1.3): вызов `wa` 437 → ≈ 78 ЦП-с (**×5,6** на вызов); первый вызов после включения платит прежнюю цену (запись склада), второй и дальше — нет. Диск: `/` 98 % занят, свободно 9,3 ГБ (ключевое ограничение) — склад пишется только для реально прочитанных файлов; оценка объёма: базовый набор раунда ≈ 1,5 ГБ (200 + 167 + 169 млн строк × 2,3–3,3 Б минус общие дни), по всем раундам ≈ 3–4,5 ГБ (догадка: сколько новых файлов добавят новые сигнальные ключи); запас — потолок `--tick-store-cap-gb` (при превышении склад только читается) и, при нужде, zstd-сжатие блоков (крейт `zstd` уже зависимость; на выборках 300 тыс. строк varint+zstd-3 = 1,1–2,3 Б/строку).
Риск: низкий (чистая функция от файла; ворота — §5).

### L2. Кэш сигналов (движок)

Фаза 1 зависит только от `(SigCfg, сторона)`, окна, набора монет и данных. Выходы фазы 1 — `Vec<TSig>` + `TickCtr` (килобайты…мегабайты). Кэш на диске (ключ: хэш `Debug(SigCfg)` + сторона + `P42_T0` + список монет + «отпечаток» входов: имена и размеры `.b42`, каталога сделок + версия формата) убирает фазу 1 целиком, когда набор сигнальных ключей раунда уже встречался.
**Доля раундов, где фаза 1 повторяется** (модель, `speed_rounds_sim.py`, настоящие сетки и автомат, синтетические ряды, 6 миров): раундов 42–49 (медиана ≈ 44), с новой сигнальной конфигурацией 6–13 (**14–28 %**), т.е. **72–86 % раундов фазу 1 не нужны**; различных сигнальных конфигураций 21–47; раундов с новой таблицей признаков 1–4. Сигнальные оси сеток — `e`, `natr_min`, `t1h`, `t24` (из 17 осей); все остальные (стоп, выходы, вход `e2`, `bm`, `rr`, `tj`, `t_high`, `q`, признаки F) — ключи выхода/портфеля/фильтра: `SigCfg` у них не меняется (фильтр признаков применяется после фазы 1, `tick_cli.rs`). Оговорка: число раундов и доля зависят от выборов процедуры — в синтетике выборы случайны; порядок величины верен, точное число — только на реальном прогоне.
Оценка выигрыша: вызов при попадании в кэш ≈ загрузка 23 + фаза 2 6 + чтение склада ≈ 30 ЦП-с (модель) против 437: **×15 на вызов** (×27 вместе с L4); средний по раундам (72–86 % попаданий) ×17–21 после L1+L2+L4+L5 (§3).
Риск: средний — ключ должен учитывать все входы фазы 1 (ошибка = устаревший кэш). Закрывается воротами §5 (холодный/тёплый кэш байт в байт на разных наборах вариантов) и тем, что `meta.json`/счётчики сохраняются в записи.

### L3. Таблицы признаков группы 6 (Python + движок)

(а) Сигнальный дамп `P42_SIGSX_ONLY` — это фаза 1: берёт выгоду из L1/L2. (б) Сборка признаков производственным кодом TK-594 — Python, 13–27 мин на окно на шорт-поток (`flow`), ≈ 60 мин на поток (§1.2). Признак кандидата — функция `(монета, sig_ms, данные окна)`; `merge_union` уже требует совпадения значений на пересечении потоков (и в G5 совпало). Досчёт только кандидатов, отсутствующих в «union» окна и стороны, а не всего потока: на потоке свёртки, расходящемся с базой по `e`/`natr_min`, перекрытие кандидатов высокое (догадка; измерить на первом потоке свёртки: доля общих ключей `(sym, sig_ms)`). Условие: значения общих ключей совпадают — `merge_union` это уже проверяет, поэтому выбор безопасен. Выигрыш — пропорционален доле повторных кандидатов; число потоков в процессе — 1–4 раундов (модель §2.2), каждый по ≤ 1 ч на сторону: до единиц часов, которые остались бы нетронутыми после L1/L2.

### L4. Ленивые NATR и бары (движок, `data.rs`)

`Sym::from_cols` строит все `NATR_PERIODS` (3) и все `TF_MINUTES` (3) для всех 556 монет на каждый вызов, а сетки используют `natr_p=30`, `tf=60` (ключи `natr_p`/`tf` в сетках не варьируются). Загрузка — 6–7,5 % вызова (измерено: 3,8 с из 60 на 91 монете) — ленивая инициализация (`OnceLock` на слот) снимает ≈ 2/3 расчёта (`natr_series` 3×, `build_bars` 3×, i128-деления). Результаты те же (чистые функции от колонок).

### L5. i128-деления → i64 с проверкой переполнения

5,9 % ЦП вызова (`u128_div_rem` 4,1 + `__divti3` 1,8) — в `first_signal`, `candidates`, `fresh_ok`, `natr_series`. Быстрый путь: `checked_mul` в i64, при переполнении — прежний i128; семантика усечения к нулю та же ⇒ байт в байт. Небольшой, но после L1 доля в оставшемся времени растёт (около четверти вызова — масштабом образца, модель).

### L6. Долгоживущий процесс движка (демон)

Держит `Sym` трёх окон, склад в памяти и кэш сигналов между раундами; раунд = команда + фаза 2. Снимает остаточные ≈ 9 ЦП-с загрузки ×3 окна на раунд. Решение — после L1–L5: пол раунда без демона ≈ 30–50 ЦП-с/окно, то есть десятки секунд; сложность и RAM (≈ 3 × 5–7 ГБ при 62 ГБ и чужих задачах) оправданы только если L1–L5 не дойдут до цели.

### L0. Приоритет ЦП (решение координатора, кода нет)

`tk599-run` имеет `CPUWeight=1` и `Nice=19` среди соседей с весом 100 — при конкуренции получает остатки. Данные §1.4: ×3 на среднем раунде (24 → 7,3 мин лучший измеренный). Меняется `systemctl set-property tk599-run CPUWeight=…` (без рестарта), но забирает ЦП у `tk600`/`tk604` — это решение о приоритете чужих задач, не моё; цифры даны. Результатов не меняет.

### Мелочи (в плане, не приоритет)

- Движок считает обе стороны для каждого варианта (фаза 2 — секунды) и задания фазы 1 для обеих сторон: после L2 отпадает само.
- Три окна подряд, 6 потоков на окно: при нехватке ЦП параллельные окна ничего не дают; при свободном — до ×1,5. Не трогать.

## 3. Ожидаемый прирост (модель; помечено)

Исходное деление ЦП на вызов `wa`, ЦП-с (измерено на образце + масштаб — модель):

| конфигурация | вызов, новая сигнальная конфигурация | вызов, кэш сигналов (L2) | к исходному |
|---|---|---|---|
| сейчас | 437 | 437 | ×1 |
| L1 | 78 | 78 | ×5,6 |
| L1 + L4 (лениво: загрузка 23 → 9) | 64 | 64 | ×6,8 |
| L1 + L4 + L5 («прочее» 45 → ≈ 30) | ≈ 49 | — | ×8,9 |
| + L2 | ≈ 49 | ≈ 16 | ×9…27 |
| средневзвешенно (14–28 % раундов с новой конфигурацией; L1+L2+L4+L5) | ≈ 21…25 | | **×17…21** |

Раунд (3 окна): сейчас среднее 24 мин (7,3…52 мин по загрузке хоста) → ≈ 3 × (16…49 ЦП-с) / (1–2 свободных ядра) = 0,5–2,5 мин + зазор Python 5–25 с. ## 4. Возобновление: что теряет перезапуск `tk599-run` на быстром пути

Прочитано в коде (`retitr_full.py`: `OutDirEvaluator.missing`, `fulfil`; `retitr_full_run.py`: `Engine.done`, `Engine.launch`, `FtabStore.ready`):

- **Кэш клеток на диске**: `npz/<хэш Req>.npz` (на 15:55 — 48 файлов, 1,7 МБ). `missing()` подгружает серию с диска, не запуская движок; хэш не зависит от бинаря/окон ⇒ после перезапуска все готовые клетки (в т.ч. шаг 0, ставки, свёртки) берутся из кэша. Недостающие — по DONE-метке `out/<окно>/<vid>/DONE` (метка ставится только после всех трёх окон пакета).
- Процедура детерминирована (бутстреп сеется `seed_of(Sc,Nc,Sr,Nr)`), а «Python-состояние» (шаги, победители) заново вычисляется из кэшированных серий за секунды (на раунд — бутстреп, зазор 1–8 с по §1.2) ⇒ перезапуск возвращается ровно в то же место.
- Таблицы признаков `ftab/<окно>/<поток>/` и `ready` — переиспользуются (`ftab_ready`); потоки считать заново не нужно.
- **Теряется**: раунд в полёте — вариантов без DONE (вызов движка перезапускается с начала окна). По замерам 7,3–52 мин (раунд b0006 — 7,3 мин). Лучше всего перезапускать на границе раунда (между `готово:` последнего окна и первым окном следующего пакета; пакеты нумеруются `bNNNN`).
- Нюанс: счётчик пакетов `Engine.n` стартует с 0 ⇒ журналы `log/bNNNN-<окно>.log` и файлы `var/bNNNN.txt` перезаписываются (косметика; `calls.tsv` в этой папке сохраняет историю таймингов; журнал `log/` лучше скопировать перед перезапуском).
- Условие корректности: новый бинарь прошёл ворота байт-в-байт (§5), иначе кэш клеток от старого бинаря перестаёт быть тем же. Выходы `out/` пишутся новыми процессами в те же каталоги — параллельно со старым юнитом нельзя (оба пишут в `out/<окно>/<vid>`): сначала остановить `tk599-run`, затем запустить.
- Команда запуска не меняется (`systemd-run … TK599_GO=1 … retitr_full_run.py run`, оболочка из handoff v3→v4); в команду движка добавляются `--tick-store`, `--sig-cache`.

## 5. Ворота «байт в байт» и порядок внедрения

Реализация — ветка `bb/tk-607-p42-ultra-speed-v1-thr_j667egy23c`; бинарь собирается `tools/p42/build-srv.sh` (`/opt/rbuild`, замок сборок, 2 ядра, nice 19), тесты и clippy — `tools/vps-check.sh <дерево> all` (на srv; Софию не использовать для счёта). Пока `tk599-run` идёт, прогоны ворот — nice 19 / малые окна, чтобы не мешать.

1. L1 (склад) → ворота: (а) ворота TK-597 `rt-fz` — клетки `L_C`, `S_C` (`/data/p42-t566/variants-rt-fz.txt`, команда как в `/data/p42-t566/run-rt-fz.sh`: `P42_DETAIL=1 P42_T0=2026-09-01`, `cache80`, сделки `/data/aggtrades/binance`, 80 суток × 566 монет; эталон — выходы `/data/p42-t566/out/rt-fz/<клетка>`) новым бинарём в пустой каталог при пустом складе (запись) и повторно при тёплом (чтение), сравнение `cmp-v21gate.sh`: `OK … различий=0` по `*-trades|daily|coinday|entryrej.csv`, `*-detail.jsonl`; (б) пятнадцать-тридцать клеток TK-599, уже посчитанных в `/data/p42-tk599/out/<w>/<vid>` (b0002: 16 вариантов × 3 окна): тот же `cmp` плюс `meta.json`. Тест на синтетике `unsorted` и «нет файла/ошибка загрузки» — в `tick_tests.rs`.
2. L4–L5 — тем же воротом (холодный склад не нужен).
3. L2 (кэш сигналов) → ворота: тёплый кэш на наборах вариантов с (i) тем же `SigCfg`, (ii) новым, (iii) смесью; `cmp` со всеми прежними выходами; счётчики `meta.json` (`signals_*`, `cand_minutes`) равны.
4. L3 — ворота: таблица `ftab.csv` потока, посчитанного заново целиком, равна таблице «union + досчёт» построчно (значения общих ключей уже проверяются `merge_union`).
5. Бинарь — PGO-сборка (приказ п. 6) — после ворот, переобучение на горячем коде (ветка `tick.rs` не горячий путь стратегии, но боевой движок счёта по приказу — PGO); ворота повторить на PGO-бинаре.
6. Решение о перезапуске `tk599-run` — за координатором; рекомендация — после ворот L1+L4+L5 (низкий риск, ×7), L2 и L3 — отдельными шагами со своими воротами, без остановки счёта.
