# Binance: проблема маршрута и конфигурация коллекторов (для ресёрча)

13.11.2026. Числа — замеры 12.11 на сервере, если не помечено «вывод».

## Проблема

**Сервер:** 5.231.25.224, Нидерланды, Debian 13, 8 vCPU, один публичный IPv4, один IPv6.
**Биржа:** Binance USDⓈ-M Futures, публичные потоки рынка, `fstream.binance.com`. DNS отдаёт 8 адресов AWS Tokyo
(13.114.143.130, 13.115.243.218, 13.159.64.123, 13.192.196.129, 13.196.122.15, 35.74.187.188, 52.198.189.93, 52.68.97.180), AAAA нет.

**Симптом.** Маршрут сервер → Binance двухрежимный:

- **Быстрый:** TCP-рукопожатие ~236–293 мс. Данные чистые, лаг биржа → приём p50 ~120 мс, p99 < 1 с.
- **Медленный:** рукопожатие ~340–380 мс. Ретрансмиты TCP, паузы приёма 3–17 с, затем пачки старых данных; лаг до 14–46 с, таймауты пинга.
- **От чего зависит режим:** от пары «исходный порт + адрес Binance». Пара держит режим: быстрая осталась быстрой 36 из 40 раз, медленная — 37 из 56. Похоже на ECMP по хешу 5-tuple на каком-то участке пути (вывод).
- **Доля быстрых пар плавает по минутам:** от 4–7 % до 50–61 %. У каждого из 8 адресов есть оба режима, быстрых по адресу 25–75 %.
- **VPS София (Болгария)** в те же минуты: 100 % подключений быстрые, ~254 мс.
- **Bybit с того же сервера** чистый всё время: рукопожатие 13–35 мс, 0 задержек.

**Что делаем:** отбрасываем соединение с рукопожатием > 300 мс и подключаемся заново с нового порта; держим 2 параллельные линии на группу
символов и снимаем дубли; при деградации на ходу открываем замену без разрыва потока; на старте (Rust) пускаем медленное соединение и потом меняем на быстрое.

**Почему мало:** лимит Binance — 300 подключений за 5 мин на адрес. Когда быстрых маршрутов 5–7 %, за лимит не набрать 50 быстрых
соединений, и обе линии группы оказываются на медленном пути.

**Сравнение коллекторов в плохую минуту (замер):** Python 18:05–18:09 GMT+4 при ~47–50 % быстрых — 0 записей с лагом > 2 с (но p99 лага книги в отдельных 10-с окнах до 36,6 с);
Rust 18:31–18:34 при 7 % быстрых — лаг книги p99 14,5 с, 177 тыс. записей с лагом > 2 с. Разные минуты; одновременный прогон 18:05–18:15 дал одинаковую долю быстрых подключений (22 % и 20 %).

**Вопросы для ресёрча:**

1. Что это за двухрежимность (ECMP, AWS Global Accelerator, CloudFront, маршрут хостера) и как её обойти с нашей стороны: выбор исходного порта, управление хешем, TCP-настройки.
2. Есть ли у Binance Futures другие точки входа к тем же публичным потокам: другие имена, региональные адреса, IPv6.
3. Как другие держат стабильный поток Binance Futures из Европы.
4. Режет ли медленный режим соединения или пакеты: поможет ли меньше соединений с большим числом потоков.

## Конфигурация: Python-коллектор (ветка `g022-integrate` @ 3f8e1ce6, `tools/collector/`)

Работал боевым 11–12.11, остановлен 12.11 (В-152).

| Что | Значение |
|---|---|
| Пул | 509–512 символов USDⓈ-M perpetual, оборот ≥ 300 тыс. $/сутки, без топ-10 |
| Лучшие bid/ask | `<symbol>@bookTicker`, `wss://fstream.binance.com/public/stream`; **32 символа на соединение → 16 групп** (раскладка А, `kind_per_conn`) |
| Сделки | `<symbol>@aggTrade`, `wss://fstream.binance.com/market/stream`; **64 символа на соединение → 8 групп** (`streams_per_conn`; 128/256 давали отставание и разрывы) |
| Mark-цена | один поток `!markPrice@arr@1s`, `/market/stream` → **1 группа** |
| Линии | **2 на группу** (`--lanes 2`), дубли снимаются при записи → **25 × 2 = 50 соединений** |
| Подписка | `SUBSCRIBE` пачками по 100 потоков |
| Отбор маршрута, шаг 1 | RTT рукопожатия ядра (SYN→SYN-ACK, `TCP_INFO`) ≤ 300 мс (`CONNECT_RTT_MAX_MS`), иначе новое подключение — новый исходный порт (ядро ОС), DNS на каждое подключение |
| Отбор маршрута, шаг 2 | после подписки 15 с проверки лага (первые 4 с не считаются): p50 ≤ 350 мс и p99 ≤ 1 500 мс, иначе путь отброшен |
| Отказов подряд | после 12 соединение принимается как есть, сторож лага остаётся |
| Сторож на ходу | p50 лага > 2 000 мс два окна подряд → замена без разрыва |
| Пинг | каждые 5 с; нет pong 10 с → `timeout` + `ping_degraded` → замена без разрыва |
| Лимит подключений | 200 за 5 мин на процесс (2/3 от 300 у Binance) |
| Реализация | asyncio + `websockets`, без сжатия; процесс на группу |

## Конфигурация: Rust-коллектор (ветка `g022-turbo` @ a32ef34f, `src/collector/`)

Работает в фоне на сервере (`soak-binance`, данные `/data/turbo-probe/soak-binance/`).

| Что | Значение |
|---|---|
| Пул | 512 символов, то же правило |
| Лучшие bid/ask | `<symbol>@bookTicker`, `/public/stream`; **32 на соединение → 16 групп** |
| Сделки | `<symbol>@aggTrade`, `/market/stream`; **64 на соединение → 8 групп** |
| Mark-цена | `!markPrice@arr@1s`, `/market/stream` → **1 группа** |
| Линии | **2 на группу** → **50 соединений** |
| Подписка | `SUBSCRIBE` пачками по 100 |
| Отбор маршрута | как в Python: RTT рукопожатия ядра ≤ 300 мс, иначе новое подключение с нового порта, DNS на каждое подключение; затем 15 с проверки лага (p50 ≤ 350, p99 ≤ 1 500 мс); после 12 отказов — как есть |
| Старт | группа без живого соединения сразу берёт медленный путь (`path_slow_accepted`) и меняет его на быстрый за 37–57 с (`path_upgrade`); группы без соединения получают подключения первыми |
| Сторож на ходу и пинг | как в Python: 5 с / 10 с, замена без разрыва; закрытие старой сессии после перекрытия |
| Лимит подключений | 280 за 5 мин на процесс; при пересменке двух процессов — 140 + 140 (`--budget-file`) |
| Реализация | поток на соединение, кольцевая очередь к записи, zstd в отдельном потоке; очередь ни разу не переполнялась |

**Отличия от Python:** только старт (медленный путь сразу, потом замена), приоритет подключений группам без соединения и лимит 280 вместо 200. Константы отбора пути, пинга и замены совпадают (сверка исполнителя 12.11, отчёт `g022-turbo` §5.10).
