Статус: **промежуточный** (эталон + Rust v0 на 1 паре × 1 сутки совпали байт в байт; очередь, 14 признаков, фандинг, PGO, другие биржи — не сделаны). Числа счёта не интерпретируются (это TK-495).
Скрипт замера: `tools/p40core/bench_parse.py`; машина — 5.231.25.224 (8 vCPU, `nice 10`, параллельно шли юниты G0 `p40-rev-*`, нагрузка ≈ 8: цифры скорости **занижены**).

## 1. Данные (факты формата)
- CHFT Binance: `/data/stakan/chft/binance_futures/<день>/<час>/<СИМВОЛ>_orderbook.parquet`, 94 контракта в часе, один row group на файл, средний файл ≈ 3,8 МБ (≈ 100 тыс. строк/МБ).
- Колонки: `received_time` (нс), `event_time` (мс), `first/final/prev_final/last_update_id`, `event_type` (`snapshot`/`update`), `side` (`bid`/`ask`), **`price`, `quantity` — строки** (не числа), `order_count`.
- Снимок = подряд идущие строки `snapshot` (в файле AAVEUSDT 03:00: 2 938 строк снимка, 367 426 `update`); `quantity = 0` — удаление уровня.

## 2. Замер 1 файла (AAVEUSDT 17.09 03:00 UTC, 370 364 строки)
| этап | время | скорость |

## 3. Узкое место и выбор (предварительно)
Алгоритм: варианты — (а) эталон dict+max/min; (б) dict + ленивые кучи; (в) Rust-ядро (парсинг строк цены в целые тики, отсортированный вектор уровней/куча); замер — (а) 11 ктрок/с, (б) 798 ктрок/с, (в) не измерен; выбран — пока (б) как проверенный эталон для «байт в байт», потому что сохраняет последовательность лучшей пары при ускорении ×73.
- После ускорения книги узким местом остаётся **чтение parquet и строка→число** (1–2 Мстрок/с на ядро, один row group = нет параллели внутри файла): параллель — по файлам (контракт×час), 8 ядер.
- Rust-ядро нужно прежде всего для совмещения двух бирж по мс (слияние потоков, as-of) и модели очереди; парсинг parquet в Rust (крейт `parquet`/arrow-rs) надо измерить против pyarrow — если не быстрее, читать pyarrow и отдавать Rust массивы (Arrow IPC/numpy) — решает замер.
- Rust установлен на 5.231.25.224 (`cargo 1.99.1`, rustup minimal, 08.11 23:55); сборку не запускали, пока идут `p40-rev-*` (В-103: не мешать).

## 6. Проход 2: заявки входа с очередью prob:3 (DOGE × 17.09, 09.11)

Код: `tools/p40core/rs/src/{book,fills}.rs` (книга/сделки; заявки), `queue.rs` (prob:3, порт hftbacktest), `main.rs` (`<out>.fills.csv`; запуск `p40core out dirA dirB trA trB lotA lotB [L_ms=500]`). Проход 1 после рефакторинга на `Book/Rows` даёт тот же sha256 (`121e8403…`). Тесты на сервере: 12 зелёных (8 очередь + 4 заявки: исполнение сделками, снятие, пересечение лучшей цены, заявка не ставится при `tc ≤ tp`).

Правила (§3.3): заявка ставится в `t0 + L_ms` на лучшую цену ноги по состоянию строго до `tp` (дорогая нога — продажа на ask, дешёвая — покупка на bid), объём впереди — показанный на уровне; снимается при `dir·d ≤ θ/2` или через `T_life = 60 с`; события с одним временем — сделка раньше строки книги; пересечение лучшей цены проверяется в конце группы (не в снимке, только при `bid < ask`). Не сделано: страховка/закрытие мейкером, выход, частичные исполнения (нет, как NoPartialFill); сверка очереди с самим hftbacktest на тех же событиях; снимок часа не уведомляет заявку об исчезнувшем уровне; лот OKX `0,01` контракта — допущение (G0).

**Механика на этой паре × сутки (факт, не вывод):** при `L_ms = 500` ни у одного из 50 эпизодов (θ=5,04: 43; 12,6: 7) заявка не ставится — `dir·d` возвращается к `θ/2` раньше `tp`. При `L_ms = 50` исполнений: θ=12,6 — продажа 1 из 7, покупка 0; θ=5,04 — продажа 5, покупка 3, обе ноги 0 из 43; при `L_ms = 0` (проверка кода, не вариант протокола) — θ=12,6: 4 и 3, θ=5,04: 20 и 23, обе ноги 0.
Время счёта прохода 2 на сутки: +3,6 с к 3,9 с (сервер под нагрузкой G0, load ≈ 9,6).

### 6.1. Правка прохода 2 по сверке с эталоном TK-501 (09.11 00:19)

Первая версия §6 была неверна по трактовке: цена бралась в `tp`, отмена — без задержки (при `L_ms = 500` заявок «не было» — это следствие трактовки, а не данных). Выровнено с эталоном Исследователя (`/root/p40ref/tools/sim.py`): цена — лучшая своей стороны в момент решения `t0` (состояние после событий ≤ `t0`); заявка приходит в `t0 + L`; решение снять — `min(t_θ/2, t0 + T_life)`, отмена вступает через `L` (`tc = решение + L`); если к приходу противоположная лучшая цена уже дошла до цены заявки — исполнение в `tp`, признак `imm` («сквозное»); события со временем ≤ `tp` заявка видит, со временем ≤ `tc` — ещё обрабатывает. Колонки `<out>.fills.csv`: `imm_sell`, `imm_buy`.
