## 7. Проход 3: выход мейкером при обеих ногах и страховка при одной (DOGE × 17.09, 09.11 00:30)

Код: `closing()` в `main.rs` (ряд d вынесен в `d_series`, эпизоды те же — проход 1 sha прежний `121e8403…`). Выход: первый момент после исполнения обеих ног с `dir·d ≤ d0/2` и определённым d; заявки на лучшей цене своей стороны (выкуп проданной ноги по бид, продажа купленной по аск) приходят через `L`, не снимаются; pnl — в bps номинала ноги, 4 мейкер-комиссии 1,26 bps. Страховка: `t_c = max(t_исполнения, отмена входа)`, закрытие мейкером на лучшей цене на `T_life` (приход `t_c+L`, снятие `t_c+T_life+L`), иначе тейкер по лучшей цене в `t_c+2L+T_life` (комиссии 1,26 + 3,15 bps). Таблица `<out>.exits.csv`: `theta,t0_ms,outcome,exit_ms,exit_kind,pnl_bps,fees_bps`. Лоты выхода — те же константы, что у входа (в эталоне 1000 USDT / цену заявки — разница в четвёртом знаке).

**Сверка с эталоном (`cmp_maker.py … <exits.csv>`, 50 эпизодов; DOGE 17.09, L=500): совпали 32 из 50 (результат, вид, pnl, время), 18 — нет** (в основном время исполнения страховочной заявки на сотни мс, в 3 случаях вид maker↔taker). Все 50 эпизодов — «одна нога» (при L=500 обеих ног нет), поэтому ветка «выход при обеих ногах» в бою не проверена — только тестом на 13 заявках входа. Причины расхождений (факт, найден трассой):
- (а) **исполнение при подходе противоположной лучшей цены уже после постановки.** В ядре (как в hftbacktest: покупка с ценой ≥ нового лучшего аска исполняется) оно есть, в `sim.py` эталона — нет (код учитывает только строки журнала уровня и сделки). Пример: θ=12,6, t0=1789633107347 — бид нашей покупки 0,08127 исчез и на нём появился аск в t_c+2444 мс; ядро исполнило там, эталон — на сквозной сделке по 0,08126 в +2635 мс. Переключатель `P40_NO_CROSS=1` отключает это в ядре: расхождений 13 из 50 (было 18).
- (б) **остаток 13 — различие очереди, не выяснено.** Пример: θ=12,6, t0=1789678976753, продажа на Binance по аску 0,08171, уровень 936 050 → 617 091 в +5744 мс без сделок, затем две сделки по 11 и 51 по этой цене в +5757 мс; эталон исполнил в +5757, ядро (без пересечения) — в +6046 (сквозная сделка по 0,08172). Формулу prob:3 (`front − (1−p)·chg + min(back − p·chg, 0)`, f(x)=x³) читаю одинаково; нужна пошаговая трасса `front` обеих реализаций на этой заявке.
- Решение о том, считать ли исполнение (а), — методики (П-40 §3.3: «очередь prob:3» = hftbacktest, где оно есть); эталон Исследователя его не содержит. Сверка очереди с кодом hftbacktest (а не с разбором на Python) не делалась.

## 10. Таблица эпизодов в схеме TK-502 (`assemble.py`, 09.11 ~00:58)

`tools/p40core/assemble.py <выход.npz> <bounds.json> [--fix] asset:day:pair:bybit:<путь к <out>>…` собирает таблицы ядра по парам×суткам (эпизоды θ=12,6 из `<out>`, `<out>.exits.csv`, `<out>.features.csv`) в npz со столбцами `p40stats.SCHEMA` + `armed`, `trunc`. Правила: строка = взведённый эпизод (ITT: нет исполнения → `net_bps` = 0; страховка включена); `conv_H` = сошлось по mid за H=600 с; `t_conv_s` = время схождения по mid, при цензуре (не сошлось за T_life) = 60 и `cens`=1; терцили — по всей выборке, границы пишутся в `bounds.json` (D1) и читаются с `--fix` (D2); `trunc`=1 — обе исполнены, выход не определён (усечение §2.2 не реализовано). Столбцы без источника в ядре (`mpu_X`, `f_oi5m`, `f_liq`, `f_phi_sign`) = −1. Проверено только дымом на DOGE × 17.09 (7 строк θ=12,6: схема, типы, терцили на 7 значениях — смысла не имеют).
