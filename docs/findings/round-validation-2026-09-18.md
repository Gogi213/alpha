# Что такое круг: валидация сценариев, две ловушки определения и решения В-60/В-61 (2026-09-18)

Владелец попросил «провалидировать, что такое круг, сценарии». Ниже — по коду
(`src/lob/strategy.rs`, `commands/lob/backtest.rs::bounce_plan`, `lob/levels.rs`) с долями из
прогона по десяти местным монетам (`data/always-on/20260912T201737Z`, 13.5 млн сигналов, 48 форм,
`--allow-unverified`, `k = 1.0`), а затем решения владельца и что из них сделано.

## 1. Круг по коду

Круг = один сигнал-касание → попытка входа → один исход.

| сценарий | что происходит | доля |
|---|---|---|
| занято | стратегия ещё не `Idle` после прошлого сигнала | 27.6 % сигналов |
| книга не готова | нет валидных bid/ask в `t0` | 2.3 % |
| вход поставлен | лимит `GTC` по `entry_px` (фронтран или `P ± 1`), живёт ровно длительность касания | 70.1 % |
| — вход пересёк спред | исполнен тейкером сразу | 40 % поставленных |
| — таймаут | не исполнился за время касания → отмена → `CancelPending` → `Idle` | 41 % поставленных |
| — исполнен | `Holding`; выход по приоритету стоп → трейл → тейк → ранний → дедлайн | 41.3 % сигналов |
| выход стоп | лучшая цена дошла до `stop_px`, рынок (IOC) | 82 % кругов |
| выход тейк | лучшая цена дошла до `take_px` (1:1 от входа), лимит | 12 % |
| выход ранний | через X с цена всё ещё на уровне, рынок | 5.6 % |
| выход дедлайн | от момента **исполнения**, рынок | 0.05 % |

Цены (`bounce_plan`): `entry_px` — цена первого фронтранера или `P ± 1` тик; `stop_px` — `before`
`P+1` / `at` `P` / `behind` `P−1`; `take_px = entry + (entry − stop)`. Гонка «исполнился, пока
летела отмена» закрыта фазой `CancelPending` (`strategy-cancel-race-2026-09-18.md`), остаток
позиции после круга — страховкой (`n_residual_flattened = 0` на всех прогонах).

## 2. Две ловушки определения (не кода)

**32 формы из 48 — не сделки.** Без фронтранера вход `P+1`, а стоп `before` тоже `P+1`: стоп
равен цене входа и срабатывает на первом опросе после исполнения. `at` (`P`) срабатывает, пока
цена просто стоит на уровне — нормальное состояние касания. Данные: у `before` и `at` 91 % стопов,
медианный круг **60 мс** (два RTT). Только `behind` ведёт себя как сделка: 62 % стопов, 19 %
тейков, 19 % ранних, круг 140 мс.

**Геометрия в тиках, издержки в bps.** Средний размах круга |вход − выход|: ZEC 0.3 bps,
XRP/ENA/SOL/DOGE/HYPE/SUI 1–1.5 bps, NEAR/LSK/STORJ 4–7 bps — против круга издержек 7.5 bps
(`MAKER_FEE_BPS` 2 + `TAKER_FEE_BPS` 5.5). Поэтому `net` у всех форм и монет ≈ минус комиссия:
от −7.6 до −13.4 bps. Сделка «стоп за тик, тейк 1:1» не может быть положительной там, где тик
меньше ~4 bps, независимо от качества плотностей. Плюс `net_bps` вычитает фиксированные 7.5 bps,
а вход, пересёкший спред (40 %), стоил 11.

Мелочи: дедлайн не срабатывает (0.05 %), четыре дедлайна дают одинаковые круги — различных форм
фактически 12; TTL входа равен длительности касания, известной задним числом (в живом контуре —
«снять при уходе цены с уровня», реализуемо).

## 3. Снятие, перенос, спуфинг — в каком сценарии

Ни в каком. Трекер уровней знает исход смерти `Pulled` (объём против уровня ≤ 20 % максимума —
сняли) и эвристику `repriced` (в кадре смерти на `±1` тик родился сопоставимый уровень), но
`repriced` «печатается как есть, в гейты не входит», а до сделки не доходит ни то, ни другое:

- снятие **до входа** — смерть уровня заканчивает касание, вход снимается по TTL: сидит внутри
  сценария «таймаут», от честного «цена не дошла» не отличим;
- снятие **после исполнения** — стратегия в `Holding` на плотность не смотрит вовсе, позиция
  едет до стопа/тейка;
- перенос — новый уровень с новым `id`, нулевым возрастом и числом касаний; «пружинку» стратегия
  не видит; замены сетапа нет: пока не `Idle`, любой сигнал — «занято».

Спека §5 «отмена сигнала по снятию участника» и «пружинка → не входить» не реализованы: нужна
ось «уровень умер/переставлен» как событие плана и решение по каждой фазе — новая ось
предрегистрации.

## 4. Что такое «касание» при `k = 1.0`

Порог `H3 = floor(k × медианный размер сделки)` при заглушке `k = 1.0` — любой уровень размером
в одну медианную сделку, то есть практически любая заявка. Отсюда у монет пула 12–101 тыс.
касаний в сутки (касание каждые 0.86 с у ARB), отсюда же −7.6 bps на всех формах: считались
сделки от случайных уровней. Сетка на таких касаниях измеряет шум, сколько бы её ни ускорять.

## 5. Решения владельца (2026-09-18) и что сделано

**В-60. Гейт «≥ 7 суток» снят: «одного дня минимум хватает».** BUSINESS-TASK строка 341 требовала
`G ≥ 7` суток как число кластеров интервала `net_fill` (Decision 9). Сделано: кластер — сутки,
когда суток в сетке не меньше `G_MIN = 7`, иначе **час UTC** (у одних суток 24 кластера,
константа `G_MIN` остаётся порогом бутстрэпа Уэбба: `6^7` реплик). Гейт: суток с кругами ≥ 1,
кластеров с кругами ≥ 7, `n ≥ 100`. Для промахов (у них нет времени в `rounds.csv`) `forms.csv`
получил столбец `signals_by_hour` (`h0:…:h23`), вердикт печатает `cluster_unit` и
`clusters_with_fills`; дамп без столбца при суток < 7 — отказ, не догадка. Тест
`few_days_get_a_verdict_through_hour_clusters`.

**В-61. Медиану убрать: плотность — либо сила, либо «от денежного объёма», либо вместе.**
Сделано в `lob/levels.rs::H3Mode` и `--h3-mode`:
- `notional` — `--h3-usd N`: уровень — плотность, если `цена × размер ≥ N` (порог в лотах
  зависит от цены: `ceil(N / (цена × лот))`, целочисленно);
- `strength` — `--h3-strength-pct S --h3-strength-window-bps W`: сила «×соседи» (roadmap §3,
  знаменатель B, буквально «крупная для стакана»): `100 × size / mean(size соседей той же стороны
  в ±W bps) ≥ S`; без соседей в окне сила не определена — уровень не рождается; считается на
  кадре префиксными суммами и бинарным поиском, аллокаций после прогрева нет;
- `both` — И.
Все три без прогрева (как `floor`). Прежние `floor`/`percentile` остались для команд уровней и
осей «×H3»; `notional`/`strength`/`both` там — отказ с текстом (единого порога в лотах нет).
Знаменатели C «×поток» и D «×глубина» не делались. Числа `N`, `S`, `W` назначает владелец —
умолчаний нет.

Первые касания на ZEC/DOGE (2 суток), для ориентира, не как решение:

| режим | ZEC касаний | DOGE касаний |
|---|---|---|
| `floor`, `k = 1.0` (было) | 26 124 | 4 558 |
| `notional --h3-usd 50000` | 258 | 134 |
| `notional --h3-usd 300000` | 2 | 3 |
| `strength 300 % в ±20 bps` | 4 797 | 8 |
| `both` (50k, 300 %, 20 bps) | 258 | 8 |

При таких касаниях прогон суток пула определяется уже не сеткой, а проходом книги для касаний
(~45 с на монету на сервере при четырёх сутках записи).

## 6. Первый боевой прогон сетки на сервере (сутки 2026-09-17, `k = 1.0`, один поток)

Три попытки упали по памяти, четвёртая идёт: (1) рост `Vec` событий удвоением — пик до 3× итога,
OOM по лимиту cgroup 2.6 ГБ (починено подсчётом событий до аллокации); (2) полный реплей держал
на монету четверо суток записей уровней и срез середины по кадрам — 2.39 ГБ на первой же монете
(починено реплеем «только касания»); (3) трэш у потолка на ARB (101 тыс. касаний): сигналы всех
48 форм заранее (600 МБ) плюс результаты до конца суток (починено: сигналы формы в потоке,
результаты в дамп сразу, порядок форм не зависит от числа потоков). Коллектор во всех попытках не
задет (`systemd-run` с `MemoryMax`, `CPUWeight=10`, `nice 19`). Темп: ~1.5 мин на монету, из них
~45 с — касания по всей записи; сутки пула ≈ 2.5 ч при одном потоке. Верно для `k = 1.0`; после
В-61 сетка на порядки меньше.
