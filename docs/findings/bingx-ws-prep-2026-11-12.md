## 3. Каналы BingX → итоговый формат (docs/collector-ws-format.md)

Подписка: `{"id":"<id>","reqType":"sub","dataType":"<SYMBOL>@<тип>"}`; ответ `{"id":"<id>","code":0,"msg":"","dataType":"","data":null}`; кадр данных `{"code":0,"dataType":"<SYMBOL>@<тип>","data":…}`; код символа — `BTC-USDT` как есть. **Числа цен/размеров — строки** (как на бирже).

### Выбор канала для `b` (лучшие bid/ask с размером): **`bookTicker`**

[док] «訂閱最優掛單 — 每200ms推送一次。» («Subscribe to best order — pushed every 200 ms»); `incrDepth`: «The push frequency for BTC-USDT and ETH-USDT is 200ms, while for other trading pairs it is 800ms.»; `depth<N>@<интервал>`: «The push interval for BTC-USDT and ETH-USDT is 200ms, and for other contracts it is 500ms.»; `ticker` — «Pushes data of 24-hour price change every 1000ms». Замер на **одних и тех же 10 самых активных символах**, одно соединение, 3 мин (W1-D, 13:38:50–13:42:00) [измерено]:

|---|---|---|---|---|
| **`bookTicker`** | 25,4 (2,5/с на символ) | 55 / 117 | 1 828 из 4 434 записей | в документации — 200 мс, на деле ≈ 385 мс на символ |
| `depth5@200ms` | 25,8 | 57 / 150 | 2 030 из 4 516 | BTC 5,0/с, ETH 4,85/с, остальные 2,0/с (интервал 500 мс по документации); без `E`/`T`/`u`, только `ts` кадра |

На топ-100 (W1-A): `bookTicker` 250,9 кадров/с — **ровно ≈ 2,6 записи/с у каждого символа** (SOL 2,63, ETH 2,61, … и у малоликвидных 2,6): канал идёт по таймеру ≈ 385 мс, а не по изменению; реально меняется верх в 35 % записей (15 474 из 44 046). Данные как на бирже (В-172): склейка делается биржей.

- **201 тема:** 200 ответов `code:0`, на 201-ю — `{"id":"bt-ELSA-USDT","code":80403,"msg":"your topic num over max 200","dataType":"","data":null}`; **соединение остаётся открытым** и продолжает отдавать 200 принятых тем (491,7 кадров/с, 100 с). Настоящий код — **80403** (как в записи изменений USDT-M); `100416` из английской страницы не встречается.
- **Без ответа `Pong`:** сервер шлёт `Ping` в 5,1 / 10,1 / … / 30,1 с (6 штук) и **закрывает соединение на 30,7–30,9 с без кадра закрытия** — и с подпиской на один символ, и на пустом соединении. **С ответом `Pong`:** пустое соединение живёт все 100 с (19 `Ping`).

## 6. Что нужно от ядра (в терминах контракта, не Python)

1. **Двоичные gzip-кадры.** Все кадры (данные, ответы на подписку, `Ping`) приходят как opcode 2 с gzip-телом; разжатие — в ядре до разбора адаптером.
2. **Пинг на уровне сообщения.** Сервер шлёт текст `Ping` раз в 5 с в gzip-кадре; ответ — текст `Pong` (не протокольный `pong`); метрика `g` по этому пингу недоступна (RTT не измерить) — нужен альтернативный источник (напр. REST `/server/time` или TCP connect).
3. **Лимиты соединения.** ≤ 200 тем (код ответа на превышение — 80403, соединение остаётся открытым), ≤ 60 соединений с IP; 892 символа × 3 вида = 2 676 тем = 14 соединений: шардинг по числу тем (частота у всех символов одинаковая: ≈ 2,6/с `bookTicker`), лимитера подключений по времени у BingX нет (в документации).
4. **Подписка по одной теме в сообщении**, темп ≤ 50/с проверен (179 тем за 3,6 с без ошибок); ответ — отдельный кадр на каждую тему.
5. **Снятие дублей.** Ключи: `b` — `u` в пределах одного соединения, **но не между линиями (у каждого соединения свой счётчик) — для двух линий `(символ, T)`**; `m` — `E` (общий для соединений: 860 общих ключей, 0 только на одном), `t` — **множество недавних `t` (окно), не порядок**: 1–2 % сделок приходят с меньшим `t` после большего (с более поздним `T`); правило «ключ ≤ последнего → дубль» их потеряет. Данные приходят по таймеру и без изменения (65 % записей `bookTicker` — повтор состояния): писать как пришло или снимать повторы состояния — решение координатора (п. 6.7).
6. **Метаданные:** размер контракта не нужен (размеры в монете); `apiStateOpen` (69 символов пула с `false`).
7. **Формат: решение координатора.** (a) `b` — склеенный по времени поток (≈ 2,6/с на символ, 35 % смен состояния); писать каждую запись (≈ 191 млн/сутки на 892 символа [вывод]) или только смены; (b) `m` по WS несёт только `p` — `i`, `r`, `T` из REST `premiumIndex` (опрос раз в N с вне цикла событий) или пустые (в формате «пусто, если нет у биржи»); (c) BTC/ETH `depth5@200ms` (5/с) — отдельный источник или нет; (d) `E` у `markPrice` ≈ 185 мс «старше» кадров — лаг этого вида не сравним с `bookTicker`.
8. **Объём.** `bookTicker` 2 209 зап/с на пул (≈ 191 млн/сутки), `markPrice` 880 зап/с (≈ 76 млн/сутки; при записи только смен ≈ 9 млн/сутки), `trade` ≈ 373 зап/с (≈ 32 млн/сутки).
9. **Пул-файл:** `pool-<день>.json` с `qv`/`meta` (в пуле 69 символов с `apiStateOpen=false`); смена пула раз в сутки — как у остальных бирж.
