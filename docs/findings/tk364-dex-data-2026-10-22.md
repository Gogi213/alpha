## Синхронизация часов и ограничения
- HL fills несут время блока (мс); у нашего бинлога — локальное время приёма Bybit-кадра. Разница часов/задержек (десятки мс) —
  ниже предела разрешения блока HL (блоки ~сотни мс); лаги <100 мс по DEX-ряду не разрешимы — только ≥ блока. Итоговое
  разрешение шага 2 — по факту первых файлов.
- Fills — это цены исполнений, а не котировки: без сделки на монете в окне ряд пустеет (тонкие монеты); L2/mid нужен для них.
- Другие DEX (on-chain Uniswap/Pancake/Raydium, прочие перп-DEX) не изучены: у них время блока 0,4 с…12 с, хуже HL; для
  шага 1 HL — единственный кандидат с мс-временем и перп-ценой. Не проверено.

## Выводы по источникам
1. Для перп-DEX с мс-временем **агрегатор ничего не добавляет к HL S3**: Dune/Allium для HL отдают те же fills (с 2025-07-27) за большие деньги или по запросу. Дешевле всего — S3 напрямую (≈ $22 за всё).
2. On-chain DEX (Uniswap/Pancake/Raydium) — время блока 0,25…12 с, цена спота, арбитражёры держат её вслед за CEX: DEX там скорее следует, а не опережает; лаги < блока не разрешимы. Годится как вторая проверка, не как первая. Массово — Dune `dex.trades` (SQL-агрегаты) либо Bitquery/Allium по запросу.
3. Рекомендация: (1) **HL S3 fills** — шаг 2 за ≈ $0,4, шаг 3 ≈ $22; (2) на on-chain — только если HL даст сигнал: Dune Plus (≈ $350–400/мес, один месяц) для SQL-агрегатов `dex.trades`.
4. Не проверено на реальных файлах: частота L2, поля fills, вход в Dune entitlement для `perp_trades`.
