### Находки поверх таблицы

- **«Вне стадий» ≈ константа на единицу.** Без ЦП: волна (1 882 − 340) / 120 единиц = **12,9 с/ед.**; QUICK5 (806 − 151) / 40 = **16,4 с/ед.** Доля 16 % в обоих случаях — потому что оба раза единиц ~ столько, сколько слотов×k. Гипотеза **[оц]**: фиксированная цена единицы (старт процесса, открытие частей суток и сайдкаров на холодном диске, освобождение 3,6 ГБ, запись ~2 000 мелких файлов). Если верно, она ∝ числу единиц: малые единицы (G=8) её **умножают**, пул внутри одного процесса — убирает. Проверит a3 (`ts` на строку).
- **«Прочитано 65 ГБ при ~47 уникальных»:** rchar 65,1 ГБ (events 52,0 + touches_load 9,9 + setup 3,2) против чтения с диска 47,3 ГБ (sdb 27,2 + sda 20,1) **[замер]**. Разница 17,8 ГБ — попадания в кэш страниц; диск почти не читает байт дважды. Значит «D+1 один раз» экономит **ЦП повторного декода (544 слот-с = 36 с)**, а не байты диска. Ожидание 485 с в довеске — это, по-видимому, холодное первое чтение, которое всё равно кто-то оплатит (проверка: стадия-wait по файлам — запрос M-1).
- **Счёт частей (ev_count): стена 244 слот-с при ЦП 0** — холодные сайдкары `.events`. Разовая подготовка сайдкаров (В-185 разрешает) убирает 244 слот-с ≈ 16 с почти бесплатно.
- **Почему ЦП волны tk048rd 7 350 с ≈ эталон 7 297 с при −13,7 % на сутках 01-15:** ЦП-с не есть мера работы. При загрузке 3 → 17 потоков user-с на ту же работу растут ×1,51 (TK-029, SMT на 8 ядрах/16 потоках); малые единицы подняли среднюю загруженность (13,4 занятых потока против ≈ 7), плюс чужой `nice`-юнит 6–17 % машины. Выигрыш «на сутках» реален, волна его съедает раздуванием. **Инвариантная мера — `perf stat -e instructions`** (запрос M-2); пока считать экономию ЦП только в парах на одной загрузке.
- **Водопад QUICK5 непредставителен для 15 суток** в круговой и простойной частях: простой 27 % против 11,9 %, круги 27,6 против 36,7 %, `nice` 17,3 против 6,3 %, холодный кэш. Представителен для «вне стадий» (16,3 против 16,0 %). Для решений — только 15-суточная волна.
- **Расхождение perf и водопада (нужен замер, не домысливать):** events в водопаде = 29 % ЦП волны (2 088 из 7 150), а perf на сутках 01-15 даёт декод+воспроизведение 11,7 % (на 01-01 — 32 %). Либо волна из 15 суток в среднем «легче» 01-15 (тогда доля декода выше — похоже на 01–10.01), либо в events водопада сидит ядро/страничные ошибки/раздувание SMT. Для оценок Ц3 беру нижний край (согласуется с тем, что мелкие правки декода c1 дали всего −2,2 % user на 01-01).
- **Расхождение по TK-049:** CEO 04:36 — «59 с против 40 с»; Инженер 04:32 (m4, после правки дедлайнов) — «36,7 с против 39,1 с, впервые не хуже». Учитываю m4 как свежее; решение «брать/не брать» — только по полным суткам парой.

## 3. Путь к ×3 и ×10 (относительно ref15 = 1 023 с)

**Где сейчас:** 786,8 с (×1,30), без PGO в этой волне.

**×3 (≈ 340 с):** цепочка по верхним вилкам **[оц]**: 787 → № 1 (−70…−110) 680–720 → № 2 (−40…−100) 580–680 → PGO (−50…−80) 500–630 → пакет № 4+6+7+8 (−55…−170) ≈ 350–570. Нижний край ЦП-пола после всех пакетов: (7 491 − PGO 1 143 − декод 1 000 − окна 300 − книга 350 − Ч3/4 0…600) / 15 ≈ **270–310 с**; пол диска **299–397 с**. Итог: ×3 достижим **только на нижних краях всех вилок сразу, и при диске на 158 МБ/с**; правдоподобнее **380–450 с (×2,3–2,7)**. Чтобы ×3 был надёжным, нужно −15 % байт (47,3 → 40 ГБ: пол диска 254–338 с) — это № 9 (измерение уже идёт, TK-050 prep). Оценка «×3 надёжно» без № 9 — не обоснована.

**×10 (≈ 100 с):** недостижим при текущих байтах: пол диска 257–299 с даёт потолок **×3,4–4,0**. Для 100 с нужно одновременно (а) байт на счёт ≤ 100 с × 158 МБ/с ≈ **16 ГБ (−66 %)** либо иное устройство хранения данных счёта; (б) ЦП ≤ ~1 500 слот-с (−80 % от 7 491; все пакеты выше дают −40…−55 %). (а) **ни одним замером не подтверждено**: лучшее измеренное −7,7 % (слияние кадров), колонки zstd-1 −3…−7 %, срез глубины 25 bps оставляет 60–73 % байт (−27…−40 %, но меняет вход — против В-172). Единственный открытый рычаг для ×10 в рамках «разовой подготовки данных» (В-185): **лента, содержащая только то, что влияет на решения** (события в пределах нужной глубины около стен/σ-лестницы, с точной эквивалентностью выхода) — её доля от байт бинлога **не измерена** (запрос M-5). Мемоизация (П2) ускоряет повторные прогоны с малой правкой клеток, но не первый прогон волны.

## 4. Проверка замеров

- **Водопад сходится по построению** (простой = бюджет − занятое), но **неразобранное = 16,0 % «вне стадий» > 3 %**. Цель < 3 % не достигнута; разбор — a3.
- Перекрёстные проверки: ожидание в стадиях 273+3+879+5+8+104 = 1 272 ≈ 1 273 ✓; events: счёт 244 + декод 149 + довесок 485 = 878 ≈ 879 ✓; диск 27,2+20,1 = 47,3 ГБ ✓.
- **Не сходится / нужен замер:** (1) events 29 % ЦП в водопаде против 11,7–32 % декод в perf (см. выше); (2) ЦП волны не сохраняется при ускорении суток (объяснение — раздувание SMT и чужой nice; недостаёт `instructions`); (3) TK-049: 59 vs 40 с (CEO) против 36,7 vs 39,1 с (Инженер m4); (4) возможно, часть «вне стадий» — ожидание слота в `xargs`, а не единица (a3 различит).
- Загрузка не чистая: `nice` 6,3 % (QUICK5 17,3 %) — абсолютные секунды ± 5 %, доли надёжнее.
