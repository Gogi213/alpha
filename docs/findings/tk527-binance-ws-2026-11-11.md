# TK-527 (G-022, шаг 1): коллектор Binance USD-M по вебсокету — итоговый отчёт (редакция 12.11)

Код: ветка `tk527-binance-ws` — `tools/collector/wscore/` (ядро, 12 модулей), `binance_ws.py` (адаптер, 123 строки), `accept_ws.py` (приёмка), тесты `test_wscore.py` + `test_binance_ws.py`.
Работает на srv 5.231.25.224: юнит `bnws-prod` (`--lanes 2`, корень `/data/bnws`, health `/data/health/binance.json`). Суточных проверок нет (В-141): приёмка — окна по 3 минуты.

## Результат

Окно 3 мин (В-141, В-140) без разрывов, переподключений и отставания пройдено трижды, **включая фазу запуска**: окно m (с запуском, до бюджета подключений), окно n (установившийся режим) и окно p (с запуском, с бюджетом подключений; п. «Окна»).
Лимиты WS — таблица ниже, запас до каждого — числом. Граница подключений (300 / 5 мин на IP) теперь следует из кода, а не из исхода окна. Узкое место одно — сетевой путь NL → AWS Токио (RTT-класс соединения).

## Что пишется

Пул: TRADING USDT PERPETUAL, `quoteVolume24h ≥ 300 000 $`, без 10 крупнейших (G-022), фиксируется на старте — 509–512 символов (на 11.11: 522 контракта, 512 после правила). Виды: `bookTicker` (лучшие bid/ask с размером; `/public`), `aggTrade` (`/market`), `markPrice@arr@1s` (mark, индекс, фандинг — один общий поток; `/market`). Без глубины (В-115).
Формат и состав — `docs/collector-ws-format.md`: дельта-текст + zstd 1, числа биржи строками как пришли (В-172), приём `local_ns` и пинг WS на записях (В-133, В-137); −34 % (book) и −51 % (trade) к сырому JSON, разбор ≈ 1 млн строк/с на ядро.
Здоровье (В-134): фрагмент шарда раз в 10 с → `/data/health/binance.json` (схема TK-529): символы, пинг, таймауты, переподключения, лаг прихода и отдачи.

## Лимиты WS и запас до них

Источник — документация Binance USD-M (Connect). Раскладка: пул 512 → 8 шардов `book` + 8 `trade` по 64 потока + 1 `mark` = 17 шардов; `--lanes 2` (две линии на шард: второй путь, тёплый запас, В-140) → **34 соединения**.

**Где ограничение именно по пропускной способности:** потоки одного шарда — 64 по bookTicker на соединение. A/B 11.11 (512 символов bookTicker): 256 потоков/соед. — 6 разрывов за ~110 с и отставание у обоих соединений; 128 — 3 разрыва, отставание у 3 из 4; 64 — 2 разрыва, отстаёт 1 из 8 — **все остальные соединения 217–228 мс**. Позже выяснено: отстаёт не «большое» соединение, а путь (см. ниже), поэтому 64 — это выбор запаса, а не найденный порог (порог между 64 и 128 потоками не искали).

### Граница подключений: бюджет в коде (новое 12.11)

Раньше верхней границы не было: 34 линии × (12 отбраковок + 1 успешное) = 442 подключения за ≈ 3,3 мин > 300 / 5 мин; плюс замены и переподключения без общего счёта.
Теперь `wscore/budget.py` — общий для процесса `ConnectBudget(200, 300 с)`: кольцо из 200 отметок времени в разделяемой памяти (`mp.Array`) под `mp.Lock`; `Session.run` занимает место **перед каждым TCP connect** (в том числе отбракованным по RTT) — единственный путь к сокету, поэтому в любом окне 300 с подключений ≤ 200 при любых отбраковках, заменах и переподключениях (тест `test_connect_budget_never_exceeds_limit_in_any_window`: 442 запроса подряд, любые 201 выданных подряд — не короче окна). Если места нет — линия ждёт (событие `connect_wait`, не разрыв), данные других линий идут. Флаг `--connect-budget` (по умолчанию 200).
Число 200 — назначаемое, **Судье**: 2/3 лимита биржи; запас 100 на неучтённое (другие клиенты с этого IP, граница окна на стороне биржи). Прочтение «Binance считает и отбракованный по RTT TCP-connect» (строгое) заложено: бюджет считает его. Прочтение «считается только WS-upgrade» — тем более внутри лимита.
Старт на 34 линии (моделирование 10⁵ запусков, число подключений = Σ по линии усечённой геометрической: попыток до принятия, максимум 13): доля плохих путей 46 % (замер 11.11) — среднее 63, p99 82, максимум 100; 60 % — 85 / 113 / 150; 64 % (окно m: 61 отбраковка + 34 = 95) — 94 / 126 / 159; 75 % — 133 / 178 / 222, превышение 200 в 0,03 % запусков, и тогда линии ждут, а не превышают лимит. Превышения 300 — ни в одном из 4·10⁵ запусков. Худший случай «все 13 попыток у всех 34 линий» (442) бюджетом растягивается: 200 сразу, остальное по мере освобождения окна — лимит биржи не нарушается ни при каком исходе.

## Узкие места

1. **Сетевой путь srv (Kerkrade NL) → AWS Токио** — лаг и «хроническое отставание» соединений. Серверы USD-M — только Токио (`3.114.13.18`, `54.250.233.203`, `18.179.86.100` и др.); один и тот же удалённый IP даёт два класса пути по порту источника.
   - Решающий замер 12.11 (`lagprobe.py`, `connprobe.py`; данные `docs/findings/tk527-lagprobe-2026-11-12/`): 1 поток BTC на соединение, одновременно голый ssl-сокет без JSON, `websockets` с `permessage-deflate` и без сжатия, плюс Sofia как контроль. **Код, библиотека, сжатие и часы (chrony 0,08 мс) ни при чём**: CPU процесса 3,5–7,5 %, очереди у нас нет (лаг во времени плоский), все три реализации дают тот же разброс.
   - Класс пути = RTT рукопожатия ядра (`tcpi_rtt` сразу после `connect`): 54 из 54 соединений без исключения — RTT ≤ 276 мс: лаг p99 ≤ 1535 мс, RTT ≥ 320 мс: p99 ≥ 1925 мс; плохих ≈ 40–64 %. `rcv_ooopack` пути не различает (6–10 % против 9–19 %, перекрываются).
   - Лечение: предфильтр по RTT при подключении — `wscore/dial.py` (`CONNECT_RTT_MAX_MS` 300, зазор 276→320 мс), отбраковка за один RTT вместо 15 с пробы лагом; вторая линия — проба лагом `PathProbe` (p50 ≤ 350, p99 ≤ 1500 мс за 15 с); сторож живого соединения (p50 > 2000 мс два окна по 10 с подряд или нет pong) → замена без разрыва на другом пути, старая закрывается после перекрытия; `--lanes 2` — второй путь всегда тёплый.
   - Остаток: `book02` в окне m отбракован 12 раз подряд (при независимых попытках ≈ 2·10⁻⁵) — вероятно, соседние порты источника дают тот же класс пути; случайный порт (`bind`) не пробовали. Площадка в Токио/Сингапуре дала бы RTT 2–70 мс вместо ≈ 250–360, но решение о площадке — не нашей роли.
2. **Размер соединения** — см. A/B выше; снят выбором 64 потоков.
3. **Лаг ответа ping** показывает ту же очередь на стороне Binance, что и лаг `local − E` (на плохом пути pong 4–5 с), — не «чистый» RTT.
4. Пропуски `a` в aggTrade (`q≠nq`, RPI-часть) — не потеря коллектора: REST `aggTrades?fromId=` их содержит, WS не присылает; `trade_a_gaps` в окнах — 0.

## Устройство: ядро + адаптер (В-142, В-143)

Ядро не знает биржу; зависимости идут только сверху вниз, карта — `wscore/__init__.py`, у каждого модуля шапка «делает / не знает».

| модуль | одна обязанность |
|---|---|
| `stats` | окно, период статистики, перцентиль |
| `codec` | формат записи: Encoder, decode, ключ дедупа |
| `writer` | файл шарда за сутки UTC, `.ok`, снятие дублей (b — `u`, t — `a`, m — `E`) |
| `path` | проба нового пути (`PathProbe`), сторож лага живой сессии (`PathWatch`) |
| `dial` | TCP connect с замером RTT; плохой путь — до TLS |
| `budget` | общий бюджет подключений процесса за 5 мин |
| `metrics` | счётчики шарда → строка статистики и фрагмент health |
| `health` | фрагменты шардов → `health.json` |
| `session` | одно соединение: бюджет, подключение, подписка, пинг, чтение кадров |
| `shard` | писатель + сессии: переподключение, смена пути без разрыва, ротация 23 ч |
| `runner` | процесс: пул, раскладка, запуск шардов, бюджет, health раз в 10 с |

Поток: кадр биржи → `session` (`Adapter.parse` → записи) → `writer` (дедуп → `Encoder` → zstd 1) → `<root>/<день UTC>/<шард>-<запуск>.tsv.zst`; `session` → `metrics` → `health`. Что формат не разбирает точно — строка `r` с кадром как пришёл. Читать с `read_across_frames=True`.

## Что придётся написать для Bybit (шаг 2) — без правок ядра

Один файл `bybit_ws.py` с классом `Adapter` (контракт — шапка `wscore/session.py`):
1. `name`, `health_default`, `streams_per_conn`, `min_quote_volume`, `top_exclude`, `kinds`, `sub_period_s` — по лимитам Bybit (замером, как здесь: лимит подключений на IP → `--connect-budget`).

3. `plan` / `url` / `subscribe_messages` — раскладка, адрес, подписка (`orderbook.1`, `publicTrade`, `tickers`).
4. `parse` — кадр Bybit → кортежи `b` / `t` / `m` (ключи дедупа `u` / id сделки / `E` должны расти по символу — проверить у Bybit); `symbol`, `lag_ms`.
5. `trade_ids_consecutive` — только если id сделок идут подряд.
6. Тест разбора кадров по образцу `test_binance_ws.py`. Сначала замерить путь до Bybit (`connprobe.py`): предфильтр RTT — порог не переносится с Binance.

1. Ротация 23 ч вживую не видели (первая prod ≈ 12.11 ~23:00 +04, линия 1 — ≈ 11:30); суточных приёмок нет (В-141).

4. Назначаемые числа — Судье: `CONNECT_RTT_MAX_MS` 300 и `PROBE_*`, `LAG_LIMIT_MS` 2000 × 2 окна, пауза 3 с / pong 10 с (подтверждены 12.11); новое — бюджет подключений 200 / 300 с и `PROBE_MAX_REJECTS` 12.
5. Не входит (договор): другие биржи, глубина, OI/ликвидации, смена пула на ходу, порт на Rust, выгрузка суток на Storage Box (TK-530).

Алгоритм: варианты — 256 / 128 / 64 потоков на соединение (A/B 11.11); отбраковка пути по лагу после подписки против RTT рукопожатия до TLS; счёт подключений — по исходу окна против общего бюджета в коде; замер — 100–130 с на вариант потоков, 54 соединения на RTT-класс, 10⁵ запусков старта; выбран — 64 потока + предфильтр RTT 300 мс + проба лагом + сторож с заменой без разрыва + `--lanes 2` + бюджет 200 / 300 с, потому что класс пути определён RTT без исключений (54/54), а лимит подключений теперь ограничен кодом, а не исходом.
