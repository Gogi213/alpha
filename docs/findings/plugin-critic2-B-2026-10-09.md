## Важно

1. **Шина вне FAIL-списка выпуска: упавшая шина откатывает исправный выпуск.** `release.py:297` (`alive_problems`) считает проблемой любой
   FAIL doctor, кроме «простоя»; `doctor.py:105,107` отдаёт `шина FAIL`, если `RPV_BUS_URL` задан, а шина не ответила за 5 с.
   Сценарий: шина (отдельный хост) недоступна → автовыпуск 1.8.N ставит, службы поднимает, verify 60 с видит FAIL шины →
   `rollback` на прежнюю → проверка снова FAIL → `rolled-back`/код 2 + сигнал владельцу. Выпуск не виноват. Тест на это не написан
   (`test_release.py` гоняет `verify` подставкой). Правка: в `alive_problems` брать только службы (`dispatch|watch|ci_watch|board_push`)
   и `копии …`; шину — WARN.
2. **Замок автовыпуска: потерянное пробуждение и 30-минутная дыра.** `release.py:374-411`.
   (а) Держатель проверяет `pending.exists()` (стр. ~405) и снимает замок (стр. ~408); второй процесс между этими строками увидел замок,
   `pending.touch()` и вышел с кодом 0 — выпуск никто не доделает (окно узкое, но три влития подряд — норма: 08.10 «три автовыпуска подряд»).
   (б) Держатель убит (перезагрузка ПК, закрыли окно) — замок живёт `LOCK_STALE_S`=1800 с; все `auto` за это время пишут
   «поставлен в очередь» и выходят 0, `pending` не обрабатывается, пока не придёт следующее влитие. Выпуск молча теряется до получаса+.
   (в) Обратное: замок не продлевается (`mtime` не трогают), а худший случай одного прохода при зависшей сети — update 2×300 с +
   `installed_version`×2×300 + клоны 120 с + restart 2×300 + verify + rollback — больше 1800 с; живой держатель теряет замок.
   Правка: pid в замке и проверка «жив ли», либо продление mtime в цикле; `pending` разбирать и при взятии устаревшего замка.
3. **Ручной `release.py update` не перезапускает службы и присмотр.** `release.py:185-205` печатает «перезапустить Claude Code» и всё.
   Планировщик присмотра зашит на `CODE_DIR` версионного каталога (`supervise.py:42,170-171`), службы — `start.spawn(CODE_DIR/…)`.
   После ручного update присмотр поднимает службы из СТАРОГО каталога (Claude Code чистит осиротевшие версии, срок ~неделя) → через
   неделю присмотр тихо умирает. `doctor` этого не видит: `scheduler_installed` (`doctor.py:49-61`) смотрит только «задание есть», не
   путь и не `Last Result`; версии работающей службы против установленной не сравниваются. Правка: doctor — сверка
   пути задания/юнита с `installed_dir` и версии службы (строка в `*.run.log`) с установленной; WARN.
4. **Сторож пишет шапку тикета по устаревшему чтению.** `watch.py:390-460`: `tkt` читается в начале итерации, затем идут ssh-пробы
   (до 20 с `probe_wait_target`, до 25 с `job_probe`), и под `ticket_lock` без перечитывания статуса пишется `status: in_progress,
   wait_for: ""` (стр. 266, 455, 469, 494). Если за это время роль сдала `result` или диспетчер уже снял ожидание — статус перетирается,
   владелец будится вторым разом, `done`-тикет оживает. Замок защищает файл, но не решение. Правка: внутри замка перечитать
   `status == waiting` и `wait_for == spec`, иначе пропустить.
5. **`probe_wait_target` определяет «производитель жив» по подстроке имени файла.** `watch.py:184-189,205`: образец — basename пути без

   совпадёт с любым чужим процессом, где встречается слово — мёртвая цель считается `producer`, страйки не копятся, ожидание висит вечно
   (ровно то, что сторож должен ловить). Правка: требовать в имени токен тикета/юнита (`tk\d+`) либо брать имя юнита из `wait_for` формы `unit:`.
6. **Секреты: `start` и `supervise` решают по-разному.** `supervise.py:100` не пробрасывает `*_TOKEN/_SECRET/_API_KEY`, а `start.py:228`

   `systemd-run --setenv=` (видна в `systemctl --user show`). `RPV_BUS_TOKEN` (README:160) задан значением → уходит в командную строку;
   а после перезапуска присмотром токена уже нет (фильтр supervise) → служба тихо без шины (401). CHANGELOG:216 обещает «без секретов» —
   верно только для `supervise.env.json`. Правка: один `_secret_name` в `project.py` для обоих; токен — только `RPV_BUS_TOKEN_FILE`.
