§H. ИТОГ
-----------------------------------------------------------------------------------------------------------
GAP-1: load errors are not in the key and are invisible per coin. ZipSrc::day maps a load error (unzip failure, parse error, spawn failure; tick.rs:292-300, errors += 1 at :296-298) to None, which signals_for_coin treats exactly like an absent day (tick.rs:573-577, missing_days). The run then exits non-zero (tick_cli.rs:563-565), but a cached entry would replay the truncated signals as a success; the zip fingerprint of the same broken file would match forever. LoadStat is one global Mutex (tick.rs:215), so the error cannot be attributed to a coin under par_map. Rule needed: write no signal-cache entries when src.stat.errors > 0 after phase 1 (visible at tick_cli.rs:400) — or return a per-(coin, day) error flag from ZipSrc.
GAP-2 (conditional on design): zip fingerprints (K9) are only effective if re-checked on READ against the CURRENT --trades dir (tick_cli.rs:352; path tick.rs:242-245), for every day recorded in the entry incl. "absent". The --trades dir path itself is not in the key; if the hit path trusts the key without re-stat, zip content / zip set / --trades dir are uncovered inputs.
GAP-3 (low, external): the bytes parse_trades sees come from the external `unzip -p` (tick.rs:258-264): binary version, PATH and its own env (UNZIP/UNZIPOPT, inherited env C08) are not in the key. Accept (zip + exit-status check make it very unlikely) or add a hash of `unzip -v` to K1/K2.
no other gaps: SigCfg+LevelCfg fully read and fully in K3 (A01-A25); Params.exit/port/filt NOT read (B02-B05); P42_T0 is the only env var read by phase 1 and is in K5 (C01); P42_SIGSX_ONLY / P42_SIGS / P42_SIGSX / P42_LEVELS / P42_DETAIL are read after phase 1 and do not affect it (C02-C06); no clock, no float, no HashMap iteration; sort_tsigs has no ties (F03); thread count/order irrelevant (F02).

WEAK-1: the .b42 fingerprint (name, size, mtime) is weak on size: the file layout is fixed (8 + 5·8·N_MIN + 4 + 24·nf bytes; data.rs:219-231), so only mtime discriminates content; mtime restored with 1-second resolution (rsync -t, cp -p, tar) or a rewrite within one tick leaves the key unchanged. Cheap fix: hash the 5 column bytes (4,608,000 bytes per coin; the whole file is already in memory at data.rs:437). Funding-only changes also invalidate (E03) — harmless.
WEAK-2: the zip fingerprint (size, mtime_s, mtime_ns) has the same property as the existing .tk store check (store.rs:223) — same-size, same-mtime, different-content replacement is not detected. Accept (precedent) or add the zip CRC from the central directory.

TRAP-1: capture fingerprints PER REQUESTED (coin, day) of each job (by_day keys, tick.rs:568-578), not per physical load: ZipSrc memoizes in the LRU (tick.rs:286-291), so a second job of the same coin never triggers a load, and a hook on load/ZipSrc::day would leave its entry without fingerprints. Also: with the LRU a load is not repeated, so take the fingerprint from the same metadata the store used (tick.rs:246-249).
TRAP-2: TSig.sym is the index in the alphabetically sorted LOADED coin list (data.rs:500; tick_cli.rs:361, :365). Per-coin entries must be keyed by the full loaded coin list (or store coin-relative and re-stamp si); keying a per-coin entry by that coin's .b42 alone returns stale sym after --symbols changes. Use the loaded names (data.rs:488-504), not the --symbols string.
TRAP-3: SrcMeta::of returns None when mtime is unavailable (store.rs:41-48) — then no fingerprint exists: do not cache that day/entry.
TRAP-4: P42_T0 must be keyed as the resolved data::t0_ms() (data.rs:51-53), not the raw env text; the first grid_start() call may panic on a bad date (data.rs:38) — call it before spawning workers.
TRAP-5: after merging cached + fresh per-coin results, sort_tsigs (tick_cli.rs:376-378) and ctr[j].add (tick_cli.rs:373) must still run; the order is total (F03), so merge order does not matter.

DIAG-1 (side effects that disappear on a cache hit): (a) stderr counters pk / pb / свежий уровень (tick_cli.rs:379-399; atomics D01-D05) and the LoadStat line "фаза 1 готова …; файлов N, строк N, не по порядку N, вне суток N, плохих строк N, ошибок N" (tick_cli.rs:400-410) are produced only by computing/loading; on a hit they under-count. They do not affect results or meta.json (tick_cli.rs:494-514), but tools/p42/tk607_gate.sh:37-39 compares exactly these lines against the reference log (REF_LOG) — a gate run with --sig-cache will show "DIFF счётчики журнала" unless the lines are replayed or excluded. Replay is additive for D01-D03 per (coin, job); NOT per job for D04-D05 (counted once per (coin, LevelCfg, Side), tick.rs:559-564) and for LoadStat (counted once per physical (coin, day) load, shared by jobs). All counters are global atomics/Mutex today (not per job), so replay needs them returned from signals_for_coin (e.g. in TickCtr) rather than read before/after.

NOTE-1: constants not listed in K6 but read in phase 1: MIN_MS (data.rs:17; tick.rs:542), T0_MS/T0_DATE (data.rs:15-16; grid default), MAGIC .b42 (data.rs:28), and the literals in D21. All are covered by K1 (executable hash). If K1 is ever relaxed (e.g. keyed by source revision instead), add them to K6.
NOTE-2: key over-coverage (harmless): COUNT_DAYS (not read in phase 1), STORE_VERSION (the store is a pure function of the zip), fr_k/fr_b_pm/f_pm (dead for some configs), .b42 funding bytes.
