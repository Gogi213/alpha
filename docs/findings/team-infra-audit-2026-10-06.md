## 1. Диспетчер и сторож на Windows

**(а) Что ломалось.** `ceo.md`: 05.10 01:51 и 02:45 — оба процесса умерли от Ctrl+C, причина не найдена; 06.10 ~15:06 — сторож.
Три строки `supervise.log` 15:17–15:22 — **не сбои**, а намеренные остановки Судьи при приёмке TK-072 (проверка присмотра: сторож
15:13:54, оба 15:21:52; лог TK-072 15:25); мой первоначальный вывод «одно внешнее событие» был неверным. Естественных смертей
после e6017bc7 (демоны игнорируют SIGINT при выводе в файл) в логе нет. `dispatch.err.log`: 9 строк `PermissionError [WinError 5]`
(первая — 04.10).

**(б) Стандарт.** Планировщик заданий Windows (триггер + повтор, `MultipleInstances=IgnoreNew`, `RestartCount`), NSSM/WinSW (не
развивается с 2017, нужен админ и бинарник; `claude -p` берёт вход из профиля пользователя — служба под SYSTEM не подходит),
systemd `--user`/launchd для Linux/Mac. Присмотр на Планировщике уже стоит; в TK-072 плагин получил ветки systemd/launchd.

**(в–г) Вердикт: оставить.** Задача Планировщика с `IgnoreNew` заменила бы pid-файлы, но потеряла бы проверку зависания
(`decide()`: процесс жив, сердцебиение старше порога → restart); убирать `supervise.py` без замены этой проверки нельзя. Условие
пересмотра: неясная смерть демона после e6017bc7 (по `supervise.log` без записи о ручном kill).

## 2. Шина событий

**Проверка позиции CEO.** «Шина не причина простоев» — **подтверждается данными**: в `dispatch.err.log` (04–06.10) ни одной строки
про шину; ошибок ssh — 339 `TimeoutExpired` из 344 строк `wait_for`. «10 обрывов связи за 2 дня» из задания **я не нашёл**
— `bus_link` пишет состояние через `on_state`, в err.log его нет; число не проверено. В `ceo-wake.log` — 8 строк с шиной, это
события (например `машина.calc.юнит.упал` 06.10 14:38), а не обрывы.

**Что шина уже даёт и что пришлось бы переписать.** Реализовано и покрыто тестами: журнал SQLite, маршруты (`routes.json`),
очереди с ack, повторная отправка устаревшего («служба.не_обработано», 600 с), удержание по блокерам, long-poll. Сервер — один
процесс, 0 перезапусков. Из этого NATS JetStream и Redis Streams готовы дают очереди, ack, повторную доставку, группы потребителей,
хранение; **не дают** «удержание по блокерам» и маршруты — их писать поверх.

| | своя шина (сейчас) | NATS JetStream | Redis Streams |
|---|---|---|---|
| Зависимости плагина | stdlib | `nats-py` (asyncio) + `nats-server` на calc | `redis` (на этой машине стоит) + `redis-server` на calc |
| Windows-клиент | да | да | да (сервер — Linux) |
| Повторная доставка, группы | свои ~150 строк | есть | есть (`XREADGROUP`/`XAUTOCLAIM`) |
| Блокеры, маршруты | есть | писать | писать |
| Безопасность | открытый порт 8788 на calc, токен `hmac.compare_digest`, TLS нет | TLS+nkeys/токены из коробки | `requirepass`/ACL, TLS по настройке |

**Цена замены:** 5–7 ч (клиент + сторож машины + блокеры/маршруты поверх, перенос тестов 386 строк, переключение диспетчера,
сутки параллельной работы) + новая служба на calc. Выигрыш на сегодняшних простоях — нулевой.

**Безопасность.** Шина — `alpha-bus.service` на calc `89.163.242.211:8788` (по `ss` Судьи; в коде умолчание `--host 0.0.0.0`,
порт 8787 в `main()` — умолчание кода, в проде не используется), HTTP без TLS, токен `hmac.compare_digest`. Порт **8787 на calc —
`alpha-board.service`, табло владельца** (телефон) — ограничение по адресам на него отрежет владельца. Дешёвое исправление без замены
шины: правило `ufw`/`nftables` на **8788** только для адресов ПК и VPS (0,3 ч) либо привязка к интерфейсу Tailscale; табло не трогать.
(Первая версия отчёта ошибочно называла 8787 и «VPS» — поправлено по разбору Судьи; «nats-server на VPS» — читать «на calc».)

**Вердикт: оставить.** Менять на NATS JetStream (предпочтение: один бинарник, ack/группы/хранение есть) **когда выполнится одно
из**: (1) сообщения пишут ≥ 2 команды или ≥ 3 машины-источника; (2) мы начинаем сами дописывать группы потребителей, хранение с
ротацией или повторную доставку с задержкой; (3) шина становится причиной простоя — два разбора подряд (пороги — решение CEO/владельца,
я их не выдумываю).

## 3. `wait_for`: ssh-опрос и пробуждения LLM

**(а) Что ломалось.** `dispatch.err.log` (04.10 18ч – 06.10 15ч): 339 `TimeoutExpired` из 344 строк `wait_for`; Windows-OpenSSH без
`ControlMaster` — каждая проверка с новым соединением. `wait_for` на старый юнит давал 84 пустых запуска. **Это уже закрыто
TK-072 (принят 15:3x):** конец юнита событием шины с InvocationID, `on_met` 1,4 с без ssh, запасной опрос 300 с.

**Токены `wait_for-met`** (`usage.py --by reason`, 15:40–15:50): 463 запуска, 342 млн кэша, 1,84 млн выхода (21 % / 19 % итога).
Но **это не потери**: 367 из 463 запусков дали ≥ 1k выхода (316 млн кэша) — роли читают результат и работают. Пустых побудок
(выход < 1k) — 96, 26 млн кэша = 1,6 % всего. Моя первая оценка «on_met по умолчанию снимает 21 %» неверна — адресуема только
доля пустых побудок.

**Остаток (в): `file:`/`.json` по ssh.** Перевести на событие «задание.готово» сторожа машины, запасной опрос 300 с: ~1 ч.
**Вердикт: заменить сейчас.** Условие выполнено: после перезапуска 15:22 в `dispatch.out.log` (с 15:22 stdout/stderr пишутся туда, не в `err.log`) 6 `TimeoutExpired` за 25 мин — 3 `file:` (`chain52.done`, `pgotrain-b15pyr4.done`, VPS `…b15pyr4-gen.done`) и 3 запасных опроса `unit:` (`tk049-alwin-g1/w1/w4`). Цена ~1 ч; опрос `unit:` — замерить в той же задаче.

## 4. `alsched` и замок

Что ломалось: `stall-protections` п.1 и 3 — замок флока держали 2,5 ч, 5 замеров испорчены ssh-командами мимо замка.
`alsched.py` (472 строки) уже даёт заявки, окна замеров, заморозку производства (`systemctl freeze`), `max-runtime`.

**Slurm на одном узле** (Debian 13 `slurm-wlm`): даёт `--time`, backfill, брони, preemption SUSPEND+GANG через cgroup freezer,
`sbatch --wait`, зависимости, учёт `sacct`. Цена: 4–6 ч (munge, slurmctld/slurmd, cgroup.conf, эксклюзивное окно замера,
перенос `snap.py`/TK-068, обучение ролей), плюс постоянная служба и её сбои. Выигрыш — учёт и зависимости; заморозку
`alsched` уже делает тем же механизмом cgroup. **Вердикт: оставить** `alsched`; Slurm — когда появится **второй узел счёта** или
`alsched` перерастёт ~800 строк / получит третью ошибку, портящую волну (числа — предложение). `benchrun.sh` снять после недели
без запусков через него (0,2 ч).

## 5. Хуки и ssh

Хуки: `delete_guard.py` 1 890 строк + тест 1 759 — разбор bash вручную; **содержимое не читал**, вердикт по нему не даю. Стандарт
