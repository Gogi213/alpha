## 1. Диспетчер и сторож на Windows

**(а) Что ломалось.** `ceo.md`: 05.10 01:51 и 02:45 — оба процесса умерли от Ctrl+C, причина не найдена. 06.10 ~15:06 — сторож
умер снова. `supervise.log`: 15:17 сторож поднят (сердцебиение 351 с), 15:22:02 диспетчер поднят с сердцебиением **14 с**
и pid «-», 15:22:03 сторож — снова (151 с). Оба упали в пределах ~5 мин друг от друга, то есть похоже на одно внешнее
событие (закрытие консоли/группы), а не на два сбоя. `dispatch.err.log`: 9 строк `tick error: PermissionError [WinError 5]`
(первая — 04.10). **Причину смерти я не установил**; гипотеза — консольный Ctrl+C/закрытие окна доходит до процессов,
запущенных из Claude через `cmd /c`; задача Планировщика без консоли его не получает. Проверяется дёшево (см. ниже).

**(б) Стандарт.** Три варианта:
- *Планировщик заданий Windows* (`schtasks`/`Register-ScheduledTask`): триггер «при входе» + повтор раз в минуту,
  `MultipleInstances=IgnoreNew` (второй экземпляр не стартует — pid-файлы и `tasklist` не нужны), `RestartCount`/`RestartInterval`
  (перезапуск при падении), `ExecutionTimeLimit=0`, без консоли. Есть на любой Windows, ноль зависимостей. `supervise.py`
  уже сидит на нём — осталось убрать WMI-запуск.
- *NSSM / WinSW*: настоящая служба с автоперезапуском. Минусы: NSSM не развивается с 2017, нужны права администратора и
  внешний бинарник; главное — `claude -p` берёт вход из профиля пользователя, служба под SYSTEM его не видит; под пользователем —
  нужен пароль в службе. Для нашего случая выигрыша над Планировщиком нет.
- *Linux/Mac для плагина*: systemd `--user` юнит с `Restart=always`, `WatchdogSec=` / launchd `KeepAlive`. Плагину нужен
  адаптер на три ОС — делать, когда плагин пойдёт на Linux/Mac (сейчас Windows-владелец).

**(в) Цена.** 1,5 ч: задачи Планировщика на диспетчер, сторож, коллектор табло; убрать `wmi_start`/pid-логику; тест на XML задачи
(как уже есть тест на команду WMI); 1 ч наблюдения — убить процесс `taskkill`, закрыть консоль, отправить Ctrl+C — задача поднимает
за ≤ 1 мин. Зависимостей нет.

**(г) Вердикт: заменить сейчас.** Принятие: 48 ч без неоднозначных смертей в `supervise.log`.

## 2. Шина событий

**Проверка позиции CEO.** «Шина не причина простоев» — **подтверждается данными**: в `dispatch.err.log` (04–06.10) ни одной строки
про шину; ошибок ssh — 339 `TimeoutExpired` из 344 строк `wait_for`. «10 обрывов связи за 2 дня» из задания **я не нашёл**
— `bus_link` пишет состояние через `on_state`, в err.log его нет; число не проверено. В `ceo-wake.log` — 8 строк с шиной, это
события (например `машина.calc.юнит.упал` 06.10 14:38), а не обрывы.

**Что шина уже даёт и что пришлось бы переписать.** Реализовано и покрыто тестами: журнал SQLite, маршруты (`routes.json`),
очереди с ack, повторная отправка устаревшего («служба.не_обработано», 600 с), удержание по блокерам, long-poll. Сервер — один
процесс, 0 перезапусков. Из этого NATS JetStream и Redis Streams готовы дают очереди, ack, повторную доставку, группы потребителей,
хранение; **не дают** «удержание по блокерам» и маршруты — их писать поверх.

| | своя шина (сейчас) | NATS JetStream | Redis Streams |
|---|---|---|---|
| Зависимости плагина | stdlib | `nats-py` (asyncio) + `nats-server` на VPS | `redis` (на этой машине стоит) + `redis-server` на VPS |
| Windows-клиент | да | да | да (сервер — Linux) |
| Повторная доставка, группы | свои ~150 строк | есть | есть (`XREADGROUP`/`XAUTOCLAIM`) |
| Блокеры, маршруты | есть | писать | писать |
| Безопасность | открытый `0.0.0.0:8787`, токен `hmac.compare_digest`, TLS нет | TLS+nkeys/токены из коробки | `requirepass`/ACL, TLS по настройке |

**Цена замены:** 5–7 ч (клиент + сторож машины + блокеры/маршруты поверх, перенос тестов 386 строк, переключение диспетчера,
сутки параллельной работы) + новая служба на VPS. Выигрыш на сегодняшних простоях — нулевой.

**Безопасность (проверить, не принято на веру):** порт слушает `0.0.0.0` без TLS; токен ходит открытым текстом по HTTP. Дешёвое
исправление, не требующее замены: привязать к интерфейсу Tailscale/ZeroTier (оба стоят на ПК) или ограничить `ufw` адресами
ПК и сервера счёта — 0,3 ч, **рекомендую сделать независимо от вердикта**.

**Вердикт: оставить.** Менять на NATS JetStream (предпочтение: один бинарник, ack/группы/хранение есть) **когда выполнится одно
из**: (1) сообщения пишут ≥ 2 команды или ≥ 3 машины-источника; (2) мы начинаем сами дописывать группы потребителей, хранение с
ротацией или повторную доставку с задержкой; (3) шина становится причиной простоя — два разбора подряд (пороги — решение CEO/владельца,
я их не выдумываю).

## 3. `wait_for`: опрос по ssh и пробуждения LLM

**(а) Что ломалось и сколько стоит.** `runs.log`: `wait_for-met` — 461 запуск из 1 436 (32 %), **341 млн токенов кэша и 1,8 млн
выхода** из 1 634 млн / 9,8 млн (21 % / 19 %). `on_met` (запуск кода вместо LLM, TK-056) использован **1 раз**. По ssh: 339
`TimeoutExpired` за ~2 суток; `wait_for` на старый юнит давал 84 пустых запуска (TK-072). Windows-OpenSSH не поддерживает
`ControlMaster`, поэтому каждая проверка — новое соединение, таймаут 8+15 с.

**(б) Стандарт.** `systemd-run --wait`/`OnSuccess=`/`OnFailure=` + push; событие шины с `InvocationID` (сделано в TK-072 п.1–2:
`юнит.запущен`, сверка без ssh); сторож машины (`tools/bus/watcher.py`) уже шлёт `юнит.остановлен/упал`, `задание.готово`.

**(в) Цена.** 2 ч: `wait_for` `unit:`/`.json` считать выполненным по событию шины, ssh — только запасной путь раз в 10 мин;
0,5 ч: правило «по умолчанию `on_met` + короткая LLM-проверка, если код вернул нестандартный итог» в README/шаблон тикета.

**(г) Вердикт: заменить сейчас** (самый дорогой по токенам и числу сбоев пункт). Критерий — доля `wait_for-met` в запусках
< половины текущей (сейчас 32 %) и 0 ssh-таймаутов в err.log за сутки; пороги — на CEO.

## 4. `alsched` и замок

Что ломалось: `stall-protections` п.1 и 3 — замок флока держали 2,5 ч, 5 замеров испорчены ssh-командами мимо замка.
`alsched.py` (472 строки) уже даёт заявки, окна замеров, заморозку производства (`systemctl freeze`), `max-runtime`.

**Slurm на одном узле** (Debian 13 `slurm-wlm`): даёт `--time`, backfill, брони, preemption SUSPEND+GANG через cgroup freezer,
`sbatch --wait`, зависимости, учёт `sacct`. Цена: 4–6 ч (munge, slurmctld/slurmd, cgroup.conf, эксклюзивное окно замера,
перенос `snap.py`/TK-068, обучение ролей), плюс постоянная служба и её сбои. Выигрыш — учёт и зависимости; заморозку
`alsched` уже делает тем же механизмом cgroup. **Вердикт: оставить** `alsched`; Slurm — когда появится **второй узел счёта** или
`alsched` перерастёт ~800 строк / получит третью ошибку, портящую волну (числа — предложение). `benchrun.sh` снять после недели
без запусков через него (0,2 ч).
