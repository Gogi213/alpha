# П-02 блок B, Г-105 и Г-85 (2×2): отчёт (2026-09-26)

**Вердикт одной строкой:**
- **Г-105 (H10, стоп `before`) — не ясно по эффективному N (< 30 суток в обоих месяцах: 28,1 август /
  20 сентябрь), но точечный эффект отрицательный и крупный в обоих месяцах, а после поправки Холма
  сентябрь формально проходит порог значимости (p_holm = 0,0216)** — направление совпадает с прежним
  замером B2 17.09 (протокол §3/H10: там все формы стопа были отрицательны). Порог эффективного N
  не сдвигается: официальный вывод — «не ясно», сентябрьская цифра — сильный кандидат на «опровергнуто»
  при следующей проверке на большем числе суток.
- **Г-85 (H7, вход `single@fr`) — не ясно** (эффективное N 14,8 август / 23 сентябрь, оба < 30); точечный
  эффект около нуля в августе (+$0,25) и положительный, но не значимый в сентябре (+$60,14, p_holm 0,459).
- **Пара Г-85×Г-105 (совместная форма `single@fr`+`before`) — не считается вовсе.** 0 сигналов на обеих

  отклоняет план при `dist_from_level < 2` (`src/commands/lob/backtest/plan.rs:135-148`) — комбинация
  форм вырождена кодом, это не «мало данных», а полное отсутствие сделок.

## Замер

Δ$/месяц = (клетка − база) по суткам, кластерный бутстреп по суткам (20 000 передискретизаций,
95%-й интервал перцентилем, p — из нормального приближения по бутстреп-SE), эффективное N —
`effective_n_from_autocorr` (`.claude/skills/alpha-research/scripts/effective_n.py`, формула
перенесена на чистый python — на деке нет numpy), капнуто сверху календарным числом суток (формула
иногда даёт N выше сырого при отрицательной автокорреляции — это артефакт метода на короткой
серии, не лишняя информация). Поправка Холма — по 6 p-значениям этого отчёта (H10×2 месяца, H7×2,
пара×2); это **не вся семья блока B** из протокола (§9/«Пары» считает до 8 — с соседями `at` и
подвыборкой по фронтрану, которые в это исполнение не входили) — Холм здесь корректен только для
представленных 6 проверок, финальная поправка по всему блоку B ещё впереди (см. «Отступления»).

**Проверка «пары бессмысленны в одиночку» (протокол, раздел «Пары»):** подтвердилась в жёсткой форме

n_submitted=0` во всех `forms.csv`), не только «часть подвыборки», как ожидал протокол для лестницы.

равен 1 тику (не ≥ 2) — `StopForm::Before`/`MidFrontrun` возвращают `None` (`plan.rs:150-161`) на
каждом касании без исключений.

## Отступления

1. **H10/сентябрь: 3 суток (09-05, 09-14, 09-15) не досчитались.** `oos-frozen.sh` под тремя
   параллельными заданиями (H10 + два прямых `bounce-grid` для H7/пары одновременно, 8 ядер) упал по
   памяти/ресурсам на этих сутках (последняя строка лога — обрыв декода на 77 млн событий, не
   содержательная ошибка); скрипт удаляет каталог упавших суток (штатное поведение `oos-frozen.sh`).
   Пересчёт этих 3 суток **не проведён** — в момент, когда это обнаружилось, батарея Steam Deck
   показывала 7% и `ACAD/online = 0` (сеть питания отключена, разряд) — по указанию задания это
   основание остановить новый счёт на деке. Анализ выше использует 20 из 23 суток парно (без смещения
   «пропуск = ноль»), но это не полная замороженная выборка — досчёт 3 суток входит в открытые пункты.
2. **Питание Steam Deck: остановлено, а не начато на 0.** Проверка `ACAD/online` перед стартом (25.09
   ~19:12 UTC) показала `1` (сеть есть) — счёт начат по правилу. Ближе к концу счёта (после ~19:40 UTC,
   уже на лёгком локальном чтении, не на тяжёлом счёте) повторная проверка показала `0`/батарея 7%
   разряжается. Новый тяжёлый счёт на деке после этого не запускался (в т.ч. п. 1 выше). **Деку нужно
   поставить на зарядку** — иначе ночная сетка 02:00 UTC и досчёт 09-05/14/15 под риском.
3. **Холм — по 6 p-значениям этого отчёта, не по всей семье блока B.** Протокол (§9/«Пары») считает
   семью блока B из 4 базовых гипотез + 4 из пар = 8 (с соседом `at` для Г-105 и подвыборкой по
   фронтрану для Г-85, которые в задание этого исполнителя не входили — только сама 2×2). Итоговая
   поправка по всему блоку B — задача сборки результатов всех исполнителей блока B вместе, не этого
   отчёта; здесь корректирую только то, что сам посчитал.
4. **Эффективное N считался чистым python, не `scripts/effective_n.py` напрямую** — на Steam Deck нет
   numpy (не устанавливался — не в цене этого счёта, установка пакетов не входила в задание).
   Формула перенесена без изменений (автокорреляция с Бартлеттовым усечением), проверена на согласие
   с описанием в скрипте; капирование сверху числом календарных суток — моё решение (формула иногда
   даёt N выше сырого при отрицательной автокорреляции короткого ряда, что не может быть больше
   независимых наблюдений по построению) — не часть протокола, отмечаю явно.
5. **Δ$ клетки «пара» — не проверка гипотезы** (см. сноску ² в таблице) — эта колонка оставлена для
   полноты 2×2, а не как результат по Г-85×Г-105.

## Вердикт

По правилу §10 дословно, раздельно по клеткам:

- **H10 (Г-105):** ни один месяц не набирает ≥ 30 эффективных суток (28,1 / 20,0) → **не ясно** в обоих
  — формально это ограничение данных, не отрицательный результат. Однако точечный эффект отрицателен
  и велик в обоих месяцах (сырой доверительный интервал августа тоже не накрывает 0), а сентябрьское
  Холм-p (0,0216) прошло бы порог 0,05, если бы не эфф.N-ограничение. Порог не двигаю (правило скилла
  «ниже ~30 — выводов нет» — жёсткое), но это самый сильный из трёх результатов пакета и совпадает по
  направлению с прежним B2 17.09 (протокол §3/H10) — приоритетный кандидат на переисполнение, когда
  эфф.N перейдёт 30 (больше суток в проверке, включая досчёт п. 1 «Отступлений»).
- **H7 (Г-85):** эфф.N < 30 в обоих месяцах (14,8 / 23,0) → **не ясно**. Точечный эффект в августе
  практически ноль, в сентябре положительный, но интервал почти касается 0 и не проходит Холм. Нет
  основания ни подтвердить, ни опровергнуть.
- **Пара Г-85×Г-105:** вердикта не даю — форма вырождена кодом (0 сигналов), протокол не задавал для
  неё числового порога. Стоит зафиксировать в `HYPOTHESES.md`/пуле как отдельное наблюдение: «вход
  `single@fr` и стоп `before`/`midfr` несовместимы почти всегда в этих данных — не комбинировать без
  изменения одной из форм (например, `stop-form at` вместо `before` с `single@fr`, или лестница вместо
  фронтрана)» — решение по формулировке за протоколом-продолжением, не за этим отчётом.

## Смысл (толкование)

Стоп `before` (перед стеной) на действующем главном варианте выглядит хуже текущего `pct2`, причём
устойчиво в обоих месяцах и на двух независимых кусках данных (сожжённый поиск здесь + прежний
частичный замер B2 17.09) — это третье по счёту наблюдение в одну сторону, хотя формально ни разу не
перешедшее порог ≥ 30 эффективных суток по отдельности. Если бы это было решением, а не протокольным
шагом, я бы предложил не тратить дальнейший бюджет испытаний на `before`/`midfr` для этого варианта и
считать вопрос закрытым «поиск−» без ещё одного протокола — но это заключение за владельцем/следующим
протоколом, не за этим отчётом. Вход `single@fr` (без ступеней вглубь стены) пока не показывает ни
вреда, ни выгоды против лестницы — деньги те же, риск (просадка) не измерялся отдельно в этом отчёте
(вне бюджета задания). Совместная форма `single@fr`+`before` — это не альтернатива для проверки:
входить фронтраном и одновременно ставить стоп «перед стеной» физически почти никогда не задаёт
корректный план сделки в этом коде; для будущей проверки синергии Г-85×Г-105 нужна другая пара форм
(например, `single@fr` + `stop-form at`, у которой такого гейта нет).
