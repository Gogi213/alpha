# Красные слоты страницы здоровья за сутки — причины (16.11.2026)

Вопрос владельца: «откуда столько проблем?». Окно — 96 слотов по 15 мин, 14.11 23:45 UTC … 15.11 23:45 UTC (время в таблицах слотов — GMT+4, в остальном UTC). Источники: `/api/v3`, sysstat (10 с, `sa14/sa15`), `series-minutes.jsonl`, `stats-*.jsonl` и `events-*.jsonl` пяти коллекторов, `/data/netwatch`, счётчики ядра (`ss -ti`, `nstat`). Скрипты — `tools/health_red/`. Изменений в боевых юнитах нет.

Исходная гипотеза — наш код или обработка. Сеть названа ниже только там, где есть доказательство независимое от нашего зонда `net`.

## A. Binance + Gate

Цифры за сутки: Binance потерял 529,8 с (15 минут с потерями), 1,73 млн опозданий, 1244 пинг-таймаута; Gate — 71,7 с, 0,50 млн, 179.

**A.1 Две биржи встают вместе, три остальные — никогда.** Бины по 10 с с `lag_p99 > 2 с` (общее покрытие 6462 бина): Binance 166, Gate 233, одновременно 143 (при независимости ждали 6,0); у 157 из 166 бинов Binance Gate встаёт в пределах ±30 с. Bybit, OKX, BingX: 0 из 166. По минутам: «плохих» минут у обеих по 25 при ожидании 1,0; 10 из 11 эпизодов Binance пересекают эпизод Gate (±2 мин); Binance×Bybit 2 (ждали 0,5), ×OKX 0, ×BingX 3 (2,7). Один хост, одно ядро, одна сетевая карта, один код сбора — разное поведение по бирже. Пример тихого хоста: 19:55–19:58 UTC (cpu 17 %, диск 5 %) — на шардах book00/08/14 сообщений за 10 с падает с 3–5 тыс. до 0,4–1,2 тыс., `lag_p99` растёт с 8 до 27 с, затем залп 8–10 тыс.; Binance за 20 с: 96 тыс. → 26 тыс. → 202 тыс.; Bybit, OKX, BingX в те же 3 минуты плоские (36–49 тыс. / 110–127 тыс. / 127 тыс., лаг 126–471 мс).

**A.2 Нагрузка хоста не объясняет.** По минутам (Binance плохих 35, хороших 1016): steal 3,42 против 2,87 %, cpu 38,5 против 42,0 %, очередь 4,1 против 4,4, iowait max 0,31 против 0,21 %, util диска max 5,7 против 4,0 %. По слотам: при cpu ≥ 60 % красных 4 из 25 (16 %), при < 60 % — 7 из 69 (10 %); пять из 11 красных слотов Binance — при cpu 17–32 %. У Gate красные слоты даже менее нагружены (медиана cpu 29,5 против 37,8 %).

**A.3 Наш процесс в остановках простаивает.** В стоп-бинах Binance против обычных: `busy_max` p50 979 против 1101 мкс, `disk_write_max` p50 4,0 против 4,4 мс, `ring_blocked_ms` и `ring_full` — 0 везде, `cpu_frac` 0,001–0,004. Данные в ядро не пришли: `recvq` на этих шардах ≤ 5 КБ.

**A.4 Счётчики ядра** (живые сокеты, `rcv_ooopack` / `segs_in`): Binance 0,91 % (370 647 из 40,66 млн), Gate 0,46 %, OKX 0,09 %, Bybit + BingX 0,097 %. У Binance все 24 IP дают 0,57–1,13 % (не один плохой сервер), медиана сокета 0,92 % при минимуме 0,51; у остальных 0,09–0,10 %. Локальных потерь нет: NIC `errors 0`, `dropped 66` из 7,06 млрд, `softnet dropped 0`, `TcpExtTCPBacklogDrop / RcvQDrop / OFODrop / IpInDiscards` = 0 за 8 суток.

**A.5 Топология.** Binance и Gate — прямые соединения в AWS Токио (RTT 244–263 и 237–265 мс); Bybit и BingX идут на CloudFront (11–17 мс), OKX — на Cloudflare (16 мс). Стоят ровно две биржи с дальним путём.

**A.6 Пинг-таймауты.** Binance 1244, из них 1243 (100 %) в бине стоянки или рядом (±10 с); Gate 179 из 179. Разброс: 16 шардов book и 128 разных IP — не один шард и не один сервер. На нашем сокете `retrans/lost/unacked > 0` лишь в 49 из 1244: наша отправка не терялась; тип `pong_only` — данные идут, pong нет.

**A.7 Нагрузка влияет на цикл, но не на опоздания.** Доля 10-с бинов с `busy_max > 10 мс` при cpu < 50 / 50–80 / ≥ 80 %: Binance 1,75 / 6,5 / 14,6 %; BingX 6,8 / 17,3 / 34,8 %. Доля бинов `lag > 2 с`: Bybit, OKX, BingX 0–1 % при любой нагрузке; Binance 1,68 / 2,75 / 2,78 %; Gate 3,4–3,8 %. Тяжёлые юниты утяжеляют наш цикл, но красные слоты A они не дают.

**A.8 Сравнение с Софией (идёт).** Тот же бинарь (sha256 совпадает), те же флаги, 10 символов Binance и 8 Gate, юниты `probe-sofia-binance` / `probe-sofia-gate` в `/opt/probe-sofia`, `CPUQuota=100%`, `MemoryMax=1G`, до 05:53 UTC. К 00:03 UTC 16.11: эпизод srv 23:58:50 (Binance и Gate, ≥ 130 с, лаг до 6,4 с) — в Софии ни Binance, ни Gate не стояли; у Софии свой эпизод Binance 00:02:30 (60 с), srv в это время не стоял. Эпизодов мало (n = 1 + 1), вывод «пути независимы» предварительный. Продолжение: `tools/health_red/ab.sh <t0> <t1>`.

Достоверность A.1: `lag_p99` в статистике — скользящий, бины стоянки держатся дольше самой стоянки (длительности по бинам завышены); сопоставления строились и по минутным рядам `late` (не скользящим) — результат тот же.

**Что менять.** В нашем коде/хосте для A ничего не указано. Диагностика (по п. 13 приказов — сразу в бой): в `stats-*.jsonl` писать приращение `rcv_ooopack`, `segs_in`, `retrans` по сокетам шарда за 10 с — каждая стоянка получит ядерную метку без ручного разбора. Решение о маршруте — не из этого отчёта.

## B. Bybit ≈3 с на слот

**B.1** Всего 70 пауз с 12.11: 64 на trade-шардах, по 3 на mark и book; по часам UTC — пики 00–01 ч (24), 22–23 ч (20), 13 ч (8); по дням 13.11 — 18, 14.11 — 33, 15.11 — 17 (роста нет). Только на 15.11: 17 пауз за сутки, 11 — на шарде trade03 (символы `KMNOUSDT … PEOPLEUSDT`, малоликвидные), длительность 3002–3487 мс (медиана 3207) — сразу за порогом 3000. В 22 UTC (слоты 02:15–02:45) на trade03: медиана 104 сообщ. за 10 с (в 23 UTC — 350); максимальный разрыв за 10 с: p50 1124 мс, p90 1893, p99 3394 — порог 3 с лежит в хвосте обычного распределения шарда. Рост 8,7 → 10,0 → 13,7 с = 3, 3 и 4 паузы по ≈3,3 с в час тишины. Опозданий нет (`lag_p99 > 2 с` — 6 бинов из 8640), пинг-таймаутов 16 за сутки, в бинах стоянки Bybit — 0.

**B.2 Независимая сверка.** Архив сделок биржи (`public.bybit.com/trading`, 75 символов шарда trade03 по порядку отсортированного пула), 14.11 после запуска (11:45 UTC): окон без сделок ≥ 3 с — ровно 1 (12:19:54,511, 3,34 с); наша пауза — одна (12:19:54,630, 3087 мс), в её окне сделок нет. 1 из 1. Паузы до 11:45 не сверялись (пул был другой). Сверка 15.11 (11 пауз) — после публикации файла за 15.11 на `public.bybit.com` (на 00:03 UTC отдаёт 404): `by3.py trade03`.

**Что менять.** Считать паузу потерей только при подтверждении: порог шарда = max(3 с, k × его обычный максимальный разрыв) или проверка второй линией / REST; для шарда с малой скоростью сообщений 3 с — норма рынка. Это правка метрики страницы, не данных.

## C. 04:00 — красные все

**C.1** Столбики красные только по `late` (потерь 0): Binance 3251, Bybit 2325, OKX 4953, BingX 1823 записей в минуту 00:00 UTC. Binance, Bybit, OKX, BingX — в бине 00:00:00–:10 UTC у всех процессов разом: `busy_max` 8–45 мс (обычно ≤ 0,5), `disk_write_max` 85–125 мс (обычно 1–4), `handoff` до 27 мс; затем залп сообщений ×2–3; `lag_p99` 2,0–4,7 с.

**C.2 Гость не получал CPU.** sysstat: 15.11 00:00:04 — steal 71,64 % за 3 с и 39,16 % за следующие 10 с (user + nice + sys всего 14,8 % и 28,5 %, idle 12,5 %); 14.11 00:00:09 — 37,57 % за 8 с; 16.11 00:00:13 — 22,26 %. Пробник `netwatch` (отдельный процесс, файлов данных не касается): 15.11 в 00:00:00,8 ICMP до шлюза без ответа, до Google в 00:00:01 — без ответа, TCP-SYN до Binance 1209–1300, до OKX 664–1071 мс, к 00:00:09 всё в норме (237 / 2–4 мс); 16.11 то же (шлюз и Google без ответа в 00:00:00, Binance 1473 мс). Таймеры systemd 14.11 стартовали в 00:00:08,9, а не в :00. Из 10 выборок steal ≥ 20 % за сутки 8 приходятся на минуту :00 часа (00:00, 03:00, 08:00, 12:00, 20:00 UTC); только 00:00 был ≥ 40 % и совпал с задержкой у четырёх бирж; в стоп-бинах Binance steal ≥ 20 % лишь в 2 из 178, Gate — в 3 из 233.

**C.3 Ротация не объясняет остановку целиком.** Гость при steal 71,6 % почти не занят — CPU забирал гипервизор (KVM). Вклад нашей суточной ротации файлов в скачок `disk_write_max` исключить нельзя: контроль в Софии (тот же бинарь, 10 символов вместо 512) в 00:00:00 всплеска не показал (`busy ≤ 0,3 мс`, `disk ≤ 1,9 мс`), но нагрузка ротации там в десятки раз меньше — контролем это слабое.

**Что менять.** Слот 00:00 UTC помечать как «остановка гостя» (steal ≥ 20 % в минуту), а не красить как сбой коллектора; свои задачи на 00:00:00 не ставить (в 00:00:15 стартует суточный python-процесс `coins`). Причину у провайдера мы не знаем.

## Строка `net` — не доказательство

В 24 ч: 6,2 % ICMP до шлюза без ответа (4744 из 76 896), 3316 из них — одиночные пропуски; ядро за 8 суток: `TcpRetransSegs / TcpOutSegs` = 1 466 542 / 4 396 156 291 = 0,033 %; сокеты короткого пути (Bybit, BingX, OKX) — внеочередных пакетов 0,04–0,26 %. Если бы терялось 3–5 %, Bybit/OKX/BingX на том же хосте стояли бы. Юнит `alpha-netwatch` — `Nice=10`, `CPUQuota=5%`. Средняя потеря строки в красных слотах Binance 4,97 %, в остальных 4,09 % — различимо слабо. Строка отражает пробник, а не путь, и в причинах выше не использована.

## Гипотеза 1 (тяжёлые юниты) — итог

По sysstat cpu слотов доходит до 80–92 %, запись — до 5–11 МБ/с (ночные `systemd-run`: аудит дыр, сетка arb cross-exit, проверяющий, пересборки arb twin, arb-live; соответствие юнитов слотам по именам не сверено — журнал за сутки не читался). Красные слоты A при этом бывают и на пустом хосте (слоты 80, 81 — cpu 17–18 %), а Bybit/OKX/BingX под той же нагрузкой не опаздывают. Эффект нагрузки — доля циклов ≥ 10 мс (A.7). Гигиена, не лекарство от A и C: compute-юнитам `Nice=19`, `CPUWeight=20`, `IOWeight=10`, `AllowedCPUs=4-7`, коллекторам `AllowedCPUs=0-3`, `CPUWeight=1000`. Перенос счёта в Софию не годится: Sofia — рабочий хост (load 3,7 на 4 ядрах), счёт там запрещён.
