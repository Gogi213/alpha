# TK-334 — пороги проверки живости (alsched, В-52)

Источник: 401 прод-задание calc (`/data/sched/jobs/*.json`, юнит `own/<id>`: `usage_usec`), wall ≥ 1800 с. Файл —
`tk334-thresholds-2026-10-21.csv` (id, имя, wall, rc, заявка, max_runtime, util = ЦП-секунды / wall / заявленные ядра).

**Ограничение:** в истории только среднее за весь прогон, оконных замеров (300 с) нет — пороги окна сверены со средним,
первые живые продления (alerts.log, «ЦП … % заявки за 5 мин») их уточнят.

| группа (wall ≥ 1800 с, с util) | n | min | p5 | p10 | p25 | медиана | p75 | p90 | max |
|---|---|---|---|---|---|---|---|---|---|
| завершились сами (rc 0) | 334 | 0,00 | 0,04 | 0,06 | 0,12 | 0,38 | 0,72 | 0,99 | 1,00 |
| сняты по лимиту (rc 124) | 6 из 18 | 0,08 | | | | 0,08 | | 0,19 | 0,19 |
| прочий rc | 8 из 49 | 0,04 | | | | 0,55 | | 1,00 | 1,00 |

- `LIVE_CPU_MIN = 0,02` — ниже p5 честных (0,04), то есть отсекает только почти неработающее: честное задание с ЦП ≥ 2 % заявки
  проверку ЦП проходит. Само по себе ЦП не доказывает живость: ниже `LIVE_CPU_BUSY` нужен ещё рост чтения диска юнита
  или свежие файлы (каталог выхода, логи, cwd) за окно.
- `LIVE_CPU_BUSY = 0,5` — выше медианы честных (0,38) и p75 снизу (0,72): при ЦП ≥ 50 % заявки живость принимается без
  файлов (считает всерьёз). Без этого порога первая половина честных заданий (ЦП 2–50 %) зависела бы от файлов/диска.
- Зависшее (`sleep`, дедлок): ЦП ≈ 0,00 → «не живо» (тест (б) в `tk334-live-2026-10-21.md`).
- Что порог НЕ ловит: холостой цикл на 100 % ЦП без записи — по ЦП не отличим от счёта (как и раньше человек видит по `ps`).
