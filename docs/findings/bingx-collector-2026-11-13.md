## 1. Что сделано

- **Адаптер** — один файл `src/collector/bingx.rs` на общем ядре (приказ 16): каналы, подписка, пул, строгий разбор кадра.
- **Ядро получило три общие вещи** (Binance, Bybit, OKX не затронуты: их вывод и тесты прежние, 61 тест `collector::` зелёный): (а) `gzip.rs` + `Exchange::gzip_frames` — все кадры BingX двоичные gzip, сессия разжимает их в потоке приёма до метки лага и разбора (состояние инфлятора на сессию, CRC и длина проверяются; не разжавшийся кадр идёт как пришёл, пишется `r` и событие `bad_frame`); (б) `Exchange::heartbeat_reply` — сердцебиение прикладного уровня (`Ping` раз в 5 с → ответ текстом `Pong` сразу, иначе соединение закрывается на ≈ 31 с): сессия отвечает и дальше кадр не передаёт; (в) событие `slow_pong` (pong позже 1 с: сессия, rtt, `tcp_info` сокета) — диагностика стоянок пути короче порога `timeout`. Формат файлов не менялся.
- **Инструменты** (`tools/turbo/`): `bxsnap.py` — REST-снимок сделок сразу после окна; `restcheck.py bingx` — сверка с REST и непрерывность id по всему пулу; `steps.sh EXCH=bingx`; `coverage.py` (`first_subscribed_s`); `stepsum.py` (расхождения, лишнее, пропуски id, ошибки снимка, охват REST, поздние после covered, остановки); `reeval.sh`; `lagevents.py`, `lanelate.py` — разбор событий лага.
- Сборка и тесты — только на Софии (`CHECK_HOST=vps`, `VPS_MIN_GB` 24–25): `cargo fmt --check`, `clippy --release --all-targets -D warnings` чисто, 61 тест `collector::` зелёный (в т. ч. 6 новых: разбор кадров и сырые формы, id сделок не по порядку и личность между линиями, раскладка и подписка, правило пула, gzip-круг и повреждённые кадры, сессия на локальном источнике с gzip + `Ping` + не-gzip кадром). Бюджет линтов `tools/lint-gate.sh`: 854 при бюджете 836 — **уже на основе** (OKX @ 33e909f7), в новых и изменённых файлах `bingx.rs`, `gzip.rs`, `session.rs`, `runner.rs`, `exchange.rs` срабатываний 0.

## 3. Как проверяется правильность и чем это отличается от OKX

**REST BingX не хранит историю сделок** [измерено]: `/openApi/swap/v2/quote/trades` отдаёт только **последние 1000 сделок символа** (параметров времени и id нет); `/v1/market/historicalTrades` без API-ключа игнорирует `fromId`. REST-проход «после лестницы» (как у OKX) увидел бы окно активной монеты только на секунды (BTC — 1000 сделок ≈ 70 с). Поэтому (**отклонение от брифа, принято координатором**): `bxsnap.py` берёт REST-снимок **сразу после окна** (T0 + 181 с; сам сбор окна к этому времени кончился, процесс дописывает последние 6 с), по **всем символам пула** (самые активные первыми, 40 запросов/с при лимите биржи 50/с; 1–5 с на ступенях ≤ 160, 9–28 с на ступени 320 и во всём пуле), следующее окно ждёт конца снимка. Сверка файлов со снимком — офлайн (`restcheck.py bingx`):

- **пропуск** — сделка из REST в окне (по `time` REST), которой нет в файлах по id; в критерий — после covered;
- **расхождение** — тот же id, но другой размер или сторона, либо цена, отличающаяся больше чем на полшага **более грубой** из двух точностей (REST и WS печатают одну цену с разной точностью у ≈ 1 % сделок: `0.051573` и `0.05157`; размер и сторона совпали у всех);
- **лишнее** — записанная сделка с id внутри диапазона id снимка, которой в снимке нет (по 50 id с каждого края списка REST не судятся: у старого края REST режет по времени при id не в порядке времени; у нового — REST отстаёт, пример BTC: id отсутствует, а соседи с обеих сторон есть);
- **время сделки не сверяется**: `T` WS позже `time` REST на 4–575 мс (p50 16 мс; −5…+575 за окно) — два времени одной биржи; поэтому окно определяется по `time` REST, а файлы читаются без верхней границы времени (запись идёт ещё несколько секунд, id не в порядке времени);
- **непрерывность id по всему пулу** — id сделок BingX **сплошные по символу** (REST и WS — один `fillId`; замер подготовки: 0 пропусков в 33 385 сделках за 90 с, 892 символа): пропущенный id между двумя записанными — потерянная сделка. Это второй, независимый от REST оракул, и он охватывает **весь пул и всё окно**, а не только хвост активных монет.

Охват REST-сверки показан в строке каждого окна («охват REST»: символов за всё окно из всех / доля сделок окна, увиденных снимком). У ступеней 10–40 доля ниже (50–94 %): сделки концентрируются в 3–5 самых активных монетах, у которых 1000 сделок покрывают от 60 до 175 с окна; на ступенях 160 и выше — 96–100 %, во всём пуле 3–4 монеты охвачены хвостом (последние 82–155 с).

## 4. Лестница нагрузки

Методика OKX/Binance 13.11, один в один: один процесс BingX за раз (на srv параллельно работали `collect-binance`, `collect-okx`, `soak-bybit`, страницы здоровья — не трогались), ступени N = 10, 20, 40, 80, 160, 320 и весь пул (894 символа, топ-N по обороту `quoteVolume`), 3 окна по 3 мин на ступень, каждое окно — новый процесс `collect run --exchange bingx --lanes 2`, пул из файла ступени, пауза 20 с, один юнит `steps.sh`, строка на окно в `status.txt` (формат как у OKX + поля BingX). Критерий «чисто»: 0 обрывов живой сессии (`error`), покрытие `mark` «символ × секунда» 100 % после covered, **пропусков REST после covered 0, расхождений 0, лишнего 0, пропусков id по пулу 0**, 0 шард-секунд без сессии, все шарды подключены. Бинарь — release без PGO: `alpha-bingx-1` md5 be2ecbbe… (лестница 1) и `alpha-bingx-2` md5 b82507a2… (лестница 2: обе линии IPv4, `slow_pong`), собраны на Софии. Файлы — `/data/bingx/ladder1/`, `/data/bingx/ladder2/` на srv (`status.txt`, `status-final.txt`, `<окно>/sum.json`, `rest.json`, `rest-snap.json.gz`).

- **Лестница 1** (линия 0 — IPv4, линия 1 — IPv6, как у OKX): 13.11, 07:46–08:59 GMT+4, ступени 10…весь пул, 21 окно. Старт ступени 10 перезапускался трижды из-за ошибок проверяющего кода на краях окна (ложные пропуски id у конца окна — id не в порядке времени; ложное «лишнее» у старого и у нового края списка REST); окна n10-w1…w3 в таблице — третьего запуска, w3 оценено заново финальным проверяющим по тем же данным и снимку (`status.txt`: `STEP 10 OK`), ступени 20…весь пул шли с финальным кодом без перезапусков.

## 5. События лага — кто опаздывает: биржа или одна линия

По приказу координатора (приёмка не выдаётся, пока не объяснён каждый эпизод поздней доставки): окна со всплесками — n20-w2 (остановки на линии), n80-w2 (450 поздних, макс. 7,1 с) и n320-w2 (5 282 поздних, p99 7,9 с, макс. 14,5 с) лестницы 1. Разбор — `lagevents.py` по файлам и событиям окон (`ladder1/lagevents.json`, `ladder2/lagevents.json`), `lanelate.py` по полному захвату кадров обеих линий (`ALPHA_COLLECT_CAPTURE=1`, полный пул, 16 мин, 4,06 млн записей: `/data/bingx/cap1/`). Файлы хранят одну копию записи (писатель снимает дубль), поэтому «поздняя запись в файле» = состояние, которое **более быстрая линия не принесла**; что делала каждая линия, видно только по событиям сессий и по захвату.

**5.1. Стоянки пути на IPv6-линии (лестница 1) — одна линия, путь, не биржа [измерено].**

| окно | время от начала, с | шард (линия / адрес) | событие | `tcp_info` в момент `timeout` | pong |
|---|---|---|---|---|---|
| n20-w2 | 146,9 / 149,1 / 149,0 | `book00`, `mark00`, `trade00` — **линия 1 / IPv6** все три | `timeout` → `ping_degraded` → `entrance_switch` (reason `late_delivery`, линия 1 переходит на IPv4) → новая сессия за 0,3–0,5 с → `path_switch` через ≈ 36 с | 5 ретрансмитов, backoff 5, RTO 7,0–7,6 с, без данных 10,9 / 12,9 / 13,4 с, не подтверждён 1 сегмент, сглаженный RTT 18–34 мс | — |
| n320-w2 | 160,4 / 161,6 | `book01`, `trade00` — **линия 1 / IPv6** | то же | 5 ретрансмитов, RTO 7,2 с, без данных 9,9 / 11,1 с, RTT 22–23 мс | `book00`: pong вернулся через 7,7 с (т. 162,1), события `timeout` нет — стоянка короче 10 с |
| n80-w2 | ≈ 87–93 | `book00` (линия не определена: события нет) | — | — | pong через 5,6 с (т. 93,3) |

- **Одна линия, не обе.** Все события `timeout`/`ping_degraded` — на линии 1 по IPv6, на линии 0 (IPv4) ни одного; стоянки шли **одновременно у нескольких шардов одного процесса** (три шарда в n20-w2 с разницей 2 с) — путь IPv6 от srv, не биржа и не код (процесс и ядро одни и те же). Тот же рисунок был у OKX: «линия 1 (IPv6 основной) у трёх шардов потеряла путь: 5 ретрансмитов TCP» (`okx-collector-2026-11-13.md`, n80-w1).
- **Поздние записи — состояния, которые держала только остановившаяся линия.** Поздние записи n320-w2 лежат в окнах `E` 150–170 с (`book00` 1 811 + 15, `book01` 2 286 + 817 из 5 282; макс. 14,5 с) — ровно стоянка линии; после восстановления пути накопленные данные приходят пачкой (лаг 7–14 с). Совпавшие состояния второй линии (IPv4) пришли вовремя и сняты дедупом.
- **Почему партнёр не закрыл дыру.** Каждая линия получает от BingX **свою выборку** состояний `bookTicker` (запись по таймеру биржи на соединение): доля состояний, пришедших по обеим линиям, зависит от пары соединений — в захвате 16 мин: `book00` 99,999 %, `book02` 99,3 %, но `book01` 31 %, `book03` 28 %, `book04` 29 % (у `trade` 99–100 %, у `mark` 96–99,9 %). Там, где выборки разные (≈ 70 % состояний шарда), остановившаяся линия — это «свои» состояния на время стоянки: партнёр их не имеет. Данные не «потеряны» (покрытие `mark` 100 %, пропусков сделок нет — они одинаковы на линиях), но состояния верха книги, которые видела только остановившаяся линия, приходят на 7–14 с позже.
- **Почему сторож лага не сработал** [вывод по `path.rs`/`session.rs`]. Сторож лага (`PathWatch`: p50 лага сессии > 2 с два окна по 10 с подряд) не видит стоянку: во время неё кадры почти не идут, выборки лага (каждый 64-й кадр) мало, а после пачки лаг падает. Сработал сторож pong: нет pong за 10 с (`PING_TIMEOUT`) → `ping_degraded` → замена за 0,3–0,5 с; значит, время обнаружения = 10 с, а стоянка сама ≥ 10 с (RTO вырос до 7 с после 5 ретрансмитов). Стоянки короче 10 с (n80-w2: pong 5,6 с, n320-w2 `book00`: 7,7 с) сторож не видит вовсе: данные приходят пачкой после восстановления.
- **RTT в момент стоянки**: сглаженный TCP RTT ядра 18–34 мс (путь до края CloudFront не менялся — стоял участок после ретрансмитов), pong прикладного ping — 5,6–7,7 с; фоновый pong (путь до сервера BingX) p50 164 мс.

**5.2. Лестница 2 (обе линии IPv4) — стоянок нет [измерено].** 12 окон: `timeout`, `ping_degraded`, `slow_pong` (pong > 1 с) — **0**; в захвате 16 мин (полный пул, 30 соединений) — 0. Это то, чем закрывается п. 5.1: IPv6-линия убрана из набора по умолчанию (запасной вход остаётся IPv6: ядро сменит на него вход линии, если IPv4 перестанет подключаться).

**5.3. Что осталось и не является стоянкой пути (поздние записи при здоровых линиях) [измерено].**

- **Холодный старт сессии.** Первый кадр каждой темы после подписки несёт устаревшее состояние: лаг у книги до ≈ 3,5 с (иногда ≈ 10 с), у `mark` 2,3–3,6 с; у линии 1, подключающейся последней (бюджет 2 в секунду: 30 соединений — до ≈ 15–17 с от старта процесса), это попадает и в окно после covered. Это основная часть поздних записей на ступенях ≥ 160 (книга 98–450 на окно, без события n320-w2) и в полном пуле (1 400–2 000 записей всех видов на окно, из них после 30-й секунды окна — 0–117); данные как на бирже (В-172), в файле видно по `E`.
- **Единичные пачки старых состояний на одном соединении (источник).** В захвате (4,06 млн записей) поздних записей в установившемся режиме (сессия принимает > 25 с, лаг > 2 с) — **47** (0,001 %): `book04` 43 и `mark02` 4; все — «изолированные, одна линия» (`lanelate.py`: `one_line_only`; стоянки сессии нет: медианный лаг сессии вокруг момента 82 / 408 мс). Пример: 43 состояния 43 разных символов с `T` на 9,1–9,9 с старше пришли **в одну и ту же миллисекунду** (rx ≈ …713,23 с) по одному соединению (`PYTH`, `RAVE`, `PUNDIX`, `POL`, `PREDICT` …) — буфер сервера по этим темам задержан ≈ 10 с и сброшен разом; у `mark02` два символа акций (`NCFXNZD2USD`, `NCSKACN2USD`) с `E` на 2,2–3,2 с старше, тоже в одну миллисекунду. Обе линии одновременно с одним и тем же старым состоянием не пришли ни разу (**«обе линии поздно по одному E» — 0 случаев**); партнёр этих состояний не имеет (другая выборка). Лестница 2 даёт тот же порядок: 0–117 записей на окно после 30-й секунды, макс. 10,1 с (в n320-w2 — до 16,1 с).
- Такие записи **не теряют данные** (покрытие 100 %, REST и id чисто) и не сторожатся ядром (путь здоров); **исправить их на нашей стороне нельзя**, видны в файле по `lag`.

**Вывод по лагу.** Эпизоды лестницы 1 (n20-w2, n80-w2, n320-w2) — стоянки пути на IPv6-линии одного процесса (TCP: 5 ретрансмитов, до 13 с без данных); они объяснены, устранены выбором IPv4 для обеих линий, повтор ступеней 20/80/320/весь пул — 12 окон без остановок. Остаток — холодный старт сессии (≈ 3,5 с, редко 10 с) и редкие (≈ 1 на 90 тыс. записей) пачки старых состояний на отдельных соединениях со стороны биржи.
