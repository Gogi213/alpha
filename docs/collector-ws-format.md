# Формат данных WS-коллекторов G-022 (В-133)

Один формат на все шесть бирж; источник истины — начало `tools/collector/wscore/codec.py` (docstring) и тест `test_roundtrip_records_exact`. Выбор формата и замеры — `docs/findings/tk527-binance-ws-2026-11-11.md` («Итоговый формат»). Состав: лучшие bid/ask с размером, сделки, mark/индекс/фандинг, пинг (В-115: глубины нет).

## Файл

`<root>/<день UTC>/<шард>-<запуск>.tsv.zst` — один файл на шард и сутки UTC; `<запуск>` = время старта процесса (с). Внутри — zstd (уровень 1), строки `поле<TAB>поле…\n`. Читать с `read_across_frames=True` (на сбросе писатель начинает новый zstd-кадр). Закрытые сутки неизменяемы: рядом `<файл>.ok` с числом записей. Сброс на диск не реже раза в 1 с (A8: ≤ 10 с; Rust-ядро — `--flush-ms`, по умолчанию 100 мс). Повторы при перекрытии соединений и линий снимает писатель, не читатель: запись — дубль, если её личность уже была за последние 120 с (Binance: book — u, trade — a, mark — E; Bybit: book — `seq`, trade — UUID сделки, mark — ts). Порядок в файле — порядок прихода; запись с меньшим ключом, пришедшая позже и ещё не виденная, пишется (читателю при необходимости — сортировать по ключу). Python-ядро снимало «ключ не больше записанного»: у Bybit `u` у входов com и kz — свои счётчики, и вторая линия отбрасывалась целиком. Остановка процесса: все сессии пишут `closed`, затем писатель закрывает файл — кадр zstd завершён (`zstd -t` проходит), `.ok` = число строк, `closed` — последняя строка (G-022: прежде `closed` писался после закрытия писателя и оставлял в конце файла незавершённый кадр; такие файлы запусков до 12.11 читаются — данные до `closed` целы, но `zstd -t` на них падает, а время приёма последней строки неверно).

## Записи (первый столбец — тип)

Числа биржи (цена, размер, ставка) — строками как пришли (В-172). `dns` — приём в нс минус приём предыдущей записи файла (первая в файле — абсолютное время приёма, нс UTC). `lag` = приём_мс − E (задержка прихода, включает сеть; чистка от сети — по записям `g`, В-137).

| тип | столбцы после `dns` | смысл |
|---|---|---|
| `b` | lag, ET, sym, du, bid, bsz, ask, asz, bn, an | лучшие bid/ask; ET = E − T; du = u − u предыдущей записи символа (первая в файле — абсолютное); **bn, an** (Rust-ядро, хвостовые столбцы с 13.11, только OKX; у Binance и Bybit столбцов нет — строка кончается на `asz`) — число ордеров на лучшем bid / ask (четвёртый элемент уровня `bbo-tbt`) |
| `t` | lag, ET, sym, da, p, q, lf, f, m, nq, x, i | сделка; da = a − (a предыдущей + 1), lf = l − f, f = f − (l предыдущей + 1), m = 0/1 (покупатель — мейкер), nq — только если ≠ q; **x** (Rust-ядро, хвостовой столбец с 12.11; в старых файлах его нет — читать как пусто) — признаки сделки: пусто — обычная, Bybit: `R` — RPI, `B` — блок-сделка, `BR` — обе; OKX: `E` — `source` = 1 (в документации WS «Enhanced Liquidity Program order», в REST — «RPI order»); **i** (Rust-ядро, хвостовой столбец с 12.11, только Bybit; у Binance столбца нет — строка кончается на `x`, файлы Binance не изменились) — id исполнения биржи строкой (UUID `execId`): по нему читатель снимает дубли между файлами двух процессов при передаче и между запусками (ключ `a = seq·1000 + номер в пачке` у двух входов расходится на 1,7 % сделок) |
| `m` | lag, sym, p, ap, P, i, r, T | mark p, индекс i, ставка фандинга r, время следующего начисления T; ap, P — если есть у биржи, иначе пусто |
| `g` | rtt_us | пинг WS: время до pong |
| `c` | what, detail | служебное: `connected` / `subscribed` / `closed` (detail — сессия, адрес) |
| `r` | кадр | то, что адаптер не разобрал точно (ответ на SUBSCRIBE, новые поля, неожиданная форма): кадр как пришёл; у массивов (mark Binance, пачка сделок Bybit) — только негодные элементы, в кадре той же формы, остальные элементы — обычные записи. Кадр данных (в нём есть время биржи), байт в байт виденный за последние 60 с на другой линии, — дубль: писатель его не пишет (как и разобранные записи); ответы на подписку и pong пишутся все |

Разности точные и обратимы: `codec.decode()` восстанавливает абсолютные значения; тест на равенство — в `test_wscore.py`. Читатель разбирает строку `split('\t')` ≈ 1 млн строк/с на ядро.

## Что обязан дать адаптер биржи

Контракт — `tools/collector/wscore/session.py`; список «что написать для Bybit» — отчёт, раздел «Что придётся написать для Bybit». Если у биржи нет поля формата (например, `ap`, `P`), столбец остаётся пустым, формат не меняется. Новое поле биржи сначала попадает в `r`; в формат вводится отдельным решением и версией, не молча.

## Здоровье

`/data/health/<биржа>.json`, схема 1 — `docs/findings/collector-health-format-2026-11-11.md`.

## Реализации и расширение формата

Формат пишут два ядра с одним форматом: Python `tools/collector/wscore/` (боевое до перевода) и Rust `src/collector/` (`alpha collect run`, G-022 / В-148, `docs/findings/g022-turbo-collector-2026-11-12.md`). Источник истины для Rust — `src/collector/codec.rs` (`Encoder`/`Decoder`, тест `codec_roundtrip_exact`); читатели (`accept_ws.py`, П-40) работают с файлами обоих без правок. Что Rust-ядро делает иначе, не меняя формата:

- **Время приёма записи неубывающее.** Кадры разных соединений проходят общую очередь; приём кадра, пришедшего в очередь «раньше» предыдущей записи файла, поднимается до приёма предыдущей (`dns` ≥ 0 всегда); счётчик `rx_clamped` в health — число **записанных строк** (не снятых дублей) с поднятым `rx` (до 14.11 счётчик считал и дубли, поэтому давал ≈ 1 % на Binance — завышение), размер поднятия — `rx_clamp_us` (p50/p99/p99.9/max за 60 с, по классам пар «тот же сокет / та же линия, другое соединение / другая линия / служебная строка» и возраст элемента на входе в писатель). Измерено 13.11 при ядерных метках: Binance 0,009–0,02 % строк, Bybit 0,003–0,014 %, OKX 0,007–0,04 %, размер медиана < 1 мс (макс до 12 мс); BingX — 0,28–1,25 % со стартовым хвостом до 3 с (кадры стояли в очереди ядра, пока подписка шла блокирующим потоком), с подпиской из реактора (`--sub-in-reactor`) 0,013–0,07 %, ≤ 4 мс. Выдержка перед записью (`--rx-hold-ms`, сортировка с запаздыванием) убирает остаток ценой задержки записи на диск, по умолчанию выключена. Формат технически хранит и отрицательный `dns` (десятичное целое), но читатели вправе считать `rx` неубывающим — контракт не меняется.
- **Метка приёма `rx` (collector-perf, решение координатора 13.11; формат файла не меняется).** До даты переключения `rx` — **пользовательская** метка: время нс UTC, снятое потоком приёма после возврата из чтения (пробуждение потока добавляет к настоящему приходу пакета p50 ≈ 114 мкс, p99 ≈ 0,5 мс, p99.9 ≈ 1,2–1,5 мс — замер 13.11, `docs/findings/collector-perf-2026-11-13.md` §1.5). После переключения (запуск с `--reactor --rx-stamp kernel`) `rx` — **ядерная метка приёма записи TLS** (`SO_TIMESTAMPNS`, режим `exact`, так работает боевой запуск): реактор находит границы целых записей TLS (`MSG_PEEK`) и снимает каждую своим `recvmsg(MSG_TRUNC)`; метка — время вхождения в ядро самого нового пакета, вошедшего в эту запись (если ядро склеило нечитанные сегменты, `tcp_try_coalesce`, у склеенных метка самого нового); кадр WS из нескольких записей получает метку записи, которая его завершила. Следствия: (1) ошибка метки **не ограничена окном реактора W** (режим «одна метка на чтение» с ошибкой ≤ W в бою не используется): измерено G4 (локальный TLS-источник, `rx` − время отправки): p50 67–112 мкс, p90 299–734 мкс, p99 3,4–5,9 мс, p99.9 не хуже прежней пользовательской метки при W 5–10 мс (Binance 10,8 против 13,9 мс, OKX 13,4 против 16,3 мс); предел точности — склейка ядром и сеть; распределение «пользователь − ядро» по чтениям пишется в health (`reactor.user_minus_kernel_us`: p50/p99/p99.9); (2) запись, пришедшая по двум линиям, берётся с **минимумом** метки (пачка шарда сортируется по метке до снятия дублей; запись закрытой пачки не переписывается); (3) метка не зависит от пробуждения потока, нагрузки CPU и длительности разбора соседних кадров; (4) абсолютная точность ограничена часами хоста (chrony: смещение, RMS и дисперсия корня — в health `host.clock`; на srv 13.11: +68 мкс, RMS 271 мкс, дисперсия 0,62 мс, без PHC) — для относительных сравнений (опережение между биржами внутри одного хоста) выигрыш реален, для абсолютной задержки биржа→хост нет; (5) разрыв семантики в непрерывном наборе данных: до и после переключения `rx` отличается в среднем на 0,1–0,5 мс (ядерная раньше) и на ошибку пачки; **дата и время переключения** — по биржам, UTC / GMT+4: OKX 2026-11-13 20:32:05.758 / 14.11 00:32:05, Bybit 20:35:28.305 / 00:35:28, BingX 20:38:46.402 / 00:38:46, Binance 20:42:02.139 / 00:42:02; признак источника метки на каждом запуске — строка `{"ts_ms", "version", "rx_stamp": "user"|"kernel", "mode": "exact"|"none", "reactor", "window_us", "worker_inline", "sub_in_reactor", "rx_hold_ms"}` в `rx-stamp.jsonl` каталога данных биржи (поля `mode`, `sub_in_reactor`, `rx_hold_ms` — с сборки `final6g` (e528d57a): OKX 13.11 23:32:35, Bybit 23:33:38, BingX 23:34:52, Binance 23:35:55 UTC; строки раньше без `mode`, все боевые запуски `final5` и позже — режим `exact`, `rx_hold_ms` 0) (суточный манифест и формат файла данных не менялись, В-172). Записи между последней остановкой прежнего процесса и первой записью нового отсутствуют (1–4 с на подключение и подписку). Остальное (неубывание `rx` по файлу, `rx_clamped`) — как ниже.
- **Сутки закрываются по часам.** Файл ушедших суток закрывается (`.ok`) через 5 с после полуночи UTC, не дожидаясь первой записи нового дня; смена суток по приёму записи — как у Python. Запись ушедших суток, пришедшая в очередь уже после закрытия (обратное давление дольше 5 с), закрытый файл не открывает: её приём поднимается до полуночи (счётчик `rx_clamped`), запись идёт в файл новых суток.
- **Сбой записи на диск не рвёт кадр.** Блок, не записанный из-за ошибки диска, дописывается тем же кодировщиком zstd с места сбоя (раз в секунду): файл остаётся одним кадром, счёт строк для `.ok` не сбрасывается, «оборванного» кадра посреди файла нет. Блок отбрасывается (`blocks_dropped`) только если кодировщик не принял из него ни байта.
- **Холодный старт.** Шард без единого соединения берёт место в бюджете подключений раньше второй линии и замен покрытых шардов и принимает путь сразу, даже медленный (RTT > 300 мс): данные пишутся с первой секунды, события `path_slow_accepted` (`why: uncovered`); улучшение пути — позже заменой без разрыва (`path_upgrade`, при неудаче `upgrade_timeout` — прежняя сессия остаётся).
- **Bybit, `b`: столбец `du` — разность сквозного `seq`**, не `u` соединения: `u` у каждого входа Bybit свой (замер 12.11: одно состояние книги — `u` 79 205 427 у com и 858 576 у kz при одинаковых `seq` и `cts`); `seq` сравним между входами и растёт по символу. Соединение-локальный `u` в файл не пишется (он есть в `ALPHA_COLLECT_CAPTURE`-захвате кадров).
- **Две линии Bybit дополняют друг друга.** L1 Bybit — снимки каждые ≈10 мс при изменении, и у разных входов набор состояний разный: из 429 891 различных состояний за 7 мин 150 984 (35 %) пришли по обеим линиям, остальные — по одной; запись объединения даёт на 58 % больше состояний, чем любая одна линия (`tools/turbo/lanecmp.py`).
- **Копии сырых кадров** снимает счёт доставок по сессиям: кадр с временем биржи, который другая сессия (линия, замена при перекрытии) уже принесла больше раз, чем эта, — копия; повтор того же кадра той же сессией — настоящая вторая доставка и пишется.
- **Первый `c connected` и последний `c closed` файла** — записи сессий; `closed` всегда до закрытия кадра zstd (порядок обеспечен очередью: писатель получает `Shutdown` после того, как все сессии закончили).

**Расширение.** Новое поле биржи сначала попадает в `r`; в формат вводится отдельным решением и версией. Допустимый способ расширения без поломки читателей — **хвостовые столбцы** записи (читатели обращаются к столбцам по номеру; нет хвоста — пусто): число ордеров на уровне у `b`, источник/вид сделки у `t` (OKX `source`, Bybit RPI), метаданные символов (`ctVal`) — рядом с пулом (`pool-<день>.json`), не в потоке. Решения координатора (12.11): `mark` пишется как шлёт биржа, без прореживания (В-172).

## События, статистика, health (Rust-ядро)

Рядом с данными: `events-<шард>.jsonl` (события `connected`, `subscribed`, `path_ok`/`path_rejected`/`path_rejected_rtt`, `path_switch`, `path_upgrade`, `rotated`, `entrance_switch`, `switch_timeout`, `upgrade_timeout`, `path_slow_accepted`, `timeout` (нет pong за 10 с; поле `data_alive` — шли ли при этом кадры), `ping_degraded` (нет pong и нет кадров — путь испорчен), `gap`, `error`, `closed`, `stopped`, `connect_wait`, `slow_pong` (pong позже 1 с: сессия, rtt и `tcp_info` сокета — стоянки пути короче порога `timeout`), `bad_frame` (кадр не разжался как gzip; BingX)), `stats-<шард>.jsonl` (окно 10 с: поля Python-ядра `msgs`, `bytes`, `max_gap_ms`, `lag_p50_ms`, `lag_p99_ms`, `cpu_frac`, `dups` + `ring_depth_max`, `ring_full`, `ring_blocked_ms`, `queue_lag_p99_ms`, `recvq_max`, `recvq_behind`, `busy_max_us`, `handoff_max_us`, `sink_depth_max`, `disk_write_max_us`), `pool-<день>.json`. `health.json` — схема 2 = схема 1 + `backpressure`, `process`, `totals`, `shards` (`src/collector/health.rs`); страница `tools/collector_health` читает обе схемы.

## OKX (Rust-ядро, G-022, 13.11)

Адаптер `src/collector/okx.rs`, разбор и решения — `docs/findings/okx-collector-2026-11-13.md`. Записи: `b` — `bbo-tbt` (`u` = `seqId`, E = T = `ts`, `bn`/`an` — число ордеров); `t` — `trades` (агрегат тейкерского ордера: `a` = `l` = `tradeId`, `f` = `tradeId − count + 1`, `m` = `side` = sell, `x` = `E` при `source` = 1); `m` — по записи на каждый кадр `mark-price` (E = `ts`, p = `markPx`, i = последний `idxPx` из `index-tickers`, r = последний `fundingRate`, T = `fundingTime` из `funding-rate`; ap и P пусты). Кадры `index-tickers` и `funding-rate` — состояние символа, отдельных записей нет; первые кадры `mark-price` до их прихода (≈ 1 с после подписки) пишутся как `r`. Личность записи для снятия дублей: `seqId`, `tradeId`, `ts` кадра `mark-price`. Не в формате: `seqId` сделки, `high24h`/`low24h`/`open24h`/`sod*` индекса, остальные поля `funding-rate`; метаданные контрактов (`ctVal` и др.) и оборот пула — в `pool-<день>.json` (`meta`, `qv`).

## BingX (Rust-ядро, G-022, 13.11)

Адаптер `src/collector/bingx.rs`, разбор и решения — `docs/findings/bingx-collector-2026-11-13.md`, подготовка — `docs/findings/bingx-ws-prep-2026-11-12.md`. Записи: `b` — `bookTicker` (склеен биржей по времени, ≈ 2,6 записи/с на символ; E = `E`, T = `T`, `u` = `u` соединения; bid/ask и размеры строками как пришли; `bn`/`an` нет); `t` — `trade` (пачка 1–8 сделок в кадре → запись на сделку: `a` = `f` = `l` = `t`, `m` = `m` («покупатель — мейкер»), размер в монете; вида/источника у сделки нет — `x` пуст); `m` — запись на каждый кадр `markPrice` (E = `E`, p = `p`; **i, r, T пусты** — индекса и ставки в потоке нет, они только по REST `premiumIndex`; ap и P пусты). Все кадры биржи — двоичные gzip: ядро разжимает их в потоке приёма (`gzip.rs`, CRC и длина проверяются) до метки лага и разбора; не разжавшийся кадр идёт дальше как пришёл (запись `r`) и пишется событие `bad_frame`. Сердцебиение — текст `Ping` раз в 5 с (в gzip), ответ текстом `Pong` сразу в потоке приёма; сами `Ping`/`Pong` в файлы не пишутся (это не данные). Пинг `g` — протокольный ping ядра (биржа отвечает протокольным pong: ≈ 177 мс — путь до сервера за CDN, а не до его края).

Личность записи для снятия дублей между линиями и заменами: book — `(символ, T)` (**`u` у каждого соединения свой**, одно и то же состояние приходит с разными `u`), trade — `t` (id сделок приходят **не по порядку** у 1–6 %: дубль — по множеству виденных id, не по «≤ последнего»), mark — `E`. Id сделок BingX по символу **сплошные** (REST и WS — один `fillId`; замер 12.11: 0 пропусков в 33 385 сделках): пропуск id в записанном диапазоне — потерянная сделка; `restcheck.py bingx` проверяет это по всему пулу. Метаданные контрактов (`size`, `quantityPrecision`, `apiStateOpen` и др.) и оборот пула — в `pool-<день>.json` (`meta`, `qv`).
