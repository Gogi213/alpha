## B1. Окно проверки паузы (`pausecheck.rs`): концы по приёму кадров, срез конца по p99 лага шарда

Требование проверяющего: оба конца паузы — по времени приёма кадров (не по тику надзора 500 мс); конец окна срезать на **измеренный p99 лага шарда**, а не на фиксированные 500 мс; тест на реальных паузах.

**Реальные паузы `trade01` Bybit 16.11 (srv, процесс `3835be7b`, 1 509 106 записей, лаг p50 / p99 / p99,9 = 107 / 133 / 319 мс).** `start` — `gap_start_ms` из `gap_end`; `tick_end = start + gap_total_ms`; приём — `rx` последней записи до и первой после (мс UTC); `e` — время биржи (мс), лаг в скобках:

| # | start | gap_total | tick_end | последняя до: rx / e (лаг) | первая после: rx / e (лаг) |
|---|---|---|---|---|---|
| 1 | 1794811416603 | 3510 | 1794811420113 | 1794811416591,3 / …416485 (106) | 1794811420268,1 / …420161 (107) |
| 2 | 1794812144854 | 3694 | 1794812148548 | 1794812144837,7 / …144731 (106) | 1794812149010,3 / …148903 (107) |
| 3 | 1794815156398 | 3065 | 1794815159463 | 1794815156383,1 / …156272 (111) | 1794815159594,1 / …159487 (107) |
| 4 | 1794816767437 | 3300 | 1794816770737 | 1794816767424,9 / …767318 (106) | 1794816770920,4 / …770809 (111) |
| 5 (09:20) | 1794818433616 | 3174 | 1794818436790 | 1794818433593,0 / …433486 (106) | 1794818437130,1 / …437023 (107) |

Что видно: `start` у надзора выше приёма последней записи на 12–23 мс (`now_ms() − gap`), `tick_end` **раньше** приёма первой записи после паузы на 131–462 мс (шаг тика, `gap_peak` — наибольшее молчание на тике). Лаг пяти краевых записей 106–111 мс (≤ p99 133): доставленная запись после паузы имеет время биржи ≥ `end_rx − p99`.

**Что сделать:**
1. Начало: `gap_start = metrics.last_frame_ms` (приём последнего кадра, мс UTC) на обнаружении паузы (`shard::supervise`, ветка `gap > thr`), а не `now_ms() − gap`.
2. Конец: в `session::frame` (на кадре уже стоит `last_frame_mono_ms.store`) — прочитать прежнее значение, а при молчании ≥ `GAP_TIMEOUT_MS` (3000, сделать `pub(crate)`) записать приём этого кадра (мс UTC, `rx`) в новое поле `ShardMetrics::gap_resume_ms` (`AtomicI64`); при конце паузы надзор берёт его как конец (если оно ≥ начала паузы; иначе — пауза закончилась обрывом соединений: конец `start + gap_peak`, `end_exact = false` в событии). Ничего тяжелее `load` + условного `store` на кадр.
3. p99 лага шарда — на **обнаружении** паузы (в окне 60 с ещё нет задержанной пачки после неё): `metrics.writer().lag_in[1]` (вид «сделки») `.snapshot(now_ms).percentile(0.99).map(us_to_ms)`, округление вверх; в запрос `PauseReq` — поле `lag_p99_ms: Option<i64>`; нет значения — запасное `LAG_FALLBACK_MS = 500` (назначаемое, Судье).
4. Окно: `lo = start_rx`, `hi = end_rx − lag_p99`; `hi ≤ lo` — вердикт `unverified` (`window_empty`). Убрать `EDGE_MS`. В событие `pause_check` добавить `lag_p99_ms`, `window_lo`, `window_hi`, `end_exact`.
5. Тест: пять реальных пауз из таблицы (константы) — крайние доставленные записи (время биржи последней до и первой после) **не** попадают в окно, середина паузы — попадает; REST с одними краевыми сделками → `Quiet`, со сделкой в середине → `Loss`. Для сравнения — что старое окно (`tick_end`, 500 мс) отличалось. Обновить тест края окна (`a_pause_with_no_exchange_trades_inside…`) и `docs/collector-ws-format.md`, `docs/archive/findings/collect-next-2026-11-16.md` §1.

## Порядок выкладки (добавить в отчёт и `COMMANDS.md`)

`v3.py` с разбором поздних строк ряда (`read_series`) должен встать **раньше или вместе** с коллектором: прежний `v3.py` присваивает `rows[t // MIN] = […]` на каждую строку с `t`, поздняя строка `{"t", "lost_ids_late"}` перезаписала бы строку минуты нулями (потеря строки минуты, столбики пропали бы). Порядок: страница (копированием, `*.prev-<метка>`) → затем коллектор.

## BingX: лаг и раскладка первого запуска (вывод проверяющего: причина — наша раскладка)

Проверяющий: первый запуск `3835be7b` раскладывал шарды по обороту (сохранённой нагрузки не было), `trade03` получил ×1,4 нагрузки (лаг 82 → 119 мс), `trade04` ×2,4 (89 → 105 мс). Это противоречит выводу исполнителя «не найдено» (`collect-next-2026-11-16.md` §5): тот вывод опирался на сдвиг только двух шардов и узлы CloudFront, но нагрузку по шардам до/после не сравнивал. **§5 отчёта пересмотреть после измерения.**

Что известно:
- Раскладка при старте: `runner.rs` (≈ стр. 480) — `SavedState::load(&args.root)` → `Weights::new(saved.rates, &start_qv)` → `spread_plans`, если `weights.informative()` (есть измерения **или** оборот). Без `pool-state.json` веса — оборот × 1e-6 (условные единицы), раскладка выравнивает оборот, не кадры/с. Файл теперь пишется после каждого опроса (`SavedState::save`), на живых биржах он есть (`pool-state.json` в корне каждого коллектора) — следующий перезапуск возьмёт измеренные веса.
- Нагрузка шардов до/после измеряется по `stats-<шард>.jsonl` (`msgs` за 10 с, см. `/tmp/bx_lag.py`-подобный разбор в `collect-next-2026-11-16.md` §5): взять средние `msgs`/10 с по шардам за 02–06 и 08–09 UTC 16.11 и сравнить с ростом лага.

**Что сделать:**
1. Измерить: нагрузка шарда (кадры/с, среднее по часам) до и после для всех шардов сделок и книги BingX (+ корреляция «нагрузка → лаг» по часам и шардам; по данным 14.11–16.11 есть смены раскладки между запусками).
2. Первый запуск без `pool-state.json`: брать измеренную нагрузку предыдущего запуска. Вариант: при пустых `rates` читать хвост последних файлов данных (`<корень>/<день>/<шард>-<запуск>.tsv.zst`: кадры zstd независимы — искать границу кадра `28 B5 2F FD` от конца файла, декодировать вперёд; считать записи по символу и виду за последние 5–10 мин) и строить `Rates` для `spread_plans`; нет и этого — раскладка не по обороту, а прежняя (алфавитная, `exch.plan`) — это не хуже предыдущего запуска. Либо разовый скрипт `seed_rates.py` пишет `pool-state.json` (`last_above: {}`, `rates`) до первого запуска (проще, но не закрывает код).
3. Показать «до/после» оценку нагрузки по шардам (`Layout::loads()`): раскладка предыдущего запуска (по `pool-<день>-<запуск>.json`) vs раскладка первого запуска (оборот) vs раскладка по измеренным весам — тест / `#[ignore]`-прогон на srv по `pool-state.json` BingX.
