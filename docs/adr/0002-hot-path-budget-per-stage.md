# Бюджет горячего пути — по этапам, не только целиком

*Источник: спека §3; PLAN.md D-РЕАКЦИЯ, D-ОРДЕР, D-HOR; манифест A04 (R79)*

## Контекст

Плотности в стакане живут секунды; владелец потребовал систему, которая
«супер быстрая сразу», чтобы не платить издержками времени, когда методика
подтвердится (R79). Первая формулировка мерила только весь путь целиком:
`recv → разбор → книга → триггер → send`.

## Решение

Путь бюджетируется по этапам (разбор, книга, триггер, ордер) и одновременно
гейтится целиком: `p99 < 5 мс` на живом потоке. Ноль аллокаций после
прогрева, время только через `Clock`, книга — предвыделенное кольцо. Ордер
собран и подписан **до** триггера — триггер делает только `send` по тёплому
аутентифицированному WS. Горизонт, до которого система не успевает
(`p99` реакции > 20% его длины), помечается `unreachable` и не входит в
вердикт.

## Почему

Рассмотрели и отвергли бюджет только на сумму всего пути — отвергнуто (A04):
превышение общего бюджета нельзя локализовать, не зная, на каком именно
этапе оно возникло.

Рассмотрели и отвергли сборку и подпись ордера в момент триггера — отвергнуто
(D-ОРДЕР): единственное ускорение, не стоящее ни денег, ни нового хоста, —
это порядок операций, и терять его ради «более простого» кода не стали.

Рассмотрели и отвергли молчаливое включение недостижимых горизонтов в общий
отчёт наравне с достижимыми — отвергнуто (D-HOR): это обещало бы эдж там,
куда система физически не успевает.

## Последствия

Каждый таск, трогающий код на пути `recv → send`, обязан проходить гейт GC:
clippy/fmt в ноль, ноль аллокаций, байт на запись, CPU/RSS на десяти
инструментах сразу, лимит топиков. Часть горизонтов (в первую очередь самые
короткие) может оказаться помеченной `unreachable` уже сейчас — это не
повод расширять бюджет искусственно, а факт, с которым отчёт обязан жить.
