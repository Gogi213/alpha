Решения (замер не нужен — поток ~десятки событий/час, узкое место — корректность ack/удержания, не скорость; В-170 так и фиксирует):
- Хранилище: sqlite3 (stdlib, WAL), не jsonl — ack, удержание и дедуп по id атомарны одной транзакцией. Таблицы: events(seq AUTOINCREMENT, id UNIQUE, addr, ts, payload), deliveries(seq, recipient, state pending|held|acked, held_for, first_sent, acked_at), blocked(tk, reason). Повторный POST с тем же id → тот же seq, без новой доставки.
- HTTP (http.server, ThreadingHTTPServer), заголовок Authorization: Bearer <токен из файла /etc/alpha-bus/token, 0600; в репо только имя>. POST /event; GET /q/<получатель>?after=<seq>&wait=25 (long-poll, отдаёт неподтверждённые с seq>after по порядку); POST /ack {recipient, seqs}; GET /health; GET /stale (очередь «не обработано»). До ack событие остаётся и пере-выдаётся при переподключении (клиент дедупит по id).
- Маршруты: routes.json (адрес-шаблон с * → получатели dispatcher|board|ceo; роль-исполнителя диспетчер берёт из шапки тикета, не шина). Адреса: задача.<TK>.задание.готово|упало|ход, машина.<host>.юнит.остановлен, сборка.готова|упала, задача.<TK>.сдано|вопрос_владельцу|статус|блокер.поставлен|блокер.снят.
- Блокеры: шина не видит тикеты (они на ПК), поэтому источник — события задача.<TK>.блокер.поставлен/снят, которые шлёт tickets.py при смене status (blocked/needs_owner/открытый вопрос/depends на незакрытый) и при done зависимости; диспетчер при каждом подключении шлёт полный снимок блокеров (лечит расхождение). Событие для TK из blocked → delivery.state=held, не будит; блокер.снят отпускает все held этого TK по порядку seq.
- «Не обработано»: N=10 мин (предлагаю; поправь, если надо) — delivery pending/выдано без ack дольше N → в /stale и событие ceo-stale для получателя ceo; диспетчер пишет его в ceo-wake.log; если диспетчер лежит, Monitor CEO читает /q/ceo напрямую.
