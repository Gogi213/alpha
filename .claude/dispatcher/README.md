# Диспетчер задач alpha (v1.5, по образцу Paperclip)

Вместо четырёх постоянных чатов ролей — очередь тикетов `.claude/tickets/*.md` и цикл, который сам
решает, кого будить `claude -p`. Только stdlib (`ticket.py`, `dispatch.py`, `tickets.py`, `watch.py`).

## v1.5 (CEO, боевой TK-005) — заголовок `### <ISO> <автор>` необязателен

Инженер дважды дописал лог строками без заголовка («- 27.09 ~23:50 (инженер, запуск 1) …») — диспетчер
считал записью только `### <ISO-время> <автор>` и дважды заблокировал живую задачу (ложный `blocked`).
Роли пишут по-разному (Исследователь — «- 27.09 23:25 [researcher]»). Теперь «роль написала что-то» =
**выросла секция «## Лог»** (`len(Ticket.log_raw)` на старте запуска против после — `T.log_section_text`/
`log_len_at_launch` в `state.json["sessions"]`), заголовок не обязателен. Упоминания `@роль` тоже
разбираются в строках без заголовка (`T.mentions_since()`): для текста внутри уже заголовленной записи
автор известен точно (самоупоминание/`dispatcher` исключаются, как раньше); для голых строк без
заголовка автор не определяется — упоминание НЕ исключается (пропущенный сигнал дороже лишнего
повтора). Промпт роли теперь называет явную команду для записи: `python .claude/dispatcher/tickets.py
comment <ID> --author <роль> --text "..."` (пишет верный заголовок сама). `wait_for: deck:` с
вложенным путём-маркером (`~/alpha/queue/done/<ID>.job`) — работает тем же фиксом v1.1 (тильда без
кавычек), проверено вживую (`~/alpha/queue/done/` на деке существует).

## Формат тикета — `.claude/tickets/<ID>.md`

Шапка между строками `---`, простые `ключ: значение`:
`id, title, owner` (researcher|engineer|judge), `status`
(backlog|todo|in_progress|waiting|in_review|done|blocked|needs_owner), `reviewer` (опц.),
`wait_for` (опц.: `file:<путь>` | `deck:<путь>` через ssh | `mention`), `updated`.
Тело — описание, затем `## Лог`: записи `### <ISO-время> <автор>` + текст; упоминания
`@researcher`/`@engineer`/`@judge`/`@ceo`. Автор и роль в упоминаниях — латинские ключи, не русские
названия. ID по умолчанию `TK-NNN` (своя нумерация, не путать с `T-NN` из `TASKS.md`/прозы CLAUDE.md).
`backlog` — перенесённая, но ещё не взятая в работу задача: диспетчер её не трогает ни по одному
правилу (даже упоминание не будит); `tickets.py start <ID>` переводит в `todo`.

## Кого будит `dispatch.tick()`

(а) `todo` → роль-владелец. (а') `in_progress` без активного запуска → роль-владелец, «продолжить»
(v1.2: без этого многошаговый тикет замирал навсегда после первой сессии — устав ролей обещает
продолжение другой сессией, а будить было некому). (б) новая запись лога с `@роль` после последнего
запуска этой роли по задаче → эта роль (любой статус, кроме `backlog`; не считаются упоминания в
записях автора `dispatcher` и самоупоминания — роль пишет `@себя` как заметку, не как будильник; `@ceo`
не запускает роль — строка в `ceo-inbox.md`). (в) `waiting` и условие `wait_for` выполнено (`file:`/
`deck:`/`ticket:<ID>` — ждать, пока другой тикет станет `done`) → владелец задачи; `mention` само не
снимается, ждём (б). (г) `done` с заданным `reviewer` → `in_review`, будит ревьюера — но не когда
последняя запись лога уже от самого ревьюера (или `dispatcher`): это штатный конец состоявшегося ревью,
не новый раунд (v1.2: раньше сверялось по `updated`-таймстампу, который становится новее записи
ревьюера сразу как роль проставляет `status` после `append_log`, и ревьюер получал повторный запуск за
свой же вердикт — особенно больно при `SESSION_SCOPE="role"`, где это единственная сессия). (д) прогон
завершился без пригодного результата — один повтор с напоминанием, второй раз подряд → `status: blocked`
+ строка в `ceo-inbox.md`. «Без пригодного результата» — это ИЛИ новой записи роли в логе нет, ИЛИ
запись есть, но `status` так и остался `todo` (роль забыла увести задачу). Таймаут сам по себе не
провал: если роль успела записать прогресс до убийства процесса — это как обычная успешная запись, не
повтор (RUN_TIMEOUT назван в промпте роли в минутах). `blocked`/`needs_owner`/`done` без `reviewer`
всегда идут строкой в `ceo-inbox.md` (дедуп); ошибка разбора тикета — тоже, по (тикет, текст ошибки).
Не больше одного активного запуска на задачу; всего `MAX_PARALLEL` (умолч. 2,
`ALPHA_DISPATCH_MAX_PARALLEL`).

## Защита от петли и перерасхода (v1.1)

- **`MAX_RUNS_PER_TICKET_HOUR`** (умолч. 6, `ALPHA_DISPATCH_MAX_RUNS_PER_TICKET_HOUR`) и **`MIN_GAP_S`**
  (умолч. 60 с, `ALPHA_DISPATCH_MIN_GAP_S`) — троттлинг решений (а)-(г): тикет просто пропускается этот
  тик (не ошибка, задача остаётся как есть, попробуем следующим тиком). Ретраи правила (д) их не
  проходят — они и так ограничены одной попыткой.
- **`DAILY_COST_USD`** (умолч. 150, `ALPHA_DISPATCH_DAILY_COST_USD`) — суточный потолок расхода
  (сумма `total_cost_usd` из JSON-вывода `claude`, копится в `state.json["daily_cost"][<дата>]` по
  календарной дате). Превышен → новые запуски (включая ретраи) не стартуют, одна строка в
  `ceo-inbox.md` на сутки (дедуп).

## Модель, усилие и деньги (v1.3 — пилот Судьи на умолчаниях CLI стоил $6,8)

Каждый запуск явно задаёт модель и усилие — раньше полагались на умолчание CLI (роли шли на Fable 5.1
xhigh). `CLAUDE_MODEL` (умолч. `claude-opus-5-5`, `ALPHA_DISPATCH_MODEL`), `ROLE_EFFORT = {"judge":
"xhigh", "engineer": "high", "researcher": "high"}`. После каждого запуска `_model_usage_warning()`
смотрит `modelUsage` в JSON-выводе — если там модель без «opus» в имени (несмотря на явный `--model`),
строка в `ceo-inbox.md` (это и есть «проверка», автоматическая на каждый запуск, а не разовая ручная).

**Бюджет задачи — только в `state.json`, роль его не видит** (владелец 27.09: «запрещено добивать
задачи до их бюджетов, раздувая токены» — ни в шапке тикета, ни в промпте). `tickets.py new --budget
S|M|L|<число>` (S=3, M=10, L=25, умолчание — M) пишет `state.json["ticket_budget"][<ID>]`; траты копятся
в `state.json["ticket_cost"][<ID>]`. Бюджет исчерпан → новые запуски по задаче (включая ретраи) не
стартуют, `status: needs_owner` + строка CEO «бюджет задачи исчерпан: потрачено $X из $Y». Промпт роли
вместо чисел бюджета получает одну строку: «Трать минимум: самый короткий путь к результату задачи;
траты каждого запуска записываются и сравниваются с результатом». `runs.log` (`ticket_spent=`) и
`tickets.py status` (колонка «потрачено», `$X/$Y`) показывают траты — только CEO.

**Потолок одного запуска** — встроенный флаг CLI `--max-budget-usd` = `min(остаток бюджета задачи,
RUN_CAP_USD)` (умолч. 8, `ALPHA_DISPATCH_RUN_CAP_USD`). Запуск без JSON (убит по таймауту или вручную)
считается потратившим весь этот потолок — консервативно, не 0 (иначе перерасход не увидеть, если
убитые запуски не пишут итог).

**Скорость** — скользящее окно 60 мин по ВСЕМ ролям сразу (не на роль/задачу): `HOUR_COST_USD` (умолч.
15, `ALPHA_DISPATCH_HOUR_COST_USD`). Превышено → все новые запуски (и ретраи) на паузе, пока сумма за
последний час не опустится ниже потолка; строка CEO — один раз на переход «не было паузы → пауза».

**Холостой ход**: запуск стоил дороже половины бюджета задачи и не оставил ни новой записи в логе, ни
смены статуса относительно того, что было на момент запуска → сразу `status: blocked` (без обычного
одного повтора правила (д) — повтор может сжечь ещё половину бюджета так же безрезультатно) + строка
CEO.

**Закрытие задачи**: когда тикет первый раз замечен в `status: done`, если к этому моменту потрачено
≥ 80% бюджета — строка CEO «закрыта на N% бюджета — проверить соразмерность» (не блокирует, просто
сигнал; проверяется один раз на задачу).

## Активные запуски переживают перезапуск диспетчера (v1.1)

Каждый запуск зеркалится в `state.json["active_runs"][<ID>]` (`pid`, роль, время старта, `run_file`) и
сохраняется на диск сразу же (не только в конце тика). При старте `tick()` вызывает
`recover_active_runs()`: если зеркало есть, а в памяти процесса записи нет (диспетчер перезапускался) —
живой `pid` подхватывается заново (без повторного запуска `claude`, опрос идёт по `pid`, не по объекту
`Popen`); уже умерший `pid` (прогон успел закончиться, пока диспетчер не работал) обрабатывается как
обычное завершение — лог проверяется, при необходимости ретрай/`blocked`, как всегда.

## Область сессии на роль — `SESSION_SCOPE`

`{"judge": "role", "researcher": "ticket", "engineer": "ticket"}` (правится в `dispatch.py` или
`ALPHA_DISPATCH_SESSION_SCOPE=judge:role,engineer:ticket`). `"ticket"` — `--resume` в пределах
(задача, роль), как раньше. `"role"` — одна долгая сессия роли на все задачи; диспетчер не запускает
вторую задачу такой роли, пока не закончена текущая (задачи — по очереди). **Ротация:** если контекст
**последнего хода** прошлого запуска роли превысил `ROTATE_TOKENS` (умолч. 250 000,
`ALPHA_DISPATCH_ROTATE_TOKENS`) — следующий запуск идёт без `--resume`, в промпт добавляется просьба
перечитать блокнот и `docs/research/reviews/` по нужной задаче. `usage` в JSON `claude -p` — сумма
`input + cache_read + cache_creation` по ВСЕМ ходам запуска, не одного хода (CEO 27.09, живой прогон:
сумма 333 886 при реальном контексте хода ~52 тыс.) — контекст последнего хода
(`_context_tokens_last`) берётся из `usage.iterations[-1]`, а без неё — оценкой `сумма // num_turns`;
оба числа видны в `runs.log` (`ctx_last=`/`ctx_sum=`).

## Запуск

```bash
python .claude/dispatcher/dispatch.py --once   # один тик, для проверки/крона
python .claude/dispatcher/dispatch.py          # цикл раз в 15 с (ALPHA_DISPATCH_INTERVAL)
python .claude/dispatcher/tickets.py new --owner researcher --title "..."   # reviewer: judge по умолчанию
python .claude/dispatcher/tickets.py new --owner engineer --title "..." --no-reviewer  # явный отказ от ревью
python .claude/dispatcher/tickets.py new --owner researcher --title "..." --backlog   # перенос из TASKS.md
python .claude/dispatcher/tickets.py new --owner engineer --title "..." --budget L    # S=3/M=10/L=25, умолч. M
python .claude/dispatcher/tickets.py start TK-001                                     # backlog → todo
python .claude/dispatcher/tickets.py comment TK-001 --author engineer --text "... @judge глянь"
python .claude/dispatcher/tickets.py status    # «потрачено» — для CEO; роли эту команду не дают
python .claude/dispatcher/tickets.py new --owner engineer --title "..." --no-reviewer \
    --executor haiku --kind file-move          # белый список kind; reviewer:judge/owner:researcher — отказ
python .claude/dispatcher/watch.py --once      # сторож CEO без модели, один цикл (для крона/планировщика)
python .claude/dispatcher/watch.py             # сторож — цикл раз в 120 с (ALPHA_WATCH_INTERVAL)
```

`reviewer: judge` по умолчанию для `owner: researcher|engineer` (v1.2: без ревьюера `done` никого не
уведомлял — тикет исследования или кода минует Судью молча, вопреки «числа владельцу — после Судьи»;
теперь и `done` без `reviewer` вовсе тоже строкой в `ceo-inbox.md`). `owner: judge` — без умолчания
(ревьюера ревьюеру не назначаем).

`CLAUDE_BIN` — путь к `claude` (по умолчанию из PATH, иначе `/c/Users/Георгий/.local/bin/claude`).
CLI на этой машине залогинен, `--permission-mode bypassPermissions` проверен и живым смоуком (27.09,
см. ниже); `dispatch.py` всегда добавляет этот флаг, `--model`/`--effort`/`--max-budget-usd` (см. ниже)
и `ALPHA_ROLE=<role>` в окружение запуска (сняв из него `*HOST_SESSION*` — иначе роль принимается за
CEO) — по `ALPHA_ROLE` `role_context.py`/`role_memory.py` берут роль без определения по названию сессии
Desktop. Вывод каждого запуска — `.claude/dispatcher/runs/<ts>-<ID>-<role>.json` (+ `.err.log`), сводка
— `.claude/dispatcher/runs.log`, состояние (`session_id` по scope, `retries`, `last_woken`,
`active_runs`, `daily_cost`, `ticket_budget`, `ticket_cost`, `cost_history`) —
`.claude/dispatcher/state.json`.

## Будим CEO — `ceo-inbox.md` + `ceo-wake.log` + хук (v1.1)

Каждая запись в `ceo-inbox.md` дублируется короткой строкой (время, задача, причина) в
`.claude/dispatcher/ceo-wake.log` — CEO держит на нём `Monitor`. Отдельно, в сессии CEO хук
`.claude/hooks/role_memory.py` (`ceo_inbox_alert()`) на каждом сообщении подмешивает в контекст
непрочитанные строки `ceo-inbox.md` (после отметки `.claude/dispatcher/.ceo-inbox-seen`, которая тут же
сдвигается) — так же, как уже подмешивается тревога Steam Deck (`deck_alert()`).

## Роль в задаче

Получив тикет через `-p`, роль работает как раньше (устав, блокнот, журнал `.claude/roles/journal/`), но
без диалога: промпт называет лимит запуска в минутах (`RUN_TIMEOUT`) — шаг длиннее выносится в фон
(юнит на Steam Deck) заранее, не дожидаясь убийства процесса — и напоминает тратить по минимуму
(бюджет задачи и остаток роли НЕ называются — только «траты каждого запуска записываются и
сравниваются с результатом», v1.3, чтобы не раздувать работу под весь бюджет). Роль делает следующий шаг,
`python .claude/dispatcher/tickets.py comment <ID> --author <role> --text "..."` (или прямой правкой
файла) — что сделала, что дальше; сама правит `status`/`wait_for` в шапке. `status: todo` для
«продолжить» не годится (v1.2: упрётся в проверку «лог есть, но status не сдвинут» и в итоге
заблокирует задачу) — если работа не закончена за один запуск, оставить `status: in_progress`: диспетчер
сам будит владельца снова (троттлинг `MIN_GAP_S`/`MAX_RUNS_PER_TICKET_HOUR`, как у любого решения), пока
статус не станет чем-то другим. Нужен другой участник — упоминание `@роль` в тексте записи (не
самоупоминание — оно не будит автора), не отдельное сообщение. Фоновая работа (юнит на Steam Deck,
долгий счёт) — `status: waiting` + `wait_for: file:<путь>|deck:<путь>|ticket:<ID>` и выйти, не ждать в
сессии. Срочно и не терпит следующего тика — `SendMessage` на `CEO` напрямую (диспетчер это не заменяет,
только разгружает поток обычных шагов).

## Пилот Судьи (TK-001, 27.09) — что починено

шапки перенесённых тикетов (п.10) — правит CEO.

## Тесты и известные ограничения

`python -m unittest discover -s .claude/dispatcher -p "test_*.py" -v` — 164 теста (129 `test_dispatch.py`
+ 35 `test_watch.py`), без сети (`watch.py`'s ssh — через инъекцию `ssh_run` в тестах; ручной
`_deck_file_exists()` при разработке v1.1/v1.2 — см. ниже), без настоящего `claude` (свой seam
`dispatch._popen`, фейковый `python`-скрипт). Живые прогоны с настоящим `claude -p` — 27.09: смоук
исследователя (~$1.34, `status: done`), пилот судьи на умолчаниях CLI ($6,8, привёл к v1.3) и
многоходовая сессия судьи на `--model`/`--effort` (реально ≈ $1,94 суммарно за оба продолженных
запуска — см. v1.4 выше, до фикса записывалось как $17,03 кумулятивных).

Ограничения v1.3: `wait_for: deck:` при пути с пробелами не гарантирует безопасное экранирование
(только простые пути `~/alpha/...` без пробелов — реальный формат путей на Steam Deck); `_pid_alive`
снижает, но не устраняет риск переиспользования pid ОС (другой процесс `claude.exe` с тем же pid
теоретически всё ещё возможен); `MAX_RUNS_PER_TICKET_HOUR`/`DAILY_COST_USD` — защита от петли, не
жёсткая гарантия (данные лежат в `state.json`, ручная правка возможна); убитый по таймауту прогон без
записанного JSON теряет `session_id` для scope `"ticket"` (ретрай стартует без `--resume` — самим
`claude` эта информация просто не была отдана), но НЕ теряет стоимость — засчитывается весь потолок
запуска (`run_cap_usd`, консервативно). `tickets.py new/status` и живой `dispatch.py` пишут один и тот
же `state.json` без блокировки файла — при одновременной работе (CLI команда ровно в момент тика)
возможна гонка «прочитал-изменил-записал», один из двух наборов правок потеряется; на практике окно
гонки — доли секунды раз в 15 с, разово не критично. Базовый контекст свежей сессии роли ≈ 52 тыс.
токенов (замер владельца); `skillOverrides` в `.claude/settings.json` скрывает навык строкой-значением
`"off"` (уже стоит на 23 навыках) — диспетчерские роли наследуют это автоматически, отдельно
настраивать не нужно.
