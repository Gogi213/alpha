# Команда alpha под диспетчером (В-138; v2 — 02.10 после аудита)

Прежние версии устава — `.claude/roles/archive/README-2026-09-27.md`, `README-2026-10-02.md`. Почему v2 —
`docs/findings/role-system-audit-2026-10-02.md` (владелец 02.10: «ок делай»).

## Состав

| роль | режим | зона |
|---|---|---|
| `CEO` | долгая сессия Desktop, говорит с владельцем | `CLAUDE.md` «СОСТОЯНИЕ», `docs/plan/SETTLED.md`, приоритеты, задачи, устав и хуки `.claude/roles/`, `.claude/hooks/`, текст навыка `.claude/skills/alpha-research/` |
| `Судья` | сессия CLI под диспетчером, одна на задачу | `docs/research/reviews/*`, планка — `docs/research/reviews/PRECEDENTS.md` |
| `Исследователь` | сессия CLI на задачу (`ALPHA_ROLE=researcher`) | `docs/research/*`, `docs/findings/*`, `docs/plan/{EXPERIMENTS,HYPOTHESES}.md`, `tools/compute/*.py`, скрипты навыка |
| `Инженер` | сессия CLI на задачу (`ALPHA_ROLE=engineer`) | `src/`, `Cargo.*`, `docs/{COMMANDS,ARCHITECTURE}.md`, `docs/efficiency-register.md`, `tools/*.sh`, `tools/systemd/`, `tools/compute/*.sh`, машины |

Чужую зону не правишь — запись в тикете и `--next <владелец зоны>`. Коммит — только своих файлов, префикс
`[CEO]`/`[Исследователь]`/`[Инженер]`/`[Судья]`, `Co-Authored-By` в конце.

## Задача = тикет, и только он

- Работа — тикет `.claude/tickets/<ID>.md`. Состояние задачи живёт **только** в его шапке (`status`, `wait_for`,
  `next`, `effort`) и `## Лог`. Журналы `.claude/roles/journal/` для тикетов не ведутся.
- **Не считать то же самое (В-213):** проход > 15 мин — только с выпиской из Летописи (`registry.py plan`), Судья проверяет до подачи; шаги внутри скриптов — через `guard.py step`; подробности — `docs/COMMANDS.md` («Летопись»), роль инженера.
- Читать: шапку, описание и последние записи лога. Старые записи — `.claude/tickets/archive/<ID>-log.md`, грепом и
  только при нужде.
- Запись в лог — `python "<плагин>/.claude/dispatcher/tickets.py" comment <ID> --author <role> --text "..."`: что сделано
  (артефакт, коммит, числа), что идёт, следующий шаг. Одна запись на шаг с результатом, не «квитанции».
  `<плагин>` = `~/.claude/plugins/cache/role-play-vibing/role-play-vibing/<версия>`; готовая команда с абсолютным путём — в контексте сессии (хук плагина). Своей копии механики в alpha нет (В-194, TK-077); `.claude/hooks/delete_guard.py` — прослойка к стражу плагина для `~/.claude/hooks/alpha_one_build.py`.
- **Передать работу другой роли** — `--next <role>` (один раз). Упоминание `@роль` в тексте никого не будит. Копий
  «для сведения» нет. `--next ceo` — только если задача встала или нужно решение владельца.
- **Ждать фоновую работу** — `status: waiting` + `wait_for` (`file:` / `deck:`), сессию не держать. Долгий счёт —
  юнитом `systemd-run` на машине с меткой `.done`. Фоновых помощников и фоновых задач внутри сессии не запускать.
- Статус правишь сам: диспетчер прозу не читает.
- Блокнот роли `.claude/roles/notes/<role>.md` — ≤ 4 КБ, только то, что нужно следующей задаче (грабли, адреса,
  приёмы); обновлять в конце задачи, не по счётчику сообщений.

## Судья и договор (В-156, сужено 02.10)

**Судья — единственный кросс-аудитор и валидатор качества; снимать его CEO запрещено (В-191, владелец 06.10):** ни убрать
`reviewer: judge`, ни остановить его запуск, ни закрыть/влить мимо приёмки; снять — только владелец цитатой. Приёмка — в
настоящей обстановке пользователя (другая команда/ОС/чистый проект), не только на данных alpha.

`reviewer: judge` ставит `CEO` только на: (а) исследование, чьи числа или вердикт идут владельцу; (б) код счёта или
горячего пути (ворота «байт в байт»); (в) необратимое — удаление данных, публикация, включение на бою. Замеры,
инфраструктура, скрипты, перенос файлов — без Судьи: в последней записи — самопроверка «что проверено чем».

С `reviewer: judge`: первая запись исполнителя — договор «Сдам · Примут, если (2–6 проверяемых пунктов) · Не входит».
Отдельно Судью ради «договор ок» не будить — договор он сверяет при приёмке; заранее (`--next judge`) — только перед
необратимым шагом. Перед сдачей — самопроверка по пунктам, затем `status: in_review`. Вердикт Судьи — таблицей по
пунктам, проверяет живой результат; любое «нет» — «вернуть» с конкретикой.

## Кто решает

Методика и объём исследования — `Судья` (`CEO` записывает в `SETTLED.md` как В-##). Порядок счёта и ресурсы — `CEO`.
Владелец — направление, деньги, риск, что исследовать. Утверждение протокола — только цитата владельца через `CEO`.
Числа владельцу — после Судьи; по прямой просьбе — сразу с пометкой «на проверке».

## Ресурсы

- Сборка cargo — только на VPS (`bash tools/vps-check.sh`), одна за раз.
- **Основное дерево — без незакоммиченных правок `src/` и `tools/` (TK-057, владелец 05.10):** кодовая задача — свой worktree и ветка; слияние в рабочую ветку — rebase на голову + `vps-check all` + fast-forward, по одному.
- Машины и что на них можно — `CLAUDE.md` «СОСТОЯНИЕ» и «Машины» (решения владельца меняются; не держать копий в уставах).
- Сетки, гейты, пробы — одним `--cells` на сутки на версию программы (В-136).
- Удаление — только внутри своей папки (В-134): проект и scratchpad; Steam Deck `~/alpha/<подкаталог>`,
  `/dev/shm/alpha-stage`; VPS `/opt/alpha-compute/<подкаталог>`; коллектор, Storage Box, `root/`/`deep/` — никогда.
  Держит `delete_guard.py` плагина.
- Долгая задача на машине (> 5 мин) пишет ход в `/data/progress/<job>.json` через `tools/compute/progress.sh` (на счётном сервере и VPS — `alpha-progress`): на каждом шаге и не реже раза в минуту. Это экран владельца `tools/pulse/pulse.py`; без файла задача на экране не видна.
- Конец серверного задания будит исполнителя сам (сборщик табло) — при условии, что задание пишет /data/progress с ticket.
- Долгое задание на сервере → `python "<плагин>/.claude/dispatcher/tickets.py" wait <ID> host:calc:/data/progress/<job>.json` (VPS — `host:vps:…`; юнит — `host:calc:unit:<имя>`; форма проверяется, свободный текст в `wait_for` диспетчер не понимает — ждать будет вечно).
- **В-178:** прогон на сервере дольше ~15 мин — сначала `tools/compute/calibrate.sh` (на серверах — `/opt/alpha-compute/bin/`):
  варианты параллельности и чтения (readahead) по 2–3 мин на своих ещё не сделанных единицах; лучший — по единиц/мин.
  В договор тикета — пункт «калибровка приложена, выбран лучший», таблица `calibrate.tsv` — в записи тикета;
  Судья без неё прогон не принимает.
- Быстрый режим (fast mode) запрещён владельцем.

## Расход

- Траты считаются (`runs.log`, `tickets.py status` — «потрачено», видит CEO). От зацикливания — пауза между запусками,
  один повтор, холостой ход и N запусков с записью без смены статуса → `blocked`. Тратить по-прежнему минимум: самый
  короткий путь к результату.
- Усилие задачи — поле `effort` в шапке (ставит `CEO`): `medium` — исполнение готового плана (замеры, скрипты, перенос,
  таблицы); `high` — код, ворота, отладка, протокол; `xhigh` — вердикт Судьи. Без поля: Исследователь и Инженер
  `high`, Судья `xhigh`.
- Длинное (логи, выводы, отчёты) — помощником `reader` (Haiku), ответ — сводка `файл:строка`; числа — из файла.
  Код — помощник `coder` (`.claude/agents/coder.md`).
- Не перечитывать то, что пришло с ролью; большие выводы — `tail`/`grep`, не целиком.
- Сроки — в темпе Claude Code (код → сборка+тесты → гейт → итого), время — по `date`, GMT+4.

## Стандарт сигналов (В-192, TK-074)

Один вид сигнала — один путь: **событие шины в очередь получателя, получатель подтверждает (ack)**. Файлы и ssh-опрос —
только запасной путь при недоступной шине, с пометкой. Опись и «было/стало» — `docs/findings/signals-inventory-2026-10-06.md`.

| Вид | Адрес события | Пишет | Читает (очередь) | Приоритет | Шина недоступна |
|---|---|---|---|---|---|
| пробуждение роли, сдача на ревью | `задача.<ID>.сдано`/`статус` | `tickets.py comment` | диспетчер | — | таймер диспетчера 15 с по `next:` в шапке |
| пробуждение CEO (`--next ceo`), `done`, `wait-for`, `model`, `summary`, `bus-up` | `задача.<ID>.к_ceo` | диспетчер | `ceo` | normal | строка в `ceo-inbox.md` `[запасной путь]` |
| блок, петля, parse-error, stop-failed | `задача.<ID>.к_ceo` | диспетчер | `ceo` | **urgent** | то же |
| тревога сторожа (`watch-*`), падение шины, ответ владельца с табло | `задача.общее.к_ceo` | `watch.py`, `ask.py`, диспетчер | `ceo` | **urgent** | то же |
| вопрос владельцу (`ВОПРОС ВЛАДЕЛЬЦУ…` в записи) | `задача.<ID>.вопрос_владельцу` | `tickets.py comment` | `ceo` | **urgent** | запись остаётся в логе тикета |
| конец задания/юнита, падение юнита, простой сервера | `машина.<M>.юнит.*`, `…задание.*` | сторож машины | диспетчер (падение — и `ceo`) | urgent при падении | `wait_for host:` — опрос по ssh |
| лимит 429 | не сигнал CEO: пауза запусков диспетчера | диспетчер | — | — | — |

- **CEO** читает очередь не постоянным монитором, а раз в 15–30 мин: `python "<плагин>/.claude/dispatcher/tickets.py" inbox`
  (срочное первым, ack пачкой; `--peek` — без ack; затем непрочитанный запасной файл; код 1 — шина недоступна).
- Новый вид сигнала: добавить в `NORMAL_KINDS` (`dispatch.py`), иначе он `urgent` (безопасная сторона), и строку в эту таблицу.
- Мимо стандарта писать `ceo-inbox.md`/`ceo-wake.log` нельзя — только через `dispatch.append_ceo_inbox`; тест
  `test_signals.py::test_no_ceo_file_writes_outside_fallback` это проверяет.
- Роль в сессии сигнал CEO не пишет в файлы руками: `tickets.py comment … --next ceo` (или `ВОПРОС ВЛАДЕЛЬЦУ`).
- Запись в эти файлы из сессии закрыта хуком `ceo_signal_guard.py` плагина (PreToolUse в `.claude/settings.json`: Write/Edit/Bash/PowerShell).
- **ssh-опрос диспетчера** — только первая проверка нового `wait_for host:` и аварийный путь (шина лежит ≥ 600 с → опрос раз в 300 с +
  тревога `bus-down-ssh`); каждый вызов — строка в `.claude/dispatcher/ssh-calls.log` (причина: первая | событие-юнита | аварийный | сверка | пропуск) —
  мерка «сутки без ssh-опроса». **Сверка** — раз в 300 с один ssh на машину по всем ждущим `host:` (страховка от пропущенного события и сорванной регистрации у сторожа); если сверка закрыла условие без события шины на машине со сторожем (calc) — строка «пропуск» и срочная тревога `recon-miss` (один раз на ключ): сторож не справился. **Исключение:** `wait_for vps:<файл>` — на VPS сторожа нет, событие не придёт, пока не поставлен сторож
  (до тех пор такое условие закрывает только первая/аварийная проверка по ssh).

## Правила для всех

- Делать то, что сказано, и как сказано. Двоякая постановка — вопрос до работы, а не свой выбор варианта.
- Оценка — не замер: прикидку помечать «оценка», допущение — называть.
- Не предлагать обходы вместо решения (В-159): аренда/смена серверов, докупка мощности, найм — только если владелец
  назвал сам.
- Согласие владельца — только его цитата с датой от `CEO`; пересказ другой роли не считается.
- **Только оптимальный алгоритм (В-170, владелец 03.10):** «нельзя просто так из воздуха взять алгоритм для большой
  задачи. надо найти оптимальный и сделать задачу максимально оптимально и быстро без потери качества». Для любой
  задачи с выбором способа (счёт, докачка, проверка, импорт, исследование) цель — оптимальный алгоритм, а не «сколько-то
  вариантов»: найти узкое место, перебрать лучшие известные способы его снять, сравнить замером на малом (скорость и
  что даёт/ловит), взять оптимальный без потери качества — только потом боевой прогон. В отчёте тикета обязательна строка
  «Алгоритм: варианты — …; замер — …; выбран — … потому что …». Нет строки — CEO возвращает работу.
- **Как было, без упрощений ради кода (В-172):** данные и симулятор повторяют биржу; упрощение — только если замер
  доказал, что результат не меняется.
- **Страницы владельца (табло, дашборды; владелец 06.10):** супер компактно и лаконично; без очевидного из вида
  («шаг 2 из 3» при подсветке), без техники (хэши, ветки, пути, номера тикетов, флаги); числа — только правдивые
  (нет данных — нет процента, а не выдуманный); каждое состояние различимо глазом. Эталон вида — утверждённый макет
  (`tools/pulse/design/`). «Готово» — только после скриншота живой страницы на ширине владельца (≈ 1470 px) и 375 px,
  сверенного с макетом по смыслу («правда ли это и понятно ли с одного взгляда»), а не по совпадению CSS.
