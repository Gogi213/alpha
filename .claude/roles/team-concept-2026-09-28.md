# Концепция команды агентов alpha: CEO · Исследователь · Инженер · Судья

Снимок на 28.09.2026 ~13:30 GMT+4, для передачи другому агенту. Документ самодостаточен: как устроена работа,
кто за что отвечает, как агенты общаются, чем их будят, где лежит состояние, какие правила и грабли. Пути — от
корня репозитория `C:\visual projects\alpha`. Живые первоисточники (при расхождении верны они):
`.claude/roles/README.md` (устав), `.claude/roles/{ceo,researcher,engineer,judge}.md` (уставы ролей),
`.claude/dispatcher/README.md` (диспетчер), `docs/plan/SETTLED.md` (решения владельца В-##).

## 1. Контекст: что делает команда

Проект alpha — торговый бот по крупным лимитным заявкам («стенам», плотностям) в стакане Bybit, написан на Rust.
Коллектор круглосуточно пишет стакан по пулу из 76 монет. Крупные уровни размечаются, а вариант стратегии получает
вердикт бэктестом с моделью очереди. Одна функция стратегии работает и в бэктесте, и в живом боте без правок.

Владелец — один человек. Он ставит направление, решает вопросы денег и риска и говорит, что исследовать. Команда —
несколько сессий Claude Code, каждая в своей роли. Цель владельца (В-120) — стабильный заработок. Главный KPI
варианта — сколько дней счёт ждёт нового максимума (доля часов, когда ожидание дольше 5 суток); считается по каждому
месяцу отдельно.

Машины:
- **Машина владельца** (Windows) — сессии, диспетчер, git. Сборки cargo на ней запрещены.
- **Steam Deck** — основной счёт: очередь заданий `alpha-gridq`, фоновые задачи только через `systemd-run --user`.
- **VPS** (4 ядра) — сборки, тесты и дополнительный счёт.
- **Коллектор** — отдельный сервер.
- **Storage Box** — единственные копии записи, удалять нельзя.

## 2. Почему так устроено (история)

1. **До 27.09** было четыре постоянные сессии Desktop, по одной на роль. Общались через `SendMessage`, CEO пересылал
   сообщения между ролями. Что пошло не так:
   - после ~10 сообщений подряд отправка вставала на паузу;
   - CEO превратился в пересыльщика;
   - роли простаивали «в ожидании», держа контекст до 300 тыс. токенов. Замер 25.09: половина всех трат приходится на
     шаги при контексте больше 300 тыс.;
   - после клира роль приходилось возобновлять вручную.
2. **Решение владельца В-138 (27.09):** «2 долгосрочных ты и судья. исследователь и инженер создаются в кли под задачи».
   - Долгие сессии — только **CEO** (Desktop, говорит с владельцем) и **Судья** (одна сессия под диспетчером).
   - **Исследователь** и **Инженер** — свежая сессия CLI (`claude -p`) на каждый запуск задачи.
   - Работа идёт через **тикеты-файлы**. Кого и когда будить, решает **диспетчер** — скрипт на Python, сделан по образцу
     Paperclip.
3. **Суть подхода:** состояние живёт в файлах, а не в разговоре. Сессия, которая ждёт, завершается, а не держит контекст.
   Роли общаются только через лог тикета с упоминанием `@роль`.

- **`coder`** — Opus 5.5, усилие medium, `.claude/agents/coder.md`. Единственный допустимый помощник, который пишет код.

Правила для всех ролей:

- Быстрый режим (fast mode) запрещён владельцем.

## 4. Роли подробно

### 4.1 CEO

Долгая сессия Desktop. С ней говорит владелец.

**Отвечает за:**
- разговор с владельцем;
- постановку задач тикетами;
- порядок счёта и ресурсы (Steam Deck, VPS, бюджеты задач);
- общее состояние проекта (`CLAUDE.md` «СОСТОЯНИЕ», `SETTLED.md`, `.memory/index.md`);
- уставы и хуки команды.

**Сам не считает и не пишет код.** CEO всегда свободен для разговора. Код, если нужен в его зоне, пишет через помощника
`coder`.

**Ставит задачу тикетом** — `python .claude/dispatcher/tickets.py new --owner <role> --title "..." --budget 60 --desc
"..."`. В описании:
- что сделать и зачем;
- где файлы;
- критерий готовности;
- ограничения ресурсов;
- **цитата владельца с датой**, если задача от него.

**Кто что решает:**

| вопрос | кто решает |
|---|---|
| новые задачи ролям | только по слову владельца (простой роли — не повод) |
| методика и объём исследования: пороги, правила вердикта, N, метрики | Судья; CEO записывает её решения в `SETTLED.md` как В-## |
| порядок счёта и ресурсы | CEO |
| направление, деньги и риск, что исследовать | владелец |

Вопрос владельцу не держит общую часть счёта: считать дальше, спросить отдельно. Заданная работа не стоит никогда.

**Будильник и сторож:**
- `Monitor` на `.claude/dispatcher/ceo-wake.log`. Туда диспетчер и сторож пишут строку на каждое событие для CEO:
  упоминание `@ceo`, `blocked`, `needs_owner`, исчерпан бюджет, тикет-сирота, тревога Steam Deck.
- Шум фильтровать по **содержанию**, а не по типу: заглушённый целиком тип пропустит заморозку машины.
- Прочитал событие → действие или вопрос владельцу, а не пересказ.
- Крон не ставится: сторожем работает `watch.py` (п. 6.4).

**С владельцем:**
- сначала результат или число, потом смысл и следующий шаг; коротко, без техники;
- решения владельца — отдельной строкой с вариантами и рекомендацией;
- время — GMT+4, только по `date`;
- числа — после проверки Судьи; по прямой просьбе — сразу, с пометкой «на проверке»;
- сроки — в темпе Claude Code: код → сборка+тесты → гейт → итого, число на каждый шаг; человеческие «дни» запрещены.

**Порядок исследования (ведёт CEO):**
1. Тикет Исследователю на протокол.
2. `@judge` проверяет протокол.
3. Протокол — владельцу; его цитату с датой CEO кладёт в тикет.
4. Счёт.
5. Отчёт.
6. `@judge` проверяет отчёт.
7. CEO докладывает владельцу.

**После каждого законченного шага** CEO обновляет `CLAUDE.md` «СОСТОЯНИЕ СЕЙЧАС» и `.memory/index.md`, а решения
владельца записывает в `SETTLED.md` (В-##, дословная цитата, дата, суть) — всё коммитом `[CEO]`.

**Нельзя:**
- трогать `.claude/dispatcher/*` (кроме чтения и перезапуска с поднятыми лимитами по решению владельца) и
  `.claude/hooks/role_memory.py`;
- пересылать сообщения между ролями (роли общаются через тикеты сами);
- включать быстрый режим.

### 4.2 Исследователь

Новая сессия CLI на каждый запуск задачи.

**Старт:**
- тикет `.claude/tickets/<ID>.md`;
- журнал задачи `.claude/roles/journal/<ID>.md` (особенно блок «ПЕРЕЕЗД»), если есть;
- блокнот роли `.claude/roles/notes/researcher.md`.

**Работа:**
- Перед любым исследовательским шагом загружает навык `.claude/skills/alpha-research/` (п. 8).
- Протокол пишется до счёта. Утверждает его только цитата владельца, которую передаёт CEO.
- Готовый протокол или отчёт — сначала `@judge` в тикете, потом `@ceo`.
- Долгий счёт — фоном, юнитом `systemd-run --user` на Steam Deck с меткой `.done`. Затем `status: waiting` +
  `wait_for: deck:<путь метки>`, и сессия выходит, а не ждёт.
- Сетки, гейты и пробы — одним вызовом `--cells` на сутки на версию программы (В-136). Поштучные «клетка × сутки»
  запрещены.

**Формат отчёта** (в лог тикета, с `@ceo`):
- итог;
- числа — месяцы отдельно, интервалы, эффективный N, число испытаний;
- что дальше;
- нужно ли решение владельца.

**Нельзя:** трогать Rust — нужен код, значит тикет Инженеру через `@ceo`.

### 4.3 Инженер

Новая сессия CLI на задачу. Старт — так же, как у Исследователя (тикет, журнал, блокнот).

**Код:**
- Обязательны `docs/ARCHITECTURE.md` (A1–A9) и семь запретов горячего пути:
  - ноль аллокаций на событие;
  - время только через трейт `Clock`;
  - без `async` с захватом состояния;
  - без REST в цикле событий;
  - ордер собран и подписан до триггера;
  - без `f64` для цены и размера;
  - без `BTreeMap`/`HashMap` на пути события.
- Новое — за флагом, по умолчанию поведение старое.
- Тесты — в `<модуль>/tests.rs`.
- Перед коммитом — `fmt --check`, `clippy -D warnings`, тесты. Всё это на VPS: `bash tools/vps-check.sh <дерево>
  all`. Cargo на машине владельца запрещён, хук отказывает.

**Выкладка:**
1. Сборка на VPS.
2. Бинарник на Steam Deck.
3. Гейт «байт в байт» против прежнего бинарника.

Ускорение без такого гейта не принимается.

**Подроль «эффективность»:**
- ищет повторную работу: сутки читаются дважды, пересчёт вместо кэша, простой ядер;
- ведёт реестр `docs/efficiency-register.md`;
- тревога очереди `ALERT-rework` — сигнал разобраться.

**«Раунд ревью»** по девяти осям (мёртвый код, дублирование, избыточность, запахи, длина файлов, сложность, лишние
сборки, лишние файлы, старая документация) — порядок в `.claude/roles/review-round.md`:
- поиск — свежими субагентами;
- сводка в `docs/findings/`;
- правки партиями по оси.

**Отчёт** (`@judge` → `@ceo`): итог · хеш · тесты · что осталось. Денежных выводов Инженер не делает.

### 4.4 Судья

Одна долгая сессия под диспетчером. Руководитель — CEO.

Мерка — навык alpha-research (ворота и отказы) и `PRECEDENTS.md`: держать прежнюю планку, а не решать заново.

**Проверку получает тикетом:** `@judge` в логе, либо `status: done` при `reviewer: judge`. Читает тикет, журнал,
протокол, отчёт, код **и сырьё**, а не переписку и не рассуждения автора.

**Протокол до утверждения** — всё ли записано до исходов:
- вопрос и решение, механизм;
- данные: что сожжено, что идёт на проверку;
- что заморожено;
- одна главная метрика;
- бюджет испытаний и размер выборки;
- правило вердикта с числами;
- пары сравнения.

**Отчёт до владельца:**
- сверить 2–3 ключевых числа с исходными файлами, пересчитав **своим кодом** (лёгкий счёт на Steam Deck, тяжёлый —
  через CEO);
- месяцы отдельно;
- интервалы и эффективный N;
- поправка на перебор (Холм);
- отступления от протокола записаны;
- вывод не сильнее замера.

**Код (гейт):** «байт в байт» с прежним поведением при умолчании; план — до кода.

**Ответ:**
- в лог тикета: «принято» или «вернуть: <пункты>», адресовано автору;
- при необходимости — файл `docs/research/reviews/<тема>-<дата>.md`;
- коммит `[Судья] <тема> — принято / вернуть: …` (CEO читает `git log`);
- правки планки — в `PRECEDENTS.md`.

**Нельзя:** искать альфу самому, писать код, править чужие файлы.

## 5. Тикеты

Файл `.claude/tickets/<ID>.md`. ID — `TK-NNN`; есть и старые `T-NN`.

```
---
id: TK-018
title: Июль для всех вариантов дашборда — один прогон
owner: researcher            # researcher | engineer | judge
status: waiting              # backlog|todo|in_progress|waiting|in_review|done|blocked|needs_owner
reviewer: judge              # по умолчанию judge для researcher/engineer; --no-reviewer — явный отказ
wait_for: deck:~/alpha/tmp-p07/jall-gate.status   # file:<путь> | deck:<путь> (ssh) | ticket:<ID> | mention
updated: 2026-09-28T13:01:36+04:00
---
Описание: что, зачем, где файлы, критерий готовности, ограничения, цитата владельца с датой.

## Лог
### 2026-09-28T12:50:32+04:00 researcher
Что сделал, что дальше. @ceo …
```

Команды:

```bash
python .claude/dispatcher/tickets.py new --owner researcher --title "..." --budget 60 --desc "..."
python .claude/dispatcher/tickets.py new --owner engineer --title "..." --no-reviewer
python .claude/dispatcher/tickets.py new ... --backlog        # диспетчер не трогает до `start`
python .claude/dispatcher/tickets.py start TK-001             # backlog → todo
python .claude/dispatcher/tickets.py comment TK-001 --author engineer --text "... @judge глянь"
python .claude/dispatcher/tickets.py status                   # траты $X/$Y — видит только CEO
```

Правила ведения тикета:

- **Статус роль правит сама.** Диспетчер прозу не понимает: не сменила статус — задача уйдёт в очередь заново.
  - Работа не закончена за один запуск → `in_progress`: диспетчер разбудит снова. `todo` для этого не годится.
  - Ждёт фоновой работы → `waiting` + `wait_for`, и сессия выходит.
  - Готово → `done`, и при `reviewer` включится ревьюер.
- **Упоминание `@роль` будит роль сразу.** Писать его, только когда роль нужна сейчас. Самоупоминание автора не будит.
  `@ceo` роль не запускает, а даёт строку в `ceo-inbox.md` и `ceo-wake.log`.
- **Общение — только через лог тикета.** Срочное, что не терпит следующего тика или требует владельца, — роль пишет
  `SendMessage` напрямую в сессию CEO.
- **Журнал задачи** `.claude/roles/journal/<ID>.md` пишет исполнитель: Цель · Сделано (шаг → артефакт, коммит) · Идёт
  сейчас (юнит, метка `.done`) · Следующий шаг · Открытые вопросы. Обновляется после каждого шага с артефактом.

## 6. Диспетчер `.claude/dispatcher/dispatch.py`

Только stdlib. Цикл раз в 15 с. Пишет `state.json` (сессии, активные запуски, траты, бюджеты) и `runs.log` (строка на
запуск: стоимость, контекст, статус). Вывод каждого запуска — `runs/<ts>-<ID>-<role>.json` и `.err.log`. Тесты — 179
штук: `python -m unittest discover -s .claude/dispatcher -p "test_*.py"`.

### 6.1 Кого будит `tick()`

- **(а)** `todo` → роль-владелец задачи.
- **(а′)** `in_progress` без активного запуска → роль-владелец («продолжи»).
- **(б)** В логе новая запись с `@роль` после последнего запуска этой роли по задаче → эта роль. Работает при любом
  статусе, кроме `backlog`. «Новое» определяется по росту текста секции «## Лог» (`log_len_at_launch`), а не по
  заголовкам.
- **(в)** `waiting`, и условие `wait_for` выполнено → владелец задачи. `deck:` проверяется по ssh, результат кэшируется
  на 60 с.
- **(г)** `done` при заданном `reviewer` → статус `in_review`, будится ревьюер. Исключение — последняя запись уже от
  самого ревьюера: это штатный конец ревью.
- **(д)** Запуск не дал пригодного результата (нет записи в логе, или статус так и остался `todo`) → один повтор с
  напоминанием; второй раз подряд → `blocked` и строка CEO. Таймаут при записанном прогрессе провалом не считается.

Ограничения:
- не больше одного активного запуска на задачу;
- всего одновременно — `MAX_PARALLEL=2`;
- Судья (`SESSION_SCOPE=role`) берёт задачи по очереди.

### 6.2 Запуск роли

Команда:

```
claude -p "<промпт>" --output-format json --permission-mode bypassPermissions \
       --model claude-opus-5-5 --effort <xhigh|high> --max-budget-usd <потолок> [--resume <session_id>]
```

Окружение: `ALPHA_ROLE=<role>`, а все переменные `*HOST_SESSION*` сняты. Иначе дочерняя сессия унаследует
идентификатор сессии CEO, и хуки примут её за CEO.

Промпт одинаковый для всех ролей:

> Ты — {role} команды alpha. Устав: .claude/roles/{role}.md, блокнот: .claude/roles/notes/{role}.md. Задача:
> .claude/tickets/{tid}.md. Лимит этого запуска — 40 мин; шаг длиннее — выноси в фон (systemd-run на Steam Deck) и
> ставь status: waiting + wait_for, не жди в сессии. Трать минимум: самый короткий путь к результату; траты каждого
> запуска записываются и сравниваются с результатом. Сделай следующий шаг; запись в лог — `tickets.py comment …` ДО
> истечения лимита; обнови status/wait_for сама (не «todo», если работа не закончена). Упоминай @роль, если нужен
> другой.

Ротация сессии: если контекст последнего хода прошлого запуска больше 250 тыс. токенов, следующий запуск идёт без
`--resume`. Тогда в промпт добавляется просьба перечитать блокнот и прежние решения.

Перезапуск диспетчера активные запуски не теряет: они зеркалятся в `state.json["active_runs"]` и подхватываются по pid.

### 6.3 Деньги и защита от перерасхода (В-139, В-149)

- **Бюджет задачи** хранится только в `state.json`. Роль его не видит — владелец: «запрещено добивать задачи до их
  бюджетов, раздувая токены».
  - Задаётся при создании: `--budget S|M|L|<число>` (S=3, M=10, L=25; по умолчанию M).
  - **С 28.09 (В-149) бюджеты открытых задач — не ниже $60.** Новые тикеты создавать сразу с `--budget 60`: по
    умолчанию будет $10, и задача встанет.
  - Бюджет исчерпан → `needs_owner`, строка CEO, новые запуски не стартуют.
  - Поднять бюджет CEO может так: дождаться пустого `active_runs`, остановить диспетчер и сторож, поправить
    `state.json["ticket_budget"]`, снять отметку «уведомлён», вернуть статус, перезапустить.
- **Потолок одного запуска:** `--max-budget-usd = min(остаток бюджета задачи, RUN_CAP_USD)`. Сейчас `RUN_CAP_USD` = $30
  (было $8).
- **Скорость и сутки:** часового и суточного потолков сейчас нет (В-149; было $15 в час и $150 в сутки). Оставлены
  переменные окружения `ALPHA_DISPATCH_*`.
- **Холостой ход:** запуск съел больше 50 % бюджета без записи в логе и без смены статуса → сразу `blocked`.
- **Задача закрыта на ≥ 80 % бюджета** → сигнал CEO «проверить соразмерность».
- **Троттлинг:** не больше 6 запусков одной задачи в час, промежуток между ними не меньше 60 с.
- **Учёт трат:** при `--resume` CLI отдаёт кумулятивную стоимость сессии. Диспетчер считает **разницу** по
  `session_id` — без этого были ложные паузы.
- В-149 снимает лимиты трат, но не объём работ: «не экономить на токенах не значит делать хуйню». Объём задаёт только
  слово владельца.

### 6.4 Сторож `watch.py` (без модели, цикл 120 с)

Проверяет:
- жив ли диспетчер;
- траты против бюджетов;
- тревоги Steam Deck `ALERT-*` по ssh, сравнивая их по содержимому без меток времени;
- простой Steam Deck при непустой очереди;
- тикеты-сироты: `in_progress` или `waiting` без новой записи дольше 2 ч;
- `blocked` и `needs_owner`.

Ошибка ssh сама по себе сигнал. Один таймаут не будит: сначала немедленный повтор, будит только третий подряд
неудачный цикл.

Находка → строка в `ceo-inbox.md` и `ceo-wake.log`. Повтор той же находки — не раньше чем через 2 ч.

Сердцебиение пишется в `watch-heartbeat.json`. «Сторожа сторожит» хук CEO: если сердцебиение старое, в контекст CEO
падает строка.

### 6.5 Как CEO узнаёт о событиях

- `Monitor` на `ceo-wake.log` — push-уведомления в сессию.
- Хук `role_memory.py` на каждом сообщении CEO подмешивает в контекст непрочитанные строки `ceo-inbox.md` и тревоги
  Steam Deck.

## 9. Исследование: навык `alpha-research`

Основа — quant-research-skill, переработанный под проект. Грузится перед **любым** исследовательским шагом, даже если
просят «быстро одно число»: одно число без шума и без счётчика испытаний — именно та ошибка, против которой навык.

Порядок:
1. Вопрос.
2. **Протокол до счёта** (`docs/research/P-NN-*.md`): механизм, данные, что сожжено, заморозка порогов, одна главная
   метрика, бюджет испытаний, правило вердикта с числами.
3. Судья проверяет протокол.
4. Утверждает владелец — цитата.
5. Счёт строго по протоколу.
6. Отчёт: месяцы отдельно, интервалы (блочный бутстреп по суткам), эффективный N, число испытаний, поправка Холма,
   ожидаемый максимум шума (дефлированный Шарп).
7. Вердикт по заранее записанному правилу.
8. Строка в журнале `JOURNAL.md` — в том числе для неудач.

Контракт данных:
- **Решение — по августу и сентябрю, каждый месяц отдельно** (В-115).
- **Июль — проверка вне выборки** (В-146: на июль идут только варианты «не в минусе» в августе и в сентябре). Остальные
  на июле показываются как «описание, не отобран» (В-151).
- Январь–июнь не считаются (В-150).
- Подобранное на месяце на нём же без разбиения не проверяется.
- Найденное на данных помечается «найдено на этих данных», а счётчик испытаний включает весь перебор.

Кто решает в исследовании:
- методику и объём — Судья;
- «деньги против KPI расходятся» — фиксируется, решает владелец;
- числа владельцу — после проверки Судьи.

## 10. Ресурсы и счёт

- **Steam Deck — очередь `alpha-gridq`.**
  - Задания ставятся через `bin/q-add.sh`, у каждого приоритет и резерв памяти.
  - Статус — `queue/STATUS`, тревоги — `queue/ALERT-*`, пауза — `queue/HOLD`.
  - Занять или освободить деку и снять `HOLD` — только CEO, а `HOLD` — только по слову владельца.
  - Загрузку считать по ресурсам (свободные ядра и память на пик задания), а не числом процессов. Перед массовой
    постановкой сверить резерв памяти задания с замером пика.
- **Одним проходом:** сетка на сутки — один `--cells` со всеми клетками всех задач на эти сутки (В-136). Параллельные
  задачи на одни и те же дни сливать в одно задание.
- **VPS** — сборки (одна за раз) и дополнительный счёт. Сутки делятся между машинами так, чтобы обе закончили
  одновременно.
- **Долгое — только юнитом `systemd-run --user` с меткой `.done`** (`nohup` через ssh умирает). Ждать через `wait_for`,
  а не опросом в сессии.
- **Экономия контекста:**
  - клир после законченной задачи, а для долгих сессий — при ~250–300 тыс.;
  - вывод команд — через `tail`/`grep`;
  - вид страницы — текстом, скриншот — только когда текст не отвечает;
  - сессия на задачу стартует налегке (≈ 52 тыс. токенов) и не перечитывает то, что пришло с ролью.

## 11. Типичный поток задачи (реальный пример TK-018, 28.09)

1. Владелец: «а че в июле вообще нихуя нету. дорабатывай!» → CEO создаёт тикет с цитатой, критерием и порядком на Steam
   Deck.
2. Диспетчер будит Исследователя (`todo`). Тот даёт оценку по шагам со временем, ставит задания на Steam Deck и VPS,
   пишет `status: waiting`, `wait_for: deck:…/jall-gate.status` и выходит.
3. Сбой: ~20 суток упали разом. Сторож и тревога дали строку CEO. CEO пишет в тикет «срочно, @researcher: причина по
   одному заданию, почини, срок цифрой». Исследователь находит причину (лишний флаг у одного прохода), чинит и
   перепоставляет. `@engineer` налаживает обратную перевозку результатов с VPS.
4. Бюджет $10 по умолчанию исчерпан → `needs_owner`. CEO поднимает его до $60 (В-149) и снова упоминает роль.
5. Владелец расширяет объём («все гипотезы на июль, недостающие — на авг/сен») → CEO записывает В-151 и пишет в тикет
   с цитатой. Исследователь первым ходом присылает таблицу «семья · вариантов · каких месяцев нет · как · минуты» и
   срок.
6. Счёт → чтение → данные дашборда → `@judge` → принято → `@ceo` публикует и докладывает владельцу: число первым,
   решение отдельной строкой.

## 12. Грабли (что уже ломалось — не повторять)

**Устройство:**

  сверяются по `modelUsage`.
- `--resume` отдаёт кумулятивную стоимость → ложные паузы. Считать разницу.
- Петли: ревьюер будился за собственный вердикт; `in_progress` замирал; `todo` после работы вёл к ложному `blocked`.
  Всё починено правилами из п. 6.1.
- Диспетчер считал записью только `### <ISO> <автор>` → ложные `blocked`. Теперь сигнал — рост секции «## Лог».
- Тикет без `--budget` получает $10 и встаёт → `--budget 60`.

**Работа CEO:**
- Двусмысленное «делай» в ответ на вопрос с вариантами принял за «да» и запустил январь–июнь без слова владельца →
  переспрашивать одним словом, не выбирать самому.
- Новый месяц считал только для 5 кандидатов, хотя все варианты шли тем же проходом почти даром → новый месяц сразу для
  ВСЕХ вариантов одним проходом; «посчитано» говорить только вместе с «для чего».
- Заглушил тревоги по типу и 69 минут не видел заморозку Steam Deck → фильтровать по содержанию; если между проверками
  нет прогресса, сразу смотреть статус машины.
- Порядок на Steam Deck сказал одной роли, а задания ставит другая → адресовать всем, кто ставит задания, и проверять
  очередь через 10 минут.
- Параллельные задачи на одни и те же сутки ставил отдельными прогонами → сливать в один `--cells`.
- Сроки называл «днями» → только в темпе CLI, в часах и минутах.
- Страницу для владельца правил патчами по его словам частями → сначала макет на одном экране и его «да», потом одна

- Число в поручении взял из счётчика испытаний, а не из таблицы клеток → числа в поручениях брать из таблицы отчёта.

- Готовое у ролей не сверял → «готово» проверять по файлу или коммиту.

## 13. Как развернуть в другом проекте (минимальный набор)

1. **Уставы:** `roles/README.md` (состав, зоны, кто решает, ресурсы, правила) и по файлу на роль. Блокноты
   `roles/notes/<role>.md` (≤ 60 строк), журналы `roles/journal/<ID>.md`.
2. **Тикеты-файлы** с шапкой из п. 5 и CLI `tickets.py` (new / comment / start / status).
3. **Диспетчер:** цикл 15 с, правила (а)–(д), `claude -p` с явными моделью, усилием и `--max-budget-usd`,
   `--permission-mode bypassPermissions`, `ALPHA_ROLE`, `--resume` по области сессии, бюджет задачи только в state,
   троттлинг, холостой ход, восстановление активных запусков.
4. **Сторож без модели** (`watch.py`) и канал будильника CEO (`ceo-inbox.md` + `ceo-wake.log` + `Monitor`).
5. **Хуки:** контекст роли на SessionStart, память роли (напоминание о блокноте, конспект при закрытии), защита
   удаления, запрет локальных сборок.
6. **Файлы состояния:** раздел «СОСТОЯНИЕ» в `CLAUDE.md` (пишет только CEO) и реестр решений владельца (дословные
   цитаты с датой).
7. **Процесс исследования навыком:** протокол до счёта → Судья → владелец → счёт → отчёт → Судья → владелец.
8. **Помощники:** `coder` (сильная модель, пишет код) и `reader` (дешёвая модель, только сводки со ссылками).
