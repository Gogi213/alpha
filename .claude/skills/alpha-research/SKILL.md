# Исследование в alpha

Бэктест — это замер, а не результат. Исследование отличается от перебора тем, что вопрос, данные,
метрика и правило вердикта записаны **до** счёта, а результат читается с шумом и числом испытаний.

Основа — навык [quant-research-skill](https://github.com/Jimmy7892/quant-research-skill) (MIT,
`LICENSE-quant-research-skill`), переработанный под проект: его справочники — `references/` (англ.),
скрипты — `scripts/`. Реклама движка ManifoldBT, просьба о звезде и расчёт размера позиции убраны
(размер задан владельцем: $500 / счёт $2500, В-89…В-91).

## Где что лежит

| что | где |
|---|---|
| протокол исследования | `docs/research/P-<NN>-<тема>.md` по шаблону `templates/protocol.md` |
| журнал (строка на шаг, включая неудачи) | `docs/research/JOURNAL.md` |
| отчёт с вердиктом | `docs/findings/<тема>-<YYYY-MM-DD>.md` по `templates/report.md` |
| реестр (строка на протокол) | `docs/plan/EXPERIMENTS.md`, раздел «П. Протоколы» |
| банк идей | `docs/plan/HYPOTHESES.md` (идея ≠ протокол) |

## Контракт данных — главное правило

- **Данные решения — август и сентябрь (В-115):** посылка «отскок от стены — альфа» месяцами не
  сжигается (практика владельца). Изменение варианта принимается, если оно лучше базы **в августе и
  в сентябре, каждый месяц отдельно**, по протоколу с порогами и правилом вердикта, записанными **до
  счёта**. Обвалы (`e-crash`) — отдельно, вне двух месяцев.
- **«Сожжено» — только для подгонки:** то, что подбирали на месяце (пороги, форма, набор), на этом
  же месяце без разбиения не проверяется — разбиение (месяц ↔ месяц: подбор на августе, проверка на
  сентябре, или наоборот; скользящее окно по неделям; CPCV `bounce-verdict`) записано в протоколе до
  счёта. Подбираемое — перекрёстно: подбор на августе → проверка на сентябре и подбор на сентябре →
  проверка на августе; решение — если держится в обе стороны. Перекрёстная подгонка — для
  подбираемого перебором; правила из практики владельца с параметрами, заданными до счёта, подгонкой
  не считаются (В-116: «да, но тут нужно осторожно»).
- **Свежие сутки (П-01) — наблюдение, не проверка (В-115):** наша запись **с 24.09**, ночной прогон
  (`nightly-grid.sh` → `fresh-days.py`) отслеживает только поломку — прогон прошёл, сделок n, ошибок
  нет, нет резкого расхождения с ожиданием. Это не условие решения и не повод ждать: числа по ним в
  решении не участвуют, один день ничего не даёт.
- **Гипотезы, найденные на августе/сентябре, проверяются там же:** отчёт помечает «найдено на этих
  данных», счётчик испытаний включает весь перебор, из которого гипотеза вышла (Холм по пакету
  протокола; в отчёте — номер этой проверки в сквозном реестре проверок на августе/сентябре
  (контекст, не поправка)). Разбиение «поиск / проверка» по дате регистрации кандидата — было в В-109, отменено
  В-115. **Конкретные Г-134…Г-138** (пометка Судьи `6278d98` п.4б/4в) — решение по ним принимает
  Судья, в рамках В-115.
- **Альфу ищем на том, что есть — не ждём** (владелец 25.09, В-109; подтверждено В-115). Новая
  гипотеза, которую ещё не подгоняли к этим данным, проверяется **внутри старых данных**: подбор на
  одной части, проверка на другой, разбиение записано в протоколе до счёта. В отчёте — пометка
  «проверено на старых данных» и деление на весь счётчик испытаний.
- **Механизм вперёд данных:** отскок от плотности — торговля практиков (`docs/transcripts/`, В-64),
  у неё есть механизм; гипотезы из правил практиков сильнее, чем найденные перебором.
- У нас OOS (`references/01,03,05,10`, англ.) = второй месяц / разбиение из протокола, не свежие
  сутки (В-115).

## Порядок работы — пять ворот

Каждый шаг кончается воротами; не прошли — это находка, а не помеха, которую обходят.

| шаг | вопрос | ворота |
|---|---|---|
| 1. Протокол | что проверяем, что нас опровергнет, что сделаем при «да»/«нет» | протокол записан, **владелец утвердил** («ок» в чате → в протокол с датой) |
| 2. Честный счёт | замер честный? | издержки и задержка В-68 включены, K1-маркеры сверки, очередь `prob:3`, без заглядывания |
| 3. Поверхность | есть край или одна удачная клетка? | для подбора — плато, а не пик; соседи того же знака |
| 4. Поправка на поиск | не перебор ли это сделал? | счётчик испытаний, DSR/PBO, шум по дням |
| 5. Вердикт | что делаем? | правило из протокола, без изменений; отчёт; строка журнала |

Справочник шага читать при входе в шаг: 1 — `references/01-framing.md`; 3 — `03-surface.md`;
4 — `04-selection-bias.md`, `07-effective-sample.md`; 5 — `05-verdict.md`, образец —
`worked-example.md`; живой бот — `10-live-monitoring.md`; просадка — `08-drawdown-risk.md`.

## Статистика в этом проекте

- **Месяцы отдельно** (август, сентябрь, октябрь…); общий столбец — только дополнительный.
- **Наблюдение — сутки, не сделка.** Сделки главного варианта сидят в одних часах (вход — когда
  падает BTC), перекрываются и коррелированы: 150 сделок — это десятки независимых наблюдений.
  t-статистику по сделкам не считать никогда. Эффективное число — `scripts/effective_n.py`
  (перекрытие по времени). Вывод — по правилу R2: знак в обоих месяцах, интервал блочного
  бутстрепа по суткам (блок ⌈n^{1/3}⌉) не накрывает 0 после Холма по пакету, эффект не держится
  на одних-двух сутках или монете. Эфф. N — справочно.
- **Сравнение вариантов выхода на одних сделках** — разница по суткам в паре, интервал
  бутстрепом по суткам: «Δ +$13 [−$20; +$41]», а не «+$13».
- **Счётчик испытаний** — всё, на что смотрели, включая отброшенное и прикинутое в чате. Поиск
  25.09 (E27–E34) — порядка 60 вариантов выхода на августе/сентябре; любой выигрыш оттуда
  делится на этот перебор (`scripts/selection_bias.py`: ожидаемый максимум шума, DSR, PBO).
- **Деньги — с размером позиции** (В-93), расстояния — в bps, время — GMT+4 для владельца.
- Число — только после того, как метод прошёл свою проверку (сверка с полным прогоном).
- **KPI «дней до перехая» (В-120)** — главный критерий отбора вариантов, деньги вторичны: в каждой таблице вариантов — колонка KPI (самый долгий период с хвостом и p90 по времени, по месяцам, по кривой закрытий); цель — стабильный заработок.
- **Не хуже базы:** для изменений, снижающих просадку или издержки, правило протокола может быть
  «нижняя граница разницы по суткам ≥ −$X в каждом месяце» (X — до счёта; В-116).

## Роли

- **Владелец** утверждает протокол до счёта и читает вердикт. Тяжёлый счёт без утверждённого
  протокола не запускать.
- **Исполнитель** (субагент ≤ 100 шагов) считает строго по протоколу; отступление — в раздел
  «Отступления» протокола и в журнал, а не молча.
- **Судья** (роль `Роль: Судья`, `.claude/roles/judge.md`): перед утверждением протокола и перед
  вердиктом ищет нарушения ворот. Для вердикта, предрегистрации — по В-39.

## Отказы (жёстко, даже если просят)

| не делать | почему |
|---|---|
| «лучший вариант — X» после перебора | это максимум шума; ответ — область/плато и её среднее |
| число без интервала и счётчика испытаний | не читается |
| принимать решение по свежим суткам | один день — ничего не даёт (В-115) |
| править и перечитывать проверку | это подгонка, как её ни назови |
| вывод, который держится на одних сутках или одной монете / интервал накрывает 0 | метрики не определены |
| t-статистика по сделкам | растёт с числом сделок, а не со знанием |
| месяцы вместе как главный результат | прячет, что работало в одном месяце |
| «направление отработано» без списка проверенного | проверенное ≠ всё возможное |
| новый опыт на августе/сентябре мимо протокола как доказательство | решает протокол с порогами до счёта, не наблюдение по ходу (В-115) |
| реализованная просадка как бюджет риска | одна реализация, хвост хуже |

Если давят «дай одно число» — дать среднее и интервал и одной фразой сказать, почему не максимум.
Писать «края нет» — нормальный и самый частый честный вывод.
