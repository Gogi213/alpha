## Что уже найдено чтением кода (проверить замером, не верить на слово)

1. `ws::parse_message` строит `serde_json::Value` (полный DOM с аллокацией на
   каждый узел) на **каждое** сообщение, затем `Vec<Event>` и `Vec<(i64,i64)>`
   для бидов/асков. Это основная стоимость разбора и аллокационный шторм.
2. `session.rs::write_market_event` пишет **zstd-кадр на каждое сообщение**
   (`writer.write_frame(&state.scratch)` после каждого события): один вызов
   компрессора и два `write_all` в голый `File` на сообщение; кадр из 1–5
   записей почти не сжимается — накладные zstd-кадра больше полезных байт.
   `lob record` (`commands::record`) уже копит `FRAME_TARGET_RECORDS = 1000`
   записей перед кадром — сессия этого не делает. Читатель кадров
   (`bybit::verify::FileReplayer::push_frame`) группирует записи по
   `(вид, exch_ts_ns)`, не по границам кадра — батчинг для него прозрачен.
3. `session.rs::run_session` копит **каждую** задержку разбора и очереди в
   `Vec<i64>` (`parse_latencies_ns`, `queue_latencies_ns`): 391 403 кадра × 2 ×
   8 байт плюс удвоение ёмкости `Vec` — это и есть рост RSS; на сутках это
   сотни мегабайт.
4. `session.rs` держит вторую `Book` на инструмент и делает `apply` на каждое
   обновление, хотя `bybit::conn::handle_raw` уже применил его к своей книге и
   не пересылает наружу ничего, что не прошло `apply`. Двойная работа.
5. `ConnEvent::Message { event: Event }` несёт владеющие `Vec` через `mpsc`
   — по две аллокации на сообщение остаётся даже после снятия DOM; ноль
   достижим только фиксированной ёмкостью (`orderbook.50` — не больше 50+50
   уровней) либо возвратом буферов. Решать по замеру: если после п. 1–4
   разбор p99 и аллокации/событие укладываются в бюджет — не усложнять.
